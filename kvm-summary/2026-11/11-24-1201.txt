New:  KVM: x86: Reject SMM on VMs with private memory
[PATCH] KVM: x86: Reject SMM on VMs with private memory
Author: Younho Choi <gdool88@gmail.com>

A VM created with private memory (KVM_X86_SW_PROTECTED_VM, SEV-SNP, TDX)
reports a single memslot address space, because kvm_arch_nr_memslot_as_ids()
returns 1 when kvm_arch_has_private_mem() is true.  Nothing, however, prevents
such a VM's vCPU from entering SMM, in which case kvm_arch_vcpu_memslots_id()
still selects address space 1.  The existing comment "SMM is currently
unsupported for guests with private memory" is not enforced anywhere.

Because address space 1 is initialised with generation 1 and is never swapped
for a private-memory VM, while address space 0's generation advances by
kvm_arch_nr_memslot_as_ids() (i.e. 1) per swap, after a single memslot
operation both address spaces have generation 1.  The per-vCPU last_used_slot
cache in kvm_vcpu_gfn_to_memslot() validates only on the generation number, so
a slot cached in address space 0 is reused for an in-SMM (address space 1)
lookup.  After that slot is deleted and freed, the stale per-vCPU cache is
dereferenced: a host-kernel use-after-free of struct kvm_memory_slot reachable
by an unprivileged process that can open /dev/kvm.  The same aliasing also
leaves SMM-root SPTEs that mmu_notifier invalidation never zaps (it walks only
address space 0), and can trigger a BUG() in the TDP MMU.

Enforce the documented assumption: do not support SMM on VMs with private
memory.  Stop advertising KVM_CAP_X86_SMM and emulating MSR_IA32_SMBASE for
such VMs (which also makes kvm_inject_smi() and guest-driven SMIs fail), and
reject enabling SMM via KVM_SET_VCPU_EVENTS.

Fixes: 89ea60c2c7b5 ("KVM: x86: Add support for "protected VMs" that can utilize private memory")
Signed-off-by: Younho Choi <gdool88@gmail.com>

New:  vfio/virtio: read migration buffers and f_pos under migf->lock
[PATCH] vfio/virtio: read migration buffers and f_pos under migf->lock
Author: Qican Ma <goonsomeway@gmail.com>

virtiovf_resume_write() reads migf->buf and migf->buf_header and checks
filp->f_pos against vhca_buf->start_pos before taking state_mutex and
migf->lock. Because virtiovf_pci_resume_device_data() opens the file via
stream_open(), FMODE_ATOMIC_POS is cleared and concurrent writes through
duplicated file descriptors are not serialized by f_pos_lock. A racing
writer in VIRTIOVF_LOAD_STATE_PREP_HEADER_DATA can free and reallocate
migf->buf_header under migf->lock while another writer still holds the
stale pointer captured before the lock.

Move the buffer pointer reads and start_pos check under migf->lock after
checking VIRTIOVF_MIGF_STATE_ERROR.

Found with an LLM-assisted code review tool and verified by inspection on
v7.4-rc4 (b6a9fa34ce4). Build-tested only due to lack of virtio VF
live-migration hardware.

New:  vfio: selftests: Add NVMe driver
[PATCH] vfio: selftests: Add NVMe driver
Author: Josh Hilke <jrhilke@google.com>

Add a VFIO selftest driver for NVMe controllers. It binds to any PCI
function with the NVMe PCI class code 01:08:02, so vfio_pci_driver_test
can run on the NVMe SSDs that are common in servers, and on the nvme
device that QEMU emulates.

NVMe has no memory-to-memory copy command, so the driver implements a
memcpy through the logical blocks at the start of the first active
namespace. memcpy_start() writes @src to the logical blocks from LBA 0,
waits for the write, and then queues @count reads of the same blocks into
@dst. The driver must wait for the write because the controller can run
the commands of a queue in any order. All @count reads are in flight when
memcpy_start() returns. The driver spreads the reads over up to 16 such
queues, because one queue holds only as many commands as the controller
allows, 2047 on the QEMU device. The memcpy commands go on I/O queues
that have interrupts disabled. send_msi() sends a flush on one more I/O
queue that has interrupts enabled.

The driver overwrites the first max_memcpy_size bytes of the namespace.
Do not use a device that holds data you want to keep.

On some controllers, a DMA error from the unmapped-IOVA tests leaves the
submission queue in an error state that only a Function Level Reset
clears. After a failed memcpy, the driver disables the controller, resets
the function with VFIO_DEVICE_RESET, and initializes the controller
again.

The driver needs a controller that supports the NVM command set, 4 KiB
memory pages, at least two I/O queue pairs, and MSI-X, along with
a namespace that has no metadata and a logical block size of at most 4 KiB.
Controllers that need one of the quirks in drivers/nvme/host/pci.c are
not supported.

The driver uses the definitions in include/linux/nvme.h through a
symbolic link, like the other drivers do with their kernel headers.

Users can verify the driver in QEMU with these commands, after they
build the kernel and the VFIO selftests:

truncate -s 64M /tmp/nvme.img
vng \
--run arch/x86/boot/bzImage \
--user root \
--disable-microvm \
--memory 4G \
--cpus 4 \
--qemu-opts="-M q35,accel=kvm,kernel-irqchip=split" \
--qemu-opts="-device intel-iommu,intremap=on,caching-mode=on" \
--qemu-opts="-drive file=/tmp/nvme.img,if=none,id=nvm,format=raw" \
--qemu-opts="-device nvme,serial=deadbeef,drive=nvm,addr=10.0" \
--append "console=ttyS0 intel_iommu=on" \
--exec "modprobe vfio-pci && \
  ./tools/testing/selftests/vfio/scripts/setup.sh 0000:00:10.0 && \
  ./tools/testing/selftests/vfio/scripts/run.sh \
  ./tools/testing/selftests/vfio/vfio_pci_driver_test"

New:  x86/fred: Add this_cpu_fred_sp() and export it for KVM
[PATCH] x86/fred: Add this_cpu_fred_sp() and export it for KVM
Author: Sohil Mehta <sohil.mehta@intel.com>

FRED adds fields to the VMCS host-state area for the stack pointers of
stack levels 1 to 3. The CPU loads these pointers on every VM exit to
ensure a valid FRED event delivery context is established immediately.
These values are per CPU, so KVM has to refresh them each time a vCPU is
loaded onto a CPU.

The stack for each level is assigned implicitly, when the FRED RSP MSRs
are programmed during CPU initialization. KVM could read the MSRs back,
but that costs three RDMSRs on every vCPU load, while the kernel already
has the values at hand. Add a helper that returns the corresponding
stack pointer for each FRED RSP MSR. Use it to program the MSRs during
init, and export it for KVM.

Key the helper on the MSR rather than on a stack level, so that KVM
never needs to know which exception stack backs which level. Eventually,
the same interface can be extended for the FRED shadow stack MSRs as
well.

New:  KVM: x86/pmu: Dynamic mediated PMU context switching
[RFC PATCH 00/26] KVM: x86/pmu: Dynamic mediated PMU context switching
Author: Yosry Ahmed <yosry@kernel.org>

When KVM uses the mediated PMU, it loads the guest context and puts it around
the inner fastpath loop, causing an expensive switch on every slowpath VM-Exit.
On microbenchmarks like CPUID, this can result in up to 3x drop in throughput
even when the host is not using the core PMU. On more realistic benchmarks like
netperf TCP_RR, it results in up to ~15% regression (at least in some setups).

This series uses a dynamic scheme for PMU context switching instead. On
slowpath VM-Exit, KVM only puts the guest context if host perf has events
conflicting with the mediated PMU. Otherwise, the guest context remains loaded
until either the vCPU is put (e.g. on context switch or return to userspace),
or perf "reclaims" it. This recovers most/all performance (at least on CPUID
and netperf) with a mediated PMU in the absence of host events. See "KVM:
x86/pmu: Put the mediated PMU context lazily on slowpath VM-Exits" for exact
numbers.

The Perf Side
-------------

Perf reclaims the PMU before executing any remote call on a CPU if the guest
context is loaded, including installing events, enabling events, etc. This is
too conservative, as perf really only needs to reclaim the PMU before an event
is both installed and enabled, but it results in a simpler and more
future-proof implementation.

There are a couple of other hiccups that perf needs to deal with outside of
reclaiming on remote calls, namely:

1. Intel PT/BTS. These PMUs are not mediated, but they use the same PMI
delivery mechanism as the mediated core PMU (i.e. LVTPC). Since they are not
mediated, they are not scheduled out while the guest context is loaded, and
their PMIs can be delivered into the guest instead of the host. Today, BTS is
never active while the guest runs (KVM doesn't allow the guest to enable it,
and VM-Exit clears DEBUGCTL), so this is limited to short windows around
VM-Entry/VM-Exit. Intel PT (in system mode) keeps tracing while the guest runs,
so its PMIs raised while the guest is running are delivered to the guest.

Lazily putting the guest context would make this worse for both, as host code
with tracing enabled could run with the guest context loaded for much longer,
most notably for BTS, which would go from short windows around VM-Entry/VM-Exit
to all of slowpath VM-Exit handling. To avoid that, this series tracks PMUs
that share the same PMI mechanism, and having events on any of them prompts KVM
to give up the PMU on slowpath VM-Exits, keeping the status quo.

Long-term, perhaps it would be better to schedule out Intel PT events while
the guest context is loaded, or somehow demux the PMIs?

2. Handling bpf_get_branch_snapshot() while the guest context is loaded (a
pre-existing bug that is more exposed by this series).

3. Clearing dirty counters when events are mmap()'d or the rdpmc attribute is
updated, which needs to reclaim the PMU first if the guest context is loaded.

NOTE: The first 5 patches fix pre-existing problems (or prepare for those
fixes) that are relevant to the series (or the dynamic switch makes them worse),
but they can be merged independently.

The KVM Side
------------

The main change is needing to access guest PMU registers in hardware while the
guest context is loaded. More specifically, the currently virtualized registers
fall into one of two categories:

1. Registers that can be read from software but must be written to hardware
(i.e. are always up-to-date in software). This includes registers that are
always intercepted or sync'd on every VM-exit, namely control registers:
eventsel, fixed_ctr_ctrl, and GLOBAL_CTRL.

2. Registers that must be read and written from hardware (i.e. software can
always be stale). This includes registers that can be updated by the guest or
hardware while the guest runs, namely counters and GLOBAL_STATUS.

Additionally, KVM needs to keep the physical and virtual LVTPC in sync while
the guest context is loaded.

KVM accessing registers in hardware as needed allows it to handle fastpath
instruction emulation with a mediated PMU, so this restriction is dropped.

Testing
-------

This was tested by new (AI-generated) extensions to PMU selftests that mostly
act as regression tests for the existing PMU, a selftest-style stress test, and
stressing perf with a real Linux VM. The selftests will be cleaned up and sent
out separately.

The full KVM x86 selftests and kvm-unit-tests were also run on Intel and AMD,
with no new failures compared to the base kernel.

Testing was done with Zide's "KVM: SVM: Drop counter MSR checks in
amd_is_valid_msr()" [1] applied, as without it saving vCPU state on AMD fails
when the guest has fewer counters than the host (KVM_GET_MSRS fails on the
unexposed counter MSRs).

New:  KVM: arm64: nv: Discard undersized TTL hints in compute_tlb_inval_range()
[PATCH v2 1/2] KVM: arm64: nv: Discard undersized TTL hints in compute_tlb_inval_range()
Author: Colton Lewis <coltonlewis@google.com>

When an L1 guest issues TLBI IPAS2E1 with a non-zero TTL hint,
compute_tlb_inval_range() takes it at face value. If the hinted size is
smaller than the actual mapping (for example, a 4kB L3 hint on a 2MB
block), kvm_pgtable_stage2_unmap() clears the entire block while
kvm_remove_guest_s2_mappings() leaves its stale tracking entry behind in
guest_s2_mappings. On 16kB or 64kB hosts, a 4kB hint also triggers
WARN_ON(size & ~PAGE_MASK) in kvm_stage2_unmap_range().

A TTL hint smaller than PAGE_SIZE or the mapped entry is wrong. Check
it against PAGE_SIZE, the shadow stage-2 leaf size, and the guest block
size encoded in KVM_NV_GUEST_MAP_SZ. If it is too small, ignore the hint
and fall through to the unhinted invalidation path.

When falling back to the maximum mapping extent with stage-2 disabled,
size it from PAGE_SIZE rather than VTCR_EL2.TG0 so 1:1 shadow blocks are
still covered.

Fixes: d1de1576dc21 ("KVM: arm64: nv: Handle FEAT_TTL hinted TLB operations")
Signed-off-by: Colton Lewis <coltonlewis@google.com>

New:  vfio/container: hold group_lock across backend ioctl passthrough
[PATCH] vfio/container: hold group_lock across backend ioctl passthrough
Author: Jeff Barnes <jeffbarnes@linux.microsoft.com>

vfio_fops_unl_ioctl() forwards unrecognized ioctls to the IOMMU backend
by reading container->iommu_driver and container->iommu_data and calling
driver->ops->ioctl() without holding container->group_lock.

When the last group is detached, vfio_group_detach_container() takes
group_lock for write, releases the backend and clears both pointers.
An ioctl running concurrently on the container fd can therefore use
backend state that is being torn down. With the Type1 backend, a
VFIO_IOMMU_GET_INFO racing with the last group detach walks iommu->
iova_list while vfio_iommu_type1_release() frees it, and faults on a
poisoned list pointer (dead000000000100).

The other container entry points that use the backend, namely
VFIO_CHECK_EXTENSION and VFIO_SET_IOMMU, already take group_lock.
Do the same for the passthrough path and hold it for read across the
backend call. This is consistent with the existing lock order, as
backends only take their own locks (e.g. iommu->lock) below group_lock.

This patch was developed with the assistance of GitHub Copilot CLI
(Claude Sonnet 5.5), which helped analyze the race, draft the fix and
this description, and build-check the result. The author reviewed the
change and tested it on a downstream 6.6 kernel.

New:  KVM: arm64: nv: Upgrade sub-page TTL hint to maximum size
[PATCH] KVM: arm64: nv: Upgrade sub-page TTL hint to maximum size
Author: Marc Zyngier <maz@kernel.org>

Should a guest be slightly foolish and submit a S2 TLBI with a TTL hint
that describe a base granule size smaller than the host's page size,
we take the resulting size at face value and feed it to the S2 unmapping
code. Which legitimately screams about something not being page-aligned.

The architecture allows us to drop the TLBI on the floor, as we don't
support a S2 granule size smaller than the host's page size. But it turns
out that doing so is proving pretty hard (we call compute_tlb_inval_range
from a number of places, none of which is amenable to an early out).

Instead, detect the annoying case, and pretend that we don't have a TTL
hint at all, leaving the size upgrade mechanism to take place and use
the largest possible size for the guest's S2 granule size.

This will still allow nonsensical stuff to get through, such as a 4kB
level 2 (aka 2MB) from a guest with a 64kB S2 base granule size running
on a 16kB page size host, but that's not worse than doing nothing, and
the host code won't get shouty.

New:  KVM: Disable preemption while pushing to the dirty ring
[PATCH 1/2] KVM: Disable preemption while pushing to the dirty ring
Author: Siddharth Mishra <smish149@asu.edu>

Disable preemption in kvm_dirty_ring_push() so that another push to the
same dirty ring cannot run in the middle of it.

kvm_dirty_ring_push() selects an entry with dirty_index, fills the entry,
and only then increments dirty_index, all with preemption enabled, e.g.
when vmx_flush_pml_buffer() pushes the logged GPAs on VM-Exit.  If the
vCPU task is preempted in that window, kvm_sched_out() calls
kvm_arch_vcpu_put() while kvm_running_vcpu still points at the vCPU, and
kvm_steal_time_set_preempted() or kvm_xen_runstate_set_preempted() marks
a page dirty, which pushes to the same ring.  That push fills the
selected entry and increments dirty_index, then the interrupted push
overwrites the entry and increments dirty_index again.  The entry after
it is never written, its flags stay zero, and the entries after that one
are dirty.

Userspace harvests the ring in order and stops at the first entry that
is not dirty, so it never harvests any later entry, and the GFN of the
overwritten push is lost.  A VMM that tracks dirty memory with the dirty
ring, e.g. for live migration or to restore a snapshot, then misses every
page that the vCPU dirties afterwards.

New:  KVM: Stop KVM_PRE_FAULT_MEMORY when the vCPU's dirty ring is full
[PATCH v3 1/3] KVM: Stop KVM_PRE_FAULT_MEMORY when the vCPU's dirty ring is full
Author: Fuad Tabba <fuad.tabba@linux.dev>

Pre-faulting can map a dirty-logged page writable, which pushes it to
the vCPU's dirty ring. KVM_RUN exits with KVM_EXIT_DIRTY_RING_FULL
before the ring overflows, but the pre-fault loop never checks it, so
one call can push more entries than the ring has free, which trips the
WARN in kvm_dirty_ring_push() and overwrites entries userspace hasn't
harvested. On x86:

  WARNING: arch/x86/kvm/../../../virt/kvm/dirty_ring.c:225 at kvm_dirty_ring_push+0x7a/0xd0
  Call Trace:
   make_spte+0x2cc/0x450
   kvm_tdp_mmu_map+0x5e1/0x7f0
   kvm_tdp_page_fault+0x12c/0x1b0
   kvm_mmu_do_page_fault+0x181/0x250
   kvm_arch_vcpu_pre_fault_memory+0x136/0x1d0
   kvm_vcpu_pre_fault_memory+0xcf/0x180
   kvm_vcpu_ioctl+0x455/0x770

Stop the loop once the ring is soft full, with the check KVM_RUN makes
before entering the guest. Return the pages already processed, or
-ENOSPC when there aren't any, since a retry can't succeed until
userspace harvests and resets the ring. s390 has the ioctl but no ring,
so give kvm_dirty_ring_check_request() a stub.

The check also sets run->exit_reason to KVM_EXIT_DIRTY_RING_FULL. On
arm64, KVM_RUN completes a pending MMIO exit only if exit_reason is
still KVM_EXIT_MMIO, and on riscv KVM_RUN does the same for its MMIO,
SBI and CSR exits. If a pre-fault stops on a full ring while such an
exit is pending, the next KVM_RUN doesn't complete it and the guest
repeats the instruction that caused the exit. Userspace can avoid that
by completing the exit with KVM_RUN before pre-faulting.

New:  KVM: Bound KVM_PRE_FAULT_MEMORY by the vCPU's dirty ring
[PATCH v3 0/3] KVM: Bound KVM_PRE_FAULT_MEMORY by the vCPU's dirty ring
Author: Fuad Tabba <fuad.tabba@linux.dev>

Hi folks,

Changes since v2 [1]:
  - Added patch 2, which warns in api.rst against calling ioctls other
    than KVM_RUN while an exit is pending. (Sean)
  - Mentioned riscv as well as arm64 in patch 1's exit_reason
    paragraph. (Lorenzo)
  - Collected Lorenzo's Acked-by on patch 3. (thanks!)

KVM_PRE_FAULT_MEMORY never checks the vCPU's dirty ring, so one call
over a large enough range of populated, dirty-logged pages overflows
it. The first patch stops the loop at the soft limit, as KVM_RUN does.
The second warns userspace against calling ioctls other than
KVM_RUN while an exit is pending. The third adds the case to
pre_fault_memory_test.

Pre-faulting isn't the only ioctl that can push past the ring's
reserve. On x86, KVM_SET_MSRS does too when it writes the wall clock or
the Hyper-V hypercall page. A guest can also push past the reserve
within one exit, for example through the arm64 ITS. What those paths
should do when the ring fills is an open question for the dirty ring
API, which I don't think belongs in this series.

I didn't include the kvm_dirty_ring_check_request() rewrite that Sean
sketched on v1, since I think it can lose a request. It tests the
request first and clears it afterwards. If the vCPU is scheduled out in
between, loongarch sets the PV preempted flag in guest memory and x86
updates a Xen guest's runstate area, either of which pushes an entry.
When that push makes the ring soft full, the request it makes is then
cleared, and the vCPU runs with the ring soft full until its next push.
Clearing first and re-setting, as the code does now, doesn't have that
window.

Based on Linux 7.4-rc2 (7475ea8b58616; also applies to kvm-x86/next
cbe54fc3462b3 with git am -3).

New:  powerpc/rtas: Handle ibm,open-errinjct return format
[PATCH v7 1/4] powerpc/rtas: Handle ibm,open-errinjct return format
Author: Narayana Murty N <nnmlinux@linux.ibm.com>

ibm,open-errinjct returns the session token in rets[0] and the status in
rets[1], unlike other RTAS functions, which return the status in rets[0].
rtas_call() would report the session token as the status and drop the
real status.

Take the status from rets[1] for this function and return the session
token in outputs[0].  This needs exactly two return cells, so reject any
other count from kernel callers with -EINVAL and a one-time warning, and
document the exception in the rtas_call() kernel-doc.

Give the rtas_output tracepoint the index of the status cell, so that it
reports rets[1] as the status and the session token as an additional
output for this function.  A call with no return cells reports status 0
instead of reading a cell that does not exist.

Ensure __fetch_rtas_last_error() and sys_rtas() initialize rtas_args.rets
to point into rtas_args.args[] after copying local arguments, preventing
tracepoint handlers from dereferencing uninitialized memory or reading
stale on-stack values.

sys_rtas() still copies the raw return cells to userspace.  It uses the
status from the right cell for hardware-error (-1) detection and, after
the lockdown check, rejects fewer than two return cells for this function.

New:  powerpc: Add RTAS based error injection support for pSeries
[PATCH v7 0/4] powerpc: Add RTAS based error injection support for pSeries
Author: Narayana Murty N <nnmlinux@linux.ibm.com>

The pSeries EEH error-injection backend currently implements a limited
software-generated MMIO failure and does not use the error-injection
services provided by RTAS.

This series replaces that implementation with the PAPR-defined RTAS
workflow based on:

- ibm,open-errinjct
- ibm,errinjct
- ibm,close-errinjct

The implementation opens an RTAS error-injection session, allocates and
prepares an RTAS-accessible work area, performs the requested injection,
releases the work area, and closes the session on both success and failure
paths.

The existing EEH userspace ABI is preserved. EEH_ERR_TYPE_32 and
EEH_ERR_TYPE_64 continue to represent generic 32-bit and 64-bit IOA
bus-error injection requests. The pSeries backend maps these values to
the corresponding RTAS error types, while the PowerNV backend explicitly
maps them to the corresponding OPAL types.

Additional generic EEH error types (EEH_ERR_TYPE_RECOVERED_SPECIAL_EVENT,
EEH_ERR_TYPE_CORRUPTED_PAGE, and the cache/TLB corruption types) are
defined in the UAPI header and mapped explicitly to RTAS firmware
encodings by the pSeries backend. Platform backends that do not support
a valid generic type return -EOPNOTSUPP.

No existing userspace ABI values are changed.

The injection path can be exercised for VFIO-assigned devices through
VFIO_EEH_PE_INJECT_ERR. The guest or userspace VFIO application continues
to use the same generic EEH type and function values, independent of
whether the host platform uses RTAS or OPAL.

For IOA bus-error injection, the VFIO sPAPR path normalizes a Linux BAR
resource address to the corresponding PCI bus address before dispatching
the request to the platform EEH backend. Address normalization is
restricted to memory and IO load/store functions whose addr argument is a
BAR-backed PCI address. Config-space and DMA functions are passed through
without translation because their addr arguments represent PCI config
register offsets and IOVA/TCE addresses respectively. The no-address form
is represented by both address and mask being zero.

The series also handles the unusual return format of ibm,open-errinjct:

rets[0] = error-injection session token
rets[1] = RTAS status

rtas_call() returns rets[1] as the status and places the session token in
outputs[0], preserving the normal kernel rtas_call() convention.

sys_rtas() continues to expose the raw RTAS return cells to userspace.
For ibm,open-errinjct, it validates that at least two return cells were
requested before entering RTAS and uses the RTAS status cell for
last-error handling. Userspace therefore continues to receive the session
token and status in their PAPR-defined positions.

The pSeries backend uses the existing RTAS work-area allocator for the
error-injection parameter buffer. The work area is allocated only after
ibm,open-errinjct succeeds and is released before ibm,close-errinjct.
RTAS work areas reside below RTAS_INSTANTIATE_MAX, so the physical address
fits in the 32-bit RTAS argument passed to firmware.

The complete open, inject, and close sequence is serialized with a mutex.
RTAS busy and extended-delay return values are handled for all three
calls. Once a session has been opened, ibm,close-errinjct is attempted
even when parameter preparation or error injection fails.

The patches are organized as follows:

1. Handle the special ibm,open-errinjct return format in rtas_call().
2. Add pSeries RTAS error-injection validation and buffer helpers.
3. Implement RTAS-based pSeries EEH error injection.
4. Normalize VFIO sPAPR IOA error-injection addresses.
5. Explicitly map generic EEH error types to OPAL types on PowerNV.

Testing was performed on PowerVM with firmware providing the RTAS
error-injection services and with corresponding QEMU support.

The corresponding QEMU v6 series is posted here:
https://lore.kernel.org/qemu-devel/20261019162541.68440-1-nnmlinux@linux.ibm.com/

New:  PCI/TSM: Support guest TSM drivers
[PATCH v1 00/10] PCI/TSM: Support guest TSM drivers
Author: Aneesh Kumar K.V (Arm) <aneesh.kumar@kernel.org>

This series adds the PCI/TSM support needed by a TEE Security Manager
(TSM) driver in a confidential guest. It adds device lock/unlock,
helpers for recording device acceptance and parsing MMIO reports, and
DMA callbacks used during PCI driver attachment. The guest TSM driver and
attestation commands using these interfaces are in follow-up series.

This series is based on Dan Williams' "[PATCH v2 00/19] PCI/TSM: TEE I/O
infrastructure" posting [1], particularly the guest LOCK/UNLOCK, ACCEPT
and MMIO report work [2-4]. It retains device_cc_accepted() and the
confidential-device acceptance model from that posting, with changes
adapted to the current PCI/TSM structures and reference APIs. Dan's
device-core acceptance helper and per-host-bridge IDE stream reporting
patch are also included.

This series does not adopt the Device Trust changes from Dan's "Device
Evidence and Trust for PCI Security Protocol (TDISP)" [5]. That work is
being developed separately in Leon Romanovsky's "driver core: Authorize
device trust before driver binding" series, [6]. Confidential-device
acceptance is kept separate from that driver-binding trust policy.

The guest flow separates three operations:

* Lock the device through tsm/lock. This requests the TEE Device Interface
  Security Protocol (TDISP) LOCKED state, so userspace can verify evidence
  about the locked configuration. Unlock releases the device configuration
  and the TSM driver's per-device state. Neither operation is permitted
  while a PCI driver is attached.
* Request device use through the attestation evidence-accept operation.
  A follow-up guest TSM driver validates the reported MMIO mappings,
  requests TDISP RUN and marks the device accepted. This series supplies
  the device acceptance state, MMIO report helpers and PCI/TSM locking
  helpers needed for that work.
* Enable DMA during PCI driver attachment, after platform DMA configuration
  and IOMMU setup, before the PCI driver's probe function. Disable DMA
  during driver detach and setup cleanup. Hold TSM user, device and module
  references until DMA cleanup finishes calling the TSM driver.

Compared with the earlier posting, evidence retrieval and acceptance use
attestation rather than PCI/TSM evidence storage and the sysfs accept
attribute.

This series is based on the IOMMUFD/TSM vIOMMU and vDEVICE work [7]. It
uses that series' TSM references, unregister waits and struct pci_tsm_context
references. The architecture-specific CCA host and guest drivers and their
SPDM attestation operations are in separate follow-up series.

The full patchset, including attestation, Device Trust, IOMMUFD,
guest_memfd and the Arm CCA host and guest changes, is available at:

  https://git.gitlab.arm.com/linux-arm/linux-cca.git
  branch: cca/topics/7.4/cca-da-integration-v1

New:  KVM: riscv: Allow rescheduling during G-stage unmap

New:  iommu: Add live update state preservation
[PATCH v8 00/18] iommu: Add live update state preservation
Author: Samiullah Khawaja <skhawaja@google.com>

Hi,

This patch series introduces a mechanism for IOMMU state preservation
across live update, including the Intel VT-d driver support
implementation.

Please take a look at the following LWN article to learn about KHO and
Live Update Orchestrator:

https://lwn.net/Articles/1033364/

This series is based on linux-next (next-20261120), which already has
the PCI base device preservation series and the LUO internal API to get
incoming/outgoing files.

The dependency on the VFIO cdev preservation series is removed in this
version. The patch that triggered the preservation of the iommufd state
of a vfio cdev is dropped, so this series can be applied and reviewed on
its own and merged without the VFIO series. Once the VFIO series is
ready, an extra patch glues it with the iommufd preservation. The series
with the extra patches is available at the following Github location:

https://github.com/samikhawaja/linux/tree/iommu/phase1-v8-vfio

Also note that patch 01 is taken from the VFIO cdev preservation series.
It exports the LUO file handler registration functions, which iommufd
also needs as it can be built as a module. It will be dropped from this
series once that patch is merged separately.

The kernel tree with all dependencies is uploaded to the following
Github location:

https://github.com/samikhawaja/linux/tree/iommu/phase1-v8

The series is targeting IOMMU tree.

Overall Goals:

The goal of this effort is to preserve the IOMMU domains, managed by
iommufd, attached to devices preserved through VFIO cdev. This allows
DMA mappings and IOMMU context of a device assigned to a VM to be
maintained across a kexec live update.

This is achieved by preserving IOMMU page tables using Generic Page
Table support, IOMMU root table and the relevant context entries across
live update.

The functionality in the previously sent RFC is split into two phases
and this series implements the Phase 1. Phase 1 implements the following
functionality:

  - Foundational work in IOMMU core and VT-d driver to preserve and
    restore IOMMU translation units, IOMMU domains and devices across
    liveupdate kexec.
  - The preservation is triggered by preserving vfio cdev FD and bound
    iommufd FD into a live update session.
  - An HWPT (and backing IOMMU domain) is only preserved if it contains
    only file type DMA mappings. Also the memfd behind such a mapping
    must have been preserved already.
  - During live update boot, the state of preserved Intel VT-d, IOMMU
    domain and devices is restored.
  - The restored IOMMU domains are reattached to the preserved devices
    during early boot.
  - The DMA ownership of restored devices is also claimed during live
    update boot. This means that any attempt to bind a non-vfio driver
    with them or binding a new iommufd with them will fail.

Architectural Overview:

The target architecture for IOMMU state preservation across a live
update involves coordination between the Live Update Orchestrator,
iommufd, and the IOMMU drivers.

The core design uses the Live Update Orchestrator's file descriptor
preservation mechanism to preserve iommufd file descriptors. The user
marks the iommufd HWPTs for preservation using a new ioctl added in this
series. Once done, the preservation of iommufd inside an LUO session is
triggered using LUO ioctls. During preservation, the LUO preserve
callback for an iommufd walks through the HWPTs it manages to identify
the ones that need to be preserved. Once identified, a new IOMMU core
API is used to preserve the iommu domain. The IOMMU core uses Generic
Page Table to preserve the page tables of these domains. The domains are
then marked as preserved.

When the user triggers the preservation of a VFIO cdev that is attached
to an iommufd that is preserved, the device attachment state of that
VFIO cdev is also preserved using an API exported by iommufd. IOMMUFD
fetches all the information that needs to be preserved and calls the
IOMMU core API to preserve the device state. The IOMMU core also
preserves state of IOMMU that is associated with this device.

The IOMMU core has LUO FLB registered with the iommufd LUO file handler
so the preserved iommu domain and iommu hardware unit state is available
during boot for early restore in the next kernel.

During boot the driver fetches the preserved state from the IOMMU core
and restores the state of preserved IOMMUs. Later when IOMMU core goes
through the devices and probes them, the iommu domains of preserved
devices are restored and the preserved devices are attached to them.
During attachment, the DMA ownership of these devices is also claimed.

Tested:

The iommufd_liveupdate_kexec_test selftest was used to verify the
preservation logic. Since vfio cdev preservation is not part of this
series, the test uses a new iommufd selftest op to trigger the device
preservation. So the kernel needs CONFIG_IOMMUFD_TEST. It was tested
using QEMU with virtual IOMMU (VT-d) support, in both legacy and
scalable mode, with virtio pcie device bound to the vfio-pci driver.
The next kernel was also booted with intel_iommu=off to verify that
VT-d is forced on.

Also Tested on an Intel machine with DSA device bound to vfio-pci
driver. Note that preservation is refused for devices where ATS is
supported, so the machine must be booted with pci=noats.

Following steps were followed for verification,

- Bind the test device with vfio-pci driver
- Run test on the machine by running

  ./iommufd_liveupdate_kexec_test <vfio-cdev-path>

- Trigger Kexec.
- After reboot, bind the device with vfio-pci driver and run the test
  again.

  ./iommufd_liveupdate_kexec_test <vfio-cdev-path> -s 2

- Test verifies that the restored device cannot be bound to a new
  iommufd, that the iommufd cannot be retrieved, as the iommufd restore
  is not supported yet, and that the session cannot be finished.

New:  KVM: arm64: nv: Allow the L1 VNCR page in cacheable PFNMAP memory
[PATCH] KVM: arm64: nv: Allow the L1 VNCR page in cacheable PFNMAP memory
Author: Jia He <justin.he@arm.com>

kvm_translate_vncr() refuses any PFN that isn't memory and injects an
SEA into the guest hypervisor. That is stricter than what the stage-2
fault path allows (kvm_s2_fault_pin_pfn()): a VM_PFNMAP or VM_MIXEDMAP
VMA whose host stage-1 attributes are cacheable is mapped cacheable at
stage-2 when FWB and DIC are present, and the guest can use such memory
as RAM (e.g. device memory that it onlines as a NUMA node). If the guest
then picks a page of that memory as the VNCR page of one of its own
guests, it takes an SEA as soon as it enters that guest.

Relax the check to match the stage-2 fault path, addressing the FIXME
added by commit 4bd7dbe0b224 ("KVM: arm64: nv: Inject SEA if guest VNCR
isn't normal memory"): look up the VMA, and allow the PFN if the VMA is
a cacheable VM_PFNMAP or VM_MIXEDMAP one and the system supports
cacheable PFNMAP at stage-2. No linear mapping is required, as VNCR
accesses use the EL2 fixmap and require no cache maintenance.
mmu_invalidate_seq is sampled before the PFN is faulted in, so a VMA
change after the lookup is caught by the mmu_invalidate_retry() check
that follows, as for the PFN itself.

Tested on a host with FEAT_FGT, FWB and DIC, with an L1 whose whole RAM
is a cacheable PFNMAP (host RAM withheld with mem= and handed to the VMM
by a test driver with remap_pfn_range()) starting an L2 guest
hypervisor. Without the patch, L2 repeatedly takes an SEA at the same PC
and fails to boot. With the patch, L2 boots successfully.

Signed-off-by: Jia He <justin.he@arm.com>

New:  KVM: arm64: nv: Discard undersized TTL hints in compute_tlb_inval_range()
[PATCH v2 1/2] KVM: arm64: nv: Discard undersized TTL hints in compute_tlb_inval_range()
Author: Colton Lewis <coltonlewis@google.com>

When an L1 guest issues TLBI IPAS2E1 with a non-zero TTL hint,
compute_tlb_inval_range() takes it at face value. If the hinted size is
smaller than the actual mapping (for example, a 4kB L3 hint on a 2MB
block), kvm_pgtable_stage2_unmap() clears the entire block while
kvm_remove_guest_s2_mappings() leaves its stale tracking entry behind in
guest_s2_mappings. On 16kB or 64kB hosts, a 4kB hint also triggers
WARN_ON(size & ~PAGE_MASK) in kvm_stage2_unmap_range().

A TTL hint smaller than PAGE_SIZE or the mapped entry is wrong. Check
it against PAGE_SIZE, the shadow stage-2 leaf size, and the guest block
size encoded in KVM_NV_GUEST_MAP_SZ. If it is too small, ignore the hint
and fall through to the unhinted invalidation path.

When falling back to the maximum mapping extent with stage-2 disabled,
size it from PAGE_SIZE rather than VTCR_EL2.TG0 so 1:1 shadow blocks are
still covered.

Fixes: d1de1576dc21 ("KVM: arm64: nv: Handle FEAT_TTL hinted TLB operations")
Signed-off-by: Colton Lewis <coltonlewis@google.com>

New:  KVM: arm64: nv: Upgrade sub-page TTL hint to maximum size
[PATCH] KVM: arm64: nv: Upgrade sub-page TTL hint to maximum size
Author: Marc Zyngier <maz@kernel.org>

Should a guest be slightly foolish and submit a S2 TLBI with a TTL hint
that describe a base granule size smaller than the host's page size,
we take the resulting size at face value and feed it to the S2 unmapping
code. Which legitimately screams about something not being page-aligned.

The architecture allows us to drop the TLBI on the floor, as we don't
support a S2 granule size smaller than the host's page size. But it turns
out that doing so is proving pretty hard (we call compute_tlb_inval_range
from a number of places, none of which is amenable to an early out).

Instead, detect the annoying case, and pretend that we don't have a TTL
hint at all, leaving the size upgrade mechanism to take place and use
the largest possible size for the guest's S2 granule size.

This will still allow nonsensical stuff to get through, such as a 4kB
level 2 (aka 2MB) from a guest with a 64kB S2 base granule size running
on a 16kB page size host, but that's not worse than doing nothing, and
the host code won't get shouty.

New:  KVM: Stop KVM_PRE_FAULT_MEMORY when the vCPU's dirty ring is full
[PATCH v3 1/3] KVM: Stop KVM_PRE_FAULT_MEMORY when the vCPU's dirty ring is full
Author: Fuad Tabba <fuad.tabba@linux.dev>

Pre-faulting can map a dirty-logged page writable, which pushes it to
the vCPU's dirty ring. KVM_RUN exits with KVM_EXIT_DIRTY_RING_FULL
before the ring overflows, but the pre-fault loop never checks it, so
one call can push more entries than the ring has free, which trips the
WARN in kvm_dirty_ring_push() and overwrites entries userspace hasn't
harvested. On x86:

  WARNING: arch/x86/kvm/../../../virt/kvm/dirty_ring.c:225 at kvm_dirty_ring_push+0x7a/0xd0
  Call Trace:
   make_spte+0x2cc/0x450
   kvm_tdp_mmu_map+0x5e1/0x7f0
   kvm_tdp_page_fault+0x12c/0x1b0
   kvm_mmu_do_page_fault+0x181/0x250
   kvm_arch_vcpu_pre_fault_memory+0x136/0x1d0
   kvm_vcpu_pre_fault_memory+0xcf/0x180
   kvm_vcpu_ioctl+0x455/0x770

Stop the loop once the ring is soft full, with the check KVM_RUN makes
before entering the guest. Return the pages already processed, or
-ENOSPC when there aren't any, since a retry can't succeed until
userspace harvests and resets the ring. s390 has the ioctl but no ring,
so give kvm_dirty_ring_check_request() a stub.

The check also sets run->exit_reason to KVM_EXIT_DIRTY_RING_FULL. On
arm64, KVM_RUN completes a pending MMIO exit only if exit_reason is
still KVM_EXIT_MMIO, and on riscv KVM_RUN does the same for its MMIO,
SBI and CSR exits. If a pre-fault stops on a full ring while such an
exit is pending, the next KVM_RUN doesn't complete it and the guest
repeats the instruction that caused the exit. Userspace can avoid that
by completing the exit with KVM_RUN before pre-faulting.

reserve. On x86, KVM_SET_MSRS does too when it writes the wall clock or
the Hyper-V hypercall page. A guest can also push past the reserve
within one exit, for example through the arm64 ITS. What those paths
should do when the ring fills is an open question for the dirty ring
API, which I don't think belongs in this series.

I didn't include the kvm_dirty_ring_check_request() rewrite that Sean
sketched on v1, since I think it can lose a request. It tests the
request first and clears it afterwards. If the vCPU is scheduled out in
between, loongarch sets the PV preempted flag in guest memory and x86
updates a Xen guest's runstate area, either of which pushes an entry.
When that push makes the ring soft full, the request it makes is then
cleared, and the vCPU runs with the ring soft full until its next push.
Clearing first and re-setting, as the code does now, doesn't have that
window.

New:  KVM: arm64: Fix THP block mapping when the PMD level is folded
[PATCH 1/2] KVM: arm64: Fix THP block mapping when the PMD level is folded
Author: Fuad Tabba <fuad.tabba@linux.dev>

When a THP backs guest memory, transparent_hugepage_adjust() rounds the
faulting gfn and pfn down to the THP's first page, and KVM maps the
whole THP with a PMD_SIZE block. However, the rounding uses a mask of
PTRS_PER_PMD - 1, and PTRS_PER_PMD is 1 when the PMD level is folded
(64K pages with a 42-bit VA, or 16K pages with a 36-bit VA). KVM then
maps PMD_SIZE worth of pages starting at the faulting page, and the
guest gets the host memory that follows the THP. With pKVM, the
hypervisor rejects the unaligned block, so the guest doesn't get that
memory.

Before the conversion to the generic page-table API, the unrounded pfn
went into a block descriptor, where the address bits below the block
size aren't part of the output address, so only the THP was mapped.

Round to PMD_SIZE >> PAGE_SHIFT pages instead.

New:  KVM: arm64: nv: Re-inject a stored SError after the exit
[PATCH] KVM: arm64: nv: Re-inject a stored SError after the exit
Author: Dan Carpenter <dan@pereq.eu>

KVM only has room for one pending exception or PC increment per vcpu.
If something is already pending and we try to add another through
kvm_pend_exception() or kvm_incr_pc(), it triggers a WARN().  If we add
an exception on top of an exception, the first one is lost.  If we add a
PC increment on top of an exception, the PC increment is lost and the
trapped instruction runs again.

Normally an exit handler records an exception or a PC increment, and
__kvm_adjust_pc() commits it before the next guest entry.  However, with
nested virtualization kvm_nested_sync_hwstate() can add an exception
before the exit handler runs.  It re-injects a stored SError after the
guest exits but before handle_exit(), which can pend the SError as an
exception.  The exit handler then records its own on top, for example an
HVC forwarded to the guest hypervisor, the FPAC for a failed ERETAA, or
the PC increment for a trapped instruction it has emulated.  This
triggers the WARN().

In this situation where we have two exceptions, the correct order is to
handle the exit first and then the SError.  Change the
kvm_nested_sync_hwstate() function to only store the SError.  Then

New:  KVM: arm64: nv: Reset MMIO state when committing a nested
[PATCH] KVM: arm64: nv: Reset MMIO state when committing a nested
Author: Dan Carpenter <dan@pereq.eu>

KVM has two ways to commit a pending exception, commit_pending_events()
which also resets the MMIO emulation state, and a direct call to
__kvm_adjust_pc() which doesn't.  The EL1 to EL2 path in
kvm_inject_nested() uses __kvm_adjust_pc(), but it needs to use
commit_pending_events() instead.

The scenario is: the vcpu exits to userspace for an MMIO access and
userspace then injects a synchronous external abort or an SError using
the KVM_SET_VCPU_EVENTS ioctl.  If the vcpu is in L2 context and L1 has
asked for the exception, then kvm_inject_nested() enters the exception
straight away and vcpu->mmio_needed stays set.  On the next KVM_RUN,
kvm_handle_mmio_return() completes the access in L1's context so it
skips the first instruction of L1's exception vector and writes the
MMIO data to one of L1's registers.

Replace the __kvm_adjust_pc() with commit_pending_events() so that the
MMIO emulation state is cleared.
