New:  KVM: nSVM: Add missing CET VMRUN consistency checks
[PATCH] KVM: nSVM: Add missing CET VMRUN consistency checks
Author: Jim Mattson <jmattson@google.com>

Per the APM, "Canonicalization and Consistency Checks,"

  [t]he following conditions are considered illegal state combinations:

   - CR4.CET=1 when CR0.WP=0
   - Any reserved bit set in S_CET
   - CR4.CET=1 and U_CET.SS=1 when EFLAGS.VM=1

Check these conditions in software before trying to VMRUN vmcb02, so that
the illegal states result in a #VMEXIT to L1 rather than an exit to
userspace with KVM_EXIT_FAIL_ENTRY.

New:  KVM: x86: Prefer exact vCPU ID matches for physical APIC map aliases
[PATCH v2 1/2] KVM: x86: Prefer exact vCPU ID matches for physical APIC map aliases
Author: Alejandro Jimenez <alejandro.j.jimenez@oracle.com>

When KVM_X2APIC_API_USE_32BIT_IDS is enabled, KVM allows events to target
a vCPU by its x2APIC ID even while the vCPU is in xAPIC mode. The optimized
physical APIC map also creates an entry for its truncated xAPIC ID.

If a vCPU with an ID > 0xff is created before a vCPU whose ID matches that
truncated xAPIC ID, the map retains the initial entry and it is not updated
to allow reaching the "low" vCPU ID via its xAPIC ID. This can result in
INIT/SIPI addressed to the xAPIC ID being delivered to the wrong vCPU.

Allow a vCPU in xAPIC mode to replace an existing entry when its vCPU ID
exactly matches the xAPIC ID. This ensures vCPUs are reachable via their
non-truncated xAPIC IDs, regardless of creation order, and preserves the
map entries using the full x2APIC IDs for vCPUs that require them.

Update the errata wording to describe this behavior, instead of promising
delivery to the vCPU with the lowest ID.

Fixes: 5bd5db385b3e ("KVM: x86: allow hotplug of VCPU with APIC ID over 0xff")

New:  KVM: x86: Fix physical APIC map routing for aliased xAPIC IDs
[PATCH v2 0/2] KVM: x86: Fix physical APIC map routing for aliased xAPIC IDs
Author: Alejandro Jimenez <alejandro.j.jimenez@oracle.com>

Fix physical APIC map routing when an xAPIC-mode vCPU with an ID above 0xff is
created before a vCPU whose ID matches its truncated xAPIC ID.
With KVM_X2APIC_API_USE_32BIT_IDS enabled, the existing alias entry in the xAPIC
range can prevent the lower-ID vCPU from being reached via its xAPIC ID, and
result in incorrect delivery of INIT/SIPI during CPU hotplug.

Following Sean's proposal [1], always allow the vCPU whose ID exactly matches
the aliased xAPIC ID to install an entry in the map, even if one is already
present. The full-ID (i.e. x2APIC ID) routes are still used to reach the
higher-ID vCPUs in xAPIC mode, preserving KVM hotplug behavior.

The standalone selftest covers both creation orders and checks delivery to both
the aliased xAPIC ID ("low") and the full x2APIC ID ("high") destinations.
Example output on an unpatched kernel:

ok 1 Destination 0x1d: Lower-ID vCPU 29 created first.
# Expected IRQ only on vCPU 29.
# Higher-ID vCPU 285: IRQ vector 0xe0 not delivered.
# Lower-ID vCPU 29: IRQ vector 0xe0 delivered.
ok 2 Destination 0x11d: Lower-ID vCPU 29 created first.
# Expected IRQ only on vCPU 285.
# Higher-ID vCPU 285: IRQ vector 0xe1 delivered.
# Lower-ID vCPU 29: IRQ vector 0xe1 not delivered.
not ok 3 Destination 0x1d: Higher-ID vCPU 285 created first.
# Expected IRQ only on vCPU 29.
# Higher-ID vCPU 285: IRQ vector 0xe0 delivered.
# Lower-ID vCPU 29: IRQ vector 0xe0 not delivered.
ok 4 Destination 0x11d: Higher-ID vCPU 285 created first.
# Expected IRQ only on vCPU 285.
# Higher-ID vCPU 285: IRQ vector 0xe1 delivered.
# Lower-ID vCPU 29: IRQ vector 0xe1 not delivered.
# Totals: pass:3 fail:1 xfail:0 xpass:0 skip:0 error:0

Note the third test case fails because vCPU 285 was created before vCPU 29.

Changes since v1 [2]:
- Prefer an exact vCPU ID match instead of selecting the lowest vCPU ID, and
update the errata wording.
- Move the selftest out of recalc_apic_map_test into a standalone
apic_id_routing_test.
- Cover both creation orders, and check delivery via the higher vCPU's full
x2APIC ID.
- Use kselftest, allowing the full-ID test to run even when an earlier alias
check fails in unpatched kernels.

New:  vfio: selftests: Automatically detect the IOMMU mode
[PATCH v3 1/5] vfio: selftests: Automatically detect the IOMMU mode
Author: David Matlack <dmatlack@google.com>

Pick the most preferred IOMMU mode that is available on the current
system when iommu_init() is passed a NULL mode, rather than always using
iommufd. Drop the global default_iommu_mode and convert its users to
pass NULL to iommu_init().

iommufd is an optional feature, and VFIO's iommufd support additionally
requires CONFIG_VFIO_DEVICE_CDEV. Hardcoding iommufd as the default
causes tests to fail with an unhelpful assert on otherwise functional
kernels that only support the legacy VFIO container:

  tools/testing/selftests/vfio/lib/iommu.c:448: Assertion Failure

  Expression: iommu->iommufd > 0
  Observed: 0xffffffffffffffff > 0
  [errno: 2 - No such file or directory]

Order iommu_modes[] by preference: iommufd, then the VFIO container,
then iommufd's VFIO container compatibility modes, with type1v2 ahead of
type1, i.e. prefer iommufd, the native VFIO container over iommufd's
emulation of it, and type1v2 over the older type1. Consider a mode
available if its container (or /dev/iommu) can be opened and supports
the mode's IOMMU type. Also require VFIO device cdevs for iommufd mode
and VFIO groups for container modes, since that is how the selftests
access devices in those modes. If no mode is available, fail with a
message suggesting that VFIO or IOMMUFD may not be loaded and enabled.

New:  x86/sev: Scan each core's own RMPOPT window
[PATCH 1/2] x86/sev: Scan each core's own RMPOPT window
Author: Ashish Kalra <Ashish.Kalra@amd.com>


rmpopt_scan_range() walked a single global [rmpopt_pa_start, rmpopt_pa_end]
range, which is only correct while every core shares one window.  Read the
executing core's own RMPOPT_BASE instead and walk only that window, so each
core optimizes the window its own RMPOPT_BASE points at.

The window is described entirely by the RMPOPT_BASE MSR: RMPOPT_BASE_ADDR
(bits 51:30) is the 1 GB-aligned base and RMPOPT_TABLE_SIZE (bits 22:1) is
the window size in GB.  Walk [base, base + size), clamped to the top of
populated memory.

Signed-off-by: Ashish Kalra <ashish.kalra@amd.com>

New:  x86/sev: Per-node RMPOPT windows for >2TB systems
[PATCH 0/2] x86/sev: Per-node RMPOPT windows for >2TB systems
Author: Ashish Kalra <Ashish.Kalra@amd.com>


RMPOPT_BASE is a per-core MSR whose optimization window covers at most 2 TB
of physical address space from its base.  The merged RMPOPT series programs
every core with the same base (start of RAM), so on a machine with more
than 2 TB of RAM only the first 2 TB is ever RMP-check-skipped; everything
above 2 TB pays full RMP checks for the life of the system.

This series extends the optimization across all of physical memory on >2 TB
systems by giving each NUMA node's cores a 2 TB window placed over that
node's own local memory.  A core overwhelmingly accesses its local node's
RAM, so spending each node's 2 TB budget on that memory puts the
optimization where the accesses land; whole-machine coverage is the union
of the per-node windows.  The <=2 TB case is unchanged: the window search
returns start-of-RAM for every node, so all cores share one window.

  Patch 1 generalizes the optimization scan to read each core's own
    RMPOPT_BASE (base and window size straight from the MSR) and walk only
    that window.  No behavioral change while every core shares one window.
  Patch 2 adds the per-node window selection and programming, and warms
    every window before the interrupts-disabled fan-out.

HW-validated on a ~3 TB 2-socket NPS2 box: every node optimizes its own
local memory and all populated memory is covered.

New:  ARM: dts: imx6ull-colibri-emmc: Add DPI display and VGA overlays
[PATCH v2 0/8] ARM: dts: imx6ull-colibri-emmc: Add DPI display and VGA overlays
Author: Francesco Dolcini <francesco@dolcini.it>


Add device tree overlays for the Toradex display accessories on the
Colibri iMX6ULL eMMC parallel RGB LCD interface, mirroring what was
recently merged for the Colibri iMX7 eMMC:

 - Capacitive Touch Display 7" Parallel, touch on the 10-way Capacitive
   Touch Interface connector (Iris v2, Aster)
 - Capacitive Touch Display 7" Parallel, touch through the Capacitive
   Touch Adapter (Eval v3)
 - Resistive Touch Display 7" Parallel (Eval v3)
 - VGA output through a non-programmable video DAC (Aster, Eval v3,
   Iris, Iris v2)

The panel, backlight and LCDIF part of each overlay is identical between
the two modules, both using the same LCDIF binding and labels. Instead
of duplicating it, each patch moves that part out of the corresponding
Colibri iMX7 eMMC overlay into a dtsi shared by the two modules and
includes it from both. Only the Atmel MaxTouch wiring, the conflicting
PWM channels and the BL_ON pinctrl and GPIO driving the VGA DAC power-save
input stay in the SoC specific overlays. The shared files follow the
imx6ul-imx6ull-*.dtsi naming already used in the same directory.

The overlay names are the Toradex product names of the accessories, and
a product name is unique only together with its vendor. Following the
discussion on the Apalis iMX6 overlays [1], the Toradex accessories get
a "tdx" vendor prefix, the same way third-party accessories on Toradex
boards already carry theirs, e.g. "rpi" in
k3-am625-verdin-rpi-display-2-7in.dtso.

Patches 1 and 2 are fixes and come first, so they can be backported
without the rename. Patch 1 (from Emanuele) drives the VGA DAC power-save
input through the BL_ON signal, without it the Eval and Aster carrier
boards show a black image. Patch 2 adds the Colibri iMX7 eMMC touch
adapter and resistive touch .dtbo to dtb-y, as they were built only as a
dependency of the combined DTBs and never shipped by dtbs_install.
Patch 3 adds the tdx vendor prefix to the existing Colibri iMX7 eMMC
display overlays. Patch 4 aligns the Colibri iMX6ULL backlight
brightness levels with the Colibri iMX7 ones, the LED driver of the 7"
displays turns off below roughly 15% duty cycle and only the three
highest of the current levels produced a visible image.

New:  KVM: arm64: Add support for self-hosted debug in protected guests
[PATCH 01/16] KVM: arm64: Add support for self-hosted debug in protected guests
Author: Fuad Tabba <fuad.tabba@linux.dev>

pKVM hides DebugVer from protected guests and makes their debug
registers RAZ/WI or UNDEFINED, so they don't have breakpoints,
watchpoints or single-step. For a non-protected guest, the host sets the
owner of the debug registers at vcpu load, from the guest's MDSCR_EL1
and OS Lock, and EL2 copies the owner and the registers in at each
entry. However, the host can't see a protected guest's registers.

Set the owner at EL2 for a protected vCPU instead, by the rules the host
uses for a non-protected guest, but keep MDCR_EL2.TDA set when the guest
is the owner. A trap handler returns to the guest without going back
through the world switch, so a handler that changes the owner switches
the debug registers itself. The PSCI CPU_ON reset runs after the vcpu
load, so it sets the owner again.

Advertise DebugVer, capped at V8P8 as for a non-protected guest, and the
breakpoint, watchpoint and context-aware breakpoint counts. The other
debug registers that took an UNDEF behave as they do for a non-protected
guest that doesn't own its debug registers.

Signed-off-by: Fuad Tabba <fuad.tabba@linux.dev>

New:  KVM: nVMX: Prevent potential user space corruption
[PATCH] KVM: nVMX: Prevent potential user space corruption
Author: Dan Carpenter <error27@gmail.com>

At the start of the function it does:

	if (is_guest_mode(vcpu) &&
	    nested_cpu_has_shadow_vmcs(vmcs12) &&
	    vmcs12->vmcs_link_pointer != INVALID_GPA)
		kvm_state.size += sizeof(user_vmx_nested_state->shadow_vmcs12);
                ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

This says if the three conditions: is_guest_mode(),
nested_cpu_has_shadow_vmcs() and != INVALID_GPA are met then we are
copying sizeof(shadow_vmcs12), which is 4k, bytes to the user.

Later, we check if the user has enough space to handle the copy and
if "user_data_size" is too small we bail out.

        if (user_data_size < kvm_state.size)
                goto out;

But at the end of the function it accidentally left out the
is_guest_mode() part of the condition so potentially we could copy more
than "user_data_size" bytes which would result in userspace corruption.
Presumably, users normally allocate enough space and we don't often
corrupt memory in practice.

Add the is_guest_mode() condition to fix this bug.

New:  KVM: arm64: nv: Skip empty spans when unmapping a shadow S2
[RFC PATCH 1/2] KVM: arm64: nv: Skip empty spans when unmapping a shadow S2
Author: Haseeb Ashraf <haseebashraf091@gmail.com>


Emulating TLBI VMALLS12E1IS unmaps the whole shadow stage-2 of the
guest hypervisor's current VMID by passing the complete nested IPA
range to kvm_stage2_unmap_range(). That walks the range in chunks of
the largest block size and calls kvm_pgtable_stage2_unmap() on each of
them, mapped or not: 262144 chunks per shadow MMU with 4kB pages and a
48-bit PARange, each ending in a range TLBI when FEAT_TLBIRANGE and
FWB are available.

Guest hypervisors such as Xen issue this TLBI while creating domains,
and an empty table is charged for the whole IPA space. A full-range
unmap of one shadow MMU takes 0.87-1.06 s on AmpereOne (Xen on KVM,
4kB pages, function_graph). On Graviton4 (Xen-on-KVM, 48-bit IPA),
twelve VMALLS12E1IS traps took 1.46-9.50 s each (median 3.09 s), all
of it in stage2_apply_range():

  22)   4.180 us    |              } /* kvm_pgtable_stage2_unmap */
  22) $ 2278329 us  |            } /* stage2_apply_range */
  22) $ 2278329 us  |          } /* __unmap_stage2_range */
  22) $ 2278330 us  |        } /* kvm_stage2_unmap_range */
  22) $ 2278331 us  |      } /* s2_mmu_unmap_range */
  22) $ 2278337 us  |    } /* kvm_s2_mmu_iterate_by_vmid */
  22) $ 2278347 us  |  } /* handle_vmalls12e1is */

Add kvm_stage2_unmap_all(). It uses kvm_pgtable_get_leaf() to find the
entry covering the current address and, if that is a zero descriptor
at least as large as an unmap chunk, skips to the end of the span
without entering the unmap walker. Everything else is unmapped chunk
by chunk as before, so populated chunks keep their unmap, cache
maintenance and table reclamation ordering. Non-zero invalid
descriptors are never skipped, as they can carry software state.

Populated chunks use the tracked unmap, and the guest stage-2 records
of a skipped span are removed under the same mmu_lock hold: nothing is
mapped there, so they are stale. Dropping them after the walk would be
wrong if mmu_lock was released, as a concurrent fault could have
mapped something behind it.

The helper ends with a VMID-wide TLBI: VMALLS12E1IS also invalidates
stage-1 translations, which the per-chunk invalidations used to do
even for empty tables. mmu_lock may be dropped between spans if the
caller allows blocking, as for the range unmap.

Only the VMALLS12E1IS handler is converted here.

Signed-off-by: Haseeb Ashraf <haseeb.ashraf@siemens.com>

New:  KVM: arm64: Register irq_bypass consumers only with GICv4
[PATCH] KVM: arm64: Register irq_bypass consumers only with GICv4
Author: Jinqian Yang <yangjinqian1@huawei.com>

kvm_arch_has_irq_bypass() on arm64 returns true unconditionally, so
every irqfd assignment registers an irq_bypass consumer even when the
hardware cannot perform GICv4 direct MSI forwarding. In that case
kvm_vgic_v4_set_forwarding() bails out at its very first check, since
vgic_supports_direct_msis() is false without has_gicv4, and the
registration becomes pure overhead: every KVM_IRQFD ioctl takes the
global irq_bypass mutex, which becomes a contention point when many
VMs boot concurrently.

Gate the registration on kvm_vgic_global_state.has_gicv4, the way x86
gates on enable_device_posted_irqs. Functionally this is a no-op:
without GICv4 the consumer registration never did anything beyond
acquiring the lock.  On a GICv3-only host booting 100 microVMs
concurrently this cuts the average boot time by ~5 ms, matching the
gain observed with CONFIG_HAVE_KVM_IRQ_BYPASS=n.

Signed-off-by: Jinqian Yang <yangjinqian1@huawei.com>

New:  KVM: arm64: Add support for self-hosted debug in protected guests
[PATCH 01/16] KVM: arm64: Add support for self-hosted debug in protected guests
Author: Fuad Tabba <fuad.tabba@linux.dev>

pKVM hides DebugVer from protected guests and makes their debug
registers RAZ/WI or UNDEFINED, so they don't have breakpoints,
watchpoints or single-step. For a non-protected guest, the host sets the
owner of the debug registers at vcpu load, from the guest's MDSCR_EL1
and OS Lock, and EL2 copies the owner and the registers in at each
entry. However, the host can't see a protected guest's registers.

Set the owner at EL2 for a protected vCPU instead, by the rules the host
uses for a non-protected guest, but keep MDCR_EL2.TDA set when the guest
is the owner. A trap handler returns to the guest without going back
through the world switch, so a handler that changes the owner switches
the debug registers itself. The PSCI CPU_ON reset runs after the vcpu
load, so it sets the owner again.

Advertise DebugVer, capped at V8P8 as for a non-protected guest, and the
breakpoint, watchpoint and context-aware breakpoint counts. The other
debug registers that took an UNDEF behave as they do for a non-protected
guest that doesn't own its debug registers.

Signed-off-by: Fuad Tabba <fuad.tabba@linux.dev>

New:  KVM: arm64: Support debug, SVE, MOPS, PIE/POE, FPMR and more in protected VMs
[PATCH 00/16] KVM: arm64: Support debug, SVE, MOPS, PIE/POE, FPMR and more in protected VMs
Author: Fuad Tabba <fuad.tabba@linux.dev>

Hi folks,

With most of the groundwork now merged, bringing protected VMs up to
the features we support for them in Android turns out not to be a big
series. So this folds self-hosted debug [1] and SVE [2], which I posted
separately last week, into one series with the rest. Both are small,
and keeping them apart would only leave a few conflicts where they add
neighbouring lines to the pVM ID-register code. The debug and SVE
patches are unchanged from those postings.

  01:     Self-hosted debug.
  02-05:  SVE, with EL2 owning a protected vCPU's SVE state.
  06-07:  Compute a protected vCPU's fine-grained traps at EL2.
  08-16:  Advertise TCR2, SCTLR2, S1PIE, S1POE, MOPS, FPMR and the
          features EL2 already handles for non-protected guests.

Tested on QEMU, in hVHE and nVHE, and on FVP for S1POE and the fields
QEMU doesn't model (CLRBHB, RPRFM, ECBHB, LSFE, LSUI, HAFT, ETS3 and
F16MM). v2 of the pKVM selftests series [3] will cover debug, SVE,
MOPS, PIE, POE and FPMR.

Based on Linux 7.4-rc1 (6628e7d4c6b25); it also applies to 7.4-rc2
(7475ea8b58616).

Cheers,
/fuad
