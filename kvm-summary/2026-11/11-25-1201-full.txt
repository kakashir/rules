[PATCH v2 3/3] KVM: arm64: nv: Allow the L1 VNCR page in cacheable PFNMAP memory
Author: Jia He <justin.he@arm.com>

kvm_translate_vncr() refuses any PFN that isn't memory and injects an
SEA into the guest hypervisor. That is stricter than what the stage-2
fault path allows (kvm_s2_fault_pin_pfn()): a VM_PFNMAP or VM_MIXEDMAP
VMA whose host stage-1 attributes are cacheable is mapped cacheable at
stage-2 when FWB and DIC are present, and the guest can use such memory
as RAM (e.g. device memory that it onlines as a NUMA node). If the guest
then picks a page of that memory as the VNCR page of one of its own
guests, it takes an SEA as soon as it enters that guest.

For VM_PFNMAP and VM_MIXEDMAP VMAs, relax the check to match the stage-2
fault path, and remove the FIXME added by commit 4bd7dbe0b224 ("KVM:
arm64: nv: Inject SEA if guest VNCR isn't normal memory"). Look up the
VMA, and allow the PFN if the VMA is a cacheable VM_PFNMAP or
VM_MIXEDMAP one and the system supports cacheable PFNMAP at stage-2. No
linear mapping is required, because VNCR accesses use the EL2 fixmap and
require no cache maintenance.

Get the HVA with gfn_to_hva_memslot_prot(), as kvm_handle_guest_abort()
does. gfn_to_hva_memslot() returns KVM_HVA_ERR_RO_BAD for a read-only
memslot, and the VMA lookup would then fail. A VNCR page in a read-only
memslot is valid and is mapped read-only since commit 2684e02bac41
("KVM: arm64: nv: Respect read-only PFN when mapping L1 VNCR").

mmu_invalidate_seq is sampled before the PFN is faulted in, so a VMA
change after the lookup is caught by the mmu_invalidate_retry() check
that follows, as for the PFN itself.

Tested on a host with FEAT_FGT, FWB and DIC, with an L1 whose whole RAM
is a cacheable PFNMAP (host RAM withheld with mem= and handed to the VMM
by a test driver with remap_pfn_range()) starting an L2 guest
hypervisor. Without the patch, L2 repeatedly takes an SEA at the same PC
and fails to boot. With the patch, L2 boots successfully.

The read-only case was tested on a Neoverse-N2 host. The guest
hypervisor's VNCR page is in a cacheable PFNMAP registered as a
read-only memslot, and a nested context reads VTTBR_EL2. When the HVA
is looked up with gfn_to_hva_memslot(), the guest hypervisor takes an
SEA. With this patch, the read returns the contents of the VNCR page.

Signed-off-by: Jia He <justin.he@arm.com>

[PATCH v2 2/3] KVM: arm64: selftests: Add a test for VNCR_EL2 translation faults
Author: Jia He <justin.he@arm.com>

Add a test where the guest hypervisor enters a nested context with
HCR_EL2.{NV,NV2} set and reads VTTBR_EL2, which FEAT_NV2 turns into a
load from the VNCR page. The last-level table that maps the VNCR page is
placed in a read-only memslot, and TCR_EL2.HA is set.

With the access flag set, KVM maps the VNCR page and the read returns
the value in that page. With the access flag clear, KVM cannot update the
descriptor and must inject an SEA on translation table walk into the
guest hypervisor. A control case with the table in a writable memslot
checks that KVM sets the access flag and maps the page.

[PATCH v2 1/3] KVM: arm64: nv: Inject an SEA when the VNCR walk cannot set the AF
Author: Jia He <justin.he@arm.com>

When the guest hypervisor enables hardware Access flag management
(TCR_EL2.HA), KVM's stage-1 walker sets the AF in the descriptor that
maps VNCR_EL2 with __kvm_at_swap_desc(). If the descriptor is in a
read-only memslot, the update fails with -EPERM and walk_s1() records an
SEA on translation table walk in the walk result.

kvm_handle_vncr_abort() does not handle -EPERM. It neither injects the
fault nor maps the VNCR page, and returns to the guest. The guest takes
the same VNCR abort again and never makes progress.

Treat -EPERM like the other walk failures and inject the recorded fault
into the guest hypervisor.

Tested with the selftest added in the next patch on a Neoverse-N2 host.
Without this patch, the vCPU exits about 1.3 million times in 5 seconds
on the same VNCR abort and makes no progress. With this patch, the
guest hypervisor receives an SEA on translation table walk at level 3.

[PATCH v2 0/3] KVM: arm64: nv: VNCR page in read-only and cacheable PFNMAP memory
Author: Jia He <justin.he@arm.com>

On a VNCR abort, KVM walks the guest hypervisor's EL2 stage-1 tables
and maps the page that VNCR_EL2 points to. This series fixes two cases
where that fails.

Patch 1 fixes a bug that predates this series. If TCR_EL2.HA is set and
the descriptor that maps VNCR_EL2 is in a read-only memslot, KVM cannot
set the AF and the walk returns -EPERM. kvm_handle_vncr_abort() has no
case for -EPERM, so the vCPU takes the same abort forever. Patch 1
injects the SEA that the walk recorded.

Patch 2 adds a selftest for this case.

Patch 3 allows the VNCR page in a cacheable VM_PFNMAP or VM_MIXEDMAP
VMA. The stage-2 fault path already maps such memory as cacheable, but
kvm_translate_vncr() rejects it and injects an SEA.

Patch 1 can be applied on its own.

Based on v7.4-rc3.

Changes since v1:
- New patches 1 and 2, for the -EPERM issue found by Sashiko.
- Patch 3: get the HVA with gfn_to_hva_memslot_prot() so that a VNCR
  page in a read-only memslot is not rejected (Sashiko).
- Patch 3: limit the stage-2 comparison in the commit message to
  VM_PFNMAP and VM_MIXEDMAP VMAs.

[PATCH v3 09/19] x86/sev: Use non-instrumented bitops in the GHCB accessors
Author: Sasha Levin <sashal@kernel.org>

The GHCB accessors are used from noinstr code, such as
__sev_es_nmi_complete(), but use test_bit() and __set_bit(), which
call the KASAN and KCSAN checks. arch/x86/coco/sev/Makefile disables
KASAN and KCSAN for noinstr.o, which turns those checks into empty
stubs, but they still have to be inlined. Instrumentation such as gcov
can prevent that and leave calls to kasan_check_write() behind in
noinstr code.

Use the arch_ bitops, which aren't instrumented, as is done elsewhere
for noinstr code.

[kvm-unit-tests PATCH v3 0/9] riscv: ACPI boot and BRS-I SBI tests
Author: Xiang W <wangxiang@iscas.ac.cn>

Hi,

This series lets RISC-V kvm-unit-tests boot on BRS-I platforms that
describe the system with UEFI + ACPI instead of a device tree, and adds
a first unit test for the SBI rules in the RISC-V Boot and Runtime
Services specification [1].

The RISC-V port currently assumes a DT for CPU bring-up, timer
frequency, ISA-string parsing and console setup. BRS-I firmware
typically does not provide a usable DT, and often has no MMIO UART
either. Without these changes the existing tests abort in setup before
they can exercise SBI.

Patches 1-4 teach the RISC-V library to initialize from ACPI when a DT
is absent:

- locate the ACPI 2.0 RSDP via the EFI configuration table
- parse MADT RINTC entries for hart / CPU bring-up
- read the timebase frequency from RHCT
- parse the ISA string from RHCT Hart Info nodes (match by ACPI UID)

Patch 5 falls back to the SBI DBCN console when UART initialization
fails, so ACPI guests without an MMIO UART can still print. Patch 6
drops the early exit in the EFI runner that previously rejected
EFI_USE_ACPI=y.

Patch 7 moves isa_init() into cpu_set_fdt() and cpu_set_acpi() so
cpu_has_extension() can read every hart's ISA bits from the boot hart,
including secondaries that have not started yet.

Patch 8 captures S-mode IMSIC interrupt file addresses at boot time.
The DT path is Andrew's posted patch [2]; the ACPI path copies
RINTC.imsic_addr only when an IMSIC structure is present in the MADT,
as ACPI requires OSPM to ignore that field otherwise.

Patch 9 adds riscv-brs, a unit test that checks the SBI requirements
from the BRS specification (version, HSM, TIME/Sstc, IPI/IMSIC,
RFENCE/IMSIC, PMU/Sscsrind+Ssccfg, and DBCN when SPCR type is 0x15).

v3 changes
==========
Address review comments from Andrew Jones on v2, except the three
points in the next section.

- call isa_init() from cpu_set_fdt() / cpu_set_acpi() rather than
  looping in cpu_init()
- RHCT parsing: (void *)node, reverse fir tree, assert_msg, treat a
  bad offset as an assert
- drop unnecessary CONFIG_EFI guards around <acpi.h>
- check Sstc and Sscsrind+Ssccfg on all present harts
- use thread_info.imsic_addr instead of parsing IMSIC in the test
- ACPI IMSIC: ignore RINTC.imsic_addr unless an IMSIC MADT structure
  is present
- coding-style nits (braces, SBI enum alignment, report_skip wrapping,
  "Initialize" capitalization)

Differences from the v2 review
==============================
1. Console policy (patch 5)

   The suggested diff prefers SBI DBCN whenever CONFIG_SBI_CONSOLE is
   set and DBCN probes successfully, with UART as a fallback.

   This version keeps UART when initialization succeeds and uses DBCN
   only if there is no usable UART. Each DBCN write is an SBI ecall,
   which is slower than an MMIO UART store, so the fast path should
   stay on UART when one is present. Guests without an MMIO UART still
   print via DBCN.

2. SBI_010 version comparison (patch 9)

   The review asked to compare (ret.value & SBI_SPEC_VERSION_MASK)
   against sbi_mk_version(2, 0). The test already decodes major and
   minor for the report string, so it compares
   sbi_mk_version(major, minor) instead. That drops the reserved bit
   the same way and avoids encoding the version a second time.

3. SBI_040 / SBI_050 IMSIC check (patch 9)

   v2 parsed DT/ACPI on every call, and the review asked to cache
   all_harts_have_imsic(). After patch 8 the check is a walk of
   cpus[].isa and cpus[].imsic_pa, so the two tests keep their own
   loops rather than sharing a cached helper.

Tested with QEMU virt:

  ./configure --arch=riscv64 \
              --cross-prefix=riscv64-linux-gnu- \
              --console=sbi --enable-efi && make

  EFI_USE_ACPI=y EFI_UEFI=/path/to/RISCV_VIRT_CODE.fd \
    ./riscv/efi/run riscv/riscv-brs.efi

[PATCH v1 21/21] hw/i386/kvm/xen_evtchn: Allow unmapping an emulated MSI PIRQ
Author: David Woodhouse <dwmw2@infradead.org>


The "unmap GSI PIRQs only" check rejected every negative gsi, which

[PATCH v1 15/21] hw/9pfs/xen-9p-backend: Validate the request header size field
Author: David Woodhouse <dwmw2@infradead.org>


A request whose header declares a size smaller than the header itself
was accepted, submitting a zero-length PDU and advancing nothing, to be
re-processed on every ring kick. Reject it instead. Set inprogress only

[PATCH v1 02/21] i386/xen: Don't resample GSI when per-vCPU upcall vector is in use
Author: David Woodhouse <dwmw2@infradead.org>


The callback_via GSI (or PCI INTx) and the per-vCPU upcall vector are
mutually exclusive delivery mechanisms for Xen event channel upcalls.
Xen itself will never assert the callback GSI for a vCPU which has a
per-vCPU upcall vector configured.

When the interrupt is acked, QEMU's resampling logic reasserts the
GSI if evtchn_upcall_pending is still set. If the guest has configured
a per-vCPU upcall vector, events are delivered through that vector and
the GSI is unexpected; a guest which receives both the vector upcall
and a spurious GSI interrupt for the same event can crash. This was
observed in production with Windows guests on a different VMM which
implements the same resampling logic.

If a per-vCPU upcall vector is configured, don't resample the GSI;
just deassert it.

[PATCH v1 03/21] i386/xen: Free Xen vCPU timers when a vCPU is destroyed
Author: David Woodhouse <dwmw2@infradead.org>


kvm_xen_init_vcpu() allocates the per-vCPU timers with the CPUState as
callback opaque, and nothing freed them on vCPU destruction. So a guest
could arm the periodic timer for a vCPU (VCPUOP_set_periodic_timer
always reaches QEMU; the kernel doesn't handle it) and eject that vCPU
via ACPI hotplug, leaving the armed timer pointing at a freed X86CPU.

Free both timers in kvm_xen_destroy_vcpu(), called from
kvm_arch_destroy_vcpu(). That runs under the BQL, as do the timer
callbacks, so it cannot race an in-flight callback. It *can* race a
timer hypercall from another vCPU — hypercalls don't take the BQL,
which is why xen_timers_lock exists — so clear the pointers under that
lock and have the periodic timer paths return -ENOENT when the timer is
gone, as for a nonexistent vCPU. The singleshot ops act only on the
calling vCPU, so cannot race its destruction.

Also move the timer_del() in do_set_periodic_timer() inside the lock,
where it should have been all along.

[PATCH v1 04/21] hw/xen: Publish backend features before setting state to InitWait
Author: David Woodhouse <dwmw2@infradead.org>


The XenbusStateInitWait transition tells the frontend that the
backend's parameters are readable, but xen_device_realize() set it
before calling the implementation's realize method — which is what
writes the feature nodes ('max-ring-page-order' et al. for xen-block,
'feature-rx-copy' for xen-net).

Linux blkfront reads 'max-ring-page-order' with xenbus_read_unsigned():
no wait, no retry, default 0. Lose the race and it silently negotiates
a single-page ring — 32 request slots instead of 256. A device
hot-plugged into a running guest loses essentially every time; at boot
the frontend doesn't come looking until long after realize finished.
Netfront reads its feature nodes the same way.

Commit 240cc11369fc ("hw/xen: Avoid crash when backend watch fires too
early") introduced this by moving the realize call after the block of
code which both populates the initial xenstore nodes *and* sets
InitWait. The crash it fixed was real — xen-block's realize processes
watch events via blkconf_geometry()'s aio_poll(), and the handlers fell
over when the nodes didn't yet exist — but only the node population
needed to come first.

So keep the node population and the 'online' write before realize, and
move only the InitWait transition after it. A watch event during
realize now finds the frontend in Initialising and no backend 'state'
node, which the handlers tolerate; none of the three realize
implementations reads the backend state. Verified against the original
2023 crash reproducer as well as the ring-order negotiation.

Fixes: 240cc11369fc ("hw/xen: Avoid crash when backend watch fires too early")

[PATCH v10 11/18] KVM: x86/pmu: Support Intel fixed counter 3 on mediated vPMU
Author: Zide Chen <zide.chen@intel.com>


Starting with Ice Lake, Intel introduced fixed counter 3, which counts
TOPDOWN.SLOTS - the number of available slots for an unhalted logical
processor.  It serves as the denominator for top-level metrics in the
Topdown Microarchitecture Analysis method.

Emulating this counter on legacy vPMU would require introducing a new
generic perf encoding for the Intel-specific TOPDOWN.SLOTS event in
order to call perf_get_hw_event_config().  This is undesirable as it
would pollute the generic perf event encoding.

Moreover, KVM does not intend to emulate IA32_PERF_METRICS in the
legacy vPMU model, and without IA32_PERF_METRICS, emulating this
counter has little practical value.  Therefore, expose fixed counter
3 to guests only when mediated vPMU is enabled.

On PMU v5+, clamp num_counters_fixed to the number of contiguous fixed
counters enumerated in CPUID.0xA:EDX[4:0] to prevent exposing non-
contiguous counter holes that KVM cannot emulate.

[PATCH v10 09/18] KVM: x86/pmu: Mask only OS/USR bits when filtering fixed counters
Author: Zide Chen <zide.chen@intel.com>

In preparation for supporting AnyThread deprecation and RDPMC Metrics Clear
Mode, mask only INTEL_FIXED_0_KERNEL and INTEL_FIXED_0_USER when updating
fixed_ctr_ctrl_hw in kvm_mediated_pmu_refresh_event_filter().

Masking the full 0xf nibble would cause two issues:

1. AnyThread for fixed counters 0-2: When a counter is allowed, copying
   the full nibble from guest-visible pmu->fixed_ctr_ctrl back into
   hardware-visible pmu->fixed_ctr_ctrl_hw would resurrect AnyThread in
   hardware, defeating SMT cross-VM isolation.

2. Metrics Clear for fixed counter 3: If an event filter denies fixed
   counter 3, clearing 0xf inadvertently strips METRICS_CLEAR_EN from
   hardware. If the guest sets METRICS_CLEAR_EN and executes native RDPMC,
   metrics will remain uncleared, returning stale data.

Masking only the OS/USR bits gates hardware counting without
clobbering other control bits, matching general-purpose counter
filtering which only masks the event ENABLE bit.

[PATCH v10 00/18] KVM: x86/pmu: Add hardware Topdown metrics support
Author: Zide Chen <zide.chen@intel.com>

Activation of the PERF_METRICS feature in hardware requires both
PERF_METRICS_AVAILABLE and the existence of fixed counter 3. However,
the presence of the IA32_PERF_METRICS MSR is architecturally decoupled
from it.

This version enforces the following dependencies between PERF_METRICS
and fixed counter 3 to comply with the SDM:

- Advertise PERF_METRICS and RDPMC_METRICS_CLEAR only when mediated vPMU
  is enabled and host perf reports num_topdown_events != 0.

  Gate on host Topdown events in addition to host fixed counter 3 so
  that this feature is advertised on known CPU models only.

- Gate IA32_PERF_METRICS and RDPMC existence solely on guest
  PERF_CAP_PERF_METRICS (per SDM Vol 4 Table 2-2). Without guest fixed
  counter 3, neither RDMSR nor RDPMC faults (#GP): all metric fields are
  reserved (~0ull), reads (RDMSR and RDPMC) succeed and return 0, writing
  0 succeeds, and only non-zero writes #GP.

  With fixed counter 3, valid metric fields are unmasked based on
  host-provided num_topdown_events.

- Gate IA32_PERF_METRICS, GLOBAL_CTRL, and RDPMC passthrough (and
  hardware context switching) on having both guest PERF_METRICS and fixed
  counter 3. If either is missing, metrics cannot count in hardware;
  accesses remain intercepted and handled cleanly in KVM software
  (e.g., emulated RDPMC succeeds and returns 0).

- Allow setting GLOBAL_CTRL[48] whenever PERF_METRICS is present on
  the guest, because the SDM defines bit 48 as an architectural control
  bit (not reserved) when PERF_METRICS is supported, even if fixed counter
  3 is absent.

- Require guest fixed counter 3 to unmask FIXED_CTR_CTRL[14]
  (METRICS_CLEAR_EN), as bit 14 resides in fixed counter 3's control nibble.
  Without fixed counter 3, bit 14 remains reserved; when enabled with
  fixed counter 3, RDPMC of metrics clears both PERF_METRICS and fixed
  counter 3 in hardware and emulation.

[PATCH v2] vfio/pci: Only lock the upstream bridge if the reset may
Author: Samiullah Khawaja <skhawaja@google.com>

Commit 962ae6892d8b ("vfio/pci: Lock upstream bridge for
vfio_pci_core_disable()") makes vfio_pci_core_disable() trylock the
upstream bridge before resetting the device, and skips the reset if the
trylock fails.

All VFs of a PF have the same upstream bridge. Take a device with two
VFs, both used by one process. When the process is killed, both VFs can
be released at the same time. The first one takes the bridge lock and
does its FLR, the second one fails the trylock and is never reset.

The bridge lock is only needed for a bus reset, which is done through
the bridge. Add pci_reset_function_needs_bridge_lock(), which returns
false if there is no upstream bridge, if bus resets are disabled for the
device, or if the device is a VF. Use it in vfio_pci_core_disable() and
pci_reset_function() to only lock the bridge when it is needed.

[PATCH] KVM: VMX: Don't disable FB_CLEAR when doing the MMIO Stale Data VERW
Author: Amirmohammad Eftekhar <amirmohammad.eftekhar@cispa.de>

Don't set FB_CLEAR_DIS for a VM-Enter that does the MMIO Stale Data VERW.
VERW doesn't overwrite the fill buffers while FB_CLEAR_DIS is set, so the
buffer clear that is meant to protect the host from a guest with access
to host MMIO currently does nothing.  Keep using FB_CLEAR_DIS for vCPUs
that can't access host MMIO, which are the guests it was added for.

Commit e6ff1d61de51 ("KVM: VMX: Handle MMIO Stale Data in VM-Enter
assembly via ALTERNATIVES_2") moved the MMIO Stale Data VERW from
vmx_vcpu_enter_exit(), where it ran before vmx_disable_fb_clear(), into
__vmx_vcpu_run(), which is called after it.  When commit 43fb862de8f6
("KVM/VMX: Move VERW closer to VMentry for MDS mitigation") moved the
unconditional VERW into the asm, vmx_update_fb_clear_dis() was taught to
leave FB_CLEAR alone if X86_FEATURE_CLEAR_CPU_BUF is set, but there is no
such check for X86_FEATURE_CLEAR_CPU_BUF_VM_MMIO.

Both end up enabled on the same hosts.  A CPU that is affected by MMIO
Stale Data but not by MDS or TAA mitigates it with
X86_FEATURE_CLEAR_CPU_BUF_VM_MMIO (unless another VERW based mitigation,
such as the one for RFDS, is enabled), and if the CPU enumerates
FB_CLEAR_CTRL, KVM disables FB_CLEAR for vCPUs whose ARCH_CAPABILITIES
enumerate neither FB_CLEAR nor immunity, e.g. QEMU CPU models that expose
arch-capabilities without fb-clear.  On those hosts, every VM-Enter of
such a vCPU with host MMIO mapped does the VERW with FB_CLEAR_DIS=1, while
sysfs still reports "Mitigation: Clear CPU buffers".

Fixes: e6ff1d61de51 ("KVM: VMX: Handle MMIO Stale Data in VM-Enter assembly via ALTERNATIVES_2")
Cc: stable@vger.kernel.org
Signed-off-by: Amirmohammad Eftekhar <amirmohammad.eftekhar@cispa.de>
---
I don't have access to a CPU that enumerates FB_CLEAR_CTRL, so this isn't
tested on affected hardware.  Instead I ran it as L1 on a vCPU that looks
like an MMIO Stale Data affected Ice Lake-SP (MDS_NO, TAA_NO, FB_CLEAR and
FB_CLEAR_CTRL), with an L2 guest that has a PCI BAR in a memslot and
ARCH_CAPABILITIES without FB_CLEAR.  L1's MCU_OPT_CTRL writes #GP, but L0
still sees the values L1 tries to write, and a watchpoint on L1's
x86_verw_sel shows where the VERW happens.  Without the patch, all 2576
MMIO VERWs came right after the write that sets FB_CLEAR_DIS; with the
patch, none of the 4478 did, and a guest without host MMIO still gets
FB_CLEAR_DIS on every entry.  Same result with QEMU running the L2 guest
with -cpu Icelake-Server-v5.

KVM selftests and kvm-unit-tests (including the vmx tests) gave the same
results with and without the patch in that setup (a few fail or time out
there either way), and it builds cleanly with KVM_INTEL=m, KVM_AMD=m and
KVM_WERROR=y.  I can share the test scripts if that helps.

6.19.y to 7.1.y still call the flag VMX_RUN_CLEAR_CPU_BUFFERS_FOR_MMIO,
so the backport needs that rename.

[PATCH v5 00/35] Introduce NVIDIA vGPU manager
Author: Alok Kumar <alkumar@nvidia.com>

Add the nova-core support needed to create and manage NVIDIA vGPU
instances on the whole-GPU SR-IOV path.

The overall control path is shown below. This series contains the
nova-core manager and PF-side lifecycle APIs. Typed PF-service
publication and the VFIO variant driver are separate series.

 +-----------------------+         +-----------------------+
 | Linux guest           |         | Windows guest         |
 | NVIDIA guest driver   |         | NVIDIA guest driver   |
 +-----------+-----------+         +-----------+-----------+
             |                                 |
 +-----------v-----------+         +-----------v-----------+
 | QEMU (VFIO user)      |         | QEMU (VFIO user)      |
 +-----------+-----------+         +-----------+-----------+
             +----------------+----------------+
                              |
                      +-------v-------+
                      |   VFIO core   |
                      +-------+-------+
                              |
        +---------------------v---------------------+
        | NVIDIA vGPU VFIO variant driver           |
        +---------------------+---------------------+
                              |
              +---------------+----------------------+
              | binds PCI VF                         | PF lifecycle API
              |                                      | open / close / reset
              v                                      v
     +--------+--------+               +-------------+-------------+
     |    PCI VF(s)    |               | nova-core (PF driver)     |
     |  (virtual GPU)  |               |       vGPU Manager        |
     +--------+--------+               |     VRAM / channels ...   |
              |                        +-------------+-------------+
              |                                      |
+-------------v--------------------------------------v----------------+
|                      NVIDIA physical GPU                            |
|            VF resources                 PF / GSP / VRAM             |
+---------------------------------------------------------------------+

The manager queries the type assigned to a VF by GSP-RM, reserves its
channel and VRAM resources, boots and configures the GSP plugin, and
handles reset and shutdown. Guest VRAM is scrubbed before reuse.

Host resources remain owned until firmware teardown and BAR unmapping
complete. Failed creation rolls back through the instance owner. If
firmware ownership is uncertain or teardown fails, the manager retains
the affected resources until device removal.

This continues the rework of the earlier vGPU RFC [2]: firmware-facing
management belongs to nova-core, while the VFIO driver binds to the VF
and uses the PF's services. The companion VFIO driver does not need its
own copies of the RM firmware headers.

The patches are organized as follows:

  1-8   VF boot information, boot state, runtime parameters and WPR2 heap.
  9-15  Typed BAR1 access, mapping ownership and VRAM allocation.
 16-18  Typed GMC payloads, command IDs and completion-event waits.
 19-23  Plugin bindings, NVKV conversion, properties and allocation.
 24-31  Plugin boot requests, communication buffers, shutdown and RPC.
 32-33  CeUtils commands and guest VRAM scrubbing.
 34     SR-IOV PF lifecycle APIs.
 35     Preserve BAR1 self-test page-table ownership until GPU teardown.

Changes since v4 [1]:

  - Rebase onto the newer r000 firmware and vGPU integration stack.
  - Include VF information in GSP_INIT in this series.
  - Add typed BAR1 MMIO access and SharedGpuMm support, and rework the
    memory helpers and VRAM slot pool for the newer interfaces.
  - Use the existing typed GMC transaction API. Add variable-length
    payload aliases, vGPU command IDs and a typed completion-event wait.
  - Place plugin ABI definitions under vgpu/fw/r000_00, keeping them
    separate from the base GSP firmware bindings.
  - Query VgpuProperties through typed requests and retain BAR0 in the
    manager for instance plugin RPC setup.
  - Fold plugin RPC buffer initialization into the communication-buffer
    and RPC transaction patches.
  - Leave per-instance plugin log export through debugfs for a follow-up.
  - Include the BAR1 self-test lifetime fix as patch 35. The test borrows
    the persistent BarUser VMM and releases its lock before BarUser::map()
    acquires it again.

[PATCH] KVM: nVMX: Allow NMI injection while NMI-blocked if vmcs12 doesn't use virtual NMIs
Author: Manuel Andreas <manuel.andreas@tum.de>

The SDM requires blocking by NMI to be clear when VM-Entry injects an NMI
only if the "virtual NMIs" VM-execution control is 1.  If virtual NMIs are
disabled, injecting an NMI while blocking by NMI is set is legal.

KVM enables virtual NMIs in vmcs02 regardless of vmcs12 (and vmcs01 always
uses virtual NMIs if enable_vnmi=true), but copies vmcs12's guest
interruptibility state and VM-Entry interruption information verbatim.
If L1 doesn't use virtual NMIs and injects an NMI while blocking by NMI
is set, the CPU thus rejects vmcs02 and KVM reflects a bogus
"VM-entry failure due to invalid guest state" to L1.

Clear blocking by NMI in vmcs02 in that case.  Delivering the injected NMI
blocks NMIs, i.e. L2 still runs with blocking by NMI set, which is the
state L2 would be in on bare metal.  Leave nmi_known_unmasked alone,
it's derived from vmcs12's original value and so remains false.

[PATCH v3] KVM: x86: Reject SMM on VMs with private memory
Author: gdool88 <gdool88@gmail.com>


A VM created with private memory (KVM_X86_SW_PROTECTED_VM, SEV-SNP, TDX)
reports one memslot address space, as kvm_arch_nr_memslot_as_ids() returns
1 when kvm_arch_has_private_mem() is true.  SMM still selects address
space 1 via kvm_arch_vcpu_memslots_id(), despite the existing comment
that SMM is unsupported for guests with private memory.

Address space 1 starts at generation 1 and is never swapped for a
private-memory VM.  Address space 0 advances by
kvm_arch_nr_memslot_as_ids() (i.e. 1) per swap, so after a single
memslot operation both address spaces have generation 1.  The per-vCPU
last_used_slot cache in kvm_vcpu_gfn_to_memslot() checks only the
generation number, so an address-space-0 slot can be reused for an
in-SMM address-space-1 lookup.  After the slot is deleted and freed, the
stale cache can cause a host-kernel use-after-free of struct
kvm_memory_slot.  This was reproduced on KVM_X86_SW_PROTECTED_VM by a
process with access to /dev/kvm.  The same aliasing can leave SMM-root
SPTEs that mmu_notifier invalidation does not zap, because it walks only
address space 0.

Enforce the documented assumption that SMM is unsupported for VMs with
private memory.  Make the VMX and SVM has_emulated_msr() hooks report
MSR_IA32_SMBASE unsupported for those VMs; TDX already reports it
unsupported.  This disables VM-scoped KVM_CAP_X86_SMM reporting and
makes kvm_inject_smi() reject KVM_SMI and APIC-delivered SMIs.  Reject
in-SMM state, pending SMIs, and smm_inside_nmi via KVM_SET_VCPU_EVENTS,
matching the !CONFIG_KVM_SMM validation.  Host-initiated SMBASE MSR
access is unchanged.

ChatGPT Codex assisted with analysis, patch drafting, and test design.

can utilize private memory")

[PATCH v1 0/2] arm64: dts: ti: Add tdx vendor prefix to display overlays
Author: Francesco Dolcini <francesco@dolcini.it>


Add a "tdx" vendor prefix to the Toradex display accessory overlays of
the Verdin AM62 and Aquila AM69, and a "-v1"/"-v2" suffix to the
Capacitive Touch Display 10.1" LVDS ones.

The overlay names are the Toradex product names of the accessories, and
a product name is unique only together with its vendor. After a long
discussion with the NXP i.MX maintainer on the Apalis iMX6 overlays [1],
we agreed to add the "tdx" vendor prefix, the same way third-party
accessories on Toradex boards already carry theirs, e.g. "rpi" in
k3-am625-verdin-rpi-display-2-7in.dtso. The Toradex display overlays in
the NXP i.MX directories already use the new names.

The same accessories are used across Toradex SoMs from different SoC
vendors, so renaming the existing overlays is the best way to give
users a consistent experience: one accessory has one name, whatever
the SoM, and the vendor prefix leaves no doubt about the product
supported by the overlay file.

[PATCH v2 0/2] vfio/pci: Provide kernel-side BAR alignment for huge page mapping
Author: Guanghui Feng <guanghuifeng@linux.alibaba.com>

VFIO PCI BAR regions support PMD/PUD huge page mapping via
vfio_pci_mmap_huge_fault() since commit f9e54c3a2f5b ("vfio/pci:
implement huge_fault support").  The huge_fault path requires both the
VA and the PFN to be aligned to the huge page boundary, checked by
is_aligned_for_order().  When alignment fails, huge_fault silently
returns VM_FAULT_FALLBACK and the mapping degrades to 4KB pages.

QEMU already handles this by pre-allocating an aligned VA region and
using MAP_FIXED, see QEMU commits 00b519c0bc ("vfio/helpers: Align
mmaps") and 3863e47828 ("hw/vfio: align mmap to power-of-2 of region
size for hugepfnmap").  Other userspace consumers (DPDK, custom VMMs,
test tools, and QEMU releases predating that change) typically call
mmap(fd, offset) with addr=0, relying on the kernel to select a suitable
VA.  Without kernel-side alignment guidance, these consumers silently
get 4KB mappings for large BARs.

This series adds a .get_unmapped_area callback to the VFIO device
file_operations, modelled after drivers/dax/device.c, that provides
PMD/PUD-aligned VA selection for BAR mappings.  It also sets
VM_HUGEPAGE on BAR VMAs, which keeps the huge mapping available to a
process that called prctl(PR_SET_THP_DISABLE,
PR_THP_DISABLE_EXCEPT_ADVISED).

Note: CONFIG_TRANSPARENT_HUGEPAGE=y is required at compile time for the
huge pfnmap infrastructure.  The runtime THP sysfs policy (enabled=never)
does NOT block VFIO BAR huge pages -- vma_file_bypass_thp_tuneables()
already bypasses it for PFNMAP VMAs with a .huge_fault handler (commit
e384abeb559d).

Performance impact for a 256MB BAR, 4KB pages vs PMD huge pages:
  - Page faults:       65536 -> 128   (512x reduction)
  - Page table memory: ~516KB -> ~4KB (129x reduction)
  - TLB pressure:      65536 entries (exceeds STLB) -> 128 entries (fits)

Patch 1 adds the vfio_device_ops callback infrastructure.
Patch 2 implements the PCI BAR alignment logic and VM_HUGEPAGE.

[PATCH v2 2/2] vfio/pci: Align BAR mappings for huge page support
Author: Guanghui Feng <guanghuifeng@linux.alibaba.com>

vfio_pci_mmap_huge_fault() is already wired up as the huge_fault handler
for BAR mappings and can install PMD or PUD sized pfnmaps when
CONFIG_TRANSPARENT_HUGEPAGE is enabled.  Whether it ever gets to do so
depends on the address the BAR VMA ended up at: is_aligned_for_order()
requires both the fault address and the pfn to be aligned to the huge
page size, and the generic mm_get_unmapped_area() only guarantees
PAGE_SIZE alignment.  When the address is unaligned the check fails,
huge_fault() returns VM_FAULT_FALLBACK without having inserted anything,
and the region silently degrades to one PAGE_SIZE fault per page.

A PCI BAR is required by the PCI bus specification to occupy a naturally
aligned, power of two sized region of physical address space, so the pfn
side of the check is already satisfied for any BAR that is at least 2MB
in size.  What is missing is the virtual address side, and that is only
fixable before the VMA is created.

QEMU already works around this in userspace: it reserves an oversized
anonymous region, rounds its address up to an alignment of
MIN(pow2ceil(region->size), 1GiB), unmaps the slack at both ends and
remaps every sparse subregion with MAP_FIXED at the aligned address, see
QEMU commits 00b519c0bc ("vfio/helpers: Align mmaps") and 3863e47828
("hw/vfio: align mmap to power-of-2 of region size for hugepfnmap").
Other consumers do not.  DPDK, custom VMMs, test tools and QEMU releases
predating that change typically call mmap(fd, offset) with addr=0 and
leave the address selection to the kernel, so they are the ones that
silently lose the huge mapping on a large BAR.  Providing the alignment
in the kernel is defence in depth as well: the kernel should not quietly
give up on a huge mapping it is able to provide just because today's
userspace happens to compensate for its absence.

Implement vfio_pci_core_get_unmapped_area() on top of the new
vfio_device_ops callback, modelled after dax_get_unmapped_area() in
drivers/dax/device.c.  It derives the largest usable page size from the
BAR length, capped at PUD_SIZE and at PMD_SIZE when the architecture
lacks CONFIG_ARCH_SUPPORTS_PUD_PFNMAP, asks for an area with enough
slack to shift the mapping up to the next aligned address, and applies
that shift.  Shifting the address preserves the offset of the mapping
within the BAR, so aligning the address also aligns the pfn.

Everything this cannot improve keeps the current behaviour.  A non-zero
address returns early, which makes the change transparent for userspace
such as QEMU that aligns the mapping itself: MAP_FIXED never reaches the
hook at all, and an explicit hint without MAP_FIXED is honoured as is.
Regions that are not mmap'able BARs, BARs smaller than PMD_SIZE, and
mappings too short to span one fully aligned huge page all take the same
fallback path.

Also set VM_HUGEPAGE on the BAR VMA.  The THP sysfs policy does not need
it, since huge pfnmaps are uncompactable and so
vma_file_bypass_thp_tuneables() ignores the tuneables for a PFNMAP VMA
that has a huge_fault handler.
thp_vma_allowable_order() is still consulted before create_huge_pmd() and
create_huge_pud() are reached, though, and it calls vma_thp_disabled(),
which reports the VMA as disabled once the process has called
prctl(PR_SET_THP_DISABLE, PR_THP_DISABLE_EXCEPT_ADVISED) unless
VM_HUGEPAGE is set.  Marking the VMA keeps the huge mapping available for
such a process instead of leaving it at the mercy of that single bypass,
and makes the intent explicit regardless of how the process or the
administrator configured THP.

[PATCH v2 1/2] vfio: Add get_unmapped_area callback to vfio_device_ops
Author: Guanghui Feng <guanghuifeng@linux.alibaba.com>

vfio exposes device regions through the device file descriptor and a
bus driver backs a region with pfnmaps over the device MMIO space when
the user calls mmap(2) on it.  Unless the user asks for a specific
address, the virtual address of the resulting VMA is picked by the
generic address selection in mm_get_unmapped_area(), which only
guarantees PAGE_SIZE alignment.

That is enough for the base mapping, but it keeps a driver from ever
backing a region with huge pfnmaps.  huge_fault() only installs a PMD
or PUD sized pfnmap when both the fault address and the pfn are aligned
to that page size, see is_aligned_for_order().  A driver can only
influence the first of those, and it cannot do so from its mmap()
callback because the address has already been fixed up by then.

Add a get_unmapped_area() callback to vfio_device_ops along with a
dispatcher in vfio_device_fops, so a bus driver can ask for an address
that is aligned to the largest page size its region can be mapped with
before the VMA is created.  Drivers that do not provide the callback,
and configurations without huge pfnmap support, fall back to
mm_get_unmapped_area() and keep the existing behaviour.

The hook is only consulted when the kernel has to choose the address:
a MAP_FIXED mapping never reaches it, and an explicit address hint is
passed through to the driver, which is expected to honour it.  The
callback therefore serves the userspace consumers that call
mmap(fd, offset) with addr=0 and rely on the kernel to pick a suitable
address for them, rather than trying to second guess userspace that
already arranges the alignment itself.

This mirrors what drivers/dax/device.c does with
dax_get_unmapped_area(), which has to satisfy the same alignment
requirement for its PMD sized pfnmaps.

[PATCH RFC v4 0/8] vsock: add datagram support to virtio and vhost
Author: Sergio Lopez <slp@redhat.com>

This RFC adds SOCK_DGRAM support to virtio-vsock and vhost-vsock through
the existing AF_VSOCK API. It is intended for guest and host services
that exchange independent requests, responses, or events and need message
boundaries and sender addresses without a stream connection or application
framing.

VIRTIO_VSOCK_F_DGRAM gates virtio traffic in both directions. Each virtio
send carries zero to 64 KiB of payload in one VIRTIO_VSOCK_TYPE_DGRAM
packet. On the RX virtqueue, the device may split a datagram across
page-sized guest buffers.
START and EOM delimit the message; the guest reassembles at most 64
fragments and 64 KiB before delivering it to a socket. Invalid or
incomplete messages are discarded. Datagram delivery is best effort:
there are no peer credits, acknowledgements, or retransmissions. Send
admission uses the socket send-memory limit, and SIOCOUTQ reports charged
send memory.

Datagram sockets have a separate port space from stream and seqpacket
sockets. The latter two continue to share their port space. Datagram
routes are chosen per destination among guest-to-host, host-to-guest, and
loopback transports, with VMCI as a fallback. VMCI still owns its socket
handle when it is present; loopback works without a directional transport.
Hyper-V continues to reject datagram sockets.

The Sashiko review of v2 also reported that a VMCI datagram bind in a
local-mode network namespace creates a receive handle in VMCI's global
port space, so a sender outside the namespace can deliver datagrams
across the namespace isolation boundary. The issue predates this series
and it's getting addressed in a separate patch:

https://lore.kernel.org/all/20261113-vsock-vmci-netns-isolation-v1-1-ced02054ea61@redhat.com

Within this series, local-mode namespaces bind datagrams only in the
core table and never create a VMCI handle.

Bobby Eshleman and Amery Hung explored this feature in their v6 series
and v7 work-in-progress branch. This series is a fresh implementation
against the current vsock code. It follows the separate datagram port
space, per-destination routing, and VMCI fallback requirements discussed
there. For guest receive buffers, it uses bounded fragmentation and
reassembly rather than full-message buffers or the earlier drop/error
queue approach:

https://lore.kernel.org/r/20240710212555.1617795-1-amery.hung@bytedance.com
https://github.com/ameryhung/linux/tree/vsock-dgram-v7

A corresponding virtio specification update has been drafted separately.
The wire format and feature negotiation still need specification review
before this series can be considered for merging.

The first patches expose the core port allocator and add datagram queue
reporting, then implement the common data path, guest and host feature
negotiation, routing, and RX fragmentation. The last patch extends
vsock_test with local and peer tests for message boundaries, routing,
connected peers, port sharing, queue accounting, and delayed reads.

Testing used QEMU with the F_DGRAM property patch below, an x86-64
KASAN/lockdep kernel, paired guest tests, and a nested Linux vhost-vsock
backend. The tested paths include 64 KiB messages, delayed-read bursts,
feature-disabled ingress, stream and seqpacket controls, and header-only
guest RX buffers. A temporary userspace backend still fails stream test
21 on both the series base and tip; that case passes with Linux vhost.
VMCI's host personality was exercised in QEMU without loopback for
self-send and with loopback for CID_HOST/CID_ANY routes. Active virtio
and VMCI coexistence used a synthetic VMCI-like fallback. A VMware
VMCI guest device and Hyper-V hardware were not exercised.

Targeted QEMU reproducers for v4 cover a filtered nonlinear skb,
repeated peeks of an empty datagram, guest own-CID routing without
loopback, and local/global namespace test behavior. The numeric
own-CID routing reproducer used a synthetic guest-to-host transport
matching virtio; the corresponding selftest has not run with a
negotiated virtio guest device.

https://lists.gnu.org/archive/html/qemu-devel/2026-10/msg08074.html

Code was written and reviewed both manually and assisted by Codex
(GPT-6.1-Sol) and Claude (Opus 4.6).

[PATCH 0/2] vfio/pci: Provide kernel-side BAR alignment for huge page mapping
Author: Guanghui Feng <guanghuifeng@linux.alibaba.com>

VFIO PCI BAR regions support PMD/PUD huge page mapping via
vfio_pci_mmap_huge_fault() since commit f9e54c3a2f5b ("vfio/pci:
implement huge_fault support").  The huge_fault path requires both the
VA and the PFN to be aligned to the huge page boundary, checked by
is_aligned_for_order().  When alignment fails, huge_fault silently

test tools, and QEMU releases predating that change) typically call
mmap(fd, offset) with addr=0, relying on the kernel to select a suitable
VA.  Without kernel-side alignment guidance, these consumers silently
get 4KB mappings for large BARs.

file_operations, modelled after drivers/dax/device.c, that provides
PMD/PUD-aligned VA selection for BAR mappings.  It also sets

huge pfnmap infrastructure.  The runtime THP sysfs policy (enabled=never)

  - Page faults:       65536 -> 128   (512x reduction)

[PATCH 2/2] vfio/pci: Align BAR mappings for huge page support
Author: Guanghui Feng <guanghuifeng@linux.alibaba.com>

vfio_pci_mmap_huge_fault() is already wired up as the huge_fault handler
for BAR mappings and can install PMD or PUD sized pfnmaps when
CONFIG_TRANSPARENT_HUGEPAGE is enabled.  Whether it ever gets to do so
depends on the address the BAR VMA ended up at: is_aligned_for_order()
requires both the fault address and the pfn to be aligned to the huge
page size, and the generic mm_get_unmapped_area() only guarantees
PAGE_SIZE alignment.  When the address is unaligned the check fails,
huge_fault() returns VM_FAULT_FALLBACK without having inserted anything,
and the region silently degrades to one PAGE_SIZE fault per page.

A PCI BAR is required by the PCI bus specification to occupy a naturally
aligned, power of two sized region of physical address space, so the pfn
side of the check is already satisfied for any BAR that is at least 2MB
in size.  What is missing is the virtual address side, and that is only
fixable before the VMA is created.

QEMU already works around this in userspace: it reserves an oversized
anonymous region, rounds its address up to an alignment of
MIN(pow2ceil(region->size), 1GiB), unmaps the slack at both ends and
remaps every sparse subregion with MAP_FIXED at the aligned address, see
QEMU commits 00b519c0bc ("vfio/helpers: Align mmaps") and 3863e47828
("hw/vfio: align mmap to power-of-2 of region size for hugepfnmap").
Other consumers do not.  DPDK, custom VMMs, test tools and QEMU releases
predating that change typically call mmap(fd, offset) with addr=0 and
leave the address selection to the kernel, so they are the ones that
silently lose the huge mapping on a large BAR.  Providing the alignment
in the kernel is defence in depth as well: the kernel should not quietly
give up on a huge mapping it is able to provide just because today's
userspace happens to compensate for its absence.

Implement vfio_pci_core_get_unmapped_area() on top of the new
vfio_device_ops callback, modelled after dax_get_unmapped_area() in
drivers/dax/device.c.  It derives the largest usable page size from the
BAR length, capped at PUD_SIZE and at PMD_SIZE when the architecture
lacks CONFIG_ARCH_SUPPORTS_PUD_PFNMAP, asks for an area with enough
slack to shift the mapping up to the next aligned address, and applies
that shift.  Shifting the address preserves the offset of the mapping
within the BAR, so aligning the address also aligns the pfn.

Everything this cannot improve keeps the current behaviour.  A non-zero
address returns early, which makes the change transparent for userspace
such as QEMU that aligns the mapping itself: MAP_FIXED never reaches the
hook at all, and an explicit hint without MAP_FIXED is honoured as is.
Regions that are not mmap'able BARs, BARs smaller than PMD_SIZE, and
mappings too short to span one fully aligned huge page all take the same
fallback path.

Also set VM_HUGEPAGE on the BAR VMA.  The THP sysfs policy does not need
it, since huge pfnmaps are uncompactable and so
vma_file_bypass_thp_tuneables() ignores the tuneables for a PFNMAP VMA
that has a huge_fault handler.
thp_vma_allowable_order() is still consulted before create_huge_pmd() and
create_huge_pud() are reached, though, and it calls vma_thp_disabled(),
which reports the VMA as disabled once the process has called
prctl(PR_SET_THP_DISABLE, PR_THP_DISABLE_EXCEPT_ADVISED) unless
VM_HUGEPAGE is set.  Marking the VMA keeps the huge mapping available for
such a process instead of leaving it at the mercy of that single bypass,
and makes the intent explicit regardless of how the process or the
administrator configured THP.

[PATCH 1/2] vfio: Add get_unmapped_area callback to vfio_device_ops
Author: Guanghui Feng <guanghuifeng@linux.alibaba.com>

vfio exposes device regions through the device file descriptor and a
bus driver backs a region with pfnmaps over the device MMIO space when
the user calls mmap(2) on it.  Unless the user asks for a specific
address, the virtual address of the resulting VMA is picked by the
generic address selection in mm_get_unmapped_area(), which only
guarantees PAGE_SIZE alignment.

backing a region with huge pfnmaps.  huge_fault() only installs a PMD

influence the first of those, and it cannot do so from its mmap()
callback because the address has already been fixed up by then.

Add a get_unmapped_area() callback to vfio_device_ops along with a
dispatcher in vfio_device_fops, so a bus driver can ask for an address
that is aligned to the largest page size its region can be mapped with
before the VMA is created.  Drivers that do not provide the callback,
and configurations without huge pfnmap support, fall back to
mm_get_unmapped_area() and keep the existing behaviour.

The hook is only consulted when the kernel has to choose the address:
a MAP_FIXED mapping never reaches it, and an explicit address hint is
passed through to the driver, which is expected to honour it.  The
callback therefore serves the userspace consumers that call
mmap(fd, offset) with addr=0 and rely on the kernel to pick a suitable
address for them, rather than trying to second guess userspace that
already arranges the alignment itself.

This mirrors what drivers/dax/device.c does with
dax_get_unmapped_area(), which has to satisfy the same alignment
requirement for its PMD sized pfnmaps.

[PATCH v2 3/3] KVM: arm64: nv: Allow the L1 VNCR page in cacheable PFNMAP memory

kvm_translate_vncr() refuses any PFN that isn't memory and injects an

fault path, and remove the FIXME added by commit 4bd7dbe0b224 ("KVM:

change after the lookup is caught by the mmu_invalidate_retry() check

is a cacheable PFNMAP (host RAM withheld with mem= and handed to the VMM

hypervisor's VNCR page is in a cacheable PFNMAP registered as a
read-only memslot, and a nested context reads VTTBR_EL2. When the HVA
is looked up with gfn_to_hva_memslot(), the guest hypervisor takes an
SEA. With this patch, the read returns the contents of the VNCR page.

[PATCH v2 1/3] KVM: arm64: nv: Inject an SEA when the VNCR walk cannot set the AF
Author: Jia He <justin.he@arm.com>

(TCR_EL2.HA), KVM's stage-1 walker sets the AF in the descriptor that
maps VNCR_EL2 with __kvm_at_swap_desc(). If the descriptor is in a

[RFC PATCH 4/6] KVM: arm64: nv: Grow the shadow S2 MMU pool on demand
Author: Nathan Chen <nathanc@nvidia.com>

A nested-capable VM gets online_vcpus * S2_MMU_PER_VCPU shadow stage-2
MMUs, with S2_MMU_PER_VCPU currently hardcoded to 2. When the guest
hypervisor runs more than that number of concurrent nested VMs,
get_s2_mmu_nested() recycles live MMUs on nearly every nested context
switch, tearing down and rebuilding shadow stage-2 tables and issuing
VMID TLB invalidations each time. This causes a sharp spike in host CPU
usage.

Keep S2_MMU_PER_VCPU as the initial allocation, and grow the VM's pool
when the guest's working set outgrows it. To keep growth from exhausting
the VMID space, grown MMUs are counted across all VMs on the host and
limited to half of what kvm_arm_vmid_nr_usable() returns.

If an allocation fails, growth stops for good, so that a VM at its
memory limit doesn't retry on every recycle.

The nested_mmus pointer table is reallocated when full. Only the table
moves, not the MMUs, so cached hw_mmu pointers stay valid.

Signed-off-by: Nathan Chen <nathanc@nvidia.com>

[RFC PATCH 2/6] KVM: arm64: nv: Pick the shadow S2 MMU to recycle with a clock
Author: Nathan Chen <nathanc@nvidia.com>

On a lookup miss, get_s2_mmu_nested() recycles the first free MMU after
the last one it picked. That MMU may hold the shadow stage-2 of a nested
VM that is still running and about to be loaded again, while the pool
has MMUs nobody has used in a long time, such as those of torn down
nested VMs. Recycling a live MMU throws away its shadow tables and
makes its nested VM fault them all back in.

Track use with an 'accessed' flag, set whenever a vcpu takes a reference
on the MMU, and pick the victim with a clock (second chance):

- A free MMU that is invalid, or wasn't used since the search last went
  past it, is recycled straight away.

- Other free MMUs have their flag cleared as the search goes past them.

- If every free MMU was used since the last pass, the first one found
  is recycled, as before.

Signed-off-by: Nathan Chen <nathanc@nvidia.com>

[RFC PATCH 0/6] KVM: arm64: nv: Grow the shadow S2 MMU pool on demand
Author: Nathan Chen <nathanc@nvidia.com>

A nested-capable VM gets 2 shadow stage-2 MMUs per vcpu. Once the guest
hypervisor runs more nested VMs than that, nearly every nested context
switch recycles a live MMU and spikes host CPU usage.

This series lets KVM grow the shadow MMU pool on demand when the pool
is too small, up to a host-wide VMID budget. It also parks grown MMUs
on a guest TLBI ALLE1 and when a guest range invalidation leaves them
empty, in order to return unused capacity.

Testing on a 16-bit VMID, 4K pages host with 64-vCPU L1 and idle
2-vCPU Firecracker L2s:

- Ramping to 300 L2s grew the pool 128 -> 192 -> 256 -> 320, with no
  host CPU usage spike observed and no VMID TLB flushes.

- Dropping to 20 L2s and forcing an ALLE1 (an L1 VMID rollover from
  churning ~66K VMs) parked all grown MMUs and returned the budget.
  Ramping back to 300 reactivated them without allocating, with no
  host CPU usage spike observed.

- VM teardown returned the budget, with no warnings in dmesg.

Testing with 14 L2s on a 4-vCPU L1 with 6 L2 guests powered off or
rebooted:

- Firecracker unmaps guest memory before exiting, and L1 issues a TLBI
  RIPAS2E1IS over all of the L2's memory, leaving its shadow MMU empty.
  Patch 6 parked 5 of the 6 MMUs, and the remaining L2 had an MMU from
  the initial pool which should never be parked. This is reclaim on
  range invalidation, not on L2 shutdown, as a range invalidation
  doesn't necessarily mean the nested VM is gone.

Known limitations:

- ALLE1 parking can't tell live idle nested VMs from dead ones. After
  an ALLE1, the remaining L2s found their MMUs parked, and each of
  their vcpus recycled an initial MMU that was empty but still valid,
  doing a whole-IPA unmap. Serialised on mmu_lock, these made L1 spike
  host CPU usage for a brief period. Skipping the unmap of an
  already empty victim would avoid this, but changes the recycle path
  and is left out of this RFC.

- On SIGTERM or SIGKILL, L1 issues no TLBI naming the L2's VMID, while
  it runs or as it is torn down. The leftover MMUs are then only parked
  on an ALLE1, which a Linux guest hypervisor only issues on its own
  VMID rollover.

For SIGTERM and SIGKILL, an alternative I prototyped is a periodic scan
that parks grown MMUs no vcpu used since the previous scan. With a 10s
period, it returned a dead nested VM's budget without taking
MMUs from live idle ones.
However, the scan has to unmap what it parks: after dropping from 300 to
20 L2s, MMU mapping took some time and could delay the vcpus of a busy
L1.

Is parking on ALLE1 and range invalidation good enough to start with,
or would you prefer a periodic scan or another signal for nested VMs
whose VMM is killed?

This series was developed with AI assistance (Anthropic Claude, through
Cursor). It was used for design trade-offs, testing, and adversarial
review of feedback received. I ran the tests on hardware, have reviewed
every change, and take full DCO responsibility for the series.

A branch can be found here with the series applied: 
https://github.com/NathanChenNVIDIA/linux/tree/rfc_alle1_nested_s2_mmu_pool_dynamic_budgeted_kvmarmnext

[PATCH] KVM: arm64: Reduce the stage-2 page cache on 64 KiB hosts
Author: Usama Arif <usama.arif@linux.dev>

When a stage-2 fault may need new page tables, KVM first tops up the
vCPU's page cache: if it holds fewer pages than the fault might need, it
is refilled to KVM_ARCH_NR_OBJS_PER_MEMORY_CACHE, which arm64 sets to
40. Unused pages stay in the cache until the vCPU is destroyed.

With 64 KiB pages, that is 2.5 MiB per vCPU, and most of it is never
used. Stage-2 has at most three levels and the root is preallocated, so
a fault needs at most two new table pages (kvm_mmu_cache_min_pages()).
As every last-level table covers 512 MiB, an 8 GiB guest needs just 17
table pages to map all of its memory, while its four vCPU caches get
filled with 160.

On a production host with 64 KiB pages running 101 VMs with four vCPUs
each, the caches were still 86% full. The memory used:

                        before      after
  per-vCPU capacity     2.5 MB     512 KB
  all 404 vCPUs         869 MB     <= 202 MB

Let's lower the capacity to 8 with 64 KiB pages, In the production
usecase above, it frees at least 667 MB. That still covers the two-page
minimum and leaves room for several table allocations per refill. 4 KB
and 16 KB pages keep 40.

The temporary cache in kvm_phys_addr_ioremap() uses the same capacity,
but it is topped up before every page it maps, so 8 is sufficient there
as well. The pKVM hypervisor memcache and the eager split cache don't
use this capacity.

Signed-off-by: Usama Arif <usama.arif@linux.dev>

[PATCH] KVM: arm64: Set PG_mte_tagged before copying MTE tags from userspace
Author: Fuad Tabba <fuad.tabba@linux.dev>

KVM_ARM_MTE_COPY_TAGS takes PG_mte_lock on a page's first tagging, and
sets PG_mte_tagged only after copying the tags in from userspace.
However, that copy faults on the same page if the VMM passes a PROT_MTE
mapping of the page as the tags buffer. The fault then spins forever in
mte_sync_tags(), waiting for PG_mte_tagged to be set.

Call sanitise_mte_tags() before the copy, so that PG_mte_tagged is
already set if the copy faults. The ioctl calls it holding a reference
on the page rather than kvm->mmu_lock, and either keeps the page from
being freed. A racing vCPU fault or __set_ptes() then finds the page
tagged and doesn't touch its tags. The guest and the VMM can read
cleared tags from the page until the copy finishes.
