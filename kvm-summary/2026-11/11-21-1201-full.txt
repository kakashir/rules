[PATCH 0/2] x86/cea: Clean up the exception stack names and declarations
Author: Sohil Mehta <sohil.mehta@intel.com>

Background
----------
This is a simple cleanup of how the x86-64 exception stacks are named and
reached. These patches started out as part [1][2] of the FRED KVM series. They
were prerequisites for the KVM enabling because the original proposal [3] was
to call __this_cpu_ist_top_va() directly from KVM. So the macro had to be
converted to a function and then be exported.

However, KVM is now planning to use a FRED-specific helper [4] which is
compiled into vmlinux so the macro directly works inside it. Therefore, FRED
KVM no longer needs any of this. Though the cleanup itself is still valuable
and makes the code clearer and the comments more accurate.

Motivation
----------
The exception stacks (DF, NMI, DB, MCE, VC) carry names too short for a header
that almost the whole x86 build pulls in, and the stacks themselves are both
declared and looked up by pasting those names into structure member names.

The first patch adds the ESTACK_ prefix to the names and the second patch
indexes the stacks by the enum that callers already pass. This removes most of
the pasting, and leaves the layout, the addresses and the guard pages exactly
as they were.

There is no change in behavior expected.

Changes from the FRED KVM v10

   to functions.
 - Expand struct exception_stacks explicitly and drop ESTACKS_MEMBERS()  
 - Rewrite most of the commit message and drop the prior tags.

[PATCH 2/2] x86/cea: Index exception stacks by the ordering enum
Author: Sohil Mehta <sohil.mehta@intel.com>

The exception stacks are generated by ESTACKS_MEMBERS(), which pastes
each stack name into a member name, once for the physical storage and
once for the CEA mapping.

The macro used to be the only thing keeping the two structures in the
same order, but there is no ordering requirement left to enforce. The
stacks are mapped one at a time and have been paired by name for a
while. Also, the sizes stopped matching once the #VC stacks became
config dependent.

So, spell out the physical storage and index the mapping by the stack
ordering enum. Also drop CEA_ESTACK_SIZE, which just duplicated
EXCEPTION_STKSZ.

The stack addresses and the guard pages are unchanged. No functional
change intended.

Signed-off-by: Sohil Mehta <sohil.mehta@intel.com>

[PATCH] KVM: x86/mmu: Prevent hugepage recovery on non-guest_memfd
Author: Ackerley Tng via B4 Relay <devnull+ackerleytng.google.com@kernel.org>


When determining the maximum mapping level outside of a page fault
(such as when disabling dirty logging), KVM queries the VM memory
attributes to determine whether a GFN is private. Userspace can mark a
GFN as private in the VM attributes even when the covering memslot is
not backed by guest_memfd.

Previously, this caused the mapping level calculation to fall into
kvm_gmem_max_mapping_level(), triggering a kernel warning.

Here's 1 way to trigger the warning on a TDX VM, with VM memory attributes
enabled on KVM.

1. Create a non-guest_memfd memslot covering a 1G-aligned base GFN with
   dirty logging enabled.
2. In that memslot, fault a shared page outside the first 2M chunk so a
   non-leaf PTE at the 1G level is installed.
3. Mark the first 2M chunk (at the 1G-aligned base GFN) private. Conversion
   zaps that 2M chunk, while the shared mapping outside it keeps the 1G
   non-leaf PTE present.
4. Disable dirty logging on the memslot.

Hugepage recovery iterates over the present 1G non-leaf PTE, sees that its
base GFN is private and the 2M range is not mixed, and calls into
kvm_gmem_max_mapping_level() without a fault context, hitting the WARN.

Return 4K as the maximum mapping level when a GFN is marked private in
a non-fault path for a memslot without guest_memfd. Fault paths already
disallow mapping private GFNs in non-guest_memfd memslots, and
returning 4K prevents hugepage recovery on such GFNs.

Fixes: a3522ac71f5e ("KVM: x86/mmu: Enforce guest_memfd's max order when recovering hugepages")
Signed-off-by: Ackerley Tng <ackerleytng@google.com>

[PATCH 1/1] vfio: Take the KVM reference only for drivers that read device->kvm
Author: Andrey Drobyshev <andrey.drobyshev@virtuozzo.com>

A device takes a reference to the KVM file of its group or device file
at the first open and drops it at the last close, so that device->kvm
stays valid for the driver in between.

QEMU's cpr-exec and cpr-transfer keep the device open while the VM is
re-created.  The first VM then stays referenced for as long as the
device is open: its file is not released, and its vcpus, mm and
in-kernel PIT thread stay with it.

To see it, start QEMU with a vfio-pci device, run cpr-exec and trace
kvm_create_vm() and kvm_destroy_vm().  The old VM is not destroyed at
the exec, and two VMs stay alive until QEMU exits.  Without the device
the old VM is destroyed at the exec.  The new VM also logs

  kvm: debugfs: duplicate directory <pid>-<fd>

because it gets the pid and fd number of the old one.

Only three drivers read device->kvm: KVMGT, vfio_ap and vfio-pci's
zdev support.  vfio_ap reads it only in open_device(), zdev also at
close, KVMGT also at close and while the guest runs.  Let them say so
with needs_kvm_ref.  Without it device->kvm stays NULL and no reference
is taken, so the device can't keep a VM alive.

Fixes: 2b48f52f2bff ("vfio: fix deadlock between group lock and kvm lock")
Signed-off-by: Andrey Drobyshev <andrey.drobyshev@virtuozzo.com>

[PATCH 0/1] vfio: fix KVM reference leak on QEMU CPR
Author: Andrey Drobyshev <andrey.drobyshev@virtuozzo.com>

When a VM has a VFIO device and QEMU does a CPR (CheckPoint and Restart)
live update, QEMU creates a new VM and keeps the device open.  The
device holds a reference to the VM it was opened with, so the old VM is
not destroyed.  It stays until the device is closed, which usually means
for as long as the guest runs.

It is one stale VM, not one per update.  It is also visible: after
cpr-exec the kernel logs "kvm: debugfs: duplicate directory <pid>-<fd>",
and the new VM gets no debugfs directory.

This patch makes the device take that reference only if its driver uses
it.

Tested on v7.4-rc3 with QEMU 11.1.50, cpr-exec and the legacy VFIO
container, in a nested setup: the L1 VM has a spare virtio-net device
behind a virtual IOMMU and passes it to an L2 VM with vfio-pci.  The
script below runs cpr-exec and counts the kvm_create_vm() and
kvm_destroy_vm() calls:

$ cat kvmref.sh

> #!/bin/bash
> 
> QEMU=/path/to/build/qemu-system-x86_64
> DEV=0000:08:00.0
> MON="/var/tmp/mon.sock"
> STATE="/var/tmp/vm.state"
> TRACING=/sys/kernel/tracing
> 
> hmp() {
>   echo "$1" | socat - "UNIX-CONNECT:${MON}" | tr -d '\r' \
>     | grep -v -e '^QEMU ' -e '^(qemu)'
> }
> 
> bind_vfio() {
>   dev="/sys/bus/pci/devices/${DEV}"
>   modprobe vfio-pci
>   echo vfio-pci > "${dev}/driver_override"
>   [[ -e "${dev}/driver" ]] && echo "${DEV}" > "${dev}/driver/unbind"
>   echo "${DEV}" > /sys/bus/pci/drivers_probe
> }
> 
> trace_off() {
>   echo nop > "${TRACING}/current_tracer"
>   echo > "${TRACING}/set_ftrace_filter"
> }
> 
> trace_on() {
>   trace_off
>   echo 'kvm_create_vm kvm_destroy_vm' > "${TRACING}/set_ftrace_filter"
>   echo function > "${TRACING}/current_tracer"
>   echo > "${TRACING}/trace"
> }
> 
> # How many VMs were created and destroyed so far
> report() {
>   created="$(grep -c 'kvm_create_vm' "${TRACING}/trace")"
>   destroyed="$(grep -c 'kvm_destroy_vm' "${TRACING}/trace")"
>   printf '%-22s created %s, destroyed %s, alive %s\n' \
>     "$1:" "${created}" "${destroyed}" "$((created - destroyed))"
> }
> 
> main() {
>   mode="${1:-vfio}"
>   cycles="${2:-1}"
> 
>   local -a args=(
>     "${QEMU}" -accel kvm -display none
>     -machine q35,aux-ram-share=on,memory-backend=ram
>     -object memory-backend-memfd,id=ram,size=512M,share=on
>     -monitor "unix:${MON},server=on,wait=off"
>   )
> 
>   if [[ "${mode}" == vfio ]]; then
>     bind_vfio
>     args+=(-device "vfio-pci,host=${DEV}")
>   fi
> 
>   trace_on
>   "${args[@]}" &
>   pid=$!
>   sleep 2
>   report 'QEMU started'
> 
>   for ((i = 1; i <= cycles; i++)); do
>     hmp 'migrate_set_parameter mode cpr-exec'
>     hmp "migrate_set_parameter cpr-exec-command ${args[*]} -incoming file:${STATE}"
>     hmp "migrate file:${STATE}"
>     sleep 3
>     report "after cpr-exec ${i}"
>   done
>   echo "pid ${pid} is still $(readlink "/proc/${pid}/exe"), $(hmp 'info status')"
> 
>   hmp quit
>   wait "${pid}"
>   sleep 1
>   report 'QEMU exited'
>   trace_off
> }
> 
> main "$@"

[PATCH] KVM: PPC: implement .flush_memslot for BookE and Book3S-PR
Author: Paolo Bonzini <pbonzini@redhat.com>

kvm_arch_flush_shadow_memslot() is called when memslots are deleted and
moved, with no MMU notifier invalidation.  This means that the shadow
pages (HPTEs for PR, TLB entries for e500) retain mappings from host
pfns to the old slot's gfns.

Implement the callback by unmapping the GFNs in the same way that Book3S-HV
does it.  Note that kvmppc_core_flush_memslot_pr() does not need TLB
invalidation, because kvmppc_mmu_pte_pflush() calls invalidate_pte()
on the entries, and that in turn invalidates the entry through either
the tlbie instruction or mmu_hash_ops.hpte_invalidate().

[PATCH v8 4/4] iommu/of: Add support for "iommu-ranges" on a

[PATCH v8 1/4] iommu/dma: Keep reserved regions below the IOVA
Author: Vikash Garodia <vikash.garodia@oss.qualcomm.com>

The IOVA allocator tracks address ranges by page frame number (PFN).
The highest node in its rbtree is a fixed anchor at PFN ~0UL, which is
embedded in the DMA cookie. dma-iommu converts reserved regions to PFNs
with iova_pfn(), which returns unsigned long. On x86-32 with PAE,
addresses are 64-bit but unsigned long is 32-bit, so the upper bits of
the PFN are lost.
A reserved region that ends at the top of the address space then gets
the anchor's PFN. reserve_iova() merges it into the anchor and lowers
the anchor's pfn_lo. At teardown, free_iova_mem() no longer recognises
the anchor and frees it to iova_cache, which corrupts the slab. PCI host
bridge windows above 16TiB and the reservation after the last PCI DMA
window hit the same problem.
Compute the PFNs in u64. Skip ranges that start above the PFN space and
clamp the end one PFN below the anchor. The allocator never hands out
those IOVAs, so nothing is lost. On 64-bit, PFNs never reach ~0UL, so
nothing changes there.

[PATCH v1 2/2] KVM: s390: make kvm_s390_vm_stop_migration() void
Author: Gautam Gala <ggala@linux.ibm.com>

kvm_s390_vm_stop_migration() returns 0 on all paths; it cannot fail.
Its caller in s390_kvm_mmu_prepare_memory_region() wraps it in
WARN(), producing a condition that is always false. The arm64 stub
returns -EINVAL but is unreachable because

Change the return type to void and drop the dead WARN(). The
KVM_S390_VM_MIGRATION_STOP attribute handler sets its result to 0
explicitly; userspace behavior is unchanged since stopping

[PATCH v1 1/2] KVM: s390: reserve mmu cache before stopping migration mode
Author: Gautam Gala <ggala@linux.ibm.com>

Creating or moving a memslot without KVM_MEM_LOG_DIRTY_PAGES stops
migration mode in s390_kvm_mmu_prepare_memory_region(). If the mmu
cache reservation fails afterwards, the ioctl returns -ENOMEM with
the memslots unchanged, but migration mode stays stopped: the CMMA
state cleared by kvm_s390_vm_stop_migration() cannot be restored,
so an in-flight migration aborts over an unrelated allocation
failure.

Reserve the mmu cache before tearing down migration mode so the
error path leaves both memslots and migration state untouched.
