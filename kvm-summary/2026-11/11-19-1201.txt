New:  KVM: x86: Fix stalled descriptor table accesses to MMIO
[PATCH] KVM: x86: Fix stalled descriptor table accesses to MMIO
Author: weichenchen <weichen.chen@linux.alibaba.com>

Use the emulated memory accessors for the explicit operands of LGDT,
LIDT, SGDT and SIDT.  When the operand has no backing memslot, the
standard accessors return X86EMUL_IO_NEEDED without queuing an MMIO
fragment.  LIDT can repeat the generic operand read at the same RIP,
and SIDT can re-enter emulation without sending a write to userspace.

Check the segment bounds of both fields before reading the limit or
base.  If the operand crosses a page boundary, pass the whole operand
to the emulated read so a fault on the second page is reported before
an MMIO exit to userspace.  Keep the separate limit and base reads on
a single page.  Use the emulator's read cache to resume after MMIO and
set NoAccess to skip the redundant generic source read.

Use the destination operand for common writeback of SGDT and SIDT.  This
keeps the entire descriptor available until userspace completes a
ten-byte MMIO write.

Fixes: c3cd7ffaf57a ("KVM: x86 emulator: x86_emulate_insn() return -1 only in case of emulation failure")
Fixes: 129a72a0d3c8 ("KVM: x86: Introduce segmented_write_std")
Signed-off-by: weichenchen <weichen.chen@linux.alibaba.com>
---
On Intel VMX/EPT, LIDT and SIDT both reached the following HLT with the
expected IDTR data for RAM and MMIO operands. LIDT completed a 2-byte
and an 8-byte MMIO read. SIDT completed an 8-byte and a 2-byte write.

With only the limit field in range in 32-bit compatibility mode, LIDT
delivered #GP(0) at the expected RIP before any userspace MMIO exit.
The same selftest passed with forced emulation. A local extension to
set_memory_region_test also covered all four descriptor-table
instructions and a split RAM/MMIO LIDT.

A standalone test of the emulator and its MMIO fragment handling used
mock page translation to check a userspace MMIO page followed by a
non-present page. All 36 cross-page load cases returned a page fault
without preparing a userspace MMIO exit or updating GDTR or IDTR.

Six KVM selftests passed. Eight kvm-unit-tests suites at a2891d9528ef
reported 445 passes, five skips and no failures. Both vendor modules
built with KVM_WERROR. Runtime testing used Intel.

New:  vfio/pci: Hold memory_lock for all calls to vfio_pci_set_power_state()
[PATCH v2 1/8] vfio/pci: Hold memory_lock for all calls to vfio_pci_set_power_state()
Author: David Matlack <dmatlack@google.com>

Hold vdev->memory_lock for write when calling vfio_pci_set_power_state()
from vfio_pci_core_disable() and vfio_pci_core_register_device(), and
assert that the lock is held for all power state transitions, not just
transitions out of D0.

vfio_pci_core_disable() calls vfio_pci_set_power_state(vdev, PCI_D0)
without holding memory_lock, which allows it to race with
vfio_pci_core_sriov_configure() when userspace writes to sriov_numvfs
while the device is being closed. If the user left the device in D3hot
via a config space write, both threads can transition the device from
D3hot to D0 concurrently. Since a config space write does not change
the runtime PM status, the device stays RPM_ACTIVE, pm_runtime_resume()
in the close path is a no-op, and vfio_pci_set_power_state() performs
the D3hot->D0 transition.

For devices with vdev->needs_pm_restore set (NoSoftRst-), this can
result in:

 - vfio_pci_core_disable() restoring the PF's BARs after
   vfio_pci_core_sriov_configure() has enabled VFs, since the D3hot->D0
   transition sleeps before restoring device state. This reproduces
   reliably with vfio_pci_power_state_test and triggers the following
   warning:

     vfio-pci 0000:01:00.0: can't update enabled VF BAR0 [mem 0xe0200000000-0xe020001ffff 64bit pref]
     WARNING: drivers/pci/iov.c:1062 at pci_iov_update_resource+0x170/0x3b0
     Call Trace:
      pci_update_resource+0x1a3/0x5b0
      __pci_set_power_state+0x597/0xb90
      vfio_pci_core_disable+0x13b/0x1180
      vfio_pci_core_close_device+0x144/0x260
      vfio_df_close+0xf2/0x210
      vfio_df_unbind_iommufd+0x89/0x140
      vfio_device_fops_release+0x85/0xf0
      __fput+0x2d6/0x720
      fput_close_sync+0xe8/0x180
      __x64_sys_close+0x7f/0xc0
      do_syscall_64+0xbc/0x320
      entry_SYSCALL_64_after_hwframe+0x76/0x7e

 - Both threads observing pdev->current_state >= PCI_D3hot and calling
   pci_load_and_free_saved_state(pdev, &vdev->pm_save) concurrently,
   resulting in a double-free of vdev->pm_save.

vfio_pci_core_register_device() cannot race with other callers since
the device is not yet registered and device_lock is held across probe,
but take the lock there as well so that the lockdep assertion can be
made unconditional and catch any future unlocked callers.

Taking memory_lock in these paths does not introduce any new lock
dependencies. vfio_pci_core_disable() already acquires memory_lock
under dev_set->lock via vfio_pci_runtime_pm_exit(), and
vfio_pci_core_register_device(), like vfio_pci_core_sriov_configure(),
runs under device_lock, which is already taken before memory_lock.

Fixes: f4162eb1e2fc ("vfio/pci: Change the PF power state to D0 before enabling VFs")
Cc: stable@vger.kernel.org
Signed-off-by: David Matlack <dmatlack@google.com>

New:  vfio/pci: Fix power state race with SR-IOV enablement
[PATCH v2 0/8] vfio/pci: Fix power state race with SR-IOV enablement
Author: David Matlack <dmatlack@google.com>

This series can be found on GitHub:

  https://github.com/dmatlack/linux/tree/vfio/set_power_state/v2

This series fixes a race between closing a vfio-pci device and enabling
SR-IOV on it, both of which can transition the device from D3hot to D0
without being serialized. On devices with NoSoftRst-, this can restore
the PF's BARs after VFs have been enabled (triggering a WARN in
pci_iov_update_resource()), or double-free vdev->pm_save.

This series also adds a selftest that exercises VFIO's handling of
power state transitions requested by userspace through the PM
capability, including a test case that reproduces the race.

This series applies on top of vfio/next (vfio-v7.4-rc1).

Series Overview
---------------

This series implements the following:

  1. Hold memory_lock for all calls to vfio_pci_set_power_state() and
     assert that it is held, which fixes the race (patch 1).

  2. Annotate the intentional lockless accesses to vdev->sriov_active
     with READ_ONCE() and WRITE_ONCE() (patch 2).

  3. Skip vfio_pci_sriov_uapi_test instead of failing when SR-IOV
     cannot be configured on the PF, e.g. because vfio-pci's
     enable_sriov module parameter is not set (patches 3-4).

  4. Add library helpers to find a PCI capability, read
     /sys/kernel/warn_count, and print kernel warnings from /dev/kmsg
     (patches 5-7).

  5. Add vfio_pci_power_state_test, which covers closing a device in
     D3hot and reopening it, enabling SR-IOV while the PF is in D3hot,
     and racing a close in D3hot against enabling SR-IOV. The test fails
     if /sys/kernel/warn_count changes during a test case, and prints
     the warnings logged to /dev/kmsg to help debug the failure
     (patch 8).

Testing
-------

All patches were build-tested individually. The series was tested on
x86_64 in a QEMU VM with an emulated Intel 82576 NIC (igb), which has
NoSoftRst- and supports SR-IOV, bound to vfio-pci:

  - Without patch 1 (KASAN kernel), close_in_d3hot_races_sriov_enable
    fails, hitting the pci_iov_update_resource() WARN on 9 or 10 of the
    test's 10 iterations.

  - With the full series (KASAN and lockdep kernels), all VFIO
    selftests pass with no warnings, KASAN reports, or lockdep splats.

To run the new test (the SR-IOV test cases are skipped unless
vfio_pci.enable_sriov=1):

  # tools/testing/selftests/vfio/scripts/setup.sh 0000:01:00.0
  # tools/testing/selftests/vfio/scripts/run.sh \
      tools/testing/selftests/vfio/vfio_pci_power_state_test

New:  KVM: SVM: Set V_IGN_TPR when enabling a dummy V_IRQ for an
[PATCH] KVM: SVM: Set V_IGN_TPR when enabling a dummy V_IRQ for an
Author: Jim Mattson <jmattson@google.com>

Per the APM, the processor takes a virtual INTR interrupt only if
V_INTR_PRIO is *strictly* greater than V_TPR, unless V_IGN_TPR is set to
bypass the priority comparison.

In svm_set_vintr(), KVM injects a dummy V_IRQ with V_INTR_PRIO=0xf to
trigger #VMEXIT(VINTR) as soon as an interrupt window opens, but it does
not set V_IGN_TPR.  If V_TPR is 0xf when the window opens--e.g. when
CR8=0xf (in L1, or in L2 with V_INTR_MASKING=0) while a TPR-independent
ExtINT or userspace IRQ-window request is pending, or in L2 with
V_INTR_MASKING=1, INTERCEPT_INTR=0, and vmcb12.int_ctl.V_TPR=0xf--the
priority comparison (0xf > 0xf) fails, and hardware masks the dummy
V_IRQ indefinitely (also stranding any VM-wide AVIC IRQ-window inhibit).

Set V_IRQ_INJECTION_BITS_MASK (which includes V_IRQ_MASK,
V_INTR_PRIO_MASK, and V_IGN_TPR_MASK) in svm_set_vintr().  Note that
svm_clear_vintr() already clears and restores V_IRQ_INJECTION_BITS_MASK.

Fixes: 649d68643ebf ("KVM: SVM: sync TPR value to V_TPR field in the VMCB")
Signed-off-by: Jim Mattson <jmattson@google.com>

New:  KVM: arm64: Force HCR_EL2.NV1 to RES0 unconditionally
[PATCH v3 1/2] KVM: arm64: Force HCR_EL2.NV1 to RES0 unconditionally
Author: Colton Lewis <coltonlewis@google.com>

ID_AA64MMFR4_EL1.E2H0 is a signed 4-bit field where:
  - 0b0000 (IMP, 0): FEAT_E2H0 is implemented.
  - 0b1111 (NI, -1): FEAT_E2H0 is not implemented, except HCR_EL2.NV1
    is implemented.
  - 0b1110 (NI_NV1, -2): Neither HCR_EL2.E2H == 0 nor HCR_EL2.NV1 is
    implemented, and HCR_EL2.NV1 is RES0.

When commit b2a324ff01fe ("KVM: arm64: Use HCR_EL2 feature map to drive
fixed-value bits") converted HCR_EL2 to hcr_feat_map[], feat_nv2_e2h0_ni()
was written as !kvm_has_feat(kvm, FEAT_E2H0), where FEAT_E2H0 checks
E2H0 >= IMP (0). This inverted the condition: feat_nv2_e2h0_ni() evaluates
to true when E2H0 < 0 (including NI_NV1), leaving HCR_EL2.NV1 writable
instead of RES0 for VHE-only nested guests where KVM advertises
ID_AA64MMFR4_EL1.E2H0 = NI_NV1.

In practice, KVM cannot handle HCR_EL2.NV1 being non-RES0 in any
configuration: limit_nv_id_reg() exposes either VHE-only EL2 with
ID_AA64MMFR4_EL1.E2H0 = NI_NV1 (and E2H0 is not userspace-writable), or
FEAT_E2H0 without FEAT_VHE or FEAT_NV. Checking E2H0 in a feature helper
is therefore unnecessary.

Drop feat_nv2_e2h0_ni() and mark HCR_EL2_NV1 as an unconditional RES0 bit
using NEEDS_FEAT_FLAG(HCR_EL2_NV1, FORCE_RESx) in hcr_feat_map[] (shared
by HCR_EL2 and NVHCR_EL2). Because HCR_EL2_NV1 is not part of the
architectural HCR_EL2_RES0 mask, check_feat_map() accounts for it as an
implementation-defined FORCE_RESx bit.

Fixes: b2a324ff01fe ("KVM: arm64: Use HCR_EL2 feature map to drive fixed-value bits")
Suggested-by: Marc Zyngier <maz@kernel.org>

New:  KVM: x86/mmu: Defer TDP MMU RCU callback barrier
[PATCH] KVM: x86/mmu: Defer TDP MMU RCU callback barrier
Author: Mark Street <streetster@gmail.com>

TDP MMU pages are freed from RCU callbacks, which return their headers to MMU slab caches. Waiting for an rcu_barrier() during every VM teardown makes each VM wait for all pending RCU callbacks, including callbacks queued by unrelated VMs.

Move the barrier to kvm_mmu_vendor_module_exit(), immediately before the MMU caches are destroyed. Set the owner of KVM stats and per-VM debugfs files to the vendor module so open files pin the module and prevent its exit while those files are active.

This keeps the caches alive until queued callbacks finish while removing the callback drain from individual VM teardown.

Signed-off-by: Mark Street <streetster@gmail.com>

New:  arm64: Support GICv5-based guests
[PATCH kvmtool v5 00/23] arm64: Support GICv5-based guests
Author: Sascha Bischoff <sascha.bischoff@arm.com>

This series adds support for GICv5-based VMs to kvmtool. These are
exposed as --irqchip=gicv5 and --irqchip=gicv5-its, where the former
creates a vGICv5 device and the latter adds a GICv5 ITS. The GICv5
specification can be found at [1].

The GICv5 support in KVM needed by --irqchip=gicv5 is available as of
Linux v7.4-rc1. The GICv5 ITS support is described in [2]; using
--irqchip=gicv5-its requires a KVM build with those changes.

The series teaches kvmtool to create the GICv5 irqchip and ITS KVM
devices. It describes the GICv5 CPU interface, IRS and ITS in the
guest DT, updates the timer and PMU interrupt descriptions, and
generates GICv5 interrupt specifiers for platform devices and PCI. It
also maps PCI MSI requester IDs to the ITS. The IRS support is built
and exposed before the ITS support, so the GICv5 irqchip support can
be merged separately from the ITS changes.

Compared with v4 [3]:

* Added Vladimir's Reviewed-by and Tested-by trailers where provided,
  and described the MSI helper's use of the global base in patch 3's
  commit message.

* Updated to check GICv5 SPI indices passed to KVM_IRQ_LINE against
  the 0-255 range that fits kvmtool's 8-bit IRQ storage, while
  retaining the 32-255 range for GICv2/v3.

* Restored blank lines inadvertently removed in patches 9 and 12.

* Made GICv5 ITS setup fall through to the common GICv5 IRS setup.

* Replaced PCI MSI property selection with a switch statement.

The v7.4-rc1 header sync includes GICv5 IRS UAPI, but not GICv5 ITS
UAPI. Patch 19 mirrors the ITS definitions from [2]. Once that UAPI
lands upstream, the headers should be resynced against the latest
Linux headers before merging the ITS support.

New:  KVM: x86/mmu: Wait for freed TDP MMU pages only before
[PATCH] KVM: x86/mmu: Wait for freed TDP MMU pages only before
Author: Qiliang Yuan <qiliang.yuan@linux.dev>

The TDP MMU frees page table pages from RCU callbacks, so that lockless
walkers never see a freed table. kvm_mmu_uninit_tdp_mmu() ends with
rcu_barrier(), which commit 7cca2d0b7e7d ("KVM: x86/mmu: Protect TDP MMU
page table memory with RCU") added so that these callbacks run before
the VM is torn down.

The callbacks only free the page table page and return its kvm_mmu_page
to mmu_page_header_cache; they do not touch the VM. Still, destroying
any VM waits for the RCU callbacks pending on every CPU, which accounts
for most of the time it takes to destroy a small VM and limits how fast
sandboxes that run one short-lived VM per task can be recycled.

Move the barrier to mmu_destroy_caches(), the only place that needs the
callbacks to have run, before mmu_page_header_cache is destroyed.

Each thread creates VMs with a 1 MiB memslot and one vCPU that touches
eight guest pages, and destroys them by closing the vCPU and VM fds; 400
VMs per run in a 32 vCPU guest with nested KVM on AMD, median of five
runs:

             destroy time per VM             VMs per second
  threads   before (ms)  after (ms)  change   before    after   change

        4         15.5        0.61     -96%      197     1105    +461%

New:  vfio/pci: Add PCIe TPH support
[PATCH v21 00/13] vfio/pci: Add PCIe TPH support
Author: Chengwen Feng <fengchengwen@huawei.com>

This patchset enables userspace-configurable PCIe TPH support for VFIO in
the **device-to-host (D2H)** scenario, bringing performance benefits for
userspace workloads such as DPDK and SPDK.

The patchset is split into two logical parts:
1. The first eight patches fix and refactor core PCI/TPH kernel code to
   export the required helper interfaces.
2. The second five patches implement the corresponding VFIO TPH
   virtualization and uAPI step by step.


Since TLP TPH ST values are not validated by the IOMMU like TLP address
fields, there exists risk of cross-tenant cache interference if untrusted
VM can program arbitrary ST tags. We introduce two-level security
gating:

The first is the VFIO-PCI module parameter tph_policy, defined as:
   Global TPH policy level (0 = default No-ST):
   0 = No-ST mode: ST programming unavailable
   1 = Add IV-ST mode: ST programming supports NONE / CPU sources
   2 = Add DS-ST mode: RESOLVE returns ST for CPU sources;
                       ST programming supports NONE / CPU sources
       Note: In this 'Add DS-ST mode', device-specific ST tables are not
             preserved across PCI resets, userspace must re-establish ST
             state after reset. The kernel cannot validate these ST
             entries, so this mode is not recommended for general
             virtualization usecases.

Note: IV-ST mode is considered safe for VM use because the ST table is
programmed exclusively via the kernel VFIO uAPI. VM cannot directly
write the architected ST table in MSI-X or config space. The hypervisor
(e.g. QEMU) will verify ST, and also when a target CPU transitions from
online to offline, the kernel automatically (add in this patchset) clears
all ST table entries mapped to that CPU, setting those ST values to zero.

The second gate is per-device opt-in. TPH programming is only permitted
after userspace successfully opt-in via the VFIO TPH feature.


Three VFIO device features are introduced in this series:
1. VFIO_DEVICE_FEATURE_TPH: control and query VFIO TPH feature
   capabilities.
2. VFIO_DEVICE_FEATURE_TPH_PROGRAM: batch program architected steering tag
   table entries.
3. VFIO_DEVICE_FEATURE_TPH_RESOLVE: resolve TPH attributes for a given CPU
   source.

The intended userspace programming model is:
1. Read the virtualized PCI TPH capability via VFIO config space access to
   discover underlying hardware TPH support.
2. Invoke VFIO_DEVICE_FEATURE_TPH SET to opt-in and obtain TPH permission.
3. Invoke VFIO_DEVICE_FEATURE_TPH GET to retrieve available TPH
   capabilities; GET returns an error if opt-in has not been performed.
4. Write the TPH control register through VFIO config space to activate
   hardware TPH.
5. Program architected ST table entries via
   VFIO_DEVICE_FEATURE_TPH_PROGRAM if the device exposes architected ST
   table.
6. Query the ST value for a given CPU ID via
   VFIO_DEVICE_FEATURE_TPH_RESOLVE for DS-ST capable devices, userspace
   may then configure the ST through device MMIO or firmware interfaces.


Key implementation details for capability virtualization:
1. The TPH capability register is virtualized according to the active
   tph_policy:
   a. No-ST policy: IV/DS mode bits, ST location and ST size fields are
      masked. Only NO-ST capability is visible to userspace.
   b. IV-ST policy: DS mode bits are masked. Userspace sees NO-ST and
      IV-ST capabilities (if hardware supports IV-ST).
   c. DS-ST policy: capability register is passed through unmodified.
2. Capability bits returned by VFIO_DEVICE_FEATURE_TPH GET follow these
   rules:
   a. If virtualized TPH exposes architected ST table:
      VFIO_DEVICE_TPH_CAP_PROG_ST_NONE and VFIO_DEVICE_TPH_CAP_PROG_ST_CPU
      are reported. These indicate userspace may use TPH_PROGRAM to update
      ST.
   b. If virtualized TPH supports DS mode:
      VFIO_DEVICE_TPH_CAP_RESOLVE_CPU_ST is reported. This indicates
      userspace can resolve CPU-ID associated ST values via TPH_RESOLVE.


Future P2P / DMABUF extension
------------------------------
The uAPI is designed to easy extend to support device-to-device (P2P) and
DMABUF-backed scenarios on top of Zhiping's P2P TPH patchset:
1. Return VFIO_DEVICE_TPH_CAP_RESOLVE_DMABUF_PH in all tph_policy in
   VFIO_DEVICE_FEATURE_TPH GET, so that userspace could resolve DMABUF's
   TPH PH info
2. Return VFIO_DEVICE_TPH_CAP_PROG_ST_DMABUF if virtualized TPH has the
   architect ST, so that userspace could program ST entries which
   associated to DMABUFs' fd
3. Return VFIO_DEVICE_TPH_CAP_RESOLVE_DMABUF_ST if virtualized TPH
   supports DS mode, so that userspace could retrieve ST value which
   associated to DMABUF's fd

New:  KVM: arm64: Force HCR_EL2.NV1 to RES0 unconditionally
[PATCH v3 1/2] KVM: arm64: Force HCR_EL2.NV1 to RES0 unconditionally
Author: Colton Lewis <coltonlewis@google.com>

ID_AA64MMFR4_EL1.E2H0 is a signed 4-bit field where:
  - 0b0000 (IMP, 0): FEAT_E2H0 is implemented.
  - 0b1111 (NI, -1): FEAT_E2H0 is not implemented, except HCR_EL2.NV1
    is implemented.
  - 0b1110 (NI_NV1, -2): Neither HCR_EL2.E2H == 0 nor HCR_EL2.NV1 is
    implemented, and HCR_EL2.NV1 is RES0.

When commit b2a324ff01fe ("KVM: arm64: Use HCR_EL2 feature map to drive

instead of RES0 for VHE-only nested guests where KVM advertises
ID_AA64MMFR4_EL1.E2H0 = NI_NV1.

configuration: limit_nv_id_reg() exposes either VHE-only EL2 with
ID_AA64MMFR4_EL1.E2H0 = NI_NV1 (and E2H0 is not userspace-writable), or
FEAT_E2H0 without FEAT_VHE or FEAT_NV. Checking E2H0 in a feature helper
is therefore unnecessary.

using NEEDS_FEAT_FLAG(HCR_EL2_NV1, FORCE_RESx) in hcr_feat_map[] (shared
by HCR_EL2 and NVHCR_EL2). Because HCR_EL2_NV1 is not part of the
architectural HCR_EL2_RES0 mask, check_feat_map() accounts for it as an
implementation-defined FORCE_RESx bit.

guest DT, updates the timer and PMU interrupt descriptions, and
generates GICv5 interrupt specifiers for platform devices and PCI. It
also maps PCI MSI requester IDs to the ITS. The IRS support is built
and exposed before the ITS support, so the GICv5 irqchip support can

New:  KVM: arm64: nv: Ignore TLBI IPAS2E1 above the IPA limit
[PATCH] KVM: arm64: nv: Ignore TLBI IPAS2E1 above the IPA limit
Author: Dan Carpenter <dan@pereq.eu>

In theory, an L1 hypervisor could issue a TLBI IPAS2E1 for an IPA
above the host's IPA limit.  The s2_mmu_unmap_ipa() function would
pass it to kvm_stage2_unmap_range(), the page table walk would fail
with -ERANGE, and that would trigger the WARN_ON() in
kvm_vm_stage2_unmap_range():

	WARN_ON(stage2_apply_range(mmu, start, start + size, fn, may_block));

The TLBI's IPA field goes up to 48 bits, so this needs a host whose IPA
limit (its PARange) is below 48 bits, and it would also need to support
nested virtualization.  There are very few CPUs which meet both these
requirements.

The fix for this is to return early.  Since there is nothing mapped above
the limit, there is nothing to do.  This matches how handle_ripas2e1is()
also ignores TLBIs that start outside the PA_bits range.

Fixes: 70109bcd701e ("KVM: arm64: nv: Handle TLBI IPAS2E1{,IS} operations")
Signed-off-by: Dan Carpenter <dan@pereq.eu>

New:  KVM: arm64: nv: Forward PIR_EL2, PIRE0_EL2 and POR_EL2
[PATCH 1/3] KVM: arm64: nv: Forward PIR_EL2, PIRE0_EL2 and POR_EL2
Author: Dan Carpenter <dan@pereq.eu>

These registers were added to KVM, but not to the encoding_to_cgt[]
table which decides when a trap is forwarded to a nested hypervisor.

The result is that if an L1 hypervisor runs its L2 with HCR_EL2.NV set
(meaning the L2 is itself a hypervisor), and the L2 accesses these
registers, KVM handles the access itself and it goes to the L1's own
registers instead of being emulated on L1.  This is quite a serious bug
because it lets the L2 change the permissions of the L1's own stage 1
translations.  It could mark everything as no-access and cause a crash
in L1 or mark everything as read-write-execute which weakens the
protections in L1.

Add the three registers with CGT_HCR_NV, MAIR_EL2 and AMAIR_EL2.

Fixes: 874ae1d48e60 ("KVM: arm64: Handle PIR{,E0}_EL2 traps")
Fixes: 5970e9903f03 ("KVM: arm64: Add basic support for POR_EL2")
Cc: stable@vger.kernel.org
Signed-off-by: Dan Carpenter <dan@pereq.eu>

New:  KVM: arm64: Donate MMIO to the hypervisor
[PATCH v4 01/13] KVM: arm64: Donate MMIO to the hypervisor
Author: Fuad Tabba <fuad.tabba@linux.dev>


Add __pkvm_host_donate_hyp_mmio() so IOMMU drivers in the hypervisor can
take ownership of the IOMMU MMIO. The range is mapped in the hypervisor
private range and annotated as owned by the hypervisor in the host
stage-2, so host accesses fault and further donations of the same range
are refused. MMIO has no struct hyp_page, so the annotation is the only
state, and a dedicated function is simpler than teaching the memory
donation path about MMIO. Donation is only allowed before the host is
de-privileged, which is when the hypervisor IOMMU drivers initialise.

Make kvm_pgtable_stage2_unmap() leave invalid counted PTEs (annotations)
in place. host_stage2_unmap_dev_all() unmaps all non-memory ranges to
recycle page-table pages under memory pressure, and would otherwise drop
the annotation and let the host fault the MMIO back in. No caller depends
on the old behaviour: host_stage2_unmap_dev_all() only covers non-memory
ranges, where no annotation existed until now, and the guest unmap paths
check that the PTE is valid first. Returning an error for counted PTEs
instead is not an option, as a non-zero visitor return stops the walk,
which would abort recycling at the first hypervisor-owned MMIO page and
inject an abort into the host for an unrelated address.

New:  KVM: ITS hardening for pKVM
[PATCH v4 00/13] KVM: ITS hardening for pKVM
Author: Fuad Tabba <fuad.tabba@linux.dev>

Hi folks,

Changes since v3 [1]:
  - The hypervisor never gives an ITT back to the host (patch 11).
  - The limit on devices per ITS now counts every DeviceID mapped since
    boot (patch 11).
  - A host read of an ITS register now aborts, unless the driver reads
    that register (patch 9).
  - Rebased on 7.4-rc3.
  - Various cleanups and wording fixes.

The ITS writes to the memory that its command queue and tables point
to, and the host programs both, so a host that controls the ITS can
write to hypervisor and protected-VM memory. With this series the
hypervisor owns the command queue, the tables and the ITTs, traps every
host access to the ITS control frame, and checks each command before
forwarding it to the ITS. The cover letter for v3 [1] describes the
design in more detail.

This series covers the ITS. The redistributors will follow in a series
of their own.

Jinjie's series [2] lets the collection table have two levels, which
this series doesn't handle. Once it's merged, I'll send patches that
make the hypervisor handle that table the way it handles the device
table.

Tested on QEMU with a program that writes forged commands, table
entries and register values to the ITS through /dev/mem from the host's
userspace. Also tested on FVP, where the ITS uses physical redistributor
addresses (GITS_TYPER.PTA). There, every secondary CPU was hotplugged
after the takeover, so that the driver maps each returning CPU's
collection through the hypervisor with a MAPC that carries a physical
address.

The series is structured as follows:

  01:     MMIO donation.
  02:     Taking host-registered MMIO regions at finalisation.
  03-06:  Driver preparation: GICv4 off, page-aligned ITTs, computing
          the wait target under the ITS lock, the shared command
          accessors.
  07:     Deprivileging the host under stop_machine().
  08-09:  The takeover: the driver's entry points, then the hypervisor
          trapping the control frame, taking the command queue and
          emulating GITS_CTLR and GITS_CBASER.
  10-11:  The tables and GITS_BASER<n>, then the ITTs.
  12:     Rejecting commands whose IDs are out of range.
  13:     Documentation.

Based on Linux 7.4-rc3 (aebb727447640).

Cheers,
/fuad

New:  KVM: arm64: Load the vcpu in KVM_SET_VCPU_EVENTS
[PATCH v2 1/2] KVM: arm64: Load the vcpu in KVM_SET_VCPU_EVENTS
Author: Dan Carpenter <dan@pereq.eu>

Nested virtualization can trigger a NULL pointer dereference of
vcpu->arch.hw_mmu in kvm_inject_nested():

Unable to handle kernel NULL pointer dereference at virtual address 0000000000000084
  kvm_vcpu_put_hw_mmu (arch/arm64/kvm/nested.c:1046) (P)
  vhe_vcpu_put (arch/arm64/kvm/arm.c:827)
  kvm_arch_vcpu_put (arch/arm64/kvm/arm.c:860)
  kvm_inject_nested (arch/arm64/kvm/emulate-nested.c:2903)
  kvm_inject_nested_serror (arch/arm64/kvm/emulate-nested.c:2976)
  kvm_inject_serror_esr (arch/arm64/kvm/inject_fault.c:365)
  __kvm_arm_vcpu_set_events (arch/arm64/kvm/guest.c:827)
  kvm_arch_vcpu_ioctl (arch/arm64/kvm/arm.c:2017 arch/arm64/kvm/arm.c:2157)
  kvm_vcpu_ioctl (arch/arm64/kvm/../../../virt/kvm/kvm_main.c:4772)

The KVM_SET_VCPU_EVENTS ioctl does not load the vcpu, it just injects a
pending SError or external abort straight away.  If the vcpu is in L2
context and L1 has asked for the exception, kvm_inject_nested() puts and
loads a vcpu that is not loaded which leads to a NULL pointer dereference.

Load the vcpu in kvm_arm_vcpu_set_events() so that kvm_inject_nested()
always finds a loaded vcpu.

Fixes: 77ee70a07357 ("KVM: arm64: nv: Honor SError exception routing / masking")
Cc: stable@vger.kernel.org
