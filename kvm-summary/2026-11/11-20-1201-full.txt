[PATCH net v2] vhost/net: Fix receive queue test in busy poll
Author: raoxu <raoxu@uniontech.com>


sock_has_rx_data() returns a positive value when receive data is
available. For sockets without a peek_len() callback, however, its
fallback returns skb_queue_empty(), which has the opposite meaning.

An AF_PACKET SOCK_RAW socket is accepted by get_raw_socket() as a
vhost-net backend, and its socket operations do not provide peek_len().
With busy polling enabled for this backend, an empty receive queue is
treated as ready and a nonempty queue as not ready. This can make
vhost_net_busy_poll() stop polling prematurely or fail to stop for
queued receive data, and invert its receive-side scheduling decision.
TUN and TAP backends provide peek_len() and are unaffected.

Negate skb_queue_empty() so the fallback matches the callback and the
readiness checks in vhost_net_busy_poll().

The issue was found during AI-assisted code review. The helper's
incorrect result was confirmed on x86_64 running 6.6.0-amd64-desktop
using a temporary diagnostic module containing the original and fixed
helpers. An AF_PACKET SOCK_RAW socket, without PACKET_RX_RING, was
bound to loopback in a private network namespace. Across three cycles
of sending and receiving a 60-byte frame, the original helper returned
1 for an empty queue and 0 for a queued frame. The fixed helper returned
0 and 1 respectively, matching socket readability in all nine checks.
This tests helper copies on real sockets, not the running vhost-net
busy-poll path; the vhost-net module was not replaced.

The patched drivers/vhost/net.o was also build-tested on the net tree
with x86_64 GCC 12.3 and W=1 under allmodconfig and allyesconfig.
No end-to-end vhost tests or kernel selftests were run.

Fixes: 1576d9860599 ("tun: switch to use skb array for tx")
Cc: stable@vger.kernel.org
Signed-off-by: Xu Rao <raoxu@uniontech.com>

[PATCH v2 5/6] KVM: Send reschedule IPIs instead of SMP function
Author: Sean Christopherson <seanjc@google.com>

When kicking multiple vCPUs for a non-waiting request, send a reschedule
IPI to each vCPU instead of batching IPIs via a single SMP function call so
that KVM can make non-waiting requests with IRQs disabled.  I.e. handle
multi-vCPU kicks the same way KVM handles single-vCPU kicks, for the exact
same reason (and more).

Avoiding SMP function calls for non-waiting requests fixes a potential
deadlock if KVM VMX triggers KVM_REQ_UNBLOCK to all vCPUs when starting
device assignmennt:

  WARNING: kernel/smp.c:943 at smp_call_function_many_cond
    kvm_make_all_cpus_request [kvm]
    kvm_arch_irq_bypass_add_producer [kvm]
    __connect [irqbypass]
    irq_bypass_register_producer [irqbypass]
    vfio_msi_set_vector_signal [vfio_pci_core]

Deliberately avoid using the per-CPU cpu_kick_mask for non-waiting to fix
an even more urgent bug on arm64, where KVM could fail to wait for a vCPU,
e.g. for a remote TLB flush, if an IRQ triggers a multi-vCPU kick in the
middle of another waiting kick.

  kvm_flush_remote_tlbs()
    kvm_make_all_cpus_request(kvm, KVM_REQ_TLB_FLUSH)
      cpumask_clear(cpus)
      kvm_make_vcpu_request(vcpu0, ...)
        kvm_vcpu_exiting_guest_mode(vcpu0)
          cmpxchg(&vcpu0->mode, IN_GUEST_MODE, EXITING_GUEST_MODE)
        __cpumask_set_cpu(vcpu0->cpu, cpus)
      <hardirq>
        irqfd_wakeup()
          ...
            kvm_make_all_cpus_request(kvm, KVM_REQ_IRQ_PENDING)
              cpumask_clear(cpus)  <-- wipes vcpu0->cpu from cpu_kick_mask
              kvm_make_vcpu_request(vcpu0, ...)
                kvm_request_needs_ipi(vcpu0, ...)  <-- false (EXITING_GUEST_MODE)
      kvm_kick_many_cpus(cpus, true)  <-- misses vcpu0->cpu

Send reschedule IPIs immediately to avoid having to re-walk the set of CPUs,
and obviously because using the per-CPU mask is unsafe.  As a bonus, it's
generally advantageous to kick vCPUs as soon as possible, e.g. so that the
target vCPU(s) can immediately process pending IRQs.

Fixes: 77e1b8332d1d ("KVM: x86: Decouple device assignment from IRQ bypass")

Closes: https://lore.kernel.org/all/20261116-b4-kvm-irq-bypass-irqs-20261116-v1-1-6cc721a062fd@cisco.com

[PATCH v2 4/6] KVM: Don't kick offline CPUs when making a multi-vCPU request
Author: Sean Christopherson <seanjc@google.com>

Don't send IPIs to offline CPUs when sending a request to multiple vCPUs,
as it's obviously unnecessary and sending a reschedule IPI (spoiler alert)
to an offline CPU will trigger a WARN in x86's native_smp_send_reschedule().

Note, as explained in commit 85b640450ddc ("KVM: Clean up benign vcpu->cpu
data races when kicking vCPUs"), checking for an online CPU is inherently
racy, but losing the race is functionally a-ok.  I.e. the goal is purely to
avoid tripping x86's WARN.

[PATCH v2 1/6] s390/smp: Export arch_smp_send_reschedule() for KVM
Author: Sean Christopherson <seanjc@google.com>

Export arch_smp_send_reschedule() so that KVM can use smp_send_reschedule()
in common "kick vCPU" code without running afoul of build issues on s390.
KVM currently uses smp_call_function_many() when kicking multiple vCPUs,
but several KVM architectures (at least arm64 and x86) kick vCPUs with IRQs
disabled.  Using SMP function calls with IRQs disabled is unsafe as it can
lead to two CPUs waiting for each other to respond to the function call,
i.e. KVM needs to use smp_send_reschedule() to avoid potential deadlock on
other architectures.

Alternatively, KVM could go out of its way to avoid smp_send_reschedule()
on s390, as KVM does when kicking a single vCPU, but given that all modules
can reach smp_send_reschedule() via kick_process(), forcing KVM to dance
around s390 adds no practical value and would add non-trivial complexity to
KVM.

Note, thanks to s390 now building kvm.ko and kvm-arm64.ko, using
EXPORT_SYMBOL_FOR_KVM doesn't Just Work.  Exporting the symbol just for KVM
would also complicate backporting the upcoming fixes to older kernels.  For
now, keep it simple.

Cc: stable@vger.kernel.org
Signed-off-by: Sean Christopherson <seanjc@google.com>

[PATCH v3 0/9] Rust VFIO PCI support and NVIDIA vGPU driver
Author: Simon Song <xinmengs@nvidia.com>

This is v3 of the Rust VFIO PCI abstractions and the NVIDIA VFIO variant
driver [1]. The driver uses nova-core's typed SR-IOV PF interface to
create, reset and release vGPU instances while VFIO provides userspace
access to the PCI device.

Patches 1-5 add the PCI helpers and callbacks the VFIO abstractions
need. Patch 6 adds the VFIO device handling common to all buses, and
patch 7 the VFIO PCI abstractions on top of it. Patch 8 publishes the
typed Nova PF interface, and patch 9 adds the NVIDIA VFIO variant
driver.

This series is based on drm-rust-next with the Rust PCI SR-IOV series
[2] applied. Patches 1-7 need nothing else. Patches 8 and 9 also depend
on Alok's vGPU manager series [3] and can follow once it has landed.

Runtime PM is not part of this series anymore. As Danilo suggested, it
will follow as a separate series based on Beata's generic Rust runtime
PM work [4], so that the rest can land independently. Until then,
vfio::pci::Registration keeps the device runtime active while it is
registered, so a VF bound to the driver is not runtime suspended.

Changes since v2:
- Drop runtime PM from this series (v2 patch 08 and the runtime PM
  parts of v2 patches 04, 09 and 12), see above.
- Put the common VFIO device handling first (v2 patch 10, now patch 6)
  and squash v2 patches 04 and 09 into one patch (patch 7) (Danilo).
- Drop the bind callback (v2 patch 06). A driver registers its VFIO
  device with vfio::pci::Registration::new(), for example from probe,
  and unregisters it by dropping the Registration (Danilo).
- Patch 1: say first what the function does in its documentation
  (Gary).
- Patch 2: return Result<u16> from vf_id(), and add a C helper so that
  it builds without CONFIG_PCI_IOV (Danilo).
- Patch 3: make DRIVER_MANAGED_DMA an unsafe marker, until the DMA
  setup tokens exist (Danilo).

[PATCH 3/3] vfio/type1: Track GUP vs PFNMAP in external page pinning
Author: Aaron Lewis <aaronlewis@google.com>

Like the DMA map/unmap path, external page pinning for emulated IOMMU
drivers (vfio_iommu_type1_pin_pages()) uses the same heuristic
(is_invalid_reserved_pfn()) to infer if a struct vfio_pfn was PFNMAP'd
or GUP-pinned in vaddr_get_pfns().

That heuristic falls apart for reserved GUP-pinned mappings such as
device-dax. They are treated as PFNMAP, so they are never unpinned,
which leaks page pins and refcounts. They are also left out of locked_vm
accounting.

Record in struct vfio_pfn whether vaddr_get_pfns() used the PFNMAP path,
and use that (vpfn->pfnmap) across all external pinning, unpinning, and
locked_vm accounting paths instead of inferring it.

As with the DMA map/unmap path, GUP-pinned reserved pages are now
charged against RLIMIT_MEMLOCK. When no IOMMU-backed domain is present,
vfio_pin_pages() on such memory can now fail with -ENOMEM where it
previously bypassed the limit.

Opportunistically, drop the forward declaration of put_pfn(), which is
no longer needed.

[PATCH 2/3] vfio/type1: Track GUP vs PFNMAP in DMA map/unmap
Author: Aaron Lewis <aaronlewis@google.com>

Both vfio_pin_pages_remote() and vfio_unpin_pages_remote() use
PageReserved() as a heuristic to infer whether a page was PFNMAP'd or
GUP-pinned in vaddr_get_pfns(). That heuristic breaks down when the same
reserved struct pages can appear on both paths:

- DevDax pages mapped from /dev/dax* are reserved and GUP-pinned.
- Those same pages mapped from /dev/mem (PFNMAP) are also reserved,
  but they are *not* GUP-pinned.

Because of this, when unpinning the DMA region, vfio_unpin_pages_remote()
doesn't know whether those reserved pages were GUP-pinned and skips
unpinning them altogether, *leaking page pins and refcounts*.

Fix this by replacing has_rsvd and has_non_rsvd in struct vfio_dma with
has_pfnmap and has_gup_pinned, tracking which path vaddr_get_pfns()
actually used, and clearing them when a DMA range is unpinned. Since
PFNMAP pages bypass struct vfio_batch, this also fixes locked_vm
accounting and batch error-unwind unpinning for reserved GUP-pinned
pages.

This isn't an exhaustive fix because mixed mappings are still allowed.
For example, if a single DMA region contains both GUP-pinned and
PFNMAP pages, vfio_unpin_pages_remote() can't tell them apart. Handle
this by preserving the existing put_pfn() fallback, and add
a comment explaining the situation.

Lastly, clear the new flags once a vfio_dma is fully unpinned. A vfio_dma
can outlive its pins and be pinned again later, after
vfio_iommu_unmap_unpin_reaccount() or a failed vfio_iommu_replay(), by
which time the user may have remapped the range. A stale has_rsvd only
selected the slower unpin path, but a stale has_pfnmap would send a
mapping that is now entirely GUP-pinned down the wrong unpin path.

[PATCH 0/3] vfio/type1: Fix pin leaks for reserved GUP-pinned pages
Author: Aaron Lewis <aaronlewis@google.com>

vfio/type1 uses PageReserved(), via is_invalid_reserved_pfn(), to guess
whether a pfn was GUP-pinned or came from a VM_PFNMAP mapping. Reserved
pfns are assumed to be PFNMAP, so they are not accounted in locked_vm
and are never unpinned.

That guess is wrong for reserved pages that GUP does pin, such as
device-dax. ZONE_DEVICE struct pages are marked PG_reserved when they
are initialized, and device-dax, unlike fsdax, can be long-term pinned.
When such memory is DMA mapped, or pinned through vfio_pin_pages(), the
pins are never dropped.

Commit f6c84a52cc41 ("vfio/type1: optimize vfio_pin_pages_remote()")
assumed that long-term GUP never returns reserved pages, so patch 2 also
drops the comment that says so.

This series records how each pfn was obtained instead of inferring it:

- Patch 1 makes vpfn_pages() count only the externally pinned pfns that
  were actually accounted. It fixes a locked_vm imbalance on its own,
  and patch 2 depends on it.
- Patch 2 tracks GUP vs PFNMAP per vfio_dma for the DMA map/unmap path.
- Patch 3 tracks it per vfio_pfn for external page pinning.

Two things to call out:

- Reserved GUP-pinned pages are now charged against RLIMIT_MEMLOCK like
  any other long-term pinned page, so mappings that used to bypass the
  limit can now fail with -ENOMEM.
- A single DMA mapping that contains both PFNMAP and GUP-pinned pfns
  still falls back to the PageReserved() heuristic on unpin, because
  type1 does not record which pfn is which. That stays correct unless
  the GUP-pinned pages are reserved. In that case their pins still leak
  and, since they are now accounted, so does their locked_vm accounting.
  Closing that needs per-range tracking.

The DMA map/unmap path (patch 2) was tested on vfio/next by adding
device-dax and /dev/mem mappings locally to vfio_dma_mapping_test:

1. 1GiB (262,144 pages) device-dax mapping, checking /proc/vmstat (after
   flushing /proc/sys/vm/stat_refresh) before and after running:

     ./vfio_dma_mapping_test -v vfio_type1v2_iommu_devdax_1gb <BDF>

   Before fix:
     nr_foll_pin_acquired: 27471 -> 289615 (+262144)
     nr_foll_pin_released: 27471 -> 27471  (+0, leaked)

   With fix:
     nr_foll_pin_acquired: 18786 -> 280930 (+262144)
     nr_foll_pin_released: 18786 -> 280930 (+262144)

2. /dev/mem (VM_PFNMAP) mapping of a reserved physical page with a valid
   struct page (memmap=4M$0x340000000), confirming DMA map/unmap still
   succeeds with +0/+0 pin deltas and no unpin warnings.

If desirable, I can add the test updates to this series, though the
changes depend on host-specific device-dax paths and reserved physical
addresses.

[PATCH v10 12/33] KVM: arm64: Set up FGT for Partitioned PMU
Author: Colton Lewis <coltonlewis@google.com>

[PATCH v10 00/33] ARM64 PMU Partitioning
Author: Colton Lewis <coltonlewis@google.com>

This series creates a new PMU scheme on ARM, a partitioned PMU that
allows reserving a subset of counters for more direct guest access,
significantly reducing overhead. More details, including performance
benchmarks, can be read in the v1 cover letter linked below.

PMU partitioning is controlled via the KVM API using
`KVM_ARM_VCPU_PMU_V3_ENABLE_PARTITION` and
`KVM_ARM_VCPU_PMU_V3_SET_NR_COUNTERS` vCPU device attributes. When
partitioning is enabled for a VM, userspace must explicitly configure a
guest event counter count strictly less than the maximum general-purpose
counters implemented by the PMU (leaving at least one general-purpose
counter for the host) prior to calling `KVM_ARM_VCPU_PMU_V3_INIT`. The
number of general-purpose counters implemented by each host PMU is
exposed in sysfs at
`/sys/bus/event_source/devices/<pmu>/caps/num_counters`. A QEMU patch
demonstrating how to use the uAPI is sent separately.

An overview of what this series accomplishes was presented at KVM
Forum 2025. Slides [1] and video [2] are linked below.

v10:

* Rebase on top of v7.4-rc3.

* Add nested virtualization (`FEAT_NV` / `FEAT_NV2`) support covering
  both an Emulated L2 PMU (`vHPMN == N_L1`, `TPM == 1`, where L1 keeps
  all `N_L1` counters and emulates L2 via L1 `perf` events) and a
  Sub-partitioned L2 PMU (`vHPMN < N_L1`, `TPM == 0`, creating a
  three-way split across `0..vHPMN-1` for L2, `vHPMN..N_L1-1` for L1,
  and `N_L1..N_phys-1` for L0) (Oliver Upton). Because ARM64 provides
  only a single physical `MDCR_EL2.HPMN` field, hardware can split the
  PMU into two counter ranges at a time rather than three. Key design
  decisions and supporting changes:

  - Keep physical `MDCR_EL2.HPMN = N_L1` at all times (`vHPMN` boundary
    and event filtering): Lowering physical `HPMN` to `vHPMN` while
    running L2 was considered and rejected because it would move L1's
    hypervisor counters (`vHPMN..N_L1-1`) into the same physical
    `>= HPMN` range as L0's host counters (`N_L1..N_phys-1`), where a
    single set of physical `MDCR_EL2.{HPME,HPMD,HLP}` bits governs both
    and breaks host/guest isolation; it would also fail for
    `vHPMN == 0` on hardware without `FEAT_HPMN0`. Instead, when
    `vHPMN < N_L1`, L0 keeps physical `HPMN = N_L1` and sets
    `MDCR_EL2.{TPM,TPMCR}` in L2, forwarding `vHPMN..N_L1-1` traps to
    L1 and handling `0..vHPMN-1` plus `PMCCNTR_EL0` in L0 directly
    against physical registers. This preserves L0 isolation and
    supports `vHPMN == 0` on all hardware; L2 events still count
    directly in hardware without L0 `perf_event` scheduling, at the
    cost of trapping L2 PMU accesses to L0 and rewriting per-counter
    filter registers on `L1 <-> L2` transitions. In L1
    (`is_hyp_ctxt()`), L0 emulates `vHPMN`, `vMDCR_EL2.HPMD`, and
    `vMDCR_EL2.HCCD` via `PMEVTYPER<n>_EL0` and `PMCCFILTR_EL0`.

  - Dynamically multiplex `vPMCR_EL0.E` and `vMDCR_EL2.HPME`: Because
    both `0..vHPMN-1` and `vHPMN..N_L1-1` sit below physical
    `HPMN = N_L1`, hardware gates both with physical `PMCR_EL0.E`.
    Rather than unconditionally trapping `PMCR_EL0` and `PMCNTEN*` for
    all `FEAT_NV` VMs (which would penalize Emulated L2 PMU where
    `vHPMN == N_L1`), L0 dynamically enables `MDCR_EL2.TPMCR` and
    `HDFG{R,W}TR_EL2.PMCNTEN` only when `vHPMN < N_L1`. L0 keeps
    architectural `PMCR_EL0` and `PMCNTENSET_EL0` in memory, sets
    physical `PMCR_EL0.E` to `vPMCR_EL0.E || vMDCR_EL2.HPME`, masks
    disabled sub-ranges out of physical `PMCNTENSET_EL0`, and gates
    overflow delivery per domain. Trapped `PMSWINC_EL0` writes (also
    enabled via `HDFGWTR_EL2` when `vHPMN < N_L1`) flush live registers
    and reuse `kvm_pmu_software_increment()` to prevent cross-partition
    chaining.

  - Bias 32-bit counters on mismatched `vPMCR_EL0.LP != vMDCR_EL2.HLP`
    (`FEAT_PMUv3p5`): When `LP == HLP`, physical `PMCR_EL0.LP` matches
    both domains directly and `PMEVCNTR<n>_EL0` stays untrapped in L1.
    When `vHPMN < N_L1` and `LP != HLP`, rather than ignoring the
    mismatch (breaking 32-bit overflow interrupts) or falling back to
    `perf_event` emulation mid-flight (requiring reservation teardown),
    L0 forces physical `PMCR_EL0.LP = 1` (64-bit overflow), dynamically
    traps `HDFG{R,W}TR_EL2.PMEVCNTRn_EL0`, and biases counters in the
    32-bit sub-range `2^32` events below 64-bit overflow
    (`0xffffffff00000000 | low32`) while tracking their upper-32-bit
    offsets and re-biasing outside interrupt/NMI context. Because
    `HDFG{R,W}TR_EL2.PMEVCNTRn_EL0` is a single trap bit covering all
    event counters (`0..30`), L1 counter reads/writes trap across both
    sub-ranges while `LP != HLP`, with zero overhead when `LP == HLP`.

  - Baseline nested support (both Emulated and Sub-partitioned L2):
    separate implemented and accessible counter masks by using
    `nr_pmu_counters` directly in `kvm_pmu_implemented_counter_mask()`,
    masking trapped guest reads of `PMCNTEN*`, `PMINTEN*`, and `PMOVS*`
    with `kvm_pmu_accessible_counter_mask()`, and ignoring
    `MDCR_EL2.HPMN` in userspace `KVM_GET_ONE_REG` / `KVM_SET_ONE_REG`
    (`set_pmreg()`, `get_pmreg()`, `get_pmcr()`) so saving/restoring a
    nested vCPU paused below EL2 preserves all VM-implemented counters
    and true `PMCR_EL0.N`; preserve host counter reservations across
    `IN_NESTED_ERET` / `IN_NESTED_EXCEPTION` transitions to avoid host
    `perf` reschedules on emulated L2 traps; read live hardware
    `PMSELR_EL0` in `check_mdcr_hpmn()` when untrapped; and forward
    fine-grained traps for selector-indexed `PMXEVTYPER_EL0` and
    `PMXEVCNTR_EL0` to L1.

* Expose the number of general-purpose counters implemented by the PMU
  in sysfs under `/sys/bus/event_source/devices/<pmu>/caps/num_counters`
  so userspace VMMs can query host PMU counter capacity when configuring
  a partitioned PMU (James Clark).

* Make `__vcpu_rmw_sys_reg()` atomic on the local CPU using
  `try_cmpxchg_local()` to prevent read-modify-write races with GICv3
  pseudo-NMI PMU interrupt handlers (`kvm_pmu_handle_guest_irq()`),
  which are not masked by `local_irq_save()` (Sashiko AI Review).

* Construct `mdcr_el2` in a local variable before assigning
  `vcpu->arch.mdcr_el2` once in `kvm_arm_setup_mdcr_el2()`, and mask
  GICv3 pseudo-NMIs (`local_daif_save()`) across hardware PMU context
  switches and `MDCR_EL2` updates (Sashiko AI Review).

* Prioritize kernel-owned pinned event groups (`is_kernel_event()`)
  ahead of userspace pinned events in `perf_event_groups_cmp()` /
  `perf_less_group_idx()` so kernel-owned per-CPU pinned events (such as
  the hardlockup NMI watchdog if toggled at runtime) are scheduled before
  userspace pinned events when `perf_pmu_resched_update()` reschedules
  events out of guest-reserved counters (James Clark, Sashiko AI Review).

* Move `kvm_vcpu_reload_pmu()` from `arch/arm64/kvm/pmu-emul.c` to
  `arch/arm64/kvm/pmu.c` in `KVM: arm64: Reorganize PMU functions`.

* Add `kvm_pmu_is_partitioned()`, `kvm_pmu_guest_counter_mask()`,
  `kvm_pmu_handle_guest_irq()`, `kvm_pmu_host_start()`, and
  `kvm_pmu_host_stop()` stubs to `arch/arm/include/asm/arm_pmuv3.h` to
  fix 32-bit `ARCH=arm` builds (kernel test robot).

* Allow identical VM-wide PMU device attributes
  (`KVM_ARM_VCPU_PMU_V3_SET_PMU`, `KVM_ARM_VCPU_PMU_V3_SET_NR_COUNTERS`,
  and `KVM_ARM_VCPU_PMU_V3_ENABLE_PARTITION`) to be applied across all
  vCPUs when userspace initializes vCPUs sequentially (`CPU_FOREACH`),
  validate `kvm_arm_pmu_part_hpmn(n) < max_counters` (requiring
  `max_counters >= 2` for `n == 0` without `FEAT_HPMN0`), and restrict
  `kvm->arch.supported_cpus` to `arm_pmu->supported_cpus` when
  partitioning is enabled.

* Centralize partitioned PMU hardware register dispatch under
  `kvm_pmu_direct_reg_read()` / `kvm_pmu_direct_reg_write()` with
  preemption disabled (`kvm_pmu_part_on_cpu()`), guard lazy ownership
  transitions in `kvm_pmu_part_overflow_status()` with
  `scoped_guard(preempt)`, avoid matching `reset_unknown()` poison bits on
  `PMCNTENSET_EL0` / `PMINTENSET_EL1` during `KVM_REQ_RELOAD_PMU`, and
  schedule `KVM_REQ_RELOAD_PMU` on `KVM_SET_ONE_REG` writes so
  `vcpu_put()` does not overwrite userspace register writes (Sashiko AI
  Review).

* Support configuring 0 guest event counters (cycle counter only) on
  Partitioned PMU hosts without `FEAT_HPMN0` whenever `max_counters >= 2`.
  Writing `MDCR_EL2.HPMN = 0` without `FEAT_HPMN0` is architecturally
  `CONSTRAINED UNPREDICTABLE`, which would otherwise prevent userspace
  from creating a cycle-counter-only partitioned guest on CPUs lacking
  `FEAT_HPMN0`. Instead, KVM programs physical `MDCR_EL2.HPMN = 1` via
  `kvm_arm_pmu_part_hpmn()`, reserves and quiesces physical counter 0
  alongside `PMCCNTR_EL0` so host perf continues using counters `1..N-1`,
  keeps `MDCR_EL2.TPMCR = 1` so trapped `PMCR_EL0` reads report `N == 0`,
  and enables fine-grained traps on `PMEVCNTRn_EL0`, `PMCNTEN`,
  `PMINTEN`, and `PMSWINC_EL0` so counter 0 stays completely hidden
  (`UNDEFINED` / RAZ / WI) while `PMCCNTR_EL0` remains untrapped on
  `FEAT_FGT` hosts. Also clamp `MDCR_EL2.HPMN` against `nr_pmu_counters`
  in `kvm_vcpu_read_pmcr()` and `kvm_pmu_direct_pmcr_read()`, and extend
  `vpmu_counter_access` to verify `PMCCFILTR_EL0`, live `PMCCNTR_EL0`
  counting, and trapped `UNDEFINED` / RAZ / WI behavior on counter 0 when
  `n == 0`.

[PATCH] KVM: arm64: nv: Fix guest stage-2 mapping leak on sub-block unmap
Author: Colton Lewis <coltonlewis@google.com>

When a shadow stage-2 block mapping (for example, 2M at PMD level) is
partially invalidated by a smaller guest unmap such as a 4K TLBI
IPAS2E1IS, kvm_pgtable_stage2_unmap() shatters and clears the entire
block descriptor in mmu->pgt. However, kvm_remove_guest_s2_mappings()
only removes a struct kvm_guest_s2_mapping node when its entire
[nested_start, nested.last] span lies within the unmap range. As a
result, every sub-block invalidation followed by a re-fault leaks a
stale block-sized tracking node in mmu->guest_s2_mappings and
kvm->arch.mmu.guest_s2_mappings until the shadow MMU is destroyed,
allowing an L1 guest to grow host kernel memory and degrade subsequent
TLBI IPAS2E1IS walks to O(N) under write_lock(&kvm->mmu_lock).

Conversely, unconditionally removing any overlapping tracking node on a
sub-block unmap would be unsafe when a shadow block mapping has been
split into a child table (such as on a page-granule fault under dirty
logging or a racing shared walk returning -EAGAIN), because sibling
sub-page PTEs outside the unmapped range remain live in mmu->pgt and
still rely on the block-sized tracking node for host MMU notifier
unmaps.

Since stage2_unmap_walker() unlinks empty child page tables in
KVM_PGTABLE_WALK_TABLE_POST as soon as their last valid entry is
cleared, check mmu->pgt via kvm_pgtable_get_leaf() on partial-overlap
candidates: when no valid entry or split sub-table remains at or below
the recorded mapping granule (!kvm_pte_valid(pte) &&
kvm_granule_size(level) >= map_size), remove and free the tracking node;
otherwise retain it to cover surviving split sub-entries.

In addition, suppress exact-match duplicate insertions in
kvm_record_guest_s2_mapping() when concurrent faults or -EAGAIN retries
record an identical (nested, canonical) range on the same shadow MMU.

[PATCH v6 4/4] selftests/mm: test fork of PMD-mapped shmem THPs
Author: Konstantin Khorenko <khorenko@virtuozzo.com>

Fork a process that maps shmem THPs with PMDs, in a VMA whose page
tables fork copies: a private mapping with an anon_vma, and a shared
one with a guard region. The child must find the PMDs before it
touches the mapping, and its exit must leave the parent's mapping and
the system-wide ShmemPmdMapped counter as they were.

With folio_dup_file_rmap_pmd() adding PTE mappings, the child's exit
takes the parent's share off ShmemPmdMapped while the parent still maps
the folios. Unmapping them drops it once more, so every mapping stays
until exit, where the kernel reports "Bad page cache", or hits a
VM_BUG_ON with CONFIG_DEBUG_VM. A kernel that leaves file THPs to a
refault in the child skips the test.

ShmemPmdMapped is system-wide, and reclaim or NUMA balancing can take a
PMD from the parent while the test runs. So the test makes up to three
attempts, each on a fresh file, and fails only if all of them see the
counter drop by exactly the parent's share: the bug does that on every
fork, other processes only by chance. It passes on the first clean
attempt and skips when none is clean.

The test mounts a tmpfs with huge=always over /tmp in a private mount
namespace, so it leaves the THP settings and the host's mounts and
files alone.

Cost
====

fork() now copies file THPs instead of leaving them to a refault, which
costs fork() a reference, an rmap update and a counter per huge PMD and
saves the child a fault per huge PMD it touches. fork() of a process
with 4 GB of shmem THPs mapped MAP_PRIVATE and an anon_vma on the VMA,
x86_64 bare metal with 4 NUMA nodes, the benchmark bound to node 0,
both kernels v7.4-rc1 (v5) with the same config, medians of 2000 forks,
range over the rounds; the exec is of /bin/true:

  +-----------------+------------+-----------------+--------------+
  | kernel          | fork()     | child reads all | fork()+exec  |
  +-----------------+------------+-----------------+--------------+
  | v7.4-rc1        | 135-141 us | 3820-4036 us    | 559-567 us   |
  | v7.4-rc1+series | 429-440 us | 1007-1036 us    | 1190-1226 us |
  +-----------------+------------+-----------------+--------------+

A child that execs right away, or touches little, pays about 0.3 us per
huge PMD for the copy and the teardown. One that faults a PMD in itself
pays about 1.8 us for it, so the copy wins once the child touches more
than about a sixth of them.

Only a narrow case pays it, a file THP that is:

- mapped MAP_PRIVATE;
- in a VMA written to at least once, so it has an anon_vma;
- a PMD-sized folio in the page cache, mapped by one PMD;
- itself never written to.

For example:

- a big data file mapped MAP_PRIVATE that is mostly read and patched
  in a few places;
- a private mapping of a memfd or tmpfs file.

[PATCH v6 2/4] mm/huge_memory: copy file THPs at fork like
Author: Konstantin Khorenko <khorenko@virtuozzo.com>

This fixes no bug: it makes fork copy a PMD the way copy_present_ptes()
copies a PTE. Until now copy_huge_pmd() skipped every folio PMD of a
non-anonymous VMA and left the child to fault them in again, while the
PTEs of the same VMA are copied.

Treat file folios as the PTE path does: take a reference, duplicate the
rmap and account them. fork then pays a reference and an rmap update
per PMD, and saves the child a fault per PMD it touches. The next patch
sends PFN mappings through the same tail.

That covers the VMAs vma_needs_copy() sends here:

- private file mappings with an anon_vma;
- VM_COPY_ON_FORK ones: uffd-wp and uffd-rwp, VM_MIXEDMAP, and
  VM_MAYBE_GUARD, which shared shmem, file and DAX mappings get from a
  guard region.

A folio over the page cache refcount limit is not copied, as in
copy_present_ptes(): the child faults it in, and fork() fails with
-ENOMEM only in a VM_MIXEDMAP VMA, which may have no fault handler.
Unlike a skipped PTE, the PMD needs no uffd marker: a file PMD never
carries the uffd bit, as protecting it splits it.

The DAX huge zero PMD is copied too, with a reference taken by
mm_get_huge_zero_folio() as for anonymous VMAs. A migration entry of a
file folio is copied and accounted like copy_nonpresent_pte() does, and
made read-only in both processes only in a CoW mapping. A device
private entry gets the same CoW check, as in copy_nonpresent_pte().

The copy then gets the same tail as __copy_present_ptes(): write
protect both sides in a CoW mapping, mark the child's copy clean in a
shared one, and drop the uffd-wp bit where the child is not armed. An
anonymous THP is now write protected only when its PMD is writable, as
a PTE is.

A page table is deposited under the copy where the fault paths deposit
one: in anonymous VMAs, and wherever the architecture needs one.

[PATCH v6 3/4] mm/huge_memory: read a special PMD under the lock
Author: Konstantin Khorenko <khorenko@virtuozzo.com>

copy_huge_pmd() reads a special PMD without the page table lock and
copies that value to the child. The mmap write lock held by fork does
not stop unmap_mapping_range(): it zaps under i_mmap_rwsem and the PMD
lock.

The zap visits the parent VMA before the child's, as dup_mmap() links
the child right after the parent in i_mmap. If it clears the parent PMD
after fork has read it, and passes the child before fork copies it, the
child keeps a mapping the driver has revoked, for example:

- vfio-pci: the child reaches the BAR after the device memory was
  disabled or the device was reset, instead of getting SIGBUS;
- panthor: the child maps the pages of an evicted buffer object after
  the driver has released them.

The same branch deposits no page table under the copy. ppc64 in hash
mode keeps the hash slot array of every huge PMD in that table, so the
child dereferences a NULL table on the first hash fault, in
__hash_page_thp(), and on the zap, in hash__pmdp_huge_get_and_clear().

Take the locks first and let vm_normal_page_pmd() tell a PFN mapping
from a folio under them, as copy_present_ptes() does with
vm_normal_page(). The zap clears the parent PMD under the same lock, so
either fork finds it none and skips it, or the copy is in place before
the zap reaches the child.

The copy of a PFN mapping then goes through the same tail as a folio:

- it gets a page table where the architecture needs one;
- in a shared mapping it is marked clean in the child, as a PTE is;
- in a CoW mapping, which only VM_MIXEDMAP allows, both sides are write
  protected instead of a warning being printed.

[RFC PATCH v3 00/10] iommu/riscv: Add nested translation (vIOMMU) support
Author: Gong Shuai <gong.shuai@sanechips.com.cn>

An IOMMU allows an OS to restrict device DMA to the intended memory.
It also gives device drivers an IOVA space that is independent of the
physical memory layout. A guest OS needs these capabilities when it
directly controls a device, just as a native OS does.

Exposing a vIOMMU to the guest is not enough for a passthrough device.
DMA from the physical device must also obey the mappings that the guest
creates through its vIOMMU. Otherwise the guest cannot use its IOMMU to
protect guest memory or provide IOVA mappings for the assigned device.

The RISC-V IOMMU architecture supports this usage with two-stage
translation. Stage 1 applies the guest's vIOMMU configuration. Stage 2
is controlled by the hypervisor and restricts the device to memory
assigned to the VM. This division gives the guest control of its own
DMA mappings without allowing the device to escape the VM.

The Linux RISC-V IOMMU driver does not yet support this model through
iommufd. A VMM cannot provide the guest stage 1 configuration to the
physical IOMMU or synchronize its translation caches after the guest
updates its page tables. This series adds the missing nested
translation support so device passthrough can work with a guest that
uses its own vIOMMU.

This is an RFC and comments on the design are welcome.

Patch organization

Patch 1 prepares device context handling for nested translation.
Patches 2 and 3 add the uAPI for nested allocation and cache
invalidation.
Patches 4 to 6 add the vIOMMU, nested domains and cache invalidation.
Patches 7 and 8 allow a VMM to discover the physical IOMMU
capabilities.
Patch 9 adds nested device attachment.
Patch 10 fixes bond unlink so it invalidates the correct address space.

Dependencies

The series applies on top of iommu/master at commit 9f9dc924a01e,
together with the RISC-V hardware dirty tracking series v7 [1] and
its dependencies.

Testing

The test requires MSI support, but the related dependencies are still
under review, so the interrupt changes are not included in this series.
The test needs the MSI remapping series v6 [2], the irqbypass series
RFC v3 [3] and a KVM client from Andrew's github repo [4]. A branch with
the complete test stack, including the additional nested interrupt
support, is available at github repo [5].

The host is a RISC-V machine whose physical IOMMU is provided by an outer
QEMU riscv-iommu model, which implements both translation stages. An NVMe
controller under it is bound to vfio-pci and passed through to the guest.
The guest is started by a QEMU built with the accel series [6][7], which
exposes a first stage IOMMU to the guest and leaves the second stage to
the host IOMMU. For simplicity the guest runs the same kernel as the host,
and inside the guest it mainly uses the normal IOMMU driver and the NVMe
driver.

The layering of the setup is

Host HW, a RISC-V virt machine from latest QEMU(v11.1.3), with a
riscv-iommu model that implements two stage translation and with the NVMe
controller

    Host OS, the kernel with this series
      riscv-iommu driver, second stage and MSI table vfio-pci and KVM

        Guest HW, QEMU with the accel series [6][7]
          riscv-iommu accel, first stage only

            Guest OS, the same kernel as the host
              riscv-iommu driver, NVMe driver

A DMA address from the NVMe controller is translated by the guest first
stage and then by the host second stage on the physical IOMMU. An MSI
address is translated by the guest first stage into a guest IMSIC address,
which the flat MSI table then resolves straight to the interrupt file of
the target vCPU, instead of walking the second stage.

    DMA    device --> guest first stage --> host second stage --> RAM
    MSI    device --> guest first stage --> MSI table --> VS-file

The host was started with

$HOST_QEMU \
  -M virt,aia=aplic-imsic,aia-guests=7,iommu-sys=on \
  -cpu rva23s64,sv48=on -nographic \
  -smp 16 -m 16G \
  -kernel $HOST_KERNEL \
  -append "root=/dev/vda rw earlycon=sbi console=ttyS0 iommufd.allow_unsafe_interrupts=1" \
  -drive file=$HOST_ROOTFS,if=none,id=d0,format=qcow2 -device virtio-blk-device,drive=d0 \
  -device pcie-root-port,id=port0,chassis=0,slot=0,addr=3.0 \
  -drive file=fake-nvme-disk.img,if=none,id=nvme0,format=qcow2 \
  -device nvme,drive=nvme0,serial=deadbeef,bus=port0,addr=0.0

and the guest with

$GUEST_QEMU \
  -machine virt,accel=kvm,aia=aplic-imsic,aia-guests=5 \
  -cpu host -nographic \
  -smp 4 -m 4G \
  -object iommufd,id=iommufd0 \
  -device riscv-iommu-pci,addr=1.0,s-stage=on,g-stage=off,accel=on \
  -device vfio-pci,host=0000:01:00.0,iommufd=iommufd0 \
  -kernel $GUEST_KERNEL \
  -append "root=/dev/vda rw earlycon=sbi console=ttyS0 iommu.passthrough=0 iommu.strict=1" \
  -drive file=$GUEST_ROOTFS,if=none,id=d0,format=qcow2 -device virtio-blk-device,drive=d0

Correctness was checked by running fio with verification enabled against
the passed through disk.

Known limitations and future work

- PASID and the process directory table are not supported.
- The ATS, PRI and T2GPA fields are validated on the nested domain, but
  ATS.INVAL and the PRI queue are not forwarded.
- One single physical IOMMU instance on host is assumed for now.
- The new uAPI types have no selftest coverage yet.

[PATCH v1 1/2] KVM: s390: vsie: Do not overwrite guest 3 state on early validity icpt
Author: Gautam Gala <ggala@linux.ibm.com>

shadow_scb() calls prepare_cpuflags() first, which can reject the SCB
provided by guest 2 with a validity interception. This happens before
the guest state (gpsw, gg14, gg15, gcr, cputm, ckc, todpr, pp) and the
control fields (gbea, fpf) are copied from the original SCB into the
shadow SCB.

The error path still calls unshadow_scb(), which copies that state from
the shadow SCB back into the original one. The shadow SCB does not hold
guest 3 state at this point:

 - For a new or recycled vsie page, get_vsie_page() has cleared the
   shadow SCB, so the guest 3 state in the guest 2 SCB is overwritten
   with zeroes.
 - For a cached vsie page that is looked up again by SCB address, the
   shadow SCB still holds the state from the end of the previous run,
   so the current guest 3 state is replaced by the old one.

No guest 3 instruction ran, yet guest 2 sees its guest 3 state (PSW,
GRs, CRs, timers) modified. unshadow_scb() also clears FPF_BPBC if
facility 82 is available, because fpf was cleared in the shadow SCB
just before, and copies back a stale ihcpu.

The SCB and the validity condition are controlled by guest 2, so this
is a correctness problem for guest 2 only and does not cross a guest or
host boundary.

Only the interception data needs to be passed on in this case. Add
unshadow_icpt() for that and use it from unshadow_scb() and from the
prepare_cpuflags() failure path, which now returns directly. The other
failure paths of shadow_scb() are reached after the guest state has
been copied and keep using unshadow_scb().

On a cached vsie page, the interception data in the shadow SCB still
holds the values of the previous run. set_validity_icpt() writes ipa,
ipb and icptcode, but not icptstatus, so a stale icptstatus would be
passed on together with the new validity interception. Also, it is not
defined what SIE stores in icptstatus, ipa and ipb when it exits without
an interception, so they must not be relied upon to be zero or unchanged.
Clear them together with icptcode when the shadow SCB is reused,
so that no stale interception data is passed on to guest 2.

[PATCH v3 1/2] x86/virt/seamldr: Support large TDX module binaries
Author: Chao Gao <chao.gao@intel.com>

TDX module binaries are limited to just under 2MB. The binary is handed
to P-SEAMLDR as a list of page physical addresses in
'struct seamldr_params', and the list must fit in a single 4KB page
along with a few other fields.

TDX modules are gaining features and are about to outgrow that limit.

The P-SEAMLDR ABI was extended to let the list continue onto more 4KB
pages. The last u64 of each page holds the physical address of the next
page, chaining the pages together.

Grow module_pages_pa_list[] so that 'struct seamldr_params' spans 16
pages, and chain the pages together in populate_pa_list().

Each page uses its last entry for chaining, so the maximum module page
count is the array size minus one entry per page. The user-supplied
image is checked against this count.

The 16-page size is somewhat arbitrary. It fits modules of up to about
32MB, far above the roughly 2MB of current modules. It wastes 60KB for
today's modules, which is fine because the memory is freed right after
the update.

Do not query P-SEAMLDR for chaining support. Userspace selects the
update image and is responsible for ensuring the module is compatible
with P-SEAMLDR.

A 496-page module (the old maximum) used to fit in a single page. Now
the last entry of that page is used for chaining, so the final address
moves to a second page and the module requires chaining support. Do not
special-case this size to make it work with a P-SEAMLDR without
chaining support. No released module has exactly 496 pages, so nothing
breaks. Leave it to userspace to ensure any future 496-page module is
paired with a P-SEAMLDR that supports chaining, as with larger modules.

Signed-off-by: Chao Gao <chao.gao@intel.com>
---

is validated, as v1 did, or use an unvalidated count. Either way it is
more code churn than a fixed 16 pages.

[PATCH v3 2/2] x86/virt/seamldr: Support multiple sigstruct pages
Author: Chao Gao <chao.gao@intel.com>

TDX module sigstructs are limited to 4KB. Each update image carries a
sigstruct, which is handed to P-SEAMLDR in 'struct seamldr_params'
along with the module binary. The structure has room for the physical
address of only one sigstruct page.

TDX modules are moving to a post-quantum signature algorithm. Its
signatures are far larger than the ones in use today, so the sigstruct
no longer fits in 4KB.

The P-SEAMLDR ABI was extended to take up to four sigstruct pages
(16KB). Setting 'version' to 1 tells P-SEAMLDR to use this layout.

Grow sigstruct_pages_pa_list[] to four entries to match. In anticipation
of this change, the list is already filled in a loop, so filling the
new entries needs no new code.

Use version 1 only when the sigstruct spans more than one page. Old
P-SEAMLDRs reject version 1, so this keeps today's modules working on
them.

Do not query P-SEAMLDR for version 1 support. Userspace selects the
update image and is responsible for ensuring the module is compatible
with P-SEAMLDR.

This series is a follow-up to the TDX module update series. As thanks
for merging that series, we agreed to take on the TDX metadata cleanup [1].
With the cleanup converging, we are starting on this work and expect it
to be merged after the cleanup.

Today a TDX module binary can be at most 496 pages and its sigstruct at
most one page. Both limits come from the P-SEAMLDR ABI.

TDX modules are outgrowing them. A post-quantum signature algorithm
pushes the sigstruct past 4KB, and new module features push the binary
past 496 pages. The P-SEAMLDR ABI was extended for both.

The kernel rejects any image over these limits. TDX modules for Diamond
Rapids exceed them, so without this series, TDX module updates fail on
Diamond Rapids. This series is all that is needed to make them work.

The image format that userspace uploads ('struct tdx_image') is generic
enough and needs no change.

== AI Usage ==

AI was used under supervision to review code and refine commit messages.

== Testing ==

Tested on a Diamond Rapids system. Updates with a module larger than 2MB
and an 8KB sigstruct work, which exercises both the chained page list
and version 1 of 'struct seamldr_params'. TDs keep running across
updates.

== P-SEAMLDR ABI changes ==

The public P-SEAMLDR specification will be updated to document these
ABI extensions. Until then, here are the changes to
'struct seamldr_params' that this series relies on:

- VERSION (offset 0) may now be 1. Version 1 support is enumerated by
bit 8 of SEAMLDR_FEATURES0.

- SIGSTRUCT_PA_1..3 (offsets 16, 24 and 32) are new. In version 1, they
hold the addresses of the second to fourth sigstruct pages, or 0 if
the sigstruct does not reach that page. In version 0, they must be 0.

- RESERVED shrinks from 104 to 80 bytes and now starts at offset 40.

- MOD_PAGES_PA_LIST (offset 128) can be chained. For a module over 495
pages, its last entry points to a 4KB page holding up to 511 more
addresses. Each such page uses its last entry to point to the next
page, until all module pages are listed. Chaining support is enumerated
by bit 11 of SEAMLDR_FEATURES0.

[PATCH v7 2/3] iommufd: Add IOMMU_GET_RECOMMENDED_RESERVATIONS ioctl
Author: Guanghui Feng <guanghuifeng@linux.alibaba.com>

Add a per-device query ioctl that reports the IOVA ranges the kernel
recommends reserving for a given device.  For PCI devices these are
the MMIO windows of the host bridge the device sits behind: DMA using
IOVAs inside those windows could be misrouted as peer-to-peer traffic
by a PCIe switch instead of reaching the root complex for IOMMU
translation.

The interface is advisory, and deliberately named after the general
concept of recommended reserved regions rather than its first source:
the kernel reports recommendations and userspace decides whether to
act on them, either by feeding them back through
IOMMU_IOAS_RESERVE_IOVAS or by avoiding the ranges in its own IOVA
allocation.  This follows the principle that PCI window information
should not be forced onto userspace through the IOMMU reserved-region
API, as established when the earlier attempt was reverted in commit
cd2c9fcf5c66 ("iommu/dma: Move PCI window region reservation back into dma specific path.")

The output reuses struct iommu_iova_range and follows the array +
count + EMSGSIZE protocol established by IOMMU_IOAS_IOVA_RANGES.
Per-device granularity is chosen because the recommendations derive
from the device's bus topology and are available immediately after
VFIO_DEVICE_BIND_IOMMUFD, before any IOAS attachment.

[PATCH v7 0/3] iommufd: Recommended reservations query and opt-in IOAS reservation
Author: Guanghui Feng <guanghuifeng@linux.alibaba.com>

This series lets userspace learn which IOVA ranges the kernel
recommends avoiding for a device, and optionally feed them back so
the IOAS allocator enforces them.

The motivating case is a PCI device behind a PCIe switch: DMA using
IOVAs that fall inside the host bridge MMIO windows may be misrouted
as peer-to-peer traffic instead of reaching the root complex for IOMMU
translation.  The DMA IOVA layer already avoids these windows
internally, but passthrough userspace had no way to learn about them.
Per commit cd2c9fcf5c66 ("iommu/dma: Move PCI window region reservation back into dma specific path.")
this information must not be forced through the IOMMU reserved-region
API, so the series is fully opt-in:

  Patch 1 adds iommu_for_each_pci_mmio_window(), a callback-based
  iterator in the IOMMU core, and refactors dma-iommu.c to share it.

  Patch 2 adds IOMMU_GET_RECOMMENDED_RESERVATIONS, a per-device query
  returning recommended ranges (currently PCI host bridge MMIO
  windows) as struct iommu_iova_range entries.  Advisory only.

  Patch 3 adds IOMMU_IOAS_RESERVE_IOVAS, letting userspace send
  chosen ranges back in to restrict the IOAS allocator: reserved
  ranges disappear from IOMMU_IOAS_IOVA_RANGES and are rejected by
  mapping.  Overlapping reservations are permitted, so the same
  ranges recommended for several devices behind one host bridge can
  each be reserved independently.

Typical flow: bind device -> query recommendations -> reserve chosen
ranges -> map.  Userspace that ignores the new ioctls sees no
behaviour change.

[PATCH v7 3/3] iommufd: Add IOMMU_IOAS_RESERVE_IOVAS ioctl
Author: Guanghui Feng <guanghuifeng@linux.alibaba.com>

Add an ioctl allowing userspace to reserve IOVA ranges in an IOAS,
creating a restriction on the address space: reserved ranges are
excluded from IOMMU_IOAS_IOVA_RANGES and rejected by mapping
operations.

This completes the opt-in flow for the kernel's reservation
recommendations: userspace queries IOMMU_GET_RECOMMENDED_RESERVATIONS
for a device, decides which ranges to honour, and feeds them back
through this ioctl so the kernel enforces them on its behalf.  Both
steps are optional; nothing changes for userspace that does not use
them.

The semantics mirror the existing internal users of
iopt_reserve_iova(): ranges conflicting with existing mappings or
allowed IOVAs fail with -EADDRINUSE, and overlapping reservations are
permitted so that recommendations queried for several devices behind
the same host bridge can each be reserved independently.  User
reservations carry a NULL owner and live until the IOAS is destroyed;
accordingly the NULL-owner cleanup in iopt_destroy_table() is no
longer conditional on CONFIG_IOMMUFD_TEST, since production userspace
can now create such reservations.

On failure the leading ranges already inserted stay reserved; because
overlaps are permitted, retrying the whole call is idempotent.

[PATCH v2] KVM: x86: Fix stalled descriptor table accesses to MMIO
Author: weichenchen <weichen.chen@linux.alibaba.com>

Use the emulated memory accessors for the explicit operands of LGDT,
LIDT, SGDT and SIDT.  When the operand has no backing memslot, the
standard accessors return X86EMUL_IO_NEEDED without queuing an MMIO
fragment.  LIDT can repeat the generic operand read at the same RIP,
and SIDT can re-enter emulation without sending a write to userspace.

Check the segment bounds of both fields, then read the whole descriptor
in one emulated access.  On a single page, this lets KVM use the
faulting GPA for both fields without translating the base field after
userspace has handled part of the read.  For a split operand, translate
both pages before exiting to userspace.  Use the emulator's read cache
to resume after MMIO and skip the redundant generic source read.

Use the destination operand for common writeback of SGDT and SIDT.  This
keeps the entire descriptor available until userspace completes a
ten-byte MMIO write.

Fixes: c3cd7ffaf57a ("KVM: x86 emulator: x86_emulate_insn() return -1 only in case of emulation failure")
Fixes: 129a72a0d3c8 ("KVM: x86: Introduce segmented_write_std")
Signed-off-by: weichenchen <weichen.chen@linux.alibaba.com>

[PATCH v10 31/33] KVM: arm64: Add vCPU device attr to partition the PMU
Author: Colton Lewis <coltonlewis@google.com>

Add the KVM_ARM_VCPU_PMU_V3_ENABLE_PARTITION vCPU device attribute to

userspace must configure guest general-purpose counters via

[PATCH v10 27/33] KVM: arm64: Emulate mismatched LP and HLP overflow
Author: Colton Lewis <coltonlewis@google.com>

When an L1 hypervisor sub-partitions its counters (vHPMN < N_L1) on
FEAT_PMUv3p5, all N_L1 guest counters lie below physical MDCR_EL2.HPMN
and share a single physical overflow width bit (PMCR_EL0.LP), whereas
architecturally counters 0..vHPMN-1 use vPMCR_EL0.LP and hypervisor
counters vHPMN..N_L1-1 use vMDCR_EL2.HLP.

When vPMCR_EL0.LP != vMDCR_EL2.HLP (and both sub-ranges are non-empty):
- Force physical PMCR_EL0.LP to 1 (64-bit hardware overflow) and bias
  each counter in the 32-bit sub-range (ovf32_mask) to
  0xffffffff00000000 | lower_32_bits(val) so hardware overflows after
  2^32 events, storing the upper-32-bit architectural offset in
  vcpu->arch.pmu.ovf32_offset[idx].
- Trap PMEVCNTR<n>_EL0 reads and writes via HDFG{R,W}TR_EL2.PMEVCNTRn_EL0
  while ovf32_mask is non-zero to translate between biased hardware
  values and architectural 64-bit values, and trigger KVM_REQ_RELOAD_PMU
  when guest PMCR_EL0.LP or MDCR_EL2.HLP changes.
- Defer re-biasing until non-interrupt context (counter reads,
  kvm_pmu_part_overflow_status(), or __kvm_pmu_put()) so NMI/IRQ
  overflow handlers remain lockless while phys_val + ovf32_offset[idx]
  stays exact modulo 2^64 across wraparound.

[PATCH v10 12/33] KVM: arm64: Set up FGT for Partitioned PMU
Author: Colton Lewis <coltonlewis@google.com>

In order to gain the best performance benefit from partitioning the
PMU, utilize fine grain traps (FEAT_FGT and FEAT_FGT2) to avoid
trapping common PMU register accesses by the guest to remove that
overhead.

Untrapped:
- PMCR_EL0
- PMUSERENR_EL0 (outside nested hypervisor context)
- PMSELR_EL0
- PMCCNTR_EL0
- PMCNTEN_EL0
- PMINTEN_EL1
- PMEVCNTRn_EL0

will do limits the effect of writes to any of these registers to the
partition of counters 0..HPMN-1. Reads from these registers will not
leak information from between guests as all these registers are
context swapped by a later patch in this series. Reads from these
registers also do not leak any information about the host's hardware

Trapped:
- PMOVS_EL0
- PMEVTYPERn_EL0
- PMCCFILTR_EL0
- PMICNTR_EL0
- PMICFILTR_EL0
- PMCEIDn_EL0
- PMMIR_EL1
- PMUSERENR_EL0 (in nested hypervisor context: writes always, reads when
  guest MDCR_EL2.TPM is set)

be injected into the guest.

PMICNTR and PMICFILTR remain trapped because KVM is not handling them
yet.

PMEVTYPERn remains trapped so KVM can limit which events guests can
count, such as disallowing counting at EL2. PMCCFILTR and PMICFILTR
are special cases of the same.

PMCEIDn and PMMIR remain trapped because they can leak information
specific to the host hardware implementation.

VHE host EL0 inside is_hyp_ctxt(vcpu) without exiting to L0 across ERET
and SVC transitions. Trap PMUSERENR_EL0 writes via HDFGWTR_EL2 in

[PATCH v10 00/33] ARM64 PMU Partitioning
Author: Colton Lewis <coltonlewis@google.com>

This series creates a new PMU scheme on ARM, a partitioned PMU that
allows reserving a subset of counters for more direct guest access,
significantly reducing overhead. More details, including performance
benchmarks, can be read in the v1 cover letter linked below.

PMU partitioning is controlled via the KVM API using
`KVM_ARM_VCPU_PMU_V3_ENABLE_PARTITION` and
`KVM_ARM_VCPU_PMU_V3_SET_NR_COUNTERS` vCPU device attributes. When
partitioning is enabled for a VM, userspace must explicitly configure a
guest event counter count strictly less than the maximum general-purpose
counters implemented by the PMU (leaving at least one general-purpose
counter for the host) prior to calling `KVM_ARM_VCPU_PMU_V3_INIT`. The
number of general-purpose counters implemented by each host PMU is
exposed in sysfs at
`/sys/bus/event_source/devices/<pmu>/caps/num_counters`. A QEMU patch
demonstrating how to use the uAPI is sent separately.

An overview of what this series accomplishes was presented at KVM
Forum 2025. Slides [1] and video [2] are linked below.

v10:

* Rebase on top of v7.4-rc3.

* Add nested virtualization (`FEAT_NV` / `FEAT_NV2`) support covering
  both an Emulated L2 PMU (`vHPMN == N_L1`, `TPM == 1`, where L1 keeps
  all `N_L1` counters and emulates L2 via L1 `perf` events) and a
  Sub-partitioned L2 PMU (`vHPMN < N_L1`, `TPM == 0`, creating a
  three-way split across `0..vHPMN-1` for L2, `vHPMN..N_L1-1` for L1,
  and `N_L1..N_phys-1` for L0) (Oliver Upton). Because ARM64 provides
  only a single physical `MDCR_EL2.HPMN` field, hardware can split the
  PMU into two counter ranges at a time rather than three. Key design
  decisions and supporting changes:

  - Keep physical `MDCR_EL2.HPMN = N_L1` at all times (`vHPMN` boundary
    and event filtering): Lowering physical `HPMN` to `vHPMN` while
    running L2 was considered and rejected because it would move L1's
    hypervisor counters (`vHPMN..N_L1-1`) into the same physical
    `>= HPMN` range as L0's host counters (`N_L1..N_phys-1`), where a
    single set of physical `MDCR_EL2.{HPME,HPMD,HLP}` bits governs both
    and breaks host/guest isolation; it would also fail for
    `vHPMN == 0` on hardware without `FEAT_HPMN0`. Instead, when
    `vHPMN < N_L1`, L0 keeps physical `HPMN = N_L1` and sets
    `MDCR_EL2.{TPM,TPMCR}` in L2, forwarding `vHPMN..N_L1-1` traps to
    L1 and handling `0..vHPMN-1` plus `PMCCNTR_EL0` in L0 directly
    against physical registers. This preserves L0 isolation and
    supports `vHPMN == 0` on all hardware; L2 events still count
    directly in hardware without L0 `perf_event` scheduling, at the
    cost of trapping L2 PMU accesses to L0 and rewriting per-counter
    filter registers on `L1 <-> L2` transitions. In L1
    (`is_hyp_ctxt()`), L0 emulates `vHPMN`, `vMDCR_EL2.HPMD`, and
    `vMDCR_EL2.HCCD` via `PMEVTYPER<n>_EL0` and `PMCCFILTR_EL0`.

  - Dynamically multiplex `vPMCR_EL0.E` and `vMDCR_EL2.HPME`: Because
    both `0..vHPMN-1` and `vHPMN..N_L1-1` sit below physical
    `HPMN = N_L1`, hardware gates both with physical `PMCR_EL0.E`.
    Rather than unconditionally trapping `PMCR_EL0` and `PMCNTEN*` for
    all `FEAT_NV` VMs (which would penalize Emulated L2 PMU where
    `vHPMN == N_L1`), L0 dynamically enables `MDCR_EL2.TPMCR` and
    `HDFG{R,W}TR_EL2.PMCNTEN` only when `vHPMN < N_L1`. L0 keeps
    architectural `PMCR_EL0` and `PMCNTENSET_EL0` in memory, sets
    physical `PMCR_EL0.E` to `vPMCR_EL0.E || vMDCR_EL2.HPME`, masks
    disabled sub-ranges out of physical `PMCNTENSET_EL0`, and gates
    overflow delivery per domain. Trapped `PMSWINC_EL0` writes (also
    enabled via `HDFGWTR_EL2` when `vHPMN < N_L1`) flush live registers
    and reuse `kvm_pmu_software_increment()` to prevent cross-partition
    chaining.

  - Bias 32-bit counters on mismatched `vPMCR_EL0.LP != vMDCR_EL2.HLP`
    (`FEAT_PMUv3p5`): When `LP == HLP`, physical `PMCR_EL0.LP` matches
    both domains directly and `PMEVCNTR<n>_EL0` stays untrapped in L1.
    When `vHPMN < N_L1` and `LP != HLP`, rather than ignoring the
    mismatch (breaking 32-bit overflow interrupts) or falling back to
    `perf_event` emulation mid-flight (requiring reservation teardown),
    L0 forces physical `PMCR_EL0.LP = 1` (64-bit overflow), dynamically
    traps `HDFG{R,W}TR_EL2.PMEVCNTRn_EL0`, and biases counters in the
    32-bit sub-range `2^32` events below 64-bit overflow
    (`0xffffffff00000000 | low32`) while tracking their upper-32-bit
    offsets and re-biasing outside interrupt/NMI context. Because
    `HDFG{R,W}TR_EL2.PMEVCNTRn_EL0` is a single trap bit covering all
    event counters (`0..30`), L1 counter reads/writes trap across both
    sub-ranges while `LP != HLP`, with zero overhead when `LP == HLP`.

  - Baseline nested support (both Emulated and Sub-partitioned L2):
    separate implemented and accessible counter masks by using
    `nr_pmu_counters` directly in `kvm_pmu_implemented_counter_mask()`,
    masking trapped guest reads of `PMCNTEN*`, `PMINTEN*`, and `PMOVS*`
    with `kvm_pmu_accessible_counter_mask()`, and ignoring
    `MDCR_EL2.HPMN` in userspace `KVM_GET_ONE_REG` / `KVM_SET_ONE_REG`
    (`set_pmreg()`, `get_pmreg()`, `get_pmcr()`) so saving/restoring a
    nested vCPU paused below EL2 preserves all VM-implemented counters
    and true `PMCR_EL0.N`; preserve host counter reservations across
    `IN_NESTED_ERET` / `IN_NESTED_EXCEPTION` transitions to avoid host
    `perf` reschedules on emulated L2 traps; read live hardware
    `PMSELR_EL0` in `check_mdcr_hpmn()` when untrapped; and forward
    fine-grained traps for selector-indexed `PMXEVTYPER_EL0` and
    `PMXEVCNTR_EL0` to L1.

* Expose the number of general-purpose counters implemented by the PMU
  in sysfs under `/sys/bus/event_source/devices/<pmu>/caps/num_counters`
  so userspace VMMs can query host PMU counter capacity when configuring
  a partitioned PMU (James Clark).

* Make `__vcpu_rmw_sys_reg()` atomic on the local CPU using
  `try_cmpxchg_local()` to prevent read-modify-write races with GICv3
  pseudo-NMI PMU interrupt handlers (`kvm_pmu_handle_guest_irq()`),
  which are not masked by `local_irq_save()` (Sashiko AI Review).

* Construct `mdcr_el2` in a local variable before assigning
  `vcpu->arch.mdcr_el2` once in `kvm_arm_setup_mdcr_el2()`, and mask
  GICv3 pseudo-NMIs (`local_daif_save()`) across hardware PMU context
  switches and `MDCR_EL2` updates (Sashiko AI Review).

* Prioritize kernel-owned pinned event groups (`is_kernel_event()`)
  ahead of userspace pinned events in `perf_event_groups_cmp()` /
  `perf_less_group_idx()` so kernel-owned per-CPU pinned events (such as
  the hardlockup NMI watchdog if toggled at runtime) are scheduled before
  userspace pinned events when `perf_pmu_resched_update()` reschedules
  events out of guest-reserved counters (James Clark, Sashiko AI Review).

* Move `kvm_vcpu_reload_pmu()` from `arch/arm64/kvm/pmu-emul.c` to
  `arch/arm64/kvm/pmu.c` in `KVM: arm64: Reorganize PMU functions`.

* Add `kvm_pmu_is_partitioned()`, `kvm_pmu_guest_counter_mask()`,
  `kvm_pmu_handle_guest_irq()`, `kvm_pmu_host_start()`, and
  `kvm_pmu_host_stop()` stubs to `arch/arm/include/asm/arm_pmuv3.h` to
  fix 32-bit `ARCH=arm` builds (kernel test robot).

* Allow identical VM-wide PMU device attributes
  (`KVM_ARM_VCPU_PMU_V3_SET_PMU`, `KVM_ARM_VCPU_PMU_V3_SET_NR_COUNTERS`,
  and `KVM_ARM_VCPU_PMU_V3_ENABLE_PARTITION`) to be applied across all
  vCPUs when userspace initializes vCPUs sequentially (`CPU_FOREACH`),
  validate `kvm_arm_pmu_part_hpmn(n) < max_counters` (requiring
  `max_counters >= 2` for `n == 0` without `FEAT_HPMN0`), and restrict
  `kvm->arch.supported_cpus` to `arm_pmu->supported_cpus` when
  partitioning is enabled.

* Centralize partitioned PMU hardware register dispatch under
  `kvm_pmu_direct_reg_read()` / `kvm_pmu_direct_reg_write()` with
  preemption disabled (`kvm_pmu_part_on_cpu()`), guard lazy ownership
  transitions in `kvm_pmu_part_overflow_status()` with
  `scoped_guard(preempt)`, avoid matching `reset_unknown()` poison bits on
  `PMCNTENSET_EL0` / `PMINTENSET_EL1` during `KVM_REQ_RELOAD_PMU`, and
  schedule `KVM_REQ_RELOAD_PMU` on `KVM_SET_ONE_REG` writes so
  `vcpu_put()` does not overwrite userspace register writes (Sashiko AI
  Review).

* Support configuring 0 guest event counters (cycle counter only) on
  Partitioned PMU hosts without `FEAT_HPMN0` whenever `max_counters >= 2`.
  Writing `MDCR_EL2.HPMN = 0` without `FEAT_HPMN0` is architecturally
  `CONSTRAINED UNPREDICTABLE`, which would otherwise prevent userspace
  from creating a cycle-counter-only partitioned guest on CPUs lacking
  `FEAT_HPMN0`. Instead, KVM programs physical `MDCR_EL2.HPMN = 1` via
  `kvm_arm_pmu_part_hpmn()`, reserves and quiesces physical counter 0
  alongside `PMCCNTR_EL0` so host perf continues using counters `1..N-1`,
  keeps `MDCR_EL2.TPMCR = 1` so trapped `PMCR_EL0` reads report `N == 0`,
  and enables fine-grained traps on `PMEVCNTRn_EL0`, `PMCNTEN`,
  `PMINTEN`, and `PMSWINC_EL0` so counter 0 stays completely hidden
  (`UNDEFINED` / RAZ / WI) while `PMCCNTR_EL0` remains untrapped on
  `FEAT_FGT` hosts. Also clamp `MDCR_EL2.HPMN` against `nr_pmu_counters`
  in `kvm_vcpu_read_pmcr()` and `kvm_pmu_direct_pmcr_read()`, and extend
  `vpmu_counter_access` to verify `PMCCFILTR_EL0`, live `PMCCNTR_EL0`
  counting, and trapped `UNDEFINED` / RAZ / WI behavior on counter 0 when
  `n == 0`.

[PATCH] KVM: arm64: nv: Fix guest stage-2 mapping leak on sub-block unmap
Author: Colton Lewis <coltonlewis@google.com>

When a shadow stage-2 block mapping (for example, 2M at PMD level) is
partially invalidated by a smaller guest unmap such as a 4K TLBI
IPAS2E1IS, kvm_pgtable_stage2_unmap() shatters and clears the entire
block descriptor in mmu->pgt. However, kvm_remove_guest_s2_mappings()
only removes a struct kvm_guest_s2_mapping node when its entire
[nested_start, nested.last] span lies within the unmap range. As a
result, every sub-block invalidation followed by a re-fault leaks a
stale block-sized tracking node in mmu->guest_s2_mappings and
kvm->arch.mmu.guest_s2_mappings until the shadow MMU is destroyed,
allowing an L1 guest to grow host kernel memory and degrade subsequent
TLBI IPAS2E1IS walks to O(N) under write_lock(&kvm->mmu_lock).

Conversely, unconditionally removing any overlapping tracking node on a
sub-block unmap would be unsafe when a shadow block mapping has been
split into a child table (such as on a page-granule fault under dirty
logging or a racing shared walk returning -EAGAIN), because sibling
sub-page PTEs outside the unmapped range remain live in mmu->pgt and
still rely on the block-sized tracking node for host MMU notifier
unmaps.

Since stage2_unmap_walker() unlinks empty child page tables in
KVM_PGTABLE_WALK_TABLE_POST as soon as their last valid entry is
cleared, check mmu->pgt via kvm_pgtable_get_leaf() on partial-overlap
candidates: when no valid entry or split sub-table remains at or below
the recorded mapping granule (!kvm_pte_valid(pte) &&
kvm_granule_size(level) >= map_size), remove and free the tracking node;
otherwise retain it to cover surviving split sub-entries.

In addition, suppress exact-match duplicate insertions in
kvm_record_guest_s2_mapping() when concurrent faults or -EAGAIN retries
record an identical (nested, canonical) range on the same shadow MMU.

[PATCH v2 4/4] KVM: arm64: nv: Update the shadow MMU's VMID for AT
Author: Dan Carpenter <dan@pereq.eu>

There is a missing kvm_arm_vmid_update() before the __load_stage2()
in __kvm_at_s1e01_fast().  The bug affects nested virtualization on
arm64.

In KVM a "stage 2" refers to the VM's page table mappings. The
__kvm_at_s1e01_fast() function emulates the AT instruction, which
translates a virtual address the way the MMU would and returns the
result.

Each stage 2 has a VMID, which the hardware uses to tag TLB and
walk-cache entries, so that one VM never uses another's entries.  There
are only 2^8 or 2^16 VMIDs, which is quite limited, so vmid.c hands
them out by generation.  When they run out, a rollover starts a new
generation and flushes the TLBs: the VMIDs active on a CPU at that
moment are kept, and every other VMID can be given to another VM.

The kvm_arm_vmid_update() function checks the VMID's generation, takes
a new VMID if it is from an old generation, and marks it as active on
this CPU.  Without this, the shadow MMU's VMID could be an old one that
now belongs to another VM, or a rollover on another CPU could hand it
to another VM while we are using it.  Either way the AT fills TLB entries
tagged with another VM's VMID.

To fix this, call kvm_arm_vmid_update() to update the VMID before loading
the shadow stage 2.  That marks it as active on the CPU.  Then at the end
of the function, undo that.  Restore the original VMID as active while
checking for and handling rollover.

[PATCH v2 3/4] KVM: arm64: nv: Clear hidden TCR2 bits for nested
Author: Dan Carpenter <dan@pereq.eu>

The previous patch added traps for TCR2_EL1 writes on VMs that have
FEAT_TCR2 but not FEAT_S1PIE or FEAT_S1POE.  This patch extends that
fix to cover nested virtualization.

The bug is that a KVM can hide the PIE and POE bits in TCR2_EL1 but a VM
can still write to them.  It obviously makes no sense to hide a register
from the VM but still allow writes. The implication of this bug is a
small information leak because a VM can determine the permission bits of
another VM's page tables.

The previous patch trapped writes to TCR2_EL1 but nested virtualization
is more complicated because we have to deal with TCR2_EL2 as well.  A
trapped TCR2_EL1 write has to go to either TCR2_EL2 or TCR2_EL1 depending
on who made it.  With nested virtualization the hidden bits can reach the
hardware in three ways:

- A guest hypervisor at vEL2 writes its TCR2_EL2.
- An L2 writes its own TCR2_EL1.
- An L1 writes its L2's TCR2_EL1 in the VNCR page, which KVM loads as is.

To fix this, remove the vcpu_has_nv() check in __compute_hfgwtr() so that
these writes are trapped too.  When the guest hypervisor is at vEL2,
update TCR2_EL2 and TCR_EL2 instead of L2's registers.  Also clear the
hidden bits in __sysreg_restore_el1_state() when it loads a guest's
TCR2_EL1.

[PATCH v2 2/4] KVM: arm64: Trap TCR2_EL1 writes when S1PIE or
Author: Dan Carpenter <dan@pereq.eu>

[PATCH v2 1/4] KVM: arm64: nv: Fix AT emulation for TCR2_EL1
Author: Dan Carpenter <dan@pereq.eu>

Arm provides an AT instruction that translates a virtual address the way
the MMU would and returns the result.  There is a bug in the way this
instruction is emulated for nested virtualization because of how TCR2_EL1
is handled.  The bug is fairly minor.

The TCR2_EL1 register has bits which turn on permission indirection
(PIE) and permission overlays (POE).  When these bits are set, the AT
instruction reads the permissions stored in PIR_EL1 and POR_EL1.  If
you have the right features and permissions then in the return value from
the AT instruction we set one bit to either 1 or 0 depending on whether
the access would be allowed or whether it would fault.

However, the bug is that just because the host has TCR2 enabled, it
doesn't mean the VM has it.  In the current code KVM doesn't load these
registers for a VM which doesn't have the features, instead the AT runs
with the host's HCRX_EL2, which has TCR2En set.  So the AT uses the
TCR2_EL1, PIR_EL1 and POR_EL1 values another VM left on the CPU, or
possibly the VMM's POR_EL0.  Likewise, for a VM which has TCR2 but not
PIE or POE, the L2's TCR2_EL1 is loaded unmasked.

The impact of this bug is that we leak a single bit of data to the L1,
but in real life it's hard to imagine how it is useful to an attacker.

Fix this by clearing the PIE and POE bits in effective_tcr2() when the
VM doesn't have those features, and use it for the L2's TCR2_EL1.  When
the AT runs on the guest hypervisor's own registers, in __kvm_at_s1e2()
and in __kvm_at_s1e01_fast(), load the guest's TCR2_EL2 for the AT and
restore the live value afterwards.

[PATCH v3 5/5] arm64: Add workaround to replace WFE with NOP for
Author: Tomohiro Misono <misono.tomohiro@fujitsu.com>

This option adds a workaround for FUJITSU-MONAKA erratum E#030004.

On affected CPUs, if a wake-up event generated by clearing the
global exclusive monitor or by a SEV instruction arrives in the
same cycle as a WFE instruction commits, the CPU may fail to
advance the program counter and re-execute the same WFE
instruction. If no further wake-up event occurs, the CPU may
remain waiting indefinitely (for example, in spinlock code).
This may cause a system hang before the generic timer event stream
is enabled. WFI, WFIT, and WFET instructions are not affected.

After the event stream is enabled (shortly after the secondary CPU
bring-up), event stream could wake up affected cores.
However, in order to prevent the condition during secondary CPU
bring-up, the workaround replaces all WFE instructions in host kernel
code with NOP using the boot alternative framework before the secondary
CPU bring-up on the MONAKA CPU.

Note that there is no need to take care of WFE usage in Host EL0 and
VHE Guest since if event stream is enabled in Host EL2, the event
reaches to every ELx & world. This effectively means FUJITSU-MONAKA
does not guarantee disabling event stream
(clocksource.arm_arch_timer.evtstrm=0) nor running nVHE guests
(kvm-arm.mode=nvhe/protected), although these configurations
are not rejected by this patch.

This only affects FUJITSU-MONAKA CPUs.

[PATCH v3 4/5] irqchip/gicv3: Add workaround for FUJITSU-MONAKA
Author: Tomohiro Misono <misono.tomohiro@fujitsu.com>


On affected FUJITSU-MONAKA CPUs, the erratum may occur when an SGI is
generated by writing to ICC_SGI0R_EL1, ICC_SGI1R_EL1, or ICC_ASGI1R_EL1,
if the operation races with CPU interface processing triggered by the
arrival of a higher-priority interrupt, an update to a pending
interrupt, or a transition of the PE to the Sleep state. When the
erratum occurs, the SGI is lost and the system register write does not
complete, causing the issuing core to hang.

Guest accesses to these registers are not affected by this erratum, as
they are trapped to EL2 and handled without issuing the affected system
register write.

Work around the erratum by writing 1 to the bit corresponding to the
target SGI INTID in GICR_ISPENDR0 of each target PE's GIC Redistributor,
instead of writing to the affected system registers.

Accessing a target PE's GICR_ISPENDR0 requires its Redistributor base to
have been discovered. Affected platforms conform to SBBR, which requires
PSCI for secondary CPU boot. They therefore do not use the ACPI Parking
protocol, which sends an IPI before the secondary CPU has initialized
its Redistributor. With PSCI, a secondary CPU discovers its
Redistributor before becoming an IPI target.

[PATCH v3 3/5] perf: arm_pmu: Add workaround for FUJITSU-MONAKA
Author: Tomohiro Misono <misono.tomohiro@fujitsu.com>

FUJITSU-MONAKA Erratum E#030002 affects FUJITSU-MONAKA CPU.

On affected FUJITSU-MONAKA CPUs, after a PMU event counter is
stopped at a value just before overflow, an overflow might still
be incorrectly detected, resulting interrupt storm in some case.

For example, if the following conditions are met:
  1) Running perf to count an event in user space only
  2) The event can also occur in kernel space
  3) The counter value is set just before the overflow
     (when using the -F option, initial counter value is -1)

when the kernel is about to return to user space after enabling
the count, an overflow interrupt is incorrectly triggered by an
event that occurred in kernel space. Since the counter value is
not updated (correctly), the interrupt handler does nothing and
returns with the same condition. This leads to another wrong interrupt
and results in an interrupt storm and eventually a softlockup.

Work around the erratum by avoiding programming PMU event counters
with values within 7 counts of overflow because the counter
can increase up to 7 at a time.
