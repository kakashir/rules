[PATCH v3 4/4] KVM: arm64: nv: Allow the L1 VNCR page in cacheable PFNMAP memory
Author: Jia He <justin.he@arm.com>

kvm_translate_vncr() refuses any PFN that isn't memory and injects an
SEA into the guest hypervisor. That is stricter than what the stage-2
fault path allows (kvm_s2_fault_pin_pfn()): a VM_PFNMAP or VM_MIXEDMAP
VMA whose host stage-1 attributes are cacheable is mapped cacheable at
stage-2 when FWB and DIC are present, and the guest can use such memory
as RAM (e.g. device memory that it onlines as a NUMA node). If the guest
then picks a page of that memory as the VNCR page of one of its own
guests, it takes an SEA as soon as it enters that guest.

For VM_PFNMAP and VM_MIXEDMAP VMAs, relax the check to match the stage-2
fault path, and remove the FIXME added by commit 4bd7dbe0b224 ("KVM:
arm64: nv: Inject SEA if guest VNCR isn't normal memory"). Look up the
VMA, and allow the PFN if the VMA is a cacheable VM_PFNMAP or
VM_MIXEDMAP one and the system supports cacheable PFNMAP at stage-2. No
linear mapping is required, because VNCR accesses use the EL2 fixmap and
require no cache maintenance.

Get the HVA with gfn_to_hva_memslot_prot(), as kvm_handle_guest_abort()
does. gfn_to_hva_memslot() returns KVM_HVA_ERR_RO_BAD for a read-only
memslot, and the VMA lookup would then fail. A VNCR page in a read-only
memslot is valid and is mapped read-only since commit 2684e02bac41
("KVM: arm64: nv: Respect read-only PFN when mapping L1 VNCR").

mmu_invalidate_seq is sampled before the PFN is faulted in, so a VMA
change after the lookup is caught by the mmu_invalidate_retry() check
that follows, as for the PFN itself.

Tested on a host with FEAT_FGT, FWB and DIC, with an L1 whose whole RAM
is a cacheable PFNMAP (host RAM withheld with mem= and handed to the VMM
by a test driver with remap_pfn_range()) starting an L2 guest
hypervisor. Without the patch, L2 repeatedly takes an SEA at the same PC
and fails to boot. With the patch, L2 boots successfully.

The read-only case was tested on a Neoverse-N2 host. The guest
hypervisor's VNCR page is in a cacheable PFNMAP registered as a
read-only memslot, and a nested context reads VTTBR_EL2. When the HVA
is looked up with gfn_to_hva_memslot(), the guest hypervisor takes an
SEA. With this patch, the read returns the contents of the VNCR page.

Signed-off-by: Jia He <justin.he@arm.com>

[PATCH v3 3/4] KVM: arm64: selftests: Add a test for VNCR_EL2 translation faults
Author: Jia He <justin.he@arm.com>

Add a test where the guest hypervisor enters a nested context with
HCR_EL2.{NV,NV2} set and reads VTTBR_EL2, which FEAT_NV2 turns into a
load from the VNCR page. The last-level table that maps the VNCR page is
placed in a read-only memslot, and TCR_EL2.HA is set.

With the access flag set, KVM maps the VNCR page and the read returns
the value in that page. With the access flag clear, KVM cannot update the
descriptor and must inject an SEA on translation table walk into the
guest hypervisor. A control case with the table in a writable memslot
checks that KVM sets the access flag and maps the page.

The VNCR page is mapped at a VA whose bits [15:12] differ from those of
its PA. On a host with 16K or 64K pages, this also checks that KVM
locates the VNCR page in the host page from its PA.

Signed-off-by: Jia He <justin.he@arm.com>

[PATCH v3 2/4] KVM: arm64: nv: Inject an SEA when the VNCR walk cannot set the AF
Author: Jia He <justin.he@arm.com>

When the guest hypervisor enables hardware Access flag management
(TCR_EL2.HA), KVM's stage-1 walker sets the AF in the descriptor that
maps VNCR_EL2 with __kvm_at_swap_desc(). If the descriptor is in a
read-only memslot, the update fails with -EPERM and walk_s1() records an
SEA on translation table walk in the walk result.

kvm_handle_vncr_abort() does not handle -EPERM. It neither injects the
fault nor maps the VNCR page, and returns to the guest. The guest takes
the same VNCR abort again and never makes progress.

-EPERM can only come from this AF update. The VNCR walk uses the EL2&0
translation regime, which has no stage-2.

Treat -EPERM like the other walk failures and inject the recorded fault
into the guest hypervisor.

Tested with the selftest added in the next patch on a Neoverse-N2 host.
Without this patch, the vCPU exits about 1.3 million times in 5 seconds
on the same VNCR abort and makes no progress. With this patch, the
guest hypervisor receives an SEA on translation table walk at level 3.

[PATCH v3 1/4] KVM: arm64: nv: Locate the VNCR page in the host page from its PA
Author: Jia He <justin.he@arm.com>

VNCR_EL2 only needs to be 4K aligned. On a host with 16K or 64K pages,
kvm_translate_vncr() records the host page that contains the guest
hypervisor's VNCR page, and that host page is mapped at the VNCR fixmap.
__compute_hcr() then takes the offset of the VNCR page in the host page
from bits [PAGE_SHIFT-1:12] of the guest's VNCR_EL2, which is a VA.

If the guest hypervisor uses a stage-1 granule smaller than the host
page, these bits of the VA and of the PA can differ. The nested context
then accesses another 4K page of the guest instead of the VNCR page.

Take the offset from the PA that the walk returns, and keep it in
vt->hpa. Use it only while the VNCR page is mapped. Otherwise the
fixmap is clear, the access faults and KVM translates VNCR_EL2 again,
so the offset does not matter.

Tested on a Neoverse-N2 host running 16K and 64K page kernels, with the
selftest added later in this series. The test maps the VNCR page at a VA
whose bits [15:12] differ from those of its PA. With the offset taken
from the VA, the nested context reads 0 instead of the value in the VNCR
page. With this patch, it reads the expected value.

Reported-by: Sashiko <sashiko-bot@kernel.org>

[PATCH v3 0/4] KVM: arm64: nv: VNCR page mapping fixes
Author: Jia He <justin.he@arm.com>

On a VNCR abort, KVM walks the guest hypervisor's EL2 stage-1 tables,
maps the page that VNCR_EL2 points to at a fixmap, and points the
hardware VNCR_EL2 at that fixmap. This series fixes three cases where
this goes wrong.

Patch 1 fixes the address that KVM programs into VNCR_EL2 on a host
with 16K or 64K pages. The fixmap maps the host page that contains the
VNCR page, and KVM takes the offset of the VNCR page in it from the VA.
If the guest hypervisor uses a smaller stage-1 granule, the VA and the
PA can have different offsets, and the nested context accesses another
page of the guest. Patch 1 takes the offset from the PA.

Patch 2 fixes a walk that cannot set the AF. If TCR_EL2.HA is set and
the descriptor that maps VNCR_EL2 is in a read-only memslot, the walk
returns -EPERM. kvm_handle_vncr_abort() has no case for -EPERM, so the
vCPU takes the same abort forever. Patch 2 injects the SEA that the
walk recorded.

Patch 3 adds a selftest for both. It maps the VNCR page at a VA whose
offset in a 16K or 64K page differs from that of its PA, and puts the
table that maps it in a read-only memslot.

Patch 4 allows the VNCR page in a cacheable VM_PFNMAP or VM_MIXEDMAP
VMA. The stage-2 fault path already maps such memory as cacheable, but
kvm_translate_vncr() rejects it and injects an SEA.

Patches 1 and 2 fix bugs that predate this series, and each can be
applied on its own.

Based on v7.4-rc3.

Author: Simon Song <xinmengs@nvidia.com>


Add Rust abstractions for PCI drivers that extend vfio-pci-core with
device-specific operations.

Provide Operations, Device and Registration with separate registration
and first-open/last-close data. Allow open data to borrow registration
data, undo PCI enablement if open fails, and drop open data before
closing the core device.

Let a driver register its VFIO device with Registration::new(), for
example from its PCI probe callback, and unregister it by dropping the
Registration. Let drivers forward PCI reset and error callbacks through
the Registration. Let vfio-pci-core select its VGA arbitration
callbacks. Because runtime PM support follows in a separate patch
series, keep the device active while it is registered.

Restrict core I/O helpers to their corresponding callback contexts. Add
region mapping helpers, and wire up VFIO core support for device
features, matching, IOMMUFD and PASID. Allow drivers to export physical
BARs as DMA buffers with per-region length limits.

Add pci::ErsResult::from_raw() for the result of the VFIO PCI core's
error handler.

[PATCH v4 0/5] Rust VFIO PCI support and NVIDIA vGPU driver
Author: Simon Song <xinmengs@nvidia.com>

This is v4 of the Rust VFIO PCI abstractions and the NVIDIA VFIO variant
driver [1]. The driver uses nova-core's typed SR-IOV PF interface to
create, reset and release vGPU instances while VFIO provides userspace
access to the PCI device.

Patches 1-5 of v3 were applied to driver-core-next, so this version
carries the remaining patches. Patch 1 adds the VFIO device handling
common to all buses. Patch 2 adds two VmaRef accessors for patch 3, the
VFIO PCI abstractions. Patch 4 publishes the typed Nova PF interface,
and patch 5 adds the NVIDIA VFIO variant driver.

This series is based on driver-core-next. Patches 1-3 need nothing else.
Patches 4 and 5 also depend on v5 of Alok's vGPU manager series [2] and
can follow once it has landed.

Runtime PM is still not part of this series. It will follow once the
generic Rust runtime PM support [3] and the PCI bus handling for it are
available. Until then, vfio::pci::Registration keeps the device runtime
active while it is registered.

[PATCH v3 01/15] KVM: selftests: Make the x86 SSE register helpers volatile
Author: David Woodhouse <dwmw2@infradead.org>


read_sse_reg() and write_sse_reg() were borrowed from KVM's
_kvm_read_sse_reg() and _kvm_write_sse_reg(). The kernel is built
without SSE, so the compiler never uses the XMM registers itself and a
plain asm() is enough there. Selftest guest code is built with SSE, and
there the asm statements have to tell the compiler what they do.

read_sse_reg() has an output and is not volatile, so the compiler may
treat it as a pure computation and move it, for example ahead of the
hypercall whose XMM output it is meant to read. write_sse_reg() has no
outputs and is therefore implicitly volatile, but it doesn't declare the
register it overwrites, so a value the compiler was keeping there does
not survive.

Mark both volatile, and declare the register each write_sse_reg() case
writes as clobbered. A read_sse_reg() after __hyperv_hypercall() now
stays after it.

That still leaves the compiler free to use an XMM register for its own
code between a write_sse_reg() and the asm which consumes it.
hyperv_write_xmm_input() in the hyperv_ipi and hyperv_tlb_flush tests
relies on that not happening; GCC 11.5 at -O2 emits nothing there.
Closing that window entirely would mean passing the XMM values as
operands of the hypercall asm itself.

[PATCH v3 06/15] KVM: x86: hyper-v: Let userspace leave a hypercall uncompleted
Author: David Woodhouse <dwmw2@infradead.org>


A VMM handling KVM_EXIT_HYPERV_HCALL can only complete the hypercall:

[PATCH v3 00/15] KVM: x86: Exit handling for Hyper-V hcalls, register intercept
Author: David Woodhouse <dwmw2@infradead.org>


Add KVM_CAP_HYPERV_FORWARD_HCALL. As with KVM_CAP_XEN_HVM and
KVM_CAP_EXIT_HYPERCALL, KVM_CHECK_EXTENSION returns a bitmask of
features and KVM_ENABLE_CAP takes the subset to enable. The first
feature, KVM_HYPERV_HCALL_FORWARD_UNKNOWN, surfaces unknown hypercalls
to userspace through the existing KVM_EXIT_HYPERV_HCALL exit.

A second feature, KVM_HYPERV_HCALL_RET, allows userspace to choose
whether/how the kernel should complete the hypercall, populating a
'ret' field with one of:

  KVM_INSN_COMPLETE   finish the instruction, as now
  KVM_INSN_GP         inject #GP(0) at it
  KVM_INSN_UD         inject #UD at it
  KVM_INSN_RESUME     do nothing; resume the guest as userspace left it

Hyper-V needs to do this in some cases, for example HvCallVtlCall and
HvCallVtlReturn are supposed to raise #UD when they are refused.

Further features will follow for HvCallVtlCall and HvCallVtlReturn on
VMs with planes, so that KVM can handle VTL transitions in the kernel.

Also add KVM_CAP_X86_REG_WRITE_FILTER for trapping control register
writes (CR0, CR4, XCR0, IDTR, LDTR, etc.).

Add KVM_CAP_X86_MSR_EXIT_INSN to allow MSR exits to gain the same
ability to COMPLETE/GP/UD/RESUME so that they can be handled by
another plane too. The existing 'error' field was already a u8 there,
so userspace can just opt in to using the new KVM_INSN_xxx values in
place of the existing 'non-zero means #GP' behaviour.

The VMware hypercall series¹ needs to fault its instruction too, and
with more than #GP. As posted, it has its exit carry a vector, an
error code and a fault address for KVM to inject. It can use the same
model, and the complex faults can be injected with KVM_SET_VCPU_EVENTS
followed by a ret of KVM_INSN_RESUME.

The completion result code deliberately does not cover:

 - PIO and MMIO. Those completions carry state which can't just be
   dropped, and VSM has no use for it: what a higher VTL intercepts
   there is the memory access, which faults before the instruction has
   done anything.

 - Guests with protected state. There is no instruction for KVM to
   leave alone, so MSR exits keep today's meaning (any non-zero value
   fails the access), a Hyper-V hypercall always completes, and a
   register write filter cannot be armed. Nor can one be armed for a
   plain SEV guest, whose instructions KVM cannot decode.

 - KVM_EXIT_HYPERCALL, KVM_EXIT_XEN and KVM_EXIT_TDX, which are
   untouched.

[PATCH v1 05/12] KVM: s390: Fix dat_entry_walk() with DAT_WALK_CONTINUE
Author: Claudio Imbrenda <imbrenda@linux.ibm.com>

When dat_entry_walk() is called specifying the DAT_WALK_CONTINUE flag,
the page table walk continues past the specified level, towards ptes.

[PATCH v1 02/12] KVM: s390: Fix potential leak in kvm_s390_get_io_int()
Author: Claudio Imbrenda <imbrenda@linux.ibm.com>

In case all of the following apply at the same time:

* a higher priority GISA interrupt is pending
* a lower priority classic interrupt is also pending
* the pending interrupt queue is full

then kvm_s390_reinject_io_int() will fail, the classic interrupt is
dropped and its memory is leaked.

Fix by checking whether the reinjection of the interrupt succeeded, and
free it if not. The interrupt is still dropped, but no leak occurs.

This is not expected to happen during normal guest operation, due to
the large maximum size of the pending interrupt queue.

[PATCH v4 00/25] KVM: s390: arm64: System Registers
Author: Steffen Eiden <seiden@linux.ibm.com>

Add system register handling for KVM/arm64 on s390. Share KVM/arm64
code, introduce ARM guest management functions for s390 hosts, and
implement host system register & exception handling.

This is the second series on the way to arm64 guests on s390. The first
series laid the KVM foundation (basic module, vCPU run, simple page
faults) and is included in v7.4. This series builds the system register
layer on top and closes the biggest of the remaining gaps towards a
functional guest support.

On top of master this series requires one patch[1] not yet merged in
order to build clean.

The series applies without those patches on master but the build will
fail or trigger warnings w/o those patches.

Regarding merging: 

Patches 1-10 can/should go via the KVM/arm64 tree. Note that PATCH 8 is
an s390 patch but is is required so be at this position. Otherwise, s390
will not compile when patch 10 is applied until patch 18. And I cannot
palce it before as the patch needs some stuff from the just shared
headers in PATCH 07.

Patches 11-25 can then be picked by KVM/s390. Those require the
perquisite patch [1] mentioned above.

A branch  with the prerequisite and this series is available at
kernel.org [2]. Another series may be added on top to that branch soon. 

Changes in detail:

arm64:

Refactor the id register fields in arch_vcpu into a dedicated structure
such that it can be reused by s390. Refactor detection of the number of
sysregs. Mark sysreg related code as shared.

A few code pieces are moved inside arm headers/code to reduce the amount
of shared sections. This adds a bit of churn in the diff but reduces the
shared marker __churn__ at the end.

The shared regions deliberately contain more code and more headers than
s390 currently needs. Larger contiguous regions mean less churn whenever
the surrounding arm64 code changes. Some of this code will be used by
later series anyways. Some of the shared code will probably never be
reused by s390 at all. I trust the compiler to remove it. The reduced
churn outweighs this drawback. Since unused function checking is
disabled for shared code [3], sharing more than required does not
introduce warnings once everything is merged.

s390:

Add s390 instruction support for ARM guest management: easr/sasr for
system register access, QAAF for feature queries, and ptff extensions
for guest time handling.

Implement complete sysreg handling for s390 including feature
sanitisation, register enumeration and access, exception injection, and
finalized page fault handling. For now s390 maintains its own sysreg
table but I intend to share the table with arm as soon as possible.

Emulation:

Guest accesses to ID registers are trapped and served from a sanitized
copy of the QAAF query results, using the ID register sanitisation and
finalisation infrastructure shared with arm64. Userspace sees and
controls guest ID registers with the usual semantics. After the first
vCPU run the values are final. All other system registers live in the
SAE save area and are accessed by the host via EASR/SASR, either on
guest traps or through the one-reg/two-reg UAPI. The save area itself is
initialized from the QAAF-provided initial save area.

Exception handling:

Unsupported or invalid guest actions now raise proper arm64 exceptions
instead of failing exits. Page faults beyond the guest's address limits
are injected as address size faults or synchronous external aborts,
mirroring arm64's kvm_handle_guest_abort() injected faults re-enter the
guest with the pending exception instead of exiting to userspace.

Features and userspace:

SVE is offered to guests at 128-bit vector length, backed by s390's
Vector Extension. Pointer authentication is passed through where
hardware support exists. The AEF capabilities are reported under
/sys/firmware/aef/, including the raw QAAF query results.

[PATCH 4/4] iommu/dma: restore flush queue use in
Author: Marek Szyprowski <m.szyprowski@samsung.com>

Commit 1acce29926d9 ("iommu/dma: simplify dma_iova_destroy() and drop
the free_iova helper") turned dma_iova_destroy() into dma_iova_unlink()
followed by dma_iova_free(). Before it, the destroy path marked its
IOTLB gather as queued for DMA-FQ domains, skipped iommu_iotlb_sync()
and handed the IOVA over to the flush queue, exactly like
__iommu_dma_unmap(). After it:

  - dma_iova_unlink() never queues its gather and always calls
    iommu_iotlb_sync() after iommu_unmap_fast(),
  - dma_iova_free() passes a NULL gather to iommu_dma_free_iova(), so
    the IOVA goes straight back to the allocator via free_iova_fast().

DMA-FQ domains therefore get strict invalidation on this path. This
includes blk_rq_dma_map(), which NVMe uses for all data transfers, so
iommu.strict=0 has no effect on NVMe I/O. On a Qualcomm Glymur CRD
(SMMUv3 without RANGE_INV, 4K pages, NVMe on PCIe Gen5 x4) sequential
fio throughput drops from 10.6/11.9 GiB/s (write/read) to the strict
mode level of ~2.7 GiB/s.

Instead of reverting, decide once in dma_iova_try_alloc() whether the
IOVA space is going to be released through the flush queue and record
it in a new DMA_IOVA_USE_FQ flag in dma_iova_state::__size, next to
DMA_IOVA_USE_SWIOTLB, so struct dma_iova_state does not grow.
dma_iova_destroy() then unmaps with a gather queued according to that
flag, skipping the sync for flush queue domains, and passes the same
gather to the IOVA free, so the IOVA space (and any page table pages
released by the unmap) goes through queue_iova() again. dma_iova_free()
honours the flag as well. The whole reservation is still freed, keeping
the size fix of the reverted commit.

A gather must always be retired, either by iommu_iotlb_sync() or by
handing it to the flush queue together with the IOVA, and the IOVA must
never be returned to the allocator while a queued invalidation for it is
still pending. To keep that obvious, the internal unlink helper only
unmaps into a gather supplied by its caller, and each caller retires it
right away: dma_iova_destroy() syncs or queues it together with the IOVA
free, exactly like __iommu_dma_unmap(), while dma_iova_unlink() always
uses a never queued gather and syncs it, as the unlinked range remains
owned by the caller and may be linked again immediately.

[PATCH kvmtool 2/3] virtio: 9p: Validate unsigned string lengths
Author: Dickson Wu via B4 Relay <devnull+dickson.wu.certik.com@kernel.org>


A guest can provide a 9p string length that exceeds the remaining
request. The decoder may then copy incomplete data and use a malformed
string. Lengths with the high bit set are valid unsigned protocol
values when the complete string is present. Truncated fixed-width
fields can also leave decoded values uninitialized, including string
pointers that handlers free on decode errors.

[PATCH net-next v6 2/2] vsock/virtio: amortize RX socket locking for stream packets
Author: Jia Jia <physicalmtea@gmail.com>

The virtio-vsock RX worker looks up a socket and takes its lock for every
packet. Retain the connected lookup reference and socket lock across a
bounded run of STREAM/RW packets for one established native socket.

Reuse the locked socket while packets match the same flow. Finish the
batch on a malformed packet, flow change, non-RW traffic, or a change to
the socket state, transport, protocol, sockmap state, or receive buffer
limits. A connected lookup miss falls back to the existing receive path,
which can still find a bound socket.

Limit an uninterrupted socket-lock ownership interval to 64 packets and
64 KiB of payload. The payload limit is one
VIRTIO_VSOCK_MAX_PKT_BUF_SIZE. Small or zero-length packets still incur
per-packet work, so an independent packet limit is needed. The 64-packet
limit uses VHOST_NET_BATCH as a reference; it is a policy choice rather
than a protocol limit.

Beyond these limits, a larger batch would only further amortize socket
lookup and lock/unlock operations, while virtqueue work, validation,
tracing, skb ownership, credit update, and queueing remain per-packet. I
therefore expect diminishing returns while the uninterrupted socket-lock
interval continues to grow, but I have not measured larger limits yet.

Only the guest virtio RX worker is changed. The benchmark exercises the
host-sender-to-guest-receiver direction, where this worker is on the
receive path. I have not measured the corresponding worker and socket-lock
overhead in vhost-vsock or vsock_loopback, and they use different worker
and locking models. Leave those paths unchanged pending separate policy
and validation. I plan to evaluate vhost-vsock separately as follow-up
work.

[PATCH v3 4/4] KVM: arm64: nv: Allow the L1 VNCR page in cacheable PFNMAP memory
Author: Jia He <justin.he@arm.com>

kvm_translate_vncr() refuses any PFN that isn't memory and injects an
SEA into the guest hypervisor. That is stricter than what the stage-2
fault path allows (kvm_s2_fault_pin_pfn()): a VM_PFNMAP or VM_MIXEDMAP
VMA whose host stage-1 attributes are cacheable is mapped cacheable at
stage-2 when FWB and DIC are present, and the guest can use such memory
as RAM (e.g. device memory that it onlines as a NUMA node). If the guest
then picks a page of that memory as the VNCR page of one of its own
guests, it takes an SEA as soon as it enters that guest.

For VM_PFNMAP and VM_MIXEDMAP VMAs, relax the check to match the stage-2
fault path, and remove the FIXME added by commit 4bd7dbe0b224 ("KVM:
arm64: nv: Inject SEA if guest VNCR isn't normal memory"). Look up the
VMA, and allow the PFN if the VMA is a cacheable VM_PFNMAP or
VM_MIXEDMAP one and the system supports cacheable PFNMAP at stage-2. No
linear mapping is required, because VNCR accesses use the EL2 fixmap and
require no cache maintenance.

Get the HVA with gfn_to_hva_memslot_prot(), as kvm_handle_guest_abort()
does. gfn_to_hva_memslot() returns KVM_HVA_ERR_RO_BAD for a read-only
memslot, and the VMA lookup would then fail. A VNCR page in a read-only
memslot is valid and is mapped read-only since commit 2684e02bac41
("KVM: arm64: nv: Respect read-only PFN when mapping L1 VNCR").

mmu_invalidate_seq is sampled before the PFN is faulted in, so a VMA
change after the lookup is caught by the mmu_invalidate_retry() check
that follows, as for the PFN itself.

Tested on a host with FEAT_FGT, FWB and DIC, with an L1 whose whole RAM
is a cacheable PFNMAP (host RAM withheld with mem= and handed to the VMM
by a test driver with remap_pfn_range()) starting an L2 guest
hypervisor. Without the patch, L2 repeatedly takes an SEA at the same PC
and fails to boot. With the patch, L2 boots successfully.

The read-only case was tested on a Neoverse-N2 host. The guest
hypervisor's VNCR page is in a cacheable PFNMAP registered as a
read-only memslot, and a nested context reads VTTBR_EL2. When the HVA
is looked up with gfn_to_hva_memslot(), the guest hypervisor takes an
SEA. With this patch, the read returns the contents of the VNCR page.

[PATCH v3 2/4] KVM: arm64: nv: Inject an SEA when the VNCR walk cannot set the AF
Author: Jia He <justin.he@arm.com>

When the guest hypervisor enables hardware Access flag management
(TCR_EL2.HA), KVM's stage-1 walker sets the AF in the descriptor that
maps VNCR_EL2 with __kvm_at_swap_desc(). If the descriptor is in a
read-only memslot, the update fails with -EPERM and walk_s1() records an
SEA on translation table walk in the walk result.

kvm_handle_vncr_abort() does not handle -EPERM. It neither injects the
fault nor maps the VNCR page, and returns to the guest. The guest takes
the same VNCR abort again and never makes progress.

-EPERM can only come from this AF update. The VNCR walk uses the EL2&0
translation regime, which has no stage-2.

into the guest hypervisor.

Without this patch, the vCPU exits about 1.3 million times in 5 seconds
on the same VNCR abort and makes no progress. With this patch, the
guest hypervisor receives an SEA on translation table walk at level 3.

[PATCH v3 1/4] KVM: arm64: nv: Locate the VNCR page in the host page from its PA
Author: Jia He <justin.he@arm.com>

VNCR_EL2 only needs to be 4K aligned. On a host with 16K or 64K pages,
kvm_translate_vncr() records the host page that contains the guest
hypervisor's VNCR page, and that host page is mapped at the VNCR fixmap.
__compute_hcr() then takes the offset of the VNCR page in the host page
from bits [PAGE_SHIFT-1:12] of the guest's VNCR_EL2, which is a VA.

If the guest hypervisor uses a stage-1 granule smaller than the host
page, these bits of the VA and of the PA can differ. The nested context
then accesses another 4K page of the guest instead of the VNCR page.

Take the offset from the PA that the walk returns, and keep it in
vt->hpa. Use it only while the VNCR page is mapped. Otherwise the
fixmap is clear, the access faults and KVM translates VNCR_EL2 again,
so the offset does not matter.

Tested on a Neoverse-N2 host running 16K and 64K page kernels, with the
selftest added later in this series. The test maps the VNCR page at a VA
whose bits [15:12] differ from those of its PA. With the offset taken
from the VA, the nested context reads 0 instead of the value in the VNCR
page. With this patch, it reads the expected value.

[PATCH] KVM: arm64: Drop a pending MMIO access when injecting an
Author: Dan Carpenter <dan@pereq.eu>

Oliver's commit bfb7a30b1986 ("KVM: arm64: Don't retire MMIO instruction
w/ pending (emulated) SError") established the rule that when userspace
injects an SError that we drop the MMIO.  An MMIO access dropped this way
runs again when the guest returns from the SError.

However, since commit 3bd107ed6b23 ("KVM: arm64: Only emulate an SError's
entry for vCPUs with NV"), a vcpu without EL2 pends the SError through
HCR_EL2.VSE instead.  The next KVM_RUN completes the access, and then
the guest takes the SError.  So the behavior is not consistent depending
on whether the vcpu has EL2 (MMIO dropped) or not (MMIO completes).

To make things consistent, drop the pending MMIO access in the non-EL2
case as well.

This change only affects unmasked SErrors, if they are masked the MMIO
always completes.  The host's copy of a protected vcpu's PSTATE always
has SErrors masked, so for protected vcpus the MMIO always completes.

I discovered this inconsistency while writing a selftest and I don't
believe real life users have noticed it.

Fixes: 3bd107ed6b23 ("KVM: arm64: Only emulate an SError's entry for vCPUs with NV")
Signed-off-by: Dan Carpenter <dan@pereq.eu>

    serror_is_masked() function returns false if effective_sctlr2_nmea()
    is set so we would have dropped the access but left the SError
    pending.

    Checking PSTATE.A also means we can drop the !vcpu_is_protected()

[PATCH v2 2/2] arm64: THPs for systems with pages bigger than 4K
Author: Vincent Donnefort <vdonnefort@google.com>

The THP support imposes guest RAM over-allocation to align the memslot

[PATCH 3/3] KVM: arm64: nv: Update the shadow MMU's VMID for AT
Author: Dan Carpenter <dan@pereq.eu>

There is a missing kvm_arm_vmid_update() before the __load_stage2()
in __kvm_at_s1e01_fast().  The bug affects nested virtualization on
arm64.

In KVM a "stage 2" refers to the VM's page table mappings. The
__kvm_at_s1e01_fast() function emulates the AT instruction, which
translates a virtual address the way the MMU would and returns the
result.

Each stage 2 has a VMID, which the hardware uses to tag TLB and
walk-cache entries, so that one VM never uses another's entries.  There
are only 2^8 or 2^16 VMIDs, which is quite limited, so vmid.c hands
them out by generation.  When they run out, a rollover starts a new
generation and flushes the TLBs: the VMIDs active on a CPU at that
moment are kept, and every other VMID can be given to another VM.

The kvm_arm_vmid_update() function checks the VMID's generation, takes
a new VMID if it is from an old generation, and marks it as active on
this CPU.  Without this, the shadow MMU's VMID could be an old one that
now belongs to another VM, or a rollover on another CPU could hand it
to another VM while we are using it.  Either way the AT fills TLB entries
tagged with another VM's VMID.

To fix this, call kvm_arm_vmid_update() to update the VMID before loading
the shadow stage 2.  That marks it as active on the CPU.  Then at the end
of the function, undo that.  Restore the original VMID as active while
checking for and handling rollover.

Fixes: 477e89cabb14 ("KVM: arm64: nv: Add basic emulation of AT S1E{0,1}{R,W}")
Cc: stable@vger.kernel.org

[PATCH 2/3] KVM: arm64: Load no-access permissions when S1PIE or
Author: Dan Carpenter <dan@pereq.eu>

A VMM can offer FEAT_TCR2 to a guest but hide FEAT_S1PIE or FEAT_S1POE,
for example to keep the VM migratable.

But the complication is that the guest can still write to the PIE, POE
and E0POE bits in TCR2_EL1, and when those bits are set the CPU uses
the permission registers.  So the guest runs with the permissions that
another VM left in PIR_EL1, PIRE0_EL1 and POR_EL1, or with the VMM's
POR_EL0.  By checking which accesses fault, the guest can work out
another VM's permission settings.  This is a kind of small information
leak.

Currently, KVM doesn't save or load PIR_EL1, PIRE0_EL1, POR_EL1 and
POR_EL0 for a guest where S1PIE or S1POE is hidden.  After this patch,
KVM switches these registers whenever the CPU has the feature, even for
a guest that doesn't have it: PIR_EL1, PIRE0_EL1 and POR_EL1 when the
vcpu is loaded and put, and POR_EL0, which the VMM uses, on every guest
entry and exit.  For a guest that doesn't have the feature, KVM loads 0
instead of the guest's value.  A permission of 0 allows no access, so if
the guest sets PIE, POE or E0POE anyway, the accesses all fault and the
information leak is gone.

Fixes: 58627b722ee2 ("KVM: arm64: Make PIR{,E0}_EL1 UNDEF if S1PIE is not advertised to the guest")
Fixes: b86c9bea6349 ("KVM: arm64: Save/restore POE registers")

[PATCH 1/3] KVM: arm64: nv: Fix AT emulation for TCR2_EL1
Author: Dan Carpenter <dan@pereq.eu>

Arm provides an AT instruction that translates a virtual address the way
the MMU would and returns the result.  We emulate this instruction by
setting up the state and calling the actual AT instruction.  There is a
bug in how the TCR2_EL1 permission bits are handled.

The TCR2_EL1 register has bits which turn on permission indirection (PIE)
and permission overlays (POE).  When these bits are set, the AT
instruction reads the permissions stored in permission registers PIR_EL1,
PIRE0_EL1, POR_EL1 and POR_EL0.  If you have the right features and
permissions then the return value from the AT instruction has bit that is
0 if the access is allowed or 1 if it would fault.

The bug is that the current code assumes that if the VM doesn't have
the feature then the host doesn't have it either, and isn't necessarily
true.  The host can have the features but disable them for a guest.  The
way the current code is written, if the VM doesn't have the features then
KVM doesn't bother to load the TCR2_EL1 or the permission registers, but
uses whatever was left there previously.

The impact of this information leak is very small.  It's hard to imagine
how knowing someone else's permission bits is useful to an attacker.
Claude suggests that potentially two guests could set up a secret
back channel where they communicate by flipping their permissions on and
off.  :)

Fix this by clearing the PIE and POE bits in effective_tcr2() when the
VM doesn't have those features, and load the result into TCR2_EL1
whenever the CPU has TCR2, not only when the VM has it.

When the AT runs on the guest hypervisor's own registers, in
__kvm_at_s1e2() and __kvm_at_s1e01_fast(), use the new load_guest_tcr2()
function to load the guest's TCR2_EL2 for the AT and restore the
original value afterwards.  If the VM doesn't have the PIE and POE
features, those bits of TCR2_EL2 are RES0 because
kvm_vcpu_apply_reg_masks() clears them.

There is a closely related bug in __kvm_at_s1e01_fast().  Here the issue
is that KVM is performing an AT command for a guest hypervisor but the
POR_EL0 isn't loaded, so we use the VMM's.  This bug is triggered when
the guest hypervisor runs with HCR_EL2.{E2H,TGE} = {1,1}.  Fix this by
loading the guest's POR_EL0 before the AT and restoring the VMM's value
afterwards.

Fixes: 23e7a34c8397 ("KVM: arm64: Add AT fast-path support for S1PIE")
Fixes: 846c993df982 ("KVM: arm64: Add POE save/restore for AT emulation fast-path")
Cc: stable@vger.kernel.org

[PATCH v4 00/25] KVM: s390: arm64: System Registers
Author: Steffen Eiden <seiden@linux.ibm.com>

Add system register handling for KVM/arm64 on s390. Share KVM/arm64
code, introduce ARM guest management functions for s390 hosts, and
implement host system register & exception handling.

This is the second series on the way to arm64 guests on s390. The first
series laid the KVM foundation (basic module, vCPU run, simple page
faults) and is included in v7.4. This series builds the system register
layer on top and closes the biggest of the remaining gaps towards a
functional guest support.

On top of master this series requires one patch[1] not yet merged in
order to build clean.

The series applies without those patches on master but the build will
fail or trigger warnings w/o those patches.

Regarding merging: 

Patches 1-10 can/should go via the KVM/arm64 tree. Note that PATCH 8 is
an s390 patch but is is required so be at this position. Otherwise, s390
will not compile when patch 10 is applied until patch 18. And I cannot
palce it before as the patch needs some stuff from the just shared
headers in PATCH 07.

Patches 11-25 can then be picked by KVM/s390. Those require the
perquisite patch [1] mentioned above.

A branch  with the prerequisite and this series is available at
kernel.org [2]. Another series may be added on top to that branch soon. 

Changes in detail:

arm64:

Refactor the id register fields in arch_vcpu into a dedicated structure
such that it can be reused by s390. Refactor detection of the number of
sysregs. Mark sysreg related code as shared.

A few code pieces are moved inside arm headers/code to reduce the amount
of shared sections. This adds a bit of churn in the diff but reduces the
shared marker __churn__ at the end.

The shared regions deliberately contain more code and more headers than
s390 currently needs. Larger contiguous regions mean less churn whenever
the surrounding arm64 code changes. Some of this code will be used by
later series anyways. Some of the shared code will probably never be
reused by s390 at all. I trust the compiler to remove it. The reduced
churn outweighs this drawback. Since unused function checking is
disabled for shared code [3], sharing more than required does not
introduce warnings once everything is merged.

s390:

Add s390 instruction support for ARM guest management: easr/sasr for
system register access, QAAF for feature queries, and ptff extensions
for guest time handling.

Implement complete sysreg handling for s390 including feature
sanitisation, register enumeration and access, exception injection, and
finalized page fault handling. For now s390 maintains its own sysreg
table but I intend to share the table with arm as soon as possible.

Emulation:

Guest accesses to ID registers are trapped and served from a sanitized
copy of the QAAF query results, using the ID register sanitisation and
finalisation infrastructure shared with arm64. Userspace sees and
controls guest ID registers with the usual semantics. After the first
vCPU run the values are final. All other system registers live in the
SAE save area and are accessed by the host via EASR/SASR, either on
guest traps or through the one-reg/two-reg UAPI. The save area itself is
initialized from the QAAF-provided initial save area.

Exception handling:

Unsupported or invalid guest actions now raise proper arm64 exceptions
instead of failing exits. Page faults beyond the guest's address limits
are injected as address size faults or synchronous external aborts,
mirroring arm64's kvm_handle_guest_abort() injected faults re-enter the
guest with the pending exception instead of exiting to userspace.

Features and userspace:

SVE is offered to guests at 128-bit vector length, backed by s390's
Vector Extension. Pointer authentication is passed through where
hardware support exists. The AEF capabilities are reported under
/sys/firmware/aef/, including the raw QAAF query results.

[PATCH v4 22/25] KVM: s390: arm64: Finalize page fault handling
Author: Steffen Eiden <seiden@linux.ibm.com>

Replace the temporary -ENOEXEC returns of the arm64-on-s390 page fault
handling with exception injection into the guest, mirroring arm64's
kvm_handle_guest_abort().

Translation faults beyond the physical address range  are injected as an
address size fault, while faults falling between the VM's IPA size and
that range are injected as a synchronous external abort. Instruction
aborts and stage-1 walk faults on host addresses that back no guest page
are injected as synchronous external aborts as well, and a
PGM-addressing from the fault-in path is injected as an address size
fault, the closest arm64 equivalent. Injected faults return 1 so the
vCPU re-enters the guest with the pending exception instead of exiting
to userspace.

[PATCH v4 5/5] arm64: Add workaround to replace WFE with NOP for
Author: Tomohiro Misono <misono.tomohiro@fujitsu.com>

This option adds a workaround for FUJITSU-MONAKA erratum E#030004.

On affected CPUs, if a wake-up event generated by clearing the
global exclusive monitor or by a SEV instruction arrives in the
same cycle as a WFE instruction commits, the CPU may fail to
advance the program counter and re-execute the same WFE
instruction. If no further wake-up event occurs, the CPU may
remain waiting indefinitely (for example, in spinlock code).
This may cause a system hang before the generic timer event stream
is enabled. WFI, WFIT, and WFET instructions are not affected.

After the event stream is enabled (shortly after the secondary CPU
bring-up), event stream could wake up affected cores.
However, in order to prevent the condition during secondary CPU
bring-up, the workaround replaces all WFE instructions in host kernel
code with NOP using the boot alternative framework before the secondary
CPU bring-up on the MONAKA CPU.

Note that there is no need to take care of WFE usage in Host EL0 and
VHE Guest since if event stream is enabled in Host EL2, the event
reaches to every ELx & world. This effectively means FUJITSU-MONAKA
does not guarantee disabling event stream
(clocksource.arm_arch_timer.evtstrm=0) nor running nVHE guests
(kvm-arm.mode=nvhe/protected), although these configurations
are not rejected by this patch.

This only affects FUJITSU-MONAKA CPUs.

[PATCH v4 4/5] irqchip/gicv3: Add workaround for FUJITSU-MONAKA
Author: Tomohiro Misono <misono.tomohiro@fujitsu.com>


On affected FUJITSU-MONAKA CPUs, the erratum may occur when an SGI is
generated by writing to ICC_SGI0R_EL1, ICC_SGI1R_EL1, or ICC_ASGI1R_EL1,
if the operation races with CPU interface processing triggered by the
arrival of a higher-priority interrupt, an update to a pending
interrupt, or a transition of the PE to the Sleep state. When the
erratum occurs, the SGI is lost and the system register write does not
complete, causing the issuing core to hang.

Guest accesses to these registers are not affected by this erratum, as
they are trapped to EL2 and handled without issuing the affected system
register write.

Work around the erratum by writing 1 to the bit corresponding to the
target SGI INTID in GICR_ISPENDR0 of each target PE's GIC Redistributor,
instead of writing to the affected system registers.

Accessing a target PE's GICR_ISPENDR0 requires its Redistributor base to
have been discovered. Affected platforms conform to SBBR, which requires
PSCI for secondary CPU boot. They therefore do not use the ACPI Parking
protocol, which sends an IPI before the secondary CPU has initialized
its Redistributor. With PSCI, a secondary CPU discovers its
Redistributor before becoming an IPI target.

[PATCH v4 3/5] perf: arm_pmu: Add workaround for FUJITSU-MONAKA
Author: Tomohiro Misono <misono.tomohiro@fujitsu.com>

FUJITSU-MONAKA Erratum E#030002 affects FUJITSU-MONAKA CPU.

On affected FUJITSU-MONAKA CPUs, after a PMU event counter is
stopped at a value just before overflow, an overflow might still
be incorrectly detected, resulting interrupt storm in some case.

For example, if the following conditions are met:
  1) Running perf to count an event in user space only
  2) The event can also occur in kernel space
  3) The counter value is set just before the overflow
     (when using the -F option, initial counter value is -1)

when the kernel is about to return to user space after enabling
the count, an overflow interrupt is incorrectly triggered by an
event that occurred in kernel space. Since the counter value is
not updated (correctly), the interrupt handler does nothing and
returns with the same condition. This leads to another wrong interrupt
and results in an interrupt storm and eventually a softlockup.

Work around the erratum by avoiding programming PMU event counters
with values within 7 counts of overflow because the counter
can increase up to 7 at a time.

Signed-off-by: Tomohiro Misono <misono.tomohiro@fujitsu.com>

---
Changes in v4:
 - Update minor wording. No code change
Changes in v3:
 - Use ERRATA_MIDR_ALL_VERSIONS macro
 - Correct the maximum number of increments at a time from 5 to 7,
   since it was found that micro-op fusion can increase the number
   of evetns counted at a time for certain events.

[PATCH v4 2/5] arm64: tlb: Add tlbi workaround for FUJITSU-MONAKA
Author: Tomohiro Misono <misono.tomohiro@fujitsu.com>

FUJITSU-MONAKA Erratum E#030001 affects FUJITSU-MONAKA CPU
when using TLBI range operations.

On affected FUJITSU-MONAKA CPUs, range-based TLBI operations
targeting a VA or IPA may fail to invalidate TLB entries when
addr[34:29] == all 1 && addr[28:0] == 0 for 512MB mappings.
The affected instructions are:
  RVA[L]E{1,2,3}*, RVAA[L]E1*, and RIPAS2[L]E1*.

Work around the erratum by dropping TLB range capability from
ID_AA64ISAR0_EL1 before detecting system capability. This means
TLB range operations are disabled on both host and guest.

Signed-off-by: Tomohiro Misono <misono.tomohiro@fujitsu.com>
