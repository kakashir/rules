[PATCH kvmtool] Makefile: Make the clean target independent of the build configuration
Author: Fuad Tabba <fuad.tabba@linux.dev>

'make clean' only removes the objects and dependency files of the
configuration it's run with ($(ARCH) and the optional libraries the
Makefile detects), so after a cross build a plain 'make clean' doesn't
remove the objects and dependency files specific to the target

Hardware-disabling the APIC through IA32_APIC_BASE turns LINT0 into the
INTR pin, so a PIC interrupt latched while LVT0 was masked becomes
injectable.  As with unmasking LVT0, KVM must request KVM_REQ_EVENT, or

=?us-ascii?Q?[PATCH_v2_1/3]_KVM:_x86:_Reevaluate_pending_interr?=
Author: Jiaming Fan <fan.jiaming@hotmail.com>


The PIC kicks vCPUs only when its output rises, and the output stays
high until the interrupt is acknowledged.  If it rises while LVT0 is
masked, unmasking LVT0 later makes the interrupt injectable, but nothing
sets KVM_REQ_EVENT, so it is never injected.  Linux guests booted with
"noapic" hit this: setup_local_APIC() masks all LVT entries through SPIV
and later writes LVT0 as unmasked ExtINT, so a PIT tick in between hangs
the guest in calibrate_delay_converge().

Request KVM_REQ_EVENT whenever an LVT entry is written unmasked.  The
trigger mode bit can't be used to filter, as the ExtINT is latched in the
PIC and Linux programs LVT0 without APIC_LVT_LEVEL_TRIGGER.

Author: Dickson Wu via B4 Relay <devnull+dickson.wu.certik.com@kernel.org>

   ? free_moved_vector+0x1b4/0x1e0

This splat is not at all unexpected, since complete_userspace_io callbacks

will call into the emulator from svm_skip_emulated_instruction().

While it's tempting to never acquire kvm->srcu for an uninitialized vCPU,
practically speaking there's no penalty to acquiring kvm->srcu "early"
as the KVM_MP_STATE_UNINITIALIZED path is a one-time thing per vCPU.  On
the other hand, seemingly innocuous helpers like kvm_apic_accept_events()
and sync_regs() can theoretically reach code that might access
SRCU-protected data structures, e.g. sync_regs() can trigger forced
existing of nested mode via kvm_vcpu_ioctl_x86_set_vcpu_events().

[PATCH 5.10.y v2 2/2] KVM: x86: Acquire kvm->srcu when handling
Author: Dickson Wu via B4 Relay <devnull+dickson.wu.certik.com@kernel.org>


commit 4bcdd831d9d01e0fb64faea50732b59b2ee88da1 upstream.

Grab kvm->srcu when processing KVM_SET_VCPU_EVENTS, as KVM will forcibly
leave nested VMX/SVM if SMM mode is being toggled, and leaving nested VMX
reads guest memory.

Note, kvm_vcpu_ioctl_x86_set_vcpu_events() can also be called from KVM_RUN
via sync_regs(), which already holds SRCU.  I.e. trying to precisely use
kvm_vcpu_srcu_read_lock() around the problematic SMM code would cause
problems.  Acquiring SRCU isn't all that expensive, so for simplicity,
grab it unconditionally for KVM_SET_VCPU_EVENTS.

[PATCH kvm-unit-tests 0/6] Test runner TLC
Author: Paolo Bonzini <pbonzini@redhat.com>

Some cleanups of the test runner, dropping some fat and preparing
for future reorganization of its functionality.  In particular I
would like to introduce a better waiver mechanism that does not
require changes to the tests.

Patches 1-2 remove the errata mechanism, as it has seen little use
and kernel version checks *in the test* are not a good way to decide
whether a test result should be waived.  While the original purpose
was to block tests that are unsafe and could cause the host to hang,
unsafe tests arguably shouldn't exist at all...

Patches 3-5 cut some of the environment functionality, specifically
not passing anymore host information to the test as they were not
read by any test.

Patch 6 finally makes unittests.cfg parsable by standard .ini syntax
parsers, such as Python's configparser.

Paolo

[PATCH v2] vhost-vdpa: skip unmapped gap in vhost_vdpa_va_map()
Author: Fang Xieyan <fangxy@xiaopeng.com>

find_vma() returns the first VMA with vm_end > uaddr; when uaddr lies
in an unmapped gap, vma->vm_start > uaddr and the offset arithmetic

	offset = (vma->vm_pgoff << PAGE_SHIFT) + uaddr - vma->vm_start;

produces an incorrect file offset, potentially wrapping in u64
arithmetic, and map_size counts the gap as part of the mapping.

Seen at runtime on v7.4-rc1: a request whose uaddr lies 0x1000
below a shared file-backed VMA starting at file offset 0 reaches
the vDPA driver's dma_map() callback as offset=0xfffffffffffff000.
Since vhost_vdpa_map() adds the range to the vhost IOTLB before
calling the backend, a successful mapping keeps an entry covering
the gap, which has no valid backing.

Skip the gap: stop if the whole remaining request is inside the gap,
otherwise shrink size, set uaddr to vm_start and advance map_iova by
the gap.  Gaps before a later VMA are left unmapped without error;
when find_vma() returns NULL because no VMA follows uaddr, the
existing -EINVAL is kept.

[PATCH v5 2/2] KVM: x86: Add support for cmpxchg16b emulation
Author: Sairaj Kodilkar <sarunkod@amd.com>

AMD and Intel both provides support for 128 bit cmpxchg operands using
cmpxchg8b/cmpxchg16b instructions (opcode 0FC7). However, kvm does not
support emulating cmpxchg16b (i.e when destination memory is 128 bit and
REX.W = 1) which causes emulation failure when QEMU guest performs a
cmpxchg16b on a memory region setup as a IO.

This failure is seen on the AMD IOMMU driver which writes 256-bit device
table entries with two 128-bit cmpxchg operations. For guests using
hardware-accelerated vIOMMU, QEMU traps device table accesses to set up
nested page tables (see [1]).  Without 128-bit cmpxchg emulation, KVM
cannot handle these traps and DTE access emulation fails.

Hence extend cmpxchg8b to perform cmpxchg16b when the destination memory
is 128 bit.Also check guest CPUID for X86_FEATURE_CX8 / X86_FEATURE_CX16
before emulating CMPXCHG8B / CMPXCHG16B, and inject #UD if userspace has
not exposed the corresponding feature. This mirrors MOVBE/RDPID handling
and ensures KVM does not emulate an instruction the VMM withheld from
the guest.

[RFC PATCH v3 2/3] target/arm/kvm: Let SYSREG_ID_AA64MMFR1_EL1_VH select an nVHE EL2
Author: Haseeb Ashraf <haseebashraf091@gmail.com>


KVM runs a nested guest with a VHE-only EL2 (HCR_EL2.E2H RES1) unless
KVM_ARM_VCPU_HAS_EL2_E2H0 is requested at KVM_ARM_VCPU_INIT time. With
that feature FEAT_VHE is hidden: ID_AA64MMFR1_EL1.VH reads 0 and
HCR_EL2.E2H is RES0. Guest hypervisors which only support nVHE, such as
Xen, can only run in the latter mode.

Do not add a dedicated machine or CPU option for it.  Derive the vCPU
init feature from the ID register field selected by the user instead:
SYSREG_ID_AA64MMFR1_EL1_VH=0 requests KVM_ARM_VCPU_HAS_EL2_E2H0.

KVM does not let userspace write ID_AA64MMFR1_EL1.VH, so the generic
"writable fields only" rule would not create the property. Expose it
explicitly when the host supports KVM_CAP_ARM_EL2_E2H0. Apply this
init-driven property before creating the scratch vCPU and use it when
initializing real vCPUs. Setting VH=0 without virtualization=on is
rejected.

KVM derives other ID register fields from the selected init mode. Re-read
ID_AA64MMFR1_EL1 and ID_AA64MMFR4_EL1 after vCPU initialization so QEMU's
cached CPU model and query-cpu-model-expansion agree with the values the
guest sees.

KVM presents a VHE-only EL2 (HCR_EL2.E2H RES1) to a nested guest unless
KVM_ARM_VCPU_HAS_EL2_E2H0 is requested at vCPU initialization. This RFC
lets an nVHE-only guest hypervisor request that mode through:

based on the rebased prerequisite commit corresponding to Eric's
arm-cpu-model-v11-rc tip e32893ddcbe643d47919f55ae33ff71be2609a77.

framework would have to introduce a separate machine or CPU property,
which was the approach rejected by Marc in v1.

    https://patchew.org/QEMU/20261030131406.461599-1-eric.auger@redhat.com/
  - Eric's v11-rc branch:

    https://patchew.org/QEMU/20261121095636.289814-1-haseebashraf091@gmail.com/

    vCPU, so full CPU-model expansion reflects the requested init mode.
  - Refresh ID_AA64MMFR1_EL1 and ID_AA64MMFR4_EL1 from KVM after vCPU
    initialization, keeping QEMU's cached model and QMP expansion in
    sync with the guest-visible registers.

expansion view; v3 fixes that without changing the guest-visible
behavior.  With VH=0, query-cpu-model-expansion now reports
ID_AA64MMFR4_EL1.NV_frac=0; with VH=1 it reports 1.

abstraction for this single case.

accepted, this nVHE functionality should wait for the framework
direction to settle. The standalone-property implementation from v1 is
available as a fallback for the implementation discussion, but I would
prefer not to make that upstream direction the default again.

TCG and HVF are unchanged by design.

[PATCH] KVM: arm64: Top up the mmu memcache on user fault for NV
Author: Lorenzo Stoakes (ARM) <ljs@kernel.org>

The S2 user fault path tops up the MMU memcache (used for page table
pre-allocation as the point at which page tables are installed may not
allocate) except when:

* It's a permission fault AND
* dirty page logging is disabled AND
* pKVM is disabled

At which point it is assumed no page table will be allocated.

However nested virtualisation adds another edge case - the mapping size of
a shadow S2 is clamped to that of the guest's own S2. If the guest
hypervisor replaces a block mapping with a table, a permission fault on the
shadow block has to be mapped at PAGE_SIZE, which requires a page table to
collapse the block into.

With the memcache empty, kvm_mmu_memory_cache_alloc() hits its
guest-triggerable WARN_ON(!nobjs) and falls back to a GFP_ATOMIC allocation
under mmu_lock, with a BUG_ON() if that fails.

Therefore, also top up the memcache for permission faults taken on a
shadow S2.

Note that dirty logging had a similar issue, addressed in commit
56fd1fc526e6 ("KVM: arm64: Top up stage-2 memcache for dirty logging
faults").

Fixes: fd276e71d1e7 ("KVM: arm64: nv: Handle shadow stage 2 page faults")
Cc: stable@vger.kernel.org
Signed-off-by: Lorenzo Stoakes (ARM) <ljs@kernel.org>

[PATCH] KVM: arm64: gic-v5: Reject an ID_BITS too large for a linear IST
Author: Fuad Tabba <fuad.tabba@linux.dev>

Without two-level IST support in the host IRS, KVM allocates a guest's
LPI IST with a single kzalloc(). The guest picks the IST's size, up to
the virtual IRS_IDR2.ID_BITS, which userspace can set as high as the
host's. With 24 ID bits the IST is at least 64MB, more than
KMALLOC_MAX_SIZE with 4K or 16K pages, and kzalloc() warns when the
guest enables the IST.

Reject an ID_BITS for which a linear IST would be larger than
KMALLOC_MAX_SIZE. This applies even for a Linux guest, which
configures a much smaller IST. Userspace writes to IRS_IDR2 are new
in this cycle, so no release has them.

Fixes: 71091136d1452 ("KVM: arm64: gic-v5: Handle userspace accesses to IRS MMIO region")
Signed-off-by: Fuad Tabba <fuad.tabba@linux.dev>
---

Notes:
    Tested on FVP, on VHE and nVHE hosts, with and without two-level IST
    support in the IRS. The vgic_v5 selftest passes. A reproducer that
    sets ID_BITS to 24 and restores an IST that wide hits the kzalloc()
    warning without this patch. With it, the IRS_IDR2 write is rejected.
    
    Based on Linux 7.4-rc3 (aebb727447640).
