New:  s390/smp: Export arch_smp_send_reschedule() for KVM
[PATCH v2 1/6] s390/smp: Export arch_smp_send_reschedule() for KVM
Author: Sean Christopherson <seanjc@google.com>

Export arch_smp_send_reschedule() so that KVM can use smp_send_reschedule()
in common "kick vCPU" code without running afoul of build issues on s390.
KVM currently uses smp_call_function_many() when kicking multiple vCPUs,
but several KVM architectures (at least arm64 and x86) kick vCPUs with IRQs
disabled.  Using SMP function calls with IRQs disabled is unsafe as it can
lead to two CPUs waiting for each other to respond to the function call,
i.e. KVM needs to use smp_send_reschedule() to avoid potential deadlock on
other architectures.

Alternatively, KVM could go out of its way to avoid smp_send_reschedule()
on s390, as KVM does when kicking a single vCPU, but given that all modules
can reach smp_send_reschedule() via kick_process(), forcing KVM to dance
around s390 adds no practical value and would add non-trivial complexity to
KVM.

Note, thanks to s390 now building kvm.ko and kvm-arm64.ko, using
EXPORT_SYMBOL_FOR_KVM doesn't Just Work.  Exporting the symbol just for KVM
would also complicate backporting the upcoming fixes to older kernels.  For
now, keep it simple.

Cc: stable@vger.kernel.org
Signed-off-by: Sean Christopherson <seanjc@google.com>

New:  vfio/type1: Skip reserved PFNs in vpfn_pages()
[PATCH 1/3] vfio/type1: Skip reserved PFNs in vpfn_pages()
Author: Aaron Lewis <aaronlewis@google.com>

vpfn_pages() is used by vfio_pin_pages_remote() and
vfio_unpin_pages_remote() to count how many pages in an IOVA range are
already accounted in dma->locked_vm via external page pinning.

However, while vfio_pin_page_external() and
vfio_iommu_unmap_unpin_reaccount() skip invalid and reserved PFNs when
accounting dma->locked_vm, vpfn_pages() counts every entry in
dma->pfn_list indiscriminately. If a reserved PFN is externally pinned,
vpfn_pages() reports it as accounted in dma->locked_vm even though it
never was.

As a result, vfio_unpin_pages_remote() inflates locked_vm when it
unwinds a failed vfio_iommu_replay(). vfio_pin_pages_remote() would
under-account for the same reason, but today it only consults
vpfn_pages() for runs that start with a non-reserved PFN. A subsequent
patch removes that restriction and relies on vpfn_pages() being exact.

Check is_invalid_reserved_pfn() in vpfn_pages() so it only counts
externally pinned PFNs that were actually accounted.

Fixes: f6c84a52cc41 ("vfio/type1: optimize vfio_pin_pages_remote()")
Fixes: d10872050ffe ("vfio/type1: batch vfio_find_vpfn() in function vfio_unpin_pages_remote()")
Signed-off-by: Aaron Lewis <aaronlewis@google.com>

New:  vfio/type1: Fix pin leaks for reserved GUP-pinned pages
[PATCH 0/3] vfio/type1: Fix pin leaks for reserved GUP-pinned pages
Author: Aaron Lewis <aaronlewis@google.com>

vfio/type1 uses PageReserved(), via is_invalid_reserved_pfn(), to guess
whether a pfn was GUP-pinned or came from a VM_PFNMAP mapping. Reserved
pfns are assumed to be PFNMAP, so they are not accounted in locked_vm
and are never unpinned.

That guess is wrong for reserved pages that GUP does pin, such as
device-dax. ZONE_DEVICE struct pages are marked PG_reserved when they
are initialized, and device-dax, unlike fsdax, can be long-term pinned.
When such memory is DMA mapped, or pinned through vfio_pin_pages(), the
pins are never dropped.

Commit f6c84a52cc41 ("vfio/type1: optimize vfio_pin_pages_remote()")
assumed that long-term GUP never returns reserved pages, so patch 2 also
drops the comment that says so.

This series records how each pfn was obtained instead of inferring it:

- Patch 1 makes vpfn_pages() count only the externally pinned pfns that
  were actually accounted. It fixes a locked_vm imbalance on its own,
  and patch 2 depends on it.
- Patch 2 tracks GUP vs PFNMAP per vfio_dma for the DMA map/unmap path.
- Patch 3 tracks it per vfio_pfn for external page pinning.

Two things to call out:

- Reserved GUP-pinned pages are now charged against RLIMIT_MEMLOCK like
  any other long-term pinned page, so mappings that used to bypass the
  limit can now fail with -ENOMEM.
- A single DMA mapping that contains both PFNMAP and GUP-pinned pfns
  still falls back to the PageReserved() heuristic on unpin, because
  type1 does not record which pfn is which. That stays correct unless
  the GUP-pinned pages are reserved. In that case their pins still leak
  and, since they are now accounted, so does their locked_vm accounting.
  Closing that needs per-range tracking.

The DMA map/unmap path (patch 2) was tested on vfio/next by adding
device-dax and /dev/mem mappings locally to vfio_dma_mapping_test:

1. 1GiB (262,144 pages) device-dax mapping, checking /proc/vmstat (after
   flushing /proc/sys/vm/stat_refresh) before and after running:

     ./vfio_dma_mapping_test -v vfio_type1v2_iommu_devdax_1gb <BDF>

   Before fix:
     nr_foll_pin_acquired: 27471 -> 289615 (+262144)
     nr_foll_pin_released: 27471 -> 27471  (+0, leaked)

   With fix:
     nr_foll_pin_acquired: 18786 -> 280930 (+262144)
     nr_foll_pin_released: 18786 -> 280930 (+262144)

2. /dev/mem (VM_PFNMAP) mapping of a reserved physical page with a valid
   struct page (memmap=4M$0x340000000), confirming DMA map/unmap still
   succeeds with +0/+0 pin deltas and no unpin warnings.

If desirable, I can add the test updates to this series, though the
changes depend on host-specific device-dax paths and reserved physical
addresses.

New:  ARM64 PMU Partitioning
[PATCH v10 00/33] ARM64 PMU Partitioning
Author: Colton Lewis <coltonlewis@google.com>

This series creates a new PMU scheme on ARM, a partitioned PMU that
allows reserving a subset of counters for more direct guest access,
significantly reducing overhead. More details, including performance
benchmarks, can be read in the v1 cover letter linked below.

PMU partitioning is controlled via the KVM API using
`KVM_ARM_VCPU_PMU_V3_ENABLE_PARTITION` and
`KVM_ARM_VCPU_PMU_V3_SET_NR_COUNTERS` vCPU device attributes. When
partitioning is enabled for a VM, userspace must explicitly configure a
guest event counter count strictly less than the maximum general-purpose
counters implemented by the PMU (leaving at least one general-purpose
counter for the host) prior to calling `KVM_ARM_VCPU_PMU_V3_INIT`. The
number of general-purpose counters implemented by each host PMU is
exposed in sysfs at
`/sys/bus/event_source/devices/<pmu>/caps/num_counters`. A QEMU patch
demonstrating how to use the uAPI is sent separately.

An overview of what this series accomplishes was presented at KVM
Forum 2025. Slides [1] and video [2] are linked below.

v10:

* Rebase on top of v7.4-rc3.

* Add nested virtualization (`FEAT_NV` / `FEAT_NV2`) support covering
  both an Emulated L2 PMU (`vHPMN == N_L1`, `TPM == 1`, where L1 keeps
  all `N_L1` counters and emulates L2 via L1 `perf` events) and a
  Sub-partitioned L2 PMU (`vHPMN < N_L1`, `TPM == 0`, creating a
  three-way split across `0..vHPMN-1` for L2, `vHPMN..N_L1-1` for L1,
  and `N_L1..N_phys-1` for L0) (Oliver Upton). Because ARM64 provides
  only a single physical `MDCR_EL2.HPMN` field, hardware can split the
  PMU into two counter ranges at a time rather than three. Key design
  decisions and supporting changes:

  - Keep physical `MDCR_EL2.HPMN = N_L1` at all times (`vHPMN` boundary
    and event filtering): Lowering physical `HPMN` to `vHPMN` while
    running L2 was considered and rejected because it would move L1's
    hypervisor counters (`vHPMN..N_L1-1`) into the same physical
    `>= HPMN` range as L0's host counters (`N_L1..N_phys-1`), where a
    single set of physical `MDCR_EL2.{HPME,HPMD,HLP}` bits governs both
    and breaks host/guest isolation; it would also fail for
    `vHPMN == 0` on hardware without `FEAT_HPMN0`. Instead, when
    `vHPMN < N_L1`, L0 keeps physical `HPMN = N_L1` and sets
    `MDCR_EL2.{TPM,TPMCR}` in L2, forwarding `vHPMN..N_L1-1` traps to
    L1 and handling `0..vHPMN-1` plus `PMCCNTR_EL0` in L0 directly
    against physical registers. This preserves L0 isolation and
    supports `vHPMN == 0` on all hardware; L2 events still count
    directly in hardware without L0 `perf_event` scheduling, at the
    cost of trapping L2 PMU accesses to L0 and rewriting per-counter
    filter registers on `L1 <-> L2` transitions. In L1
    (`is_hyp_ctxt()`), L0 emulates `vHPMN`, `vMDCR_EL2.HPMD`, and
    `vMDCR_EL2.HCCD` via `PMEVTYPER<n>_EL0` and `PMCCFILTR_EL0`.

  - Dynamically multiplex `vPMCR_EL0.E` and `vMDCR_EL2.HPME`: Because
    both `0..vHPMN-1` and `vHPMN..N_L1-1` sit below physical
    `HPMN = N_L1`, hardware gates both with physical `PMCR_EL0.E`.
    Rather than unconditionally trapping `PMCR_EL0` and `PMCNTEN*` for
    all `FEAT_NV` VMs (which would penalize Emulated L2 PMU where
    `vHPMN == N_L1`), L0 dynamically enables `MDCR_EL2.TPMCR` and
    `HDFG{R,W}TR_EL2.PMCNTEN` only when `vHPMN < N_L1`. L0 keeps
    architectural `PMCR_EL0` and `PMCNTENSET_EL0` in memory, sets
    physical `PMCR_EL0.E` to `vPMCR_EL0.E || vMDCR_EL2.HPME`, masks
    disabled sub-ranges out of physical `PMCNTENSET_EL0`, and gates
    overflow delivery per domain. Trapped `PMSWINC_EL0` writes (also
    enabled via `HDFGWTR_EL2` when `vHPMN < N_L1`) flush live registers
    and reuse `kvm_pmu_software_increment()` to prevent cross-partition
    chaining.

  - Bias 32-bit counters on mismatched `vPMCR_EL0.LP != vMDCR_EL2.HLP`
    (`FEAT_PMUv3p5`): When `LP == HLP`, physical `PMCR_EL0.LP` matches
    both domains directly and `PMEVCNTR<n>_EL0` stays untrapped in L1.
    When `vHPMN < N_L1` and `LP != HLP`, rather than ignoring the
    mismatch (breaking 32-bit overflow interrupts) or falling back to
    `perf_event` emulation mid-flight (requiring reservation teardown),
    L0 forces physical `PMCR_EL0.LP = 1` (64-bit overflow), dynamically
    traps `HDFG{R,W}TR_EL2.PMEVCNTRn_EL0`, and biases counters in the
    32-bit sub-range `2^32` events below 64-bit overflow
    (`0xffffffff00000000 | low32`) while tracking their upper-32-bit
    offsets and re-biasing outside interrupt/NMI context. Because
    `HDFG{R,W}TR_EL2.PMEVCNTRn_EL0` is a single trap bit covering all
    event counters (`0..30`), L1 counter reads/writes trap across both
    sub-ranges while `LP != HLP`, with zero overhead when `LP == HLP`.

  - Baseline nested support (both Emulated and Sub-partitioned L2):
    separate implemented and accessible counter masks by using
    `nr_pmu_counters` directly in `kvm_pmu_implemented_counter_mask()`,
    masking trapped guest reads of `PMCNTEN*`, `PMINTEN*`, and `PMOVS*`
    with `kvm_pmu_accessible_counter_mask()`, and ignoring
    `MDCR_EL2.HPMN` in userspace `KVM_GET_ONE_REG` / `KVM_SET_ONE_REG`
    (`set_pmreg()`, `get_pmreg()`, `get_pmcr()`) so saving/restoring a
    nested vCPU paused below EL2 preserves all VM-implemented counters
    and true `PMCR_EL0.N`; preserve host counter reservations across
    `IN_NESTED_ERET` / `IN_NESTED_EXCEPTION` transitions to avoid host
    `perf` reschedules on emulated L2 traps; read live hardware
    `PMSELR_EL0` in `check_mdcr_hpmn()` when untrapped; and forward
    fine-grained traps for selector-indexed `PMXEVTYPER_EL0` and
    `PMXEVCNTR_EL0` to L1.

* Expose the number of general-purpose counters implemented by the PMU
  in sysfs under `/sys/bus/event_source/devices/<pmu>/caps/num_counters`
  so userspace VMMs can query host PMU counter capacity when configuring
  a partitioned PMU (James Clark).

* Make `__vcpu_rmw_sys_reg()` atomic on the local CPU using
  `try_cmpxchg_local()` to prevent read-modify-write races with GICv3
  pseudo-NMI PMU interrupt handlers (`kvm_pmu_handle_guest_irq()`),
  which are not masked by `local_irq_save()` (Sashiko AI Review).

* Construct `mdcr_el2` in a local variable before assigning
  `vcpu->arch.mdcr_el2` once in `kvm_arm_setup_mdcr_el2()`, and mask
  GICv3 pseudo-NMIs (`local_daif_save()`) across hardware PMU context
  switches and `MDCR_EL2` updates (Sashiko AI Review).

* Prioritize kernel-owned pinned event groups (`is_kernel_event()`)
  ahead of userspace pinned events in `perf_event_groups_cmp()` /
  `perf_less_group_idx()` so kernel-owned per-CPU pinned events (such as
  the hardlockup NMI watchdog if toggled at runtime) are scheduled before
  userspace pinned events when `perf_pmu_resched_update()` reschedules
  events out of guest-reserved counters (James Clark, Sashiko AI Review).

* Move `kvm_vcpu_reload_pmu()` from `arch/arm64/kvm/pmu-emul.c` to
  `arch/arm64/kvm/pmu.c` in `KVM: arm64: Reorganize PMU functions`.

* Add `kvm_pmu_is_partitioned()`, `kvm_pmu_guest_counter_mask()`,
  `kvm_pmu_handle_guest_irq()`, `kvm_pmu_host_start()`, and
  `kvm_pmu_host_stop()` stubs to `arch/arm/include/asm/arm_pmuv3.h` to
  fix 32-bit `ARCH=arm` builds (kernel test robot).

* Allow identical VM-wide PMU device attributes
  (`KVM_ARM_VCPU_PMU_V3_SET_PMU`, `KVM_ARM_VCPU_PMU_V3_SET_NR_COUNTERS`,
  and `KVM_ARM_VCPU_PMU_V3_ENABLE_PARTITION`) to be applied across all
  vCPUs when userspace initializes vCPUs sequentially (`CPU_FOREACH`),
  validate `kvm_arm_pmu_part_hpmn(n) < max_counters` (requiring
  `max_counters >= 2` for `n == 0` without `FEAT_HPMN0`), and restrict
  `kvm->arch.supported_cpus` to `arm_pmu->supported_cpus` when
  partitioning is enabled.

* Centralize partitioned PMU hardware register dispatch under
  `kvm_pmu_direct_reg_read()` / `kvm_pmu_direct_reg_write()` with
  preemption disabled (`kvm_pmu_part_on_cpu()`), guard lazy ownership
  transitions in `kvm_pmu_part_overflow_status()` with
  `scoped_guard(preempt)`, avoid matching `reset_unknown()` poison bits on
  `PMCNTENSET_EL0` / `PMINTENSET_EL1` during `KVM_REQ_RELOAD_PMU`, and
  schedule `KVM_REQ_RELOAD_PMU` on `KVM_SET_ONE_REG` writes so
  `vcpu_put()` does not overwrite userspace register writes (Sashiko AI
  Review).

* Support configuring 0 guest event counters (cycle counter only) on
  Partitioned PMU hosts without `FEAT_HPMN0` whenever `max_counters >= 2`.
  Writing `MDCR_EL2.HPMN = 0` without `FEAT_HPMN0` is architecturally
  `CONSTRAINED UNPREDICTABLE`, which would otherwise prevent userspace
  from creating a cycle-counter-only partitioned guest on CPUs lacking
  `FEAT_HPMN0`. Instead, KVM programs physical `MDCR_EL2.HPMN = 1` via
  `kvm_arm_pmu_part_hpmn()`, reserves and quiesces physical counter 0
  alongside `PMCCNTR_EL0` so host perf continues using counters `1..N-1`,
  keeps `MDCR_EL2.TPMCR = 1` so trapped `PMCR_EL0` reads report `N == 0`,
  and enables fine-grained traps on `PMEVCNTRn_EL0`, `PMCNTEN`,
  `PMINTEN`, and `PMSWINC_EL0` so counter 0 stays completely hidden
  (`UNDEFINED` / RAZ / WI) while `PMCCNTR_EL0` remains untrapped on

New:  KVM: arm64: nv: Fix guest stage-2 mapping leak on sub-block unmap
[PATCH] KVM: arm64: nv: Fix guest stage-2 mapping leak on sub-block unmap
Author: Colton Lewis <coltonlewis@google.com>

When a shadow stage-2 block mapping (for example, 2M at PMD level) is
partially invalidated by a smaller guest unmap such as a 4K TLBI
IPAS2E1IS, kvm_pgtable_stage2_unmap() shatters and clears the entire
block descriptor in mmu->pgt. However, kvm_remove_guest_s2_mappings()
only removes a struct kvm_guest_s2_mapping node when its entire
[nested_start, nested.last] span lies within the unmap range. As a
result, every sub-block invalidation followed by a re-fault leaks a
stale block-sized tracking node in mmu->guest_s2_mappings and
kvm->arch.mmu.guest_s2_mappings until the shadow MMU is destroyed,
allowing an L1 guest to grow host kernel memory and degrade subsequent
TLBI IPAS2E1IS walks to O(N) under write_lock(&kvm->mmu_lock).

Conversely, unconditionally removing any overlapping tracking node on a
sub-block unmap would be unsafe when a shadow block mapping has been
split into a child table (such as on a page-granule fault under dirty
logging or a racing shared walk returning -EAGAIN), because sibling
sub-page PTEs outside the unmapped range remain live in mmu->pgt and
still rely on the block-sized tracking node for host MMU notifier
unmaps.

Since stage2_unmap_walker() unlinks empty child page tables in
KVM_PGTABLE_WALK_TABLE_POST as soon as their last valid entry is
cleared, check mmu->pgt via kvm_pgtable_get_leaf() on partial-overlap
candidates: when no valid entry or split sub-table remains at or below
the recorded mapping granule (!kvm_pte_valid(pte) &&
kvm_granule_size(level) >= map_size), remove and free the tracking node;
otherwise retain it to cover surviving split sub-entries.

In addition, suppress exact-match duplicate insertions in
kvm_record_guest_s2_mapping() when concurrent faults or -EAGAIN retries
record an identical (nested, canonical) range on the same shadow MMU.

====

fork() now copies file THPs instead of leaving them to a refault, which
costs fork() a reference, an rmap update and a counter per huge PMD and
saves the child a fault per huge PMD it touches. fork() of a process
with 4 GB of shmem THPs mapped MAP_PRIVATE and an anon_vma on the VMA,
x86_64 bare metal with 4 NUMA nodes, the benchmark bound to node 0,
both kernels v7.4-rc1 (v5) with the same config, medians of 2000 forks,
range over the rounds; the exec is of /bin/true:

  +-----------------+------------+-----------------+--------------+
  | kernel          | fork()     | child reads all | fork()+exec  |
  +-----------------+------------+-----------------+--------------+
  | v7.4-rc1        | 135-141 us | 3820-4036 us    | 559-567 us   |
  | v7.4-rc1+series | 429-440 us | 1007-1036 us    | 1190-1226 us |
  +-----------------+------------+-----------------+--------------+

A child that execs right away, or touches little, pays about 0.3 us per
huge PMD for the copy and the teardown. One that faults a PMD in itself
pays about 1.8 us for it, so the copy wins once the child touches more
than about a sixth of them.

Only a narrow case pays it, a file THP that is:

- mapped MAP_PRIVATE;
- in a VMA written to at least once, so it has an anon_vma;
- a PMD-sized folio in the page cache, mapped by one PMD;
- itself never written to.

For example:

- a big data file mapped MAP_PRIVATE that is mostly read and patched
  in a few places;
- a private mapping of a memfd or tmpfs file.

New:  iommu/riscv: Add nested translation (vIOMMU) support
[RFC PATCH v3 00/10] iommu/riscv: Add nested translation (vIOMMU) support
Author: Gong Shuai <gong.shuai@sanechips.com.cn>

An IOMMU allows an OS to restrict device DMA to the intended memory.
It also gives device drivers an IOVA space that is independent of the
physical memory layout. A guest OS needs these capabilities when it
directly controls a device, just as a native OS does.

Exposing a vIOMMU to the guest is not enough for a passthrough device.
DMA from the physical device must also obey the mappings that the guest
creates through its vIOMMU. Otherwise the guest cannot use its IOMMU to
protect guest memory or provide IOVA mappings for the assigned device.

The RISC-V IOMMU architecture supports this usage with two-stage
translation. Stage 1 applies the guest's vIOMMU configuration. Stage 2
is controlled by the hypervisor and restricts the device to memory
assigned to the VM. This division gives the guest control of its own
DMA mappings without allowing the device to escape the VM.

The Linux RISC-V IOMMU driver does not yet support this model through
iommufd. A VMM cannot provide the guest stage 1 configuration to the
physical IOMMU or synchronize its translation caches after the guest
updates its page tables. This series adds the missing nested
translation support so device passthrough can work with a guest that
uses its own vIOMMU.

This is an RFC and comments on the design are welcome.

Patch organization

Patch 1 prepares device context handling for nested translation.
Patches 2 and 3 add the uAPI for nested allocation and cache
invalidation.
Patches 4 to 6 add the vIOMMU, nested domains and cache invalidation.
Patches 7 and 8 allow a VMM to discover the physical IOMMU
capabilities.
Patch 9 adds nested device attachment.
Patch 10 fixes bond unlink so it invalidates the correct address space.

Dependencies

The series applies on top of iommu/master at commit 9f9dc924a01e,
together with the RISC-V hardware dirty tracking series v7 [1] and
its dependencies.

Testing

The test requires MSI support, but the related dependencies are still
under review, so the interrupt changes are not included in this series.
The test needs the MSI remapping series v6 [2], the irqbypass series
RFC v3 [3] and a KVM client from Andrew's github repo [4]. A branch with
the complete test stack, including the additional nested interrupt
support, is available at github repo [5].

The host is a RISC-V machine whose physical IOMMU is provided by an outer
QEMU riscv-iommu model, which implements both translation stages. An NVMe
controller under it is bound to vfio-pci and passed through to the guest.
The guest is started by a QEMU built with the accel series [6][7], which
exposes a first stage IOMMU to the guest and leaves the second stage to
the host IOMMU. For simplicity the guest runs the same kernel as the host,
and inside the guest it mainly uses the normal IOMMU driver and the NVMe
driver.

The layering of the setup is

Host HW, a RISC-V virt machine from latest QEMU(v11.1.3), with a
riscv-iommu model that implements two stage translation and with the NVMe
controller

    Host OS, the kernel with this series
      riscv-iommu driver, second stage and MSI table vfio-pci and KVM

        Guest HW, QEMU with the accel series [6][7]
          riscv-iommu accel, first stage only

            Guest OS, the same kernel as the host
              riscv-iommu driver, NVMe driver

A DMA address from the NVMe controller is translated by the guest first
stage and then by the host second stage on the physical IOMMU. An MSI
address is translated by the guest first stage into a guest IMSIC address,
which the flat MSI table then resolves straight to the interrupt file of
the target vCPU, instead of walking the second stage.

    DMA    device --> guest first stage --> host second stage --> RAM
    MSI    device --> guest first stage --> MSI table --> VS-file

The host was started with

$HOST_QEMU \
  -M virt,aia=aplic-imsic,aia-guests=7,iommu-sys=on \
  -cpu rva23s64,sv48=on -nographic \
  -smp 16 -m 16G \
  -kernel $HOST_KERNEL \
  -append "root=/dev/vda rw earlycon=sbi console=ttyS0 iommufd.allow_unsafe_interrupts=1" \
  -drive file=$HOST_ROOTFS,if=none,id=d0,format=qcow2 -device virtio-blk-device,drive=d0 \
  -device pcie-root-port,id=port0,chassis=0,slot=0,addr=3.0 \
  -drive file=fake-nvme-disk.img,if=none,id=nvme0,format=qcow2 \
  -device nvme,drive=nvme0,serial=deadbeef,bus=port0,addr=0.0

and the guest with

$GUEST_QEMU \
  -machine virt,accel=kvm,aia=aplic-imsic,aia-guests=5 \
  -cpu host -nographic \
  -smp 4 -m 4G \
  -object iommufd,id=iommufd0 \
  -device riscv-iommu-pci,addr=1.0,s-stage=on,g-stage=off,accel=on \
  -device vfio-pci,host=0000:01:00.0,iommufd=iommufd0 \
  -kernel $GUEST_KERNEL \
  -append "root=/dev/vda rw earlycon=sbi console=ttyS0 iommu.passthrough=0 iommu.strict=1" \
  -drive file=$GUEST_ROOTFS,if=none,id=d0,format=qcow2 -device virtio-blk-device,drive=d0

Correctness was checked by running fio with verification enabled against
the passed through disk.

Known limitations and future work

- PASID and the process directory table are not supported.
- The ATS, PRI and T2GPA fields are validated on the nested domain, but
  ATS.INVAL and the PRI queue are not forwarded.
- One single physical IOMMU instance on host is assumed for now.
- The new uAPI types have no selftest coverage yet.

New:  KVM: s390: vsie: Do not overwrite guest 3 state on early validity icpt
[PATCH v1 1/2] KVM: s390: vsie: Do not overwrite guest 3 state on early validity icpt
Author: Gautam Gala <ggala@linux.ibm.com>

shadow_scb() calls prepare_cpuflags() first, which can reject the SCB
provided by guest 2 with a validity interception. This happens before
the guest state (gpsw, gg14, gg15, gcr, cputm, ckc, todpr, pp) and the
control fields (gbea, fpf) are copied from the original SCB into the
shadow SCB.

The error path still calls unshadow_scb(), which copies that state from
the shadow SCB back into the original one. The shadow SCB does not hold
guest 3 state at this point:

 - For a new or recycled vsie page, get_vsie_page() has cleared the
   shadow SCB, so the guest 3 state in the guest 2 SCB is overwritten
   with zeroes.
 - For a cached vsie page that is looked up again by SCB address, the
   shadow SCB still holds the state from the end of the previous run,
   so the current guest 3 state is replaced by the old one.

No guest 3 instruction ran, yet guest 2 sees its guest 3 state (PSW,
GRs, CRs, timers) modified. unshadow_scb() also clears FPF_BPBC if
facility 82 is available, because fpf was cleared in the shadow SCB
just before, and copies back a stale ihcpu.

The SCB and the validity condition are controlled by guest 2, so this
is a correctness problem for guest 2 only and does not cross a guest or
host boundary.

Only the interception data needs to be passed on in this case. Add
unshadow_icpt() for that and use it from unshadow_scb() and from the
prepare_cpuflags() failure path, which now returns directly. The other
failure paths of shadow_scb() are reached after the guest state has
been copied and keep using unshadow_scb().

On a cached vsie page, the interception data in the shadow SCB still
holds the values of the previous run. set_validity_icpt() writes ipa,
ipb and icptcode, but not icptstatus, so a stale icptstatus would be
passed on together with the new validity interception. Also, it is not
defined what SIE stores in icptstatus, ipa and ipb when it exits without
an interception, so they must not be relied upon to be zero or unchanged.
Clear them together with icptcode when the shadow SCB is reused,
so that no stale interception data is passed on to guest 2.

New:  x86/virt/seamldr: Support large TDX module binaries
[PATCH v3 1/2] x86/virt/seamldr: Support large TDX module binaries
Author: Chao Gao <chao.gao@intel.com>

TDX module binaries are limited to just under 2MB. The binary is handed
to P-SEAMLDR as a list of page physical addresses in
'struct seamldr_params', and the list must fit in a single 4KB page
along with a few other fields.

TDX modules are gaining features and are about to outgrow that limit.

The P-SEAMLDR ABI was extended to let the list continue onto more 4KB
pages. The last u64 of each page holds the physical address of the next
page, chaining the pages together.

Grow module_pages_pa_list[] so that 'struct seamldr_params' spans 16
pages, and chain the pages together in populate_pa_list().

Each page uses its last entry for chaining, so the maximum module page
count is the array size minus one entry per page. The user-supplied
image is checked against this count.

The 16-page size is somewhat arbitrary. It fits modules of up to about
32MB, far above the roughly 2MB of current modules. It wastes 60KB for
today's modules, which is fine because the memory is freed right after
the update.

Do not query P-SEAMLDR for chaining support. Userspace selects the
update image and is responsible for ensuring the module is compatible
with P-SEAMLDR.

A 496-page module (the old maximum) used to fit in a single page. Now
the last entry of that page is used for chaining, so the final address
moves to a second page and the module requires chaining support. Do not
special-case this size to make it work with a P-SEAMLDR without
chaining support. No released module has exactly 496 pages, so nothing
breaks. Leave it to userspace to ensure any future 496-page module is
paired with a P-SEAMLDR that supports chaining, as with larger modules.

This series is a follow-up to the TDX module update series. As thanks
for merging that series, we agreed to take on the TDX metadata cleanup [1].
With the cleanup converging, we are starting on this work and expect it
to be merged after the cleanup.

Today a TDX module binary can be at most 496 pages and its sigstruct at
most one page. Both limits come from the P-SEAMLDR ABI.

TDX modules are outgrowing them. A post-quantum signature algorithm
pushes the sigstruct past 4KB, and new module features push the binary
past 496 pages. The P-SEAMLDR ABI was extended for both.

The kernel rejects any image over these limits. TDX modules for Diamond
Rapids exceed them, so without this series, TDX module updates fail on
Diamond Rapids. This series is all that is needed to make them work.

The image format that userspace uploads ('struct tdx_image') is generic
enough and needs no change.

== AI Usage ==

AI was used under supervision to review code and refine commit messages.

== Testing ==

Tested on a Diamond Rapids system. Updates with a module larger than 2MB
and an 8KB sigstruct work, which exercises both the chained page list
and version 1 of 'struct seamldr_params'. TDs keep running across
updates.

== P-SEAMLDR ABI changes ==

The public P-SEAMLDR specification will be updated to document these
ABI extensions. Until then, here are the changes to
'struct seamldr_params' that this series relies on:

- VERSION (offset 0) may now be 1. Version 1 support is enumerated by
bit 8 of SEAMLDR_FEATURES0.

- SIGSTRUCT_PA_1..3 (offsets 16, 24 and 32) are new. In version 1, they
hold the addresses of the second to fourth sigstruct pages, or 0 if
the sigstruct does not reach that page. In version 0, they must be 0.

- RESERVED shrinks from 104 to 80 bytes and now starts at offset 40.

- MOD_PAGES_PA_LIST (offset 128) can be chained. For a module over 495
pages, its last entry points to a 4KB page holding up to 511 more
addresses. Each such page uses its last entry to point to the next
page, until all module pages are listed. Chaining support is enumerated
by bit 11 of SEAMLDR_FEATURES0.

New:  iommufd: Recommended reservations query and opt-in IOAS reservation
[PATCH v7 0/3] iommufd: Recommended reservations query and opt-in IOAS reservation
Author: Guanghui Feng <guanghuifeng@linux.alibaba.com>

This series lets userspace learn which IOVA ranges the kernel
recommends avoiding for a device, and optionally feed them back so
the IOAS allocator enforces them.

The motivating case is a PCI device behind a PCIe switch: DMA using
IOVAs that fall inside the host bridge MMIO windows may be misrouted
as peer-to-peer traffic instead of reaching the root complex for IOMMU
translation.  The DMA IOVA layer already avoids these windows
internally, but passthrough userspace had no way to learn about them.
Per commit cd2c9fcf5c66 ("iommu/dma: Move PCI window region reservation back into dma specific path.")
this information must not be forced through the IOMMU reserved-region
API, so the series is fully opt-in:

  Patch 1 adds iommu_for_each_pci_mmio_window(), a callback-based
  iterator in the IOMMU core, and refactors dma-iommu.c to share it.

  Patch 2 adds IOMMU_GET_RECOMMENDED_RESERVATIONS, a per-device query
  returning recommended ranges (currently PCI host bridge MMIO
  windows) as struct iommu_iova_range entries.  Advisory only.

  Patch 3 adds IOMMU_IOAS_RESERVE_IOVAS, letting userspace send
  chosen ranges back in to restrict the IOAS allocator: reserved
  ranges disappear from IOMMU_IOAS_IOVA_RANGES and are rejected by
  mapping.  Overlapping reservations are permitted, so the same
  ranges recommended for several devices behind one host bridge can
  each be reserved independently.

Typical flow: bind device -> query recommendations -> reserve chosen
ranges -> map.  Userspace that ignores the new ioctls sees no
behaviour change.

New:  ARM64 PMU Partitioning
[PATCH v10 00/33] ARM64 PMU Partitioning
Author: Colton Lewis <coltonlewis@google.com>

This series creates a new PMU scheme on ARM, a partitioned PMU that
allows reserving a subset of counters for more direct guest access,
significantly reducing overhead. More details, including performance
benchmarks, can be read in the v1 cover letter linked below.

PMU partitioning is controlled via the KVM API using
`KVM_ARM_VCPU_PMU_V3_ENABLE_PARTITION` and
`KVM_ARM_VCPU_PMU_V3_SET_NR_COUNTERS` vCPU device attributes. When
partitioning is enabled for a VM, userspace must explicitly configure a
guest event counter count strictly less than the maximum general-purpose
counters implemented by the PMU (leaving at least one general-purpose
counter for the host) prior to calling `KVM_ARM_VCPU_PMU_V3_INIT`. The
number of general-purpose counters implemented by each host PMU is
exposed in sysfs at
`/sys/bus/event_source/devices/<pmu>/caps/num_counters`. A QEMU patch
demonstrating how to use the uAPI is sent separately.

An overview of what this series accomplishes was presented at KVM
Forum 2025. Slides [1] and video [2] are linked below.

v10:

* Rebase on top of v7.4-rc3.

* Add nested virtualization (`FEAT_NV` / `FEAT_NV2`) support covering
  both an Emulated L2 PMU (`vHPMN == N_L1`, `TPM == 1`, where L1 keeps
  all `N_L1` counters and emulates L2 via L1 `perf` events) and a
  Sub-partitioned L2 PMU (`vHPMN < N_L1`, `TPM == 0`, creating a
  three-way split across `0..vHPMN-1` for L2, `vHPMN..N_L1-1` for L1,
  and `N_L1..N_phys-1` for L0) (Oliver Upton). Because ARM64 provides
  only a single physical `MDCR_EL2.HPMN` field, hardware can split the
  PMU into two counter ranges at a time rather than three. Key design
  decisions and supporting changes:

  - Keep physical `MDCR_EL2.HPMN = N_L1` at all times (`vHPMN` boundary
    and event filtering): Lowering physical `HPMN` to `vHPMN` while
    running L2 was considered and rejected because it would move L1's
    hypervisor counters (`vHPMN..N_L1-1`) into the same physical
    `>= HPMN` range as L0's host counters (`N_L1..N_phys-1`), where a
    single set of physical `MDCR_EL2.{HPME,HPMD,HLP}` bits governs both
    and breaks host/guest isolation; it would also fail for
    `vHPMN == 0` on hardware without `FEAT_HPMN0`. Instead, when
    `vHPMN < N_L1`, L0 keeps physical `HPMN = N_L1` and sets
    `MDCR_EL2.{TPM,TPMCR}` in L2, forwarding `vHPMN..N_L1-1` traps to
    L1 and handling `0..vHPMN-1` plus `PMCCNTR_EL0` in L0 directly
    against physical registers. This preserves L0 isolation and
    supports `vHPMN == 0` on all hardware; L2 events still count
    directly in hardware without L0 `perf_event` scheduling, at the
    cost of trapping L2 PMU accesses to L0 and rewriting per-counter
    filter registers on `L1 <-> L2` transitions. In L1
    (`is_hyp_ctxt()`), L0 emulates `vHPMN`, `vMDCR_EL2.HPMD`, and
    `vMDCR_EL2.HCCD` via `PMEVTYPER<n>_EL0` and `PMCCFILTR_EL0`.

  - Dynamically multiplex `vPMCR_EL0.E` and `vMDCR_EL2.HPME`: Because
    both `0..vHPMN-1` and `vHPMN..N_L1-1` sit below physical
    `HPMN = N_L1`, hardware gates both with physical `PMCR_EL0.E`.
    Rather than unconditionally trapping `PMCR_EL0` and `PMCNTEN*` for
    all `FEAT_NV` VMs (which would penalize Emulated L2 PMU where
    `vHPMN == N_L1`), L0 dynamically enables `MDCR_EL2.TPMCR` and
    `HDFG{R,W}TR_EL2.PMCNTEN` only when `vHPMN < N_L1`. L0 keeps
    architectural `PMCR_EL0` and `PMCNTENSET_EL0` in memory, sets
    physical `PMCR_EL0.E` to `vPMCR_EL0.E || vMDCR_EL2.HPME`, masks
    disabled sub-ranges out of physical `PMCNTENSET_EL0`, and gates
    overflow delivery per domain. Trapped `PMSWINC_EL0` writes (also
    enabled via `HDFGWTR_EL2` when `vHPMN < N_L1`) flush live registers
    and reuse `kvm_pmu_software_increment()` to prevent cross-partition
    chaining.

  - Bias 32-bit counters on mismatched `vPMCR_EL0.LP != vMDCR_EL2.HLP`
    (`FEAT_PMUv3p5`): When `LP == HLP`, physical `PMCR_EL0.LP` matches
    both domains directly and `PMEVCNTR<n>_EL0` stays untrapped in L1.
    When `vHPMN < N_L1` and `LP != HLP`, rather than ignoring the
    mismatch (breaking 32-bit overflow interrupts) or falling back to
    `perf_event` emulation mid-flight (requiring reservation teardown),
    L0 forces physical `PMCR_EL0.LP = 1` (64-bit overflow), dynamically
    traps `HDFG{R,W}TR_EL2.PMEVCNTRn_EL0`, and biases counters in the
    32-bit sub-range `2^32` events below 64-bit overflow
    (`0xffffffff00000000 | low32`) while tracking their upper-32-bit
    offsets and re-biasing outside interrupt/NMI context. Because
    `HDFG{R,W}TR_EL2.PMEVCNTRn_EL0` is a single trap bit covering all
    event counters (`0..30`), L1 counter reads/writes trap across both
    sub-ranges while `LP != HLP`, with zero overhead when `LP == HLP`.

  - Baseline nested support (both Emulated and Sub-partitioned L2):
    separate implemented and accessible counter masks by using
    `nr_pmu_counters` directly in `kvm_pmu_implemented_counter_mask()`,
    masking trapped guest reads of `PMCNTEN*`, `PMINTEN*`, and `PMOVS*`
    with `kvm_pmu_accessible_counter_mask()`, and ignoring
    `MDCR_EL2.HPMN` in userspace `KVM_GET_ONE_REG` / `KVM_SET_ONE_REG`
    (`set_pmreg()`, `get_pmreg()`, `get_pmcr()`) so saving/restoring a
    nested vCPU paused below EL2 preserves all VM-implemented counters
    and true `PMCR_EL0.N`; preserve host counter reservations across
    `IN_NESTED_ERET` / `IN_NESTED_EXCEPTION` transitions to avoid host
    `perf` reschedules on emulated L2 traps; read live hardware
    `PMSELR_EL0` in `check_mdcr_hpmn()` when untrapped; and forward
    fine-grained traps for selector-indexed `PMXEVTYPER_EL0` and
    `PMXEVCNTR_EL0` to L1.

* Expose the number of general-purpose counters implemented by the PMU
  in sysfs under `/sys/bus/event_source/devices/<pmu>/caps/num_counters`
  so userspace VMMs can query host PMU counter capacity when configuring

New:  KVM: arm64: nv: Fix guest stage-2 mapping leak on sub-block unmap
[PATCH] KVM: arm64: nv: Fix guest stage-2 mapping leak on sub-block unmap
Author: Colton Lewis <coltonlewis@google.com>

When a shadow stage-2 block mapping (for example, 2M at PMD level) is
partially invalidated by a smaller guest unmap such as a 4K TLBI
IPAS2E1IS, kvm_pgtable_stage2_unmap() shatters and clears the entire
block descriptor in mmu->pgt. However, kvm_remove_guest_s2_mappings()
only removes a struct kvm_guest_s2_mapping node when its entire
[nested_start, nested.last] span lies within the unmap range. As a
result, every sub-block invalidation followed by a re-fault leaks a
stale block-sized tracking node in mmu->guest_s2_mappings and
kvm->arch.mmu.guest_s2_mappings until the shadow MMU is destroyed,
allowing an L1 guest to grow host kernel memory and degrade subsequent
TLBI IPAS2E1IS walks to O(N) under write_lock(&kvm->mmu_lock).

Conversely, unconditionally removing any overlapping tracking node on a
sub-block unmap would be unsafe when a shadow block mapping has been
split into a child table (such as on a page-granule fault under dirty
logging or a racing shared walk returning -EAGAIN), because sibling
sub-page PTEs outside the unmapped range remain live in mmu->pgt and
still rely on the block-sized tracking node for host MMU notifier
unmaps.

Since stage2_unmap_walker() unlinks empty child page tables in
KVM_PGTABLE_WALK_TABLE_POST as soon as their last valid entry is
cleared, check mmu->pgt via kvm_pgtable_get_leaf() on partial-overlap
candidates: when no valid entry or split sub-table remains at or below
the recorded mapping granule (!kvm_pte_valid(pte) &&
kvm_granule_size(level) >= map_size), remove and free the tracking node;
otherwise retain it to cover surviving split sub-entries.

In addition, suppress exact-match duplicate insertions in
kvm_record_guest_s2_mapping() when concurrent faults or -EAGAIN retries
record an identical (nested, canonical) range on the same shadow MMU.

New:  KVM: arm64: nv: Fix AT emulation for TCR2_EL1
[PATCH v2 1/4] KVM: arm64: nv: Fix AT emulation for TCR2_EL1
Author: Dan Carpenter <dan@pereq.eu>

Arm provides an AT instruction that translates a virtual address the way
the MMU would and returns the result.  There is a bug in the way this
instruction is emulated for nested virtualization because of how TCR2_EL1
is handled.  The bug is fairly minor.

The TCR2_EL1 register has bits which turn on permission indirection
(PIE) and permission overlays (POE).  When these bits are set, the AT
instruction reads the permissions stored in PIR_EL1 and POR_EL1.  If
you have the right features and permissions then in the return value from
the AT instruction we set one bit to either 1 or 0 depending on whether
the access would be allowed or whether it would fault.

However, the bug is that just because the host has TCR2 enabled, it
doesn't mean the VM has it.  In the current code KVM doesn't load these
registers for a VM which doesn't have the features, instead the AT runs
with the host's HCRX_EL2, which has TCR2En set.  So the AT uses the
TCR2_EL1, PIR_EL1 and POR_EL1 values another VM left on the CPU, or
possibly the VMM's POR_EL0.  Likewise, for a VM which has TCR2 but not
PIE or POE, the L2's TCR2_EL1 is loaded unmasked.

The impact of this bug is that we leak a single bit of data to the L1,
but in real life it's hard to imagine how it is useful to an attacker.

Fix this by clearing the PIE and POE bits in effective_tcr2() when the
VM doesn't have those features, and use it for the L2's TCR2_EL1.  When
the AT runs on the guest hypervisor's own registers, in __kvm_at_s1e2()
and in __kvm_at_s1e01_fast(), load the guest's TCR2_EL2 for the AT and
restore the live value afterwards.

Fixes: 477e89cabb14 ("KVM: arm64: nv: Add basic emulation of AT S1E{0,1}{R,W}")
Fixes: 23e7a34c8397 ("KVM: arm64: Add AT fast-path support for S1PIE")
