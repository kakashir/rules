New:  LoongArch: KVM: Fix uninitialized stack read in dmsintc_inject_irq()
[PATCH] LoongArch: KVM: Fix uninitialized stack read in dmsintc_inject_irq()
Author: Daolong Zhang <dlzhangak@isoftstone.com>

In dmsintc_inject_irq(), the local array 'vector[4]' is declared on the
stack without initialization, and each element 'vector[i]' is only
assigned when atomic64_read(&ds->vector_map[i]) is non-zero.

Whenever any of the four 64-bit words in ds->vector_map[] is zero (for
example, when an MSI interrupt targets a single word, or when INT_AVEC
is injected via KVM_INTERRUPT with an empty vector_map), the remaining
elements of 'vector[]' retain uninitialized kernel stack contents. The
subsequent checks on vector[0..3] then OR those uninitialized stack
values into the guest's hardware LOONGARCH_CSR_ISR0..3 registers,
injecting spurious interrupt vectors into the guest and leaking host
kernel stack data into guest-visible CSRs.

Zero-initialize 'vector[4]' on declaration to prevent reading
uninitialized stack memory.

Fixes: 03de5eecb0f0 ("LoongArch: KVM: Add DMSINTC inject msi to vCPU")
Signed-off-by: Daolong Zhang <dlzhangak@isoftstone.com>

[PATCH v4 1/2] KVM: Disallow prefetching PFNs (for SPTEs) via VMAs
Author: Sean Christopherson <seanjc@google.com>

Disallow prefetching SPTEs via fast GUP, i.e. by VMA lookup, for gmem-only
memslots as the whole point of gmem-only memslots is that KVM MMUs should

mappings based on the to-be-invalidated VMA (as is intended).

New:  KVM: x86: Start IRQ bypass with local interrupts enabled
[PATCH] KVM: x86: Start IRQ bypass with local interrupts enabled
Author: Satish Kharat <satishkh@cisco.com>

Move the first IRQ-bypass notification after releasing irqfds.lock so
that the vendor callback runs with local interrupts enabled.

On Intel, pi_start_bypass() issues KVM_REQ_UNBLOCK to the vCPUs through
kvm_make_all_cpus_request(). If another CPU needs to be kicked, this can
reach smp_call_function_many(), which requires local interrupts enabled.
Calling the hook inside spin_lock_irq() violates that requirement and
triggered the following warning during VFIO MSI-X setup:

  WARNING: kernel/smp.c:943 at smp_call_function_many_cond
    kvm_make_all_cpus_request [kvm]
    kvm_arch_irq_bypass_add_producer [kvm]
    __connect [irqbypass]
    irq_bypass_register_producer [irqbypass]
    vfio_msi_set_vector_signal [vfio_pci_core]

The SMP API documents a possible deadlock in this context, including for
non-waiting calls. No deadlock was observed in this case.

Keep producer publication, bypass accounting and IRTE error rollback under
the existing lock. The IRQ bypass mutex still serializes producer
callbacks after irqfds.lock is released. Notify only for a successful
first attachment, after any IRTE failure has been ruled out.

An LLM assisted with implementation, code review and test automation.

New:  KVM: arm64: Fix inverted E2H0 check for HCR_EL2.NV1
[PATCH v1 1/2] KVM: arm64: Fix inverted E2H0 check for HCR_EL2.NV1
Author: Colton Lewis <coltonlewis@google.com>

ID_AA64MMFR4_EL1.E2H0 is a signed 4-bit field where:
  - 0b0000 (IMP, 0): FEAT_E2H0 is implemented.
  - 0b1111 (NI, -1): FEAT_E2H0 is not implemented, except HCR_EL2.NV1
    is implemented.
  - 0b1110 (NI_NV1, -2): Neither HCR_EL2.E2H == 0 nor HCR_EL2.NV1 is
    implemented, and HCR_EL2.NV1 is RES0.

Prior to commit b2a324ff01fe ("KVM: arm64: Use HCR_EL2 feature map to
drive fixed-value bits"), kvm_init_nv_sysregs() marked HCR_EL2.NV1 as
RES0 when !kvm_has_feat(kvm, ID_AA64MMFR4_EL1, E2H0, NI), i.e., when the
signed E2H0 field is less than NI (-1), which matches NI_NV1 (-2).

When converting HCR_EL2 to the feature map, feat_nv2_e2h0_ni() was
written as !kvm_has_feat(kvm, FEAT_E2H0), where FEAT_E2H0 checks
E2H0 >= IMP (0). This inverted the condition: feat_nv2_e2h0_ni()
evaluates to true when E2H0 < 0 (including NI_NV1), leaving HCR_EL2.NV1
writable instead of RES0 for VHE-only nested guests where KVM advertises
ID_AA64MMFR4_EL1.E2H0 = NI_NV1.

Check kvm_has_feat(kvm, ID_AA64MMFR4_EL1, E2H0, NI) in
feat_nv2_e2h0_ni() so that HCR_EL2.NV1 is treated as implemented only
when E2H0 is IMP or NI, and forced to RES0 when E2H0 is NI_NV1.

Fixes: b2a324ff01fe ("KVM: arm64: Use HCR_EL2 feature map to drive fixed-value bits")
Signed-off-by: Colton Lewis <coltonlewis@google.com>

[PATCH v6 00/17] x86/msr: Inline rdmsr/wrmsr instructions
Author: Juergen Gross <jgross@suse.com>

When building a kernel with CONFIG_PARAVIRT_XXL the paravirt
infrastructure will always use functions for reading or writing MSRs,
even when running on bare metal.

Switch to inline RDMSR/WRMSR instructions in this case, reducing the
paravirt overhead.

The first patch is a prerequisite fix for alternative patching. Its
is needed due to the initial indirect call needs to be padded with
NOPs in some cases with the following patches.

In order to make this less intrusive, some further reorganization of
the MSR access helpers is done in the patches 2-5.

The next 5 patches are converting the non-paravirt case to use direct
inlining of the MSR access instructions, including the WRMSRNS
instruction and the immediate variants of RDMSR and WRMSR if possible.

Patches 11-13 are some further preparations for making the real switch
to directly patch in the native MSR instructions easier.

Patch 14 is switching the paravirt MSR function interface from normal
call ABI to one more similar to the native MSR instructions.

Patch 15 is a little cleanup patch.

Patch 16 is the final step for patching in the native MSR instructions
when not running as a Xen PV guest.

Patch 17 converts the rest of the MSR helpers to __always_inline.

This series has been tested to work with Xen PV and on bare metal.

New:  KVM: arm64: CCA: Prepare Realm memory management
[PATCH v3 00/11] KVM: arm64: CCA: Prepare Realm memory management
Author: Steven Price <steven.price@arm.com>

This series adds the memory management plumbing for CCA, building on the
basic RMM support [1]. Thanks to everyone who reviewed and tested v2.

The patches introduce internal Realm VM state, prepare Realm stage-2
setup and teardown, and provide RTT mapping and invalidation helpers.
Realm memslots are restricted to the lower half of the IPA space because
the protected and shared halves alias each other. The final patch
connects the helpers to KVM's stage-2 MMU operations.

This is the memory management portion of the larger Realm host series.
Realm descriptor creation, REC entry and exit, activation, and the new
uAPI follow in the integration stack. This series alone does not enable
Realm creation.

The integration branch [2] includes Realm creation, REC entry and exit,
and the remaining host support on top of this series. The MM branch [3]
contains just this series.

Changes since v2:
- Move RMM mode reservation and RMI availability and feature checks to
  the integration stack.
- Require mmap-capable guest_memfd backing for all arm64 VMs and route
  all guest_memfd faults through gmem_abort().
- Store the Realm Descriptor physical address from initial Realm setup,
  and improve SRO cleanup and RTT teardown error handling.
- Use a local MMU cache for RTT invalidation, handle failed splits, and
  validate returned RTT levels.
- Bound protected RMI mapping calls to the encoded range and tighten
  RTT creation, retry, and error handling.
- Split common stage-2 destruction dispatch into its own patch before
  registering the Realm stage-2 MMU operations.

Changes since v1:
- Add a guest_memfd prerequisite patch that checks whether the backing
  file supports mmap when preparing an arm64 memslot.
- Combine the RMI availability and feature checks into one patch, and
  move Realm vCPU feature restrictions to the integration stack.
- Correct Realm IPA sizing and RTT teardown, including teardown before
  activation, RTT accounting, and handling of missing or folded RTTs.
- Rework RTT mapping to respect IPA and physical alignment, handle
  partial RMI progress, and retry interrupted operations.

New:  x86/msr: Drop 32-bit MSR interfaces
[PATCH v6 00/12] x86/msr: Drop 32-bit MSR interfaces
Author: Juergen Gross <jgross@suse.com>

For accessing the MSR registers on the local CPU, there are 2 types of
interfaces: the "modern" 64-bit ones (rdmsrq() etc.) and the 32-bit
ones (rdmsr() etc.) which are using the upper and lower 32-bit halves
of the 64-bit wide MSR register values.

The 32-bit interfaces are not optimal for 3 reasons:

- They are based on primitives using 64-bit sized values anyway.

- Modern x86 CPUs have added support for MSR access instructions using
  an immediate value instead of a register for addressing the MSR,
  while the value is in a 64-bit register.

- rdmsr() is a macro storing the upper and lower 32-bit halves in
  variables specified as macro parameters. This is obscuring variable
  assignment through a macro. Additionally rdmsrq() is mimicking this
  pattern by being a macro, too, with the target variable specified as
  a parameter as well.

For those reasons drop the 32-bit interfaces for accessing the x86 MSR
registers completely and only use the 64-bit variants.

This allows to switch all "high-level" MSR access macros to inline
functions in the end.

This series will be used as the base for further reorganisation of the
MSR access functions, especially for completely inlining the MSR
access instructions even with paravirtualization being active.

Based on kernel 7.4-rc3.

IMHO at least patches 2 and 3 should be applied rather sooner than later
in order to avoid new instances of the 32-bit variants of the *_safe()
functions creeping in again.

New:  coco/tdx-host: Create metadata for an SPDM session
[RFC PATCH 1/7] coco/tdx-host: Create metadata for an SPDM session
Author: Chao Gao <chao.gao@intel.com>

The TDX module talks to the device over a Security Protocol and Data
Model (SPDM) session. It needs host memory for each session's metadata,
and reports the number of pages required in its global metadata.

TDX module with TDH.SPDM.CREATE. Keep the returned session ID for later
SEAMCALLs. When tearing the session down, reclaim the memory with

New:  TDX: Enable PCIe link encryption for trusted I/O
[RFC PATCH 0/7] TDX: Enable PCIe link encryption for trusted I/O
Author: Chao Gao <chao.gao@intel.com>

Hi all,

This series adds PCIe link encryption on TDX hosts. Yilun previously
posted one large series with all the changes needed for this [1]. That
series has been split up, and the parts are being posted separately.
This RFC is posted for early review. It is not yet seeking review from
the x86 maintainers.

The SEAMCALL wrappers this series uses are in a separate series, not
yet posted. So, their names and parameters may still change.

Today, userspace sets up link encryption by writing to the PCI/TSM
"connect" sysfs attribute. A proposal under discussion [2] adds CTLV
attestation commands [3] to this flow, so that userspace can select and
verify the device's certificates before the IDE stream is set up. This
series uses only the "connect" attribute. I will convert it to the new
flow once the discussion settles.

== Background ==

With shared I/O, devices cannot access a confidential VM's private
memory, so the VM bounces I/O data through memory it shares with the
host. With trusted I/O, the VM establishes trust in a device and then
lets it access private memory directly, which avoids the bouncing.

The device's MMIO and DMA traffic then carries private data across PCIe
links and switches. A physical attacker on a link, or a malicious
switch, could read, modify or replay that traffic. PCIe link encryption
protects the traffic between the root port and the device against these
attacks, which keeps switches out of the VM's TCB.

Link encryption builds on:

  - Integrity and Data Encryption (IDE) [4], the PCIe feature that
    encrypts and integrity-protects data exchanged between the root port
    (part of the CPU's root complex) and the device.

  - The Security Protocol and Data Model (SPDM) [5], a protocol for
    authenticating a device and setting up a secure session with it.

  - Data Object Exchange (DOE) [6], a PCIe feature that provides a
    mailbox in the device's config space.

At a high level, setting up link encryption means opening an SPDM
session with the device through its DOE mailbox, configuring an IDE
stream on both the root port and the device, and programming the
stream's keys into the root port and sending them to the device over
the SPDM session.

The TEE Security Manager (TSM) is a trusted platform component, such as
the TDX module or AMD's Secure Processor firmware. The work is split
between the TSM and the host kernel. The TSM runs the SPDM session and
handles the keys. It doesn't own the device, so the host kernel configures
the device's IDE settings and relays SPDM messages between the TSM and
the device.

== This series ==

This series adds a TDX-TSM driver to the TDX host services module
(tdx-host.ko). The driver registers the TDX module as a TSM with the
PCI/TSM framework [7] and implements its connect and disconnect
operations. PCI/TSM calls them when userspace writes to a device's
"connect" and "disconnect" sysfs attributes.

Connect sets up the SPDM session, the IDE stream and its keys through
SEAMCALLs, and disconnect tears them down.

During some SEAMCALLs, the TDX module may need to exchange several SPDM
messages with the device. The kernel calls such a SEAMCALL in a loop.
Each time it returns an SPDM message with a dedicated status code, the
kernel sends the message through the device's DOE mailbox and calls the
SEAMCALL again with the device's reply, until the SEAMCALL completes.

== Points for discussion ==

1. Raw DOE frames (See patch 3)

The TDX module produces and consumes whole DOE objects, header included,
but the PCI DOE API takes payloads only. The TDX-TSM driver therefore
strips and rebuilds the DOE header itself. The code is small, but it
puts DOE format details in a TSM driver, while the DOE core already
handles them. A PCI DOE API that takes whole objects would keep them in
the core, but the TDX-TSM driver would be its only user. Is such an API
worth adding, or can we live with the DOE format handling in the
TDX-TSM driver?

2. Default IDE Stream (See patch 5)

TDISP requires each device to have one default IDE stream [8]. The PCI
core does not set Default Stream, so each TSM driver sets it itself, by
looking up the device's IDE settings with pci_ide_to_settings() and
setting default_stream. AMD's driver already does this, and the TDX-TSM
driver does the same. Since the requirement is shared, the PCI core
could instead set Default Stream on the device's TC0 stream, which is
what TDISP expects. Should this move into the PCI core now, or can it be
a later cleanup?

== Limitations ==

The TDX module configures the root port's IDE settings and accepts
only one address range for the stream. The root port therefore encrypts
only traffic to the device's prefetchable MMIO range, and a device with
no prefetchable range cannot be connected. We are evaluating whether
this can be lifted.

Link encryption needs the root complex to enter a TDX mode, in which
only the TDX module can configure the root port's IDE settings. The
kernel opts in to this mode with TDH.IOMMU.SETUP. As its name suggests,
this SEAMCALL also puts the IOMMU into TDX mode, which changes the
IOMMU's behavior. Unfortunately, the two cannot be enabled separately,
even though link encryption does not need IOMMU TDX mode.

This series replaces the halt-polling histogram Kconfig patch, as a first
step towards a general plan for KVM stats.

Take a VM with 8 vCPUs on x86.  Each vCPU has 1104 bytes of stats, 768 of
which are the three halt-polling histograms, i.e. 6KiB for the VM.  The VM
also gets ~95 debugfs entries (one file per stat, plus a directory and a few
files per vCPU), each costing a dentry and an inode, i.e. ~70KiB, all
duplicating the binary stats.

The plan:

 1. Counters stay embedded in the stats structs; they're cheap and
    monitoring wants them always on.

 2. Arrays and histograms move to a separately allocated block, controlled
    by kvm.extended_stats (default on).  The binary stats ABI doesn't change;
    the values read as zero if the block isn't allocated.  (patch 4)

 3. Debug-only data goes to tracepoints and is aggregated with BPF.  Adding
    the halt-polling time to kvm_vcpu_wakeup is enough to rebuild the three
    histograms.  (patch 1)

In addition, kvm.per_vm_debugfs (default on) allows skipping the per-VM
debugfs directories.  (patch 3)  Patch 2 fixes an arm64 bug that this
makes easy to hit: nested stage-2 ptdump files end up in the debugfs root
if the VM has no debugfs directory.

With patch 4, struct vcpu_vmx shrinks from 8384 to 7616 bytes and struct
vcpu_svm from 6728 to 5968 bytes.

Tested on Intel with KVM selftests in all three configurations (default,
kvm.extended_stats=0, kvm.per_vm_debugfs=0).  Build-tested on powerpc and
arm64.

New:  KVM: VMX: Disallow 16-bit busy TSS (type 3) for TR in IA-32e mode
[PATCH] KVM: VMX: Disallow 16-bit busy TSS (type 3) for TR in IA-32e mode
Author: zhangdaolong <dlzhangak@isoftstone.com>

According to Intel SDM Vol. 3C, "Checks on Guest Segment Registers", the
TR segment type must be 11 (64-bit busy TSS) when the "IA-32e mode guest"
VM-entry control is 1, and may be 3 (16-bit busy TSS) or 11 (32-bit busy
TSS) only when "IA-32e mode guest" is 0.

Currently, tr_valid() unconditionally allows type 3 even when the guest is
in IA-32e mode (long mode). When emulate_invalid_guest_state is enabled,
this causes __vmx_guest_state_valid() to falsely report a valid guest state
for a 64-bit guest with a 16-bit busy TSS, resulting in a hardware VM-Entry
failure (EXIT_REASON_INVALID_STATE / KVM_EXIT_FAIL_ENTRY) instead of
emulating the invalid guest state.

Check is_long_mode(vcpu) in tr_valid() and reject type 3 when the vCPU is
in IA-32e mode.

Fixes: 648dfaa7df2d ("KVM: VMX: Add Guest State Validity Checks")

New:  KVM: arm64: Fix inverted E2H0 check for HCR_EL2.NV1
[PATCH v1 1/2] KVM: arm64: Fix inverted E2H0 check for HCR_EL2.NV1
Author: Colton Lewis <coltonlewis@google.com>

ID_AA64MMFR4_EL1.E2H0 is a signed 4-bit field where:
  - 0b0000 (IMP, 0): FEAT_E2H0 is implemented.
  - 0b1111 (NI, -1): FEAT_E2H0 is not implemented, except HCR_EL2.NV1
    is implemented.
  - 0b1110 (NI_NV1, -2): Neither HCR_EL2.E2H == 0 nor HCR_EL2.NV1 is
    implemented, and HCR_EL2.NV1 is RES0.

Prior to commit b2a324ff01fe ("KVM: arm64: Use HCR_EL2 feature map to
drive fixed-value bits"), kvm_init_nv_sysregs() marked HCR_EL2.NV1 as
RES0 when !kvm_has_feat(kvm, ID_AA64MMFR4_EL1, E2H0, NI), i.e., when the
signed E2H0 field is less than NI (-1), which matches NI_NV1 (-2).

When converting HCR_EL2 to the feature map, feat_nv2_e2h0_ni() was
written as !kvm_has_feat(kvm, FEAT_E2H0), where FEAT_E2H0 checks
E2H0 >= IMP (0). This inverted the condition: feat_nv2_e2h0_ni()
evaluates to true when E2H0 < 0 (including NI_NV1), leaving HCR_EL2.NV1
writable instead of RES0 for VHE-only nested guests where KVM advertises
ID_AA64MMFR4_EL1.E2H0 = NI_NV1.

Check kvm_has_feat(kvm, ID_AA64MMFR4_EL1, E2H0, NI) in
feat_nv2_e2h0_ni() so that HCR_EL2.NV1 is treated as implemented only
when E2H0 is IMP or NI, and forced to RES0 when E2H0 is NI_NV1.

Fixes: b2a324ff01fe ("KVM: arm64: Use HCR_EL2 feature map to drive fixed-value bits")

New:  KVM: arm64: nv: Fix NULL dereference in kvm_inject_nested()
[PATCH] KVM: arm64: nv: Fix NULL dereference in kvm_inject_nested()
Author: Dan Carpenter <dan@pereq.eu>

There is a NULL dereference of vcpu->arch.hw_mmu in kvm_inject_nested()

Unable to handle kernel NULL pointer dereference at virtual address 0000000000000084
  kvm_vcpu_put_hw_mmu (arch/arm64/kvm/nested.c:1046) (P)
  vhe_vcpu_put (arch/arm64/kvm/arm.c:827)
  kvm_arch_vcpu_put (arch/arm64/kvm/arm.c:860)
  kvm_inject_nested (arch/arm64/kvm/emulate-nested.c:2903)
  kvm_inject_nested_serror (arch/arm64/kvm/emulate-nested.c:2976)
  kvm_inject_serror_esr (arch/arm64/kvm/inject_fault.c:365)
  __kvm_arm_vcpu_set_events (arch/arm64/kvm/guest.c:827)
  kvm_arch_vcpu_ioctl (arch/arm64/kvm/arm.c:2017 arch/arm64/kvm/arm.c:2157)
  kvm_vcpu_ioctl (arch/arm64/kvm/../../../virt/kvm/kvm_main.c:4772)

KVM_SET_VCPU_EVENTS does not load the vcpu, but it injects a pending
SError or external abort straight away.  If the vcpu is in L2 context
and L1 has asked for the exception, kvm_inject_nested() puts and loads
a vcpu that is not loaded.  vcpu->arch.hw_mmu is NULL when the vcpu is
not loaded, so kvm_vcpu_put_hw_mmu() dereferences a NULL pointer.

To fix this bug, only put and load the vcpu when it is loaded, similar
to what kvm_reset_vcpu() does.  When the vcpu is not loaded there is
nothing to switch: the next kvm_arch_vcpu_load() loads L1's context.

New:  drivers/virt: pkvm: Zero and clean memory before sharing it with the host
[PATCH] drivers/virt: pkvm: Zero and clean memory before sharing it with the host
Author: Fuad Tabba <fuad.tabba@linux.dev>


On pKVM, set_memory_decrypted() shares pages with the host in place and
without cache maintenance. The atomic pool, dma-direct and dynamic
SWIOTLB pools zero their memory only after sharing it, so unless the
page allocator has zeroed it, the host can read whatever the guest last
left in it. Zeroing first isn't enough on its own, as the zeroes may not
have been written back to memory, and a host that maps the pages
Non-cacheable then reads the old contents.

Zero the range and clean it to the PoC before sharing it, so that no
caller can hand the host stale data.

New:  mm: Add an allocator for CoCo shared memory
[PATCH v10 01/13] mm: Add an allocator for CoCo shared memory
Author: Aneesh Kumar K.V (Arm) <aneesh.kumar@kernel.org>

Confidential-computing guests may require memory shared with the host to
be aligned and transitioned in units larger than PAGE_SIZE. Several DMA
users need struct page-backed allocations satisfying these requirements.
Provide a common allocator instead of requiring each user to open-code
this sequence.

Add alloc_cc_shared_pages() and its node-aware variant. The allocator
rounds the requested size to the architecture's shared granule,
allocates suitably aligned contiguous pages and transitions the
complete range to shared state. It also preserves the caller's GFP
policy.

A private-to-shared transition may alter memory contents. Mask
__GFP_ZERO from the underlying allocation and when requested, clear the
complete transitioned range after cc_make_shared() succeeds.

Return the page and transitioned size so free_cc_shared_pages() can
restore the complete range to private state before freeing it. If
private state cannot be established, retain the allocation instead of
returning a possibly shared page to the buddy allocator.

Also provide the shared-granule geometry and byte-oriented transition
helpers used by the allocator and by callers managing their own backing
memory.

New:  coco: guest: Add a shared-granule allocator for host-shared memory
[PATCH v10 00/13] coco: guest: Add a shared-granule allocator for host-shared memory
Author: Aneesh Kumar K.V (Arm) <aneesh.kumar@kernel.org>


This series tightens the alignment requirements for buffers that are shared
between confidential-computing guests and the host, and adds a common
allocator for host-shared memory.

When a guest runs with private memory, buffers shared with the hypervisor
are not only accessed by the guest. They are also accessed by the host
kernel, and the host may manage the corresponding shared/private state at a
granularity larger than the guest page size.

Architectures such as Arm can detect incorrect accesses to Realm physical
address space PFNs through GPC faults. However, relying on that as the only
line of defence is fragile and can still lead to kernel crashes. The risk
is especially visible for shared buffers that are later mmapped into
userspace, such as guest_memfd or dma-buf backed allocations. Once
userspace can access the mapping, the kernel cannot guarantee that
applications will only touch the intended 4K region rather than the whole
host page mapped into their address space. Those userspace addresses may
also be passed back into the kernel and accessed through the linear map,
resulting in a GPC fault.

To avoid this, host-shared buffers must satisfy two constraints:

  - the address must be aligned to the CoCo shared-granule size
  - the size must be a multiple of that granule size

The series adds a common CoCo shared-memory layer for enforcing these
constraints. It provides shared-granule geometry and range-validation
helpers, byte-oriented private/shared transition helpers, and
alloc_cc_shared_pages(). The allocator rounds a request to the architecture
shared granule, allocates suitably aligned contiguous pages, transitions
the complete allocation to shared state, and returns the transitioned size
alongside the page.

The corresponding free helper restores the complete allocation to private
state before returning it to the buddy allocator. If private state cannot
be restored safely, the allocation is deliberately leaked rather than
returning potentially shared memory for unrelated use.

The series also makes zeroing part of private-to-shared transitions, with
each architecture clearing memory at the appropriate point. Callers must
therefore initialize shared buffers after the transition; existing contents
are not preserved.

The shared-granule size defaults to PAGE_SIZE and can be overridden by an
architecture. The arm64 CCA changes to discover the host's IPA state change
alignment are not included in this series.

GIC ITS command queues and tables and the dma-buf system_cc_shared heap
use the common allocator. DMA direct, atomic DMA pools and SWIOTLB retain
their allocation paths and use the common layout or transition helpers.
Restricted DMA pools are checked for shared-granule alignment.

Hyper-V users of set_memory_encrypted() and set_memory_decrypted() are not
changed to use cc_make_shared() by this series. Those paths are not
currently used by the arm64 CCA code path, and therefore are not part of
the arm64 CCA IPA state change alignment problem addressed here.

New:  KVM: arm64: Give the host timer interrupts a separate lockdep class
[PATCH 1/2] KVM: arm64: Give the host timer interrupts a separate lockdep class
Author: Jia He <justin.he@arm.com>

With a GICv5 guest, kvm_timer_vcpu_put() clears the active state of the
host timer interrupts with irq_set_irqchip_state(), which takes their
irq_desc lock. On preemption this runs from kvm_sched_out() with the
runqueue lock held:

  &rq->__lock --> &irq_desc_lock_class

By default, all irq descriptors share a single lockdep class, so this
closes a cycle with any interrupt that queues affinity notifier work
under its own descriptor lock (mlx5, for example), as already seen with
the GICv4 vPE doorbells:

  &irq_desc_lock_class --> &pool->lock --> &p->pi_lock --> &rq->__lock

For the timer interrupts this is a false positive. Nothing that runs
under their descriptor lock leads back to the scheduler:

- They are requested only by KVM, with request_percpu_irq(). Per-CPU
  interrupts are never threaded (irq_set_percpu_devid() sets
  IRQ_NOTHREAD), so there is no irq thread to wake, unlike the vPE
  doorbells with threadirqs.

- Their affinity is fixed and never changed, so no affinity notifier
  work or thread affinity update is triggered.

- The irqchip callbacks reached under the lock (the KVM timer_chip,
  forwarding to the GIC) only access GIC registers.

Give them a separate lockdep class. This is done for all vGIC types, as
none of the above is specific to GICv5. Both timers share the class, so
dependencies between them are still checked.

New:  KVM: arm64: gic-v5: Fix irq_desc locks taken under the runqueue lock
[PATCH 0/2] KVM: arm64: gic-v5: Fix irq_desc locks taken under the runqueue lock
Author: Jia He <justin.he@arm.com>

With a GICv5 guest, kvm_sched_out() takes irq_desc locks with the
runqueue lock held in two places. Lockdep reports both as a circular
dependency with any interrupt that queues affinity notifier work under
its own descriptor lock:

- kvm_timer_vcpu_put() clears the active state of the host timer
  interrupts. These are per-CPU and never threaded, so this one is a
  false positive. Patch 1 gives them a separate lockdep class, as
  commit 7100185bdc11 ("irqchip/gic-v4: Use a separate lockdep class for
  vPE doorbell IRQs") in kvmarm/fixes does for the GICv4 vPE doorbells.

- vgic_v5_put() can move the vPE doorbell with irq_set_affinity() when
  the vcpu thread is scheduled out in the middle of WFI. This came up in
  the review of "KVM: arm64: gic-v5: Request doorbells when VPEs enter
  WFI", where the resident check was expected to make it unreachable.
  It is reachable, because vgic_v5_load() makes the vPE resident again
  when the halting vcpu thread is scheduled back in. As the doorbell can
  be force-threaded, this can wake its irq thread under the runqueue
  lock, so patch 2 stops moving the doorbell from kvm_sched_out()
  rather than hiding it from lockdep.

Tested on the Arm FVP Base RevC AEMvA GICv5 model (11.31.28, 8 CPUs,
VHE) with PROVE_LOCKING, on top of eedaa7d61f1e.

Lockdep reproduction: to provide the other half of the cycle, a test
module registers an affinity notifier on the UART interrupt and changes
its affinity a few times.

- Patch 1: the vgic_v5 selftest pinned to CPU0 next to a busy loop.
  Without the patch, lockdep reports the cycle through
  kvm_timer_vcpu_put(). With it there is no report, and &rq->__lock
  depends on the new class instead of &irq_desc_lock_class.

- Patch 2: a vcpu executing WFI in a loop, woken by an SPI every 5ms,
  with halt_poll_ns at 50ms and the vcpu thread moved to another CPU
  every 1ms. A kprobe on irq_set_affinity() saw 11 calls from
  kvm_sched_out() without the patch, together with the lockdep report
  quoted in the commit message, and none with it. The doorbell is still
  moved from kvm_vcpu_wfi() itself (51 and 61 calls).

PREEMPT_RT reproduction: PREEMPT_RT force-threads the vPE doorbell, so
patch 2 also fixes a real inversion. Without the patch, and without the
test module, the same WFI test makes lockdep report the cycle closed by
the doorbell's own irq thread: irq_set_affinity() from kvm_vcpu_wfi()
wakes the thread under the descriptor lock, while kvm_sched_out() takes
the descriptor lock under the runqueue lock. The model stops making
progress right after the report. With patch 2 there is no report and the
test completes. (Booting PREEMPT_RT on the GICv5 model also needs
"arm64: smp: Don't force-thread the GICv5 IPIs", posted separately.)

New:  KVM: arm64: nv: Fix AT emulation for TCR2_EL1
[PATCH 1/2] KVM: arm64: nv: Fix AT emulation for TCR2_EL1
Author: Dan Carpenter <dan@pereq.eu>

Arm provides an AT instruction that translates a virtual address the way
the MMU would and returns the result.  There is a bug in the way this
instruction is emulated for nested virtualization because of how TCR2_EL1
is handled.  The bug is fairly minor.

The TCR2_EL1 register has bits which turn on permission indirection
(PIE) and permission overlays (POE).  When these bits are set, the AT
instruction reads the permissions stored in PIR_EL1 and POR_EL1.  If
you have the right features and permissions then in the return value from
the AT instruction we set one bit to either 1 or 0 depending on whether
the access would be allowed or whether it would fault.

However, the bug is that just because the host has TCR2 enabled, it
doesn't mean the VM has it.  KVM doesn't load these registers for a VM
which doesn't have the features, instead the AT runs with the host's
HCRX_EL2, which has TCR2En set.  So the AT uses the TCR2_EL1, PIR_EL1 and
POR_EL1 values another VM left on the CPU, or possibly the VMM's POR_EL0.
Likewise, for a VM which has TCR2 but not PIE or POE, the L2's TCR2_EL1
is loaded unmasked.

The impact of this bug is that we leak a single bit of data to the L1,
but in real life it's hard to imagine how it is useful to an attacker.

Fix this by writing zero to TCR2_EL1 when the VM doesn't have TCR2, and
by clearing the PIE and POE bits when the VM doesn't have those
features.  Also it should be effective_tcr2(vcpu, TR_EL10) to read the
TCR2 for the L1 instead of vcpu_read_sys_reg(vcpu, TCR2_EL1).
