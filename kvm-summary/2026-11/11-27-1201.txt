New:  KVM: x86: pull kvm->srcu read-side to
[PATCH 5.10.y v2 1/2] KVM: x86: pull kvm->srcu read-side to
Author: Dickson Wu via B4 Relay <devnull+dickson.wu.certik.com@kernel.org>


commit 8d25b7beca7ed6ca34f53f0f8abd009e2be15d94 upstream.

kvm_arch_vcpu_ioctl_run is already doing srcu_read_lock/unlock in two
places, namely vcpu_run and post_kvm_run_save, and a third is actually
needed around the call to vcpu->arch.complete_userspace_io to avoid
the following splat:

  WARNING: suspicious RCU usage
  arch/x86/kvm/pmu.c:190 suspicious rcu_dereference_check() usage!
  other info that might help us debug this:
  rcu_scheduler_active = 2, debug_locks = 1
  1 lock held by CPU 28/KVM/370841:
  #0: ff11004089f280b8 (&vcpu->mutex){+.+.}-{3:3}, at: kvm_vcpu_ioctl+0x87/0x730 [kvm]
  Call Trace:
   <TASK>
   dump_stack_lvl+0x59/0x73
   reprogram_fixed_counter+0x15d/0x1a0 [kvm]
   kvm_pmu_trigger_event+0x1a3/0x260 [kvm]
   ? free_moved_vector+0x1b4/0x1e0
   complete_fast_pio_in+0x8a/0xd0 [kvm]

This splat is not at all unexpected, since complete_userspace_io callbacks
can execute similar code to vmexits.  For example, SVM with nrips=false
will call into the emulator from svm_skip_emulated_instruction().

While it's tempting to never acquire kvm->srcu for an uninitialized vCPU,
practically speaking there's no penalty to acquiring kvm->srcu "early"
as the KVM_MP_STATE_UNINITIALIZED path is a one-time thing per vCPU.  On
the other hand, seemingly innocuous helpers like kvm_apic_accept_events()
and sync_regs() can theoretically reach code that might access
SRCU-protected data structures, e.g. sync_regs() can trigger forced
existing of nested mode via kvm_vcpu_ioctl_x86_set_vcpu_events().

New:  KVM: PPC: Book3S: Hold a reference to sPAPR TCE tables during hcalls
[PATCH v2 1/3] KVM: PPC: Book3S: Hold a reference to sPAPR TCE tables during hcalls
Author: Narayana Murty N <nnmlinux@linux.ibm.com>

Commit cad32d9d42e8 ("KVM: PPC: Book3s: Retire H_PUT_TCE/etc real
mode handlers") moved TCE hypercalls to preemptible virtual
mode. However, kvmppc_find_table() returns a table pointer without
holding a reference, allowing concurrent fd release to free it
while a hypercall is still using it.

Add a kref to the sPAPR TCE table and acquire it under RCU during
lookup. Release the reference when the hypercall completes.

Use kvm->srcu to synchronize active table accesses with fd release
before dropping the locked-memory accounting.

New:  Add support for cmpxchg16b emulation
[PATCH v5 0/2] Add support for cmpxchg16b emulation
Author: Sairaj Kodilkar <sarunkod@amd.com>

This series adds 128-bit compare-exchange support needed for KVM to
emulate guest cmpxchg16b instructions.

The AMD IOMMU driver updates 256-bit device table entries with two
128-bit cmpxchg operations.  For hardware-accelerated vIOMMU, QEMU traps
those DTE accesses to install nested page tables [1].  KVM must emulate
guest cmpxchg16b on the trapped MMIO regions; without that, DTE access
emulation fails.

Patch 1: extends the x86 user CMPXCHG helpers with
__try_cmpxchg128_user_asm() (cmpxchg16b on x86-64), wired into
unsafe_try_cmpxchg_user().

Patch 2: extends KVM CMPXCHG8B emulation to 16-byte operands (REX.W=1) and
uses the new helper for atomic 16-byte compare-exchange on guest RAM via
emulator_cmpxchg_emulated().

You can find the KUT to test this series at [2].

[1] https://github.com/AMDESE/qemu-iommu/blob/wip/for_iommufd_hw_queue-v8_amd_viommu_20260106/hw/i386/amd_viommu.c#L517
[2] https://lore.kernel.org/kvm/20260706062153.346-1-sarunkod@amd.com/T/#u

New:  x86/uaccess: Extend CMPXCHG user helpers to 128-bit operands
[PATCH v5 1/2] x86/uaccess: Extend CMPXCHG user helpers to 128-bit operands
Author: Sairaj Kodilkar <sarunkod@amd.com>

Extend the existing user CMPXCHG helpers to support 16-byte operands on
x86-64, using LOCK_PREFIX "cmpxchg16b".  This mirrors the existing
__try_cmpxchg64_user_asm() / cmpxchg8b path provided for 32-bit kernels,
where KVM needs an atomic compare-exchange wider than the generic
cmpxchg helper can provide.

On 32-bit kernels, stub the helper to generate build failure because
cmpxchg16b requires 64-bit GPRs and is not available.

KVM uses this to atomically emulate guest cmpxchg16b on guest RAM mapped
via userspace addresses.

New:  arm/kvm: select an nVHE-only EL2 with SYSREG_ID_AA64MMFR1_EL1_VH
[RFC PATCH v3 0/3] arm/kvm: select an nVHE-only EL2 with SYSREG_ID_AA64MMFR1_EL1_VH
Author: Haseeb Ashraf <haseebashraf091@gmail.com>


Hi,

KVM presents a VHE-only EL2 (HCR_EL2.E2H RES1) to a nested guest unless
KVM_ARM_VCPU_HAS_EL2_E2H0 is requested at vCPU initialization. This RFC
lets an nVHE-only guest hypervisor request that mode through:

  -M virt,virtualization=on -accel kvm \
      -cpu host,SYSREG_ID_AA64MMFR1_EL1_VH=0

The series builds on Eric Auger's remaining v11 SYSREG framework. It is
based on the rebased prerequisite commit corresponding to Eric's
arm-cpu-model-v11-rc tip e32893ddcbe643d47919f55ae33ff71be2609a77.
This dependency is intentional: a version which works without that
framework would have to introduce a separate machine or CPU property,
which was the approach rejected by Marc in v1.

References:

  - Eric's v11 series:
    https://patchew.org/QEMU/20261030131406.461599-1-eric.auger@redhat.com/
  - Eric's v11-rc branch:
    https://github.com/eauger/qemu/commits/arm-cpu-model-v11-rc
  - My v1:
    https://patchew.org/QEMU/20261121095636.289814-1-haseebashraf091@gmail.com/

Changes since v2:

  - Apply init-driven SYSREG properties before creating the scratch
    vCPU, so full CPU-model expansion reflects the requested init mode.
  - Refresh ID_AA64MMFR1_EL1 and ID_AA64MMFR4_EL1 from KVM after vCPU
    initialization, keeping QEMU's cached model and QMP expansion in
    sync with the guest-visible registers.

Eric correctly pointed out that KVM already updates the guest-visible
derived ID registers. The v2 gap was limited to QEMU's cache/model
expansion view; v3 fixes that without changing the guest-visible
behavior.  With VH=0, query-cpu-model-expansion now reports
ID_AA64MMFR4_EL1.NV_frac=0; with VH=1 it reports 1.

For the init-driven property question, this series keeps VH as an
explicit exception because KVM_CAP_ARM_EL2_E2H0 currently exposes no
writable-ID-register equivalent.  A generic framework table can be
considered if more such fields arise; there is no need to add a broader
abstraction for this single case.

This RFC therefore also asks maintainers to confirm that using a
SYSREG_<REG>_<FIELD> property for a value selected at vCPU init is an
acceptable extension of Eric's framework. If that model is not
accepted, this nVHE functionality should wait for the framework
direction to settle. The standalone-property implementation from v1 is
available as a fallback for the implementation discussion, but I would
prefer not to make that upstream direction the default again.

TCG and HVF are unchanged by design.

Testing on an AmpereOne A192-32X with host kernel 6.18.29-arm64:

  - TCG-only and KVM-only builds succeeded.
  - TCG rejects SYSREG_ID_AA64MMFR1_EL1_VH.
  - arm-cpu-features passed.
  - All three AArch64 KVM functional selftests passed.
  - QMP full expansion reports the KVM-derived MMFR4 state for both
    VH=0 and VH=1.
  - Linux 6.12.67 initialized KVM in nVHE mode with VH=0 and VHE mode
    with VH=1; QNX Hypervisor 8.0.5 reached login with both values.
  - Xen dom0 reached login with VH=0 and did not boot with VH=1.

Thanks,
Haseeb

New:  KVM: arm64: Top up the mmu memcache on user fault for NV
[PATCH] KVM: arm64: Top up the mmu memcache on user fault for NV
Author: Lorenzo Stoakes (ARM) <ljs@kernel.org>

The S2 user fault path tops up the MMU memcache (used for page table
pre-allocation as the point at which page tables are installed may not
allocate) except when:

* It's a permission fault AND
* dirty page logging is disabled AND
* pKVM is disabled

At which point it is assumed no page table will be allocated.

However nested virtualisation adds another edge case - the mapping size of
a shadow S2 is clamped to that of the guest's own S2. If the guest
hypervisor replaces a block mapping with a table, a permission fault on the
shadow block has to be mapped at PAGE_SIZE, which requires a page table to
collapse the block into.

With the memcache empty, kvm_mmu_memory_cache_alloc() hits its
guest-triggerable WARN_ON(!nobjs) and falls back to a GFP_ATOMIC allocation
under mmu_lock, with a BUG_ON() if that fails.

Therefore, also top up the memcache for permission faults taken on a
shadow S2.

Note that dirty logging had a similar issue, addressed in commit
56fd1fc526e6 ("KVM: arm64: Top up stage-2 memcache for dirty logging
faults").

Fixes: fd276e71d1e7 ("KVM: arm64: nv: Handle shadow stage 2 page faults")

New:  KVM: arm64: gic-v5: Reject an ID_BITS too large for a linear IST
[PATCH] KVM: arm64: gic-v5: Reject an ID_BITS too large for a linear IST
Author: Fuad Tabba <fuad.tabba@linux.dev>

Without two-level IST support in the host IRS, KVM allocates a guest's
LPI IST with a single kzalloc(). The guest picks the IST's size, up to
the virtual IRS_IDR2.ID_BITS, which userspace can set as high as the
host's. With 24 ID bits the IST is at least 64MB, more than
KMALLOC_MAX_SIZE with 4K or 16K pages, and kzalloc() warns when the
guest enables the IST.

Reject an ID_BITS for which a linear IST would be larger than
KMALLOC_MAX_SIZE. This applies even for a Linux guest, which
configures a much smaller IST. Userspace writes to IRS_IDR2 are new
in this cycle, so no release has them.

Fixes: 71091136d1452 ("KVM: arm64: gic-v5: Handle userspace accesses to IRS MMIO region")
Signed-off-by: Fuad Tabba <fuad.tabba@linux.dev>
---

Notes:
    Tested on FVP, on VHE and nVHE hosts, with and without two-level IST
    support in the IRS. The vgic_v5 selftest passes. A reproducer that
    sets ID_BITS to 24 and restores an IST that wide hits the kzalloc()
    warning without this patch. With it, the IRS_IDR2 write is rejected.
    
    Based on Linux 7.4-rc3 (aebb727447640).
