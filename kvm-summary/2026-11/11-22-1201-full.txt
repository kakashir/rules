[RFC PATCH v2 2/3] target/arm/kvm: Let SYSREG_ID_AA64MMFR1_EL1_VH select an nVHE EL2
Author: Haseeb Ashraf <haseebashraf091@gmail.com>


KVM runs a nested guest with a VHE-only EL2 (HCR_EL2.E2H RES1) unless
KVM_ARM_VCPU_HAS_EL2_E2H0 is requested at KVM_ARM_VCPU_INIT time.  With
that feature FEAT_VHE is hidden: ID_AA64MMFR1_EL1.VH reads 0 and
HCR_EL2.E2H is RES0.  Guest hypervisors which only support nVHE, such as
Xen, can only run in the latter mode.

Do not add a dedicated machine or CPU option for it.  Derive the vCPU
init feature from the ID register field selected by the user instead:
SYSREG_ID_AA64MMFR1_EL1_VH=0 requests KVM_ARM_VCPU_HAS_EL2_E2H0.

KVM does not let userspace write ID_AA64MMFR1_EL1.VH, so the generic
"writable fields only" rule would not create the property.  Expose it
explicitly when the host supports KVM_CAP_ARM_EL2_E2H0.  As KVM already
reports the requested value after vCPU init, applying the property does
not need a KVM_SET_ONE_REG for this field, and the query-cpu-model-expansion
dry run on the scratch vCPU skips it.  Setting VH=0 without
virtualization=on is rejected.

Only ID_AA64MMFR1_EL1.VH is updated in QEMU's copy of the ID registers.
Other fields which KVM derives from E2H0 (e.g. ID_AA64MMFR4_EL1) are
not refreshed.

Suggested-by: Marc Zyngier <maz@kernel.org>
Suggested-by: Volodymyr Babchuk <Volodymyr_Babchuk@epam.com>
Signed-off-by: Haseeb Ashraf <haseeb.ashraf@siemens.com>

[RFC PATCH v2 0/3] arm/kvm: select an nVHE-only EL2 with SYSREG_ID_AA64MMFR1_EL1_VH
Author: Haseeb Ashraf <haseebashraf091@gmail.com>


Hi,

KVM presents a VHE-only EL2 (HCR_EL2.E2H RES1) to a nested guest unless
KVM_ARM_VCPU_HAS_EL2_E2H0 is requested at vCPU initialization.  Guest
hypervisors which only support nVHE, such as Xen, cannot run in that
mode.  This series lets the user select an nVHE-only EL2 with:

  -M virt,virtualization=on -accel kvm \
      -cpu host,SYSREG_ID_AA64MMFR1_EL1_VH=0

Following Marc's feedback on v1, this is built on Eric Auger's
SYSREG_<REG>_<FIELD> framework instead of a new machine or CPU
property.  It is an RFC because that framework is not merged yet.

Dependencies
------------

The series applies on top of the remaining patches of Eric's v11 [1],
which are on his arm-cpu-model-v11-rc branch [2], rebased on current
master.  On current master those patches need two mechanical build
fixes: object_property_add() now takes &uint64_type_info, and
kvm_feature_idx_to_idregs_idx() must sit after kvm_arm_sve_get_vls()
instead of inside it.  The fixes belong to Eric's series and are not
part of these three patches.

Questions
---------

 - KVM does not let userspace write ID_AA64MMFR1_EL1.VH, so the generic
   "writable fields only" rule would not create the property.  Patch 2
   treats VH as selected through a vCPU init feature and exposes it as
   an exception.  Is that acceptable, or would you prefer a generic
   representation of such fields in the framework?
 - Only VH is updated in QEMU's copy of the ID registers.  Other fields
   which KVM derives from E2H0, for example ID_AA64MMFR4_EL1, are not
   refreshed.  Is that acceptable, or should QEMU re-read the ID
   registers after vCPU initialization?

Scope
-----

TCG and HVF are unchanged by design.  The property is available for the
host (and max) CPU model with KVM, when the host kernel advertises
KVM_CAP_ARM_EL2_E2H0.  Xen and QNX already boot with TCG, where
HCR_EL2.E2H is under the control of the guest.

Changes since v1 [3]:

  - Removed the dedicated virt machine and ARM CPU "vhe" properties.
  - Switched to Eric's SYSREG ID-register framework and use
    SYSREG_ID_AA64MMFR1_EL1_VH to select an nVHE-only EL2.
  - Exposed the property only when KVM advertises
    KVM_CAP_ARM_EL2_E2H0.
  - Derived KVM_ARM_VCPU_HAS_EL2_E2H0 from VH and rejected VH=0 when
    virtualization is disabled.
  - Added documentation and a KVM functional selftest which verifies
    that the guest hypervisor initializes in nVHE mode.

Testing
-------

Validation was performed on an AmpereOne A192-32X (Ampere-1a) running
host kernel 6.18.29+3-arm64:

  - TCG-only, KVM-only and aarch64-linux-user builds succeeded.
  - TCG rejects SYSREG_ID_AA64MMFR1_EL1_VH because the property does not
    exist for that accelerator.
  - The existing AArch64 KVM nVHE and VHE selftests pass under TCG.
  - The arm-cpu-features qtest passes.
  - Linux 6.12.67 initialized KVM in nVHE mode with VH=0 and in VHE mode
    with VH=1; both boots reached login.
  - QNX Hypervisor 8.0.5 reached login with both values and reported the
    corresponding ID register state.
  - Xen dom0 reached login with VH=0.  With VH=1, Xen did not boot.
  - The complete AArch64 KVM functional suite passed, including the new
    nVHE-only selftest.

Not tested: live migration, and hosts other than AmpereOne.

[PATCH v2 1/3] RISC-V: KVM: Order writes to the SBI STA shared structure
Author: Koichiro Den <den@valinux.co.jp>

The guest checks the sequence before and after reading steal time. If
the final even sequence becomes visible before the updated steal time,
the guest can accept a stale value. CSR accesses are weakly ordered;
toggling sstatus.SUM in get_user() and put_user() does not guarantee
that the guest observes those stores in order.

Pair the read barriers in pv_time_steal_clock() with write barriers.

Fixes: e9f12b5fff8a ("RISC-V: KVM: Implement SBI STA extension")
Signed-off-by: Koichiro Den <den@valinux.co.jp>

Changes since v1:

[PATCH v2 0/3] RISC-V: KVM: Lessen steal time update overhead
Author: Koichiro Den <den@valinux.co.jp>

Hi,

For guests that register an SBI STA shared-memory area, this small patch
set reduces update overhead by batching user accesses and also skipping
updates when run_delay is unchanged.

Tested on SpacemiT K3:
The benchmark uses KVM selftest helpers. The guest registers its STA
shared memory and calls GUEST_UCALL_NONE() in a loop. The vCPU thread is
pinned to one host CPU and re-enters KVM_RUN after each exit.

The table shows the median vCPU thread CPU time per round trip (from
host userspace to the guest and back), measured with
CLOCK_THREAD_CPUTIME_ID. Each case has five runs of 1,000,000
iterations, preceded by 10,000 warm-up iterations per run.
Below, "contended" adds a busy loop on that CPU.

                Before      After
  ------------  ----------  -------------------
  uncontended   2900.01 ns  2669.59 ns (-7.95%)
  contended     2876.42 ns  2670.01 ns (-7.18%)

Based off of riscv_kvm_next, commit e9bf49bbc422 ("RISC-V: KVM: Fix
G-stage page table memory leak on VM destroy")

[PATCH 1/1] hw/arm/virt: add vhe option for nested virtualization
Author: Haseeb Ashraf <haseebashraf091@gmail.com>


Add a vhe machine property for the virt board. When virtualization=on,
VHE remains enabled by default, but vhe=off allows nVHE/type-1 guest
hypervisors to run without VHE.

Propagate the setting to the ARM CPU, limit TCG to nVHE mode, and request
the KVM_ARM_VCPU_HAS_EL2_E2H0 vCPU initialization flag when VHE is
disabled. Reject vhe=off when the selected accelerator cannot provide
the requested behavior. The option has no effect unless
virtualization=on is also set.

Document the option, and make the nested virtualization functional test
pass a vhe setting matching the kernel mode.

Tested nested virtualization with KVM on arm64 hosts using L0 kernel
versions 6.18.29 and 7.2.11. A Linux 6.12.67 guest initialized KVM in
nVHE mode with vhe=off and VHE mode with vhe=on. QNX Hypervisor 8.0.5
detected EL1 host hypervisor support with vhe=off and EL2 host
hypervisor support with vhe=on. Xen booted dom0 to the login prompt with
vhe=off, but did not boot with vhe=on.

Tested with TCG on an AmpereOne A192-32X host. QNX Hypervisor 8.0.5
boots with both vhe settings, and Xen boots its dom0 with vhe=off.

Suggested-by: Volodymyr Babchuk <volodymyr.babchuk@epam.com>
Signed-off-by: Haseeb Ashraf <haseeb.ashraf@siemens.com>
