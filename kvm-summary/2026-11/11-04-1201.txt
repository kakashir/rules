New:  vsock: assign the guest vsock device to a
[PATCH net-next v5 0/7] vsock: assign the guest vsock device to a
Author: Bobby Eshleman <bobbyeshleman@meta.com>

vsock network namespaces let a host put each VM in a namespace of its
own. A guest has no equivalent yet. It has a single G2H device that
cannot be assigned to a network namespace.

This series lets a guest move that device into a network namespace. A
new generic netlink family, "vsock", supports the command
VSOCK_CMD_DEV_NETNS_SET which assigns the device to the namespace the
request was sent from. The namespace's existing ns_mode then decides who
may use it: a "global" namespace shares the device with every other
global namespace, and a "local" namespace keeps the host connection to
itself. The device starts out in the initial namespace, so until the
command is issued nothing has moved and no mode has changed. There is no
explicit unassign as assigning the device back to the initial namespace
is equivalent.

The command requires CAP_NET_ADMIN in the initial user namespace, so
that an unprivileged user namespace cannot claim the device.

Connections that can no longer reach the device after a move are reset,
so that a namespace which has lost access cannot keep using a socket it
opened while it still had access. The assignment holds a reference on
the namespace, so deleting that namespace does not move the device; only
another assignment does.

Transports opt in through a new netns_assign_allow flag. Only
virtio-vsock sets it here, because it is the only guest transport
that I am able to test against.

Based off of Stefano's original series:

New:  KVM: x86/mmu: Allocate memslot rmaps on demand
[RFC PATCH 0/5] KVM: x86/mmu: Allocate memslot rmaps on demand
Author: Fred Griffoul <griffoul@gmail.com>


When an L1 guest runs a nested guest, KVM allocates rmaps for all of
L1's memory the first time it creates a shadow root, one 8-byte head
per 4 KiB page. For an L1 with 4 TiB of memory that is 8 GiB, allocated
at once on the first nested VM-Enter, whether L2 maps 1% or all of L1's
memory. Sean pointed at this cost on Mushahid's lpage_info patch [1].

This RFC allocates rmaps in page-sized chunks instead, when the first
SPTE in a chunk's range is added. Each memslot keeps a per-level
directory of chunks, 8 bytes per 2 MiB at the 4 KiB level, so the 4 TiB
L1 above allocates 16 MiB on the first nested VM-Enter. A missing chunk
reads as empty rmaps and slot walks skip it. When L2 maps every gfn,
rmaps cost what they did before plus the directory.

Patches 1 and 2 prepare the slot walk and the debugfs rmap statistics,
with no functional change. Patch 3 does the chunking. Patches 4 and 5
add a selftest in which L2 writes pages around chunk boundaries and
checks the dirty log after the memslot is write-protected, including
eager splitting of nested huge pages.

I would like feedback on:
  - The data structure. A directory of page-sized chunks keeps lookups
    to one extra load. An xarray would be simpler to grow but adds a
    tree walk to every rmap lookup.
  - Freeing chunks once they are empty. That would let the shadow MMU
    page limit bound rmap memory too, but lockless aging reads chunks
    without mmu_lock, so freeing needs an RCU grace period. I left it
    out of this RFC.
  - Doing the same for gfn_write_track, 2 bytes per 4 KiB page, which
    is still allocated for every memslot on the first shadow root.

Limitations:
  - Chunks are only freed with the memslot.
  - Eager page splitting on dirty-log enable splits L2's huge mappings,
    so every 2 MiB that L2 mapped with a huge page then gets a chunk.

The series is based on kvm.git next.

[1] https://lore.kernel.org/all/arr1VgGZmgUmY4hc@google.com/

New:  KVM: Add helpers to allocate memslot metadata
[PATCH] KVM: Add helpers to allocate memslot metadata
Author: Fred Griffoul <griffoul@gmail.com>


__vcalloc() makes every allocation at least one page, so a memslot
that spans a single page uses 8 KiB of vmalloc for 8 bytes of
lpage_info, plus 4 KiB for a 16-byte dirty bitmap once dirty logging
is enabled. The waste grows with the number of memslots and VMs on a
host. kvcalloc() avoids it for small arrays, but refuses allocations
above INT_MAX bytes, which the rmap and write-tracking arrays of a
large memslot exceed.

Add kvm_memslot_metadata_alloc() and kvm_memslot_metadata_free(),
which use kvzalloc() up to INT_MAX bytes and vmalloc above, and route
the dirty bitmap, rmaps, lpage_info and write-tracking arrays through
them. That way, how KVM allocates memslot metadata is decided in one
place instead of at each array.

Suggested-by: Sean Christopherson <seanjc@google.com>
Link: https://lore.kernel.org/all/arr1VgGZmgUmY4hc@google.com/

New:  KVM: nSVM: Validate L1 host save state restored on RSM from SMM
[PATCH] KVM: nSVM: Validate L1 host save state restored on RSM from SMM
Author: Abdelali Maddane <ma.08@web.de>

When an SMI is taken while L2 is running, svm_enter_smm() saves L1's host
state into the HSAVE area (ordinary guest memory pointed to by
MSR_VM_HSAVE_PA).  On RSM, svm_leave_smm() copies that state back into
vmcb01 and builds the nested MMU from it, but unlike KVM_SET_NESTED_STATE
it does not validate the restored state.

Because the HSAVE area is guest memory, L1 can modify it while the vCPU is
in SMM so that RSM loads an impossible EFER.LMA=3D1 && EFER.LME=3D0 combin=
ation
(e.g. together with CR4.PAE=3D0).  kvm_calc_cpu_role() then computes a 4- =
or
5-level role while shadow_mmu_init_context() wires up the 2-level paging32
template, and FNAME(walk_addr_generic) indexes out of bounds of the
fixed-size guest_walker arrays.  On kernels carrying the KVM_BUG_ON()
backstop in kvm_calc_cpu_role() this is a guest-triggerable KVM_BUG_ON()
(dead VM, or a host panic with panic_on_warn); on older kernels it is an
out-of-bounds access in the page-table walker.

Validate the restored L1 host state in svm_leave_smm() with the same check=
s
KVM_SET_NESTED_STATE already applies to L1 host state, factored out into
nested_svm_check_l1_save().  A failed check fails RSM, which is the correc=
t
response to an impossible saved state.

The patch, reproducer, and this changelog were developed with substantial
help from an AI assistant (Anthropic's Claude Code), directed and reviewed
by the submitter.  Tested by the submitter on an AMD EPYC host: without th=
e
patch a reproducer triggers the guest-reachable KVM_BUG_ON() in
kvm_calc_cpu_role(); with the patch the reproducer is rejected, and the
smm_test and svm_nested_shutdown_test selftests still pass.

Fixes: 37be407b2ce8 ("KVM: nSVM: Fix L1 state corruption upon return from =
SMM")
Signed-off-by: Abdelali Maddane <ma.08@web.de>

Motivation
==========
The firmware on s390x machines allows for tracking a variety of statistics
relating to zPCI devices in a function measurement block (FMB). However,
the kernel currently lacks a structured mechanism of sharing this
information with userspace, beyond /sys/kernel/debug/pci/ID/statistics.
This can lead to shortcomings when running a guest on KVM with PCI
passthrough devices, as QEMU is unable to provide an accurate FMB snapshot
to the guest.

Proposal
========
We propose adding a new VFIO device feature to zPCI passthrough devices,
allowing userspace programs to read the latest FMB snapshot as it is
written by the firmware. We ensure that function measurement enablement is
preserved across device resets on the host. Furthermore, we guard against
host tampering with the FMB via sysfs when the zPCI device is in
passthrough to protect the VM's state.

I'd appreciate some feedback on these patches.

New:  KVM: register asynchronous page fault waits with interrupts disabled
[PATCH 1/2] KVM: register asynchronous page fault waits with interrupts disabled
Author: Paolo Bonzini <pbonzini@redhat.com>

Asynchronous page fault handling has some wonky code to detect page ready
notifications that are sent before the waiter is registered.  When page
ready notifications for asynchronous page faults were separated from
not-present notifications and turned into an interrupt, this code was
unwittingly made almost-redundant.  Page ready notification is now delayed
until after interrupts are enabled; and for an asynchronous page faults
that occur outside guest mode, Linux never enables interrupts between the
delivery of the #PF exception and the call to kvm_async_pf_queue_task().
Therefore, the dummy allocation path is fully dead on that common path.

For the nested virtualization case, however, vmx.c and svm.c do
record in the interrupt-disabled region whether a #PF vmexit is an
asynchronous page fault, but they defer registration of the waiter until
kvm_handle_page_fault().  Because of this, the vCPU thread can be preempted
before kvm_async_pf_task_wait_schedule() is called, and apf_task_wake_one()
may them not find the vCPU thread in the waiters list.  It then allocates
the struct kvm_task_sleep_node* on behalf of the task that received the
asynchronous page fault.  Besides keeping alive the wonky code, allocating
the node from an hardirq-disabled region is a problem for PREEMPT_RT kernels,
as duly reported by syzkaller.

Split registration from wait so that the caller decides where to
put the node and so that KVM can anticipate the registration before
interrupts are enabled.  KVM cannot use a node on the stack like
kvm_async_pf_task_wait_schedule() does, but it can place it in the vCPU
struct instead.

New:  KVM: remove the dummy allocation case from async page fault handling
[PATCH 0/2] KVM: remove the dummy allocation case from async page fault handling
Author: Paolo Bonzini <pbonzini@redhat.com>

Asynchronous page fault handling is supposedly able to detect page
ready notifications that are sent before the waiter is registered,
but this code is broken for PREEMPT_RT because it tries to allocate in
hardirq-disabled context.

This code however is almost dead, because page ready notification will
happen on the same vCPU as the waiter and not until after the waiter
enables interrupts.  Outside guest mode, interrupts are only enabled once
the waiter has registered itself, and this guarantees that an outstanding
(non-spurious) waiter will always be found.  This unfortunately is not
the case for asynchronous page faults that are delivered while in guest
mode, but that can be fixed and the dubious code removed.

New:  PCI/P2PDMA: Honor device-specific ACS redirection
[PATCH v12 01/19] PCI/P2PDMA: Honor device-specific ACS redirection
Author: Leon Romanovsky <leon@kernel.org>


Some ports, such as Zhaoxin Switch Downstream Ports, redirect peer-to-peer
traffic without an ACS capability, as their device-specific ACS quirks
report. P2PDMA reads only ACS Control, so below such a port it hands out
bus addresses for traffic that goes to the host bridge.

endpoint quirks, which only describe traffic between an endpoint's own
functions. Skip bridges on a root bus: they never sit between two peers,
and the AMD southbridge quirk may sleep there during DMA mapping.

pci=disable_acs_redir= cannot override a quirk, so name such ports
separately.

New:  PCI/P2PDMA: Route peer-to-peer DMA by TLP class
[PATCH v12 00/19] PCI/P2PDMA: Route peer-to-peer DMA by TLP class
Author: Leon Romanovsky <leon@kernel.org>

PCI P2PDMA applies Request and Completion Redirect throughout both paths.
This misclassifies asymmetric and nested switches, and reports one answer
for every kind of TLP.

Three ACS controls act on TLP attributes the Requester chooses rather
than on the topology: Translation Blocking and Direct Translated P2P act on
a Request's Address Type, and Completion Redirect skips Completions carrying
Relaxed Ordering.

Evaluate each direction at the path divergence, decide every class from the
one walk, and treat a client with ATS enabled as translating unless its
driver declares per-mapping ATS.

This completes the P2PDMA side; dma-buf and mlx5 follow separately.

Signed-off-by: Leon Romanovsky <leonro@nvidia.com>

New:  KVM: x86/mmu: Batch masked dirty clearing within leaf page
[PATCH] KVM: x86/mmu: Batch masked dirty clearing within leaf page
Author: Hao Zhang <hao_zhang_kdev@163.com>


Walk the TDP page tables down to L2 when clearing a dirty-log bitmap word,
and update the selected 4KiB SPTEs directly in each child page table.

clear_dirty_pt_masked() currently uses the generic TDP iterator to visit
individual leaf mappings. For a densely populated bitmap word, this repeats
the iterator's traversal and entry checks for adjacent SPTEs in the same
page table. Sparse masks can also cause unselected entries to be visited.

Use the existing minimum-level iterator to locate each L1 page table
through its parent. The GFN range covered by a bitmap word can cross a
2MiB boundary. Clip a private copy of the mask to each table's coverage,
keeping bit indices relative to the original GFN.

Locate the first covered SPTE once per batch, then use relative offsets for
the selected bits. This avoids recomputing the SPTE index in the inner loop
and avoids reading and checking unselected 4KiB entries.

The write side of mmu_lock keeps the parent-child link stable, and the RCU
read-side critical section protects the page-table memory. Retain the
existing SPTE update helper and tracing semantics. Continue to skip huge
mappings, as before. Preserve the generic iterator and the caller's TLB
flush behavior.

For an 8-vCPU dirty-log benchmark with a 768MiB tracked region, reduce
KVM_CLEAR_DIRTY_LOG time by approximately 42-51% on the tested Intel host
with PML enabled.

New:  KVM: arm64: Use S1E1A when Stage-1 PIE is supported
[PATCH] KVM: arm64: Use S1E1A when Stage-1 PIE is supported
Author: Will Deacon <will@kernel.org>

On a system with stage-1 PIE, a guest can try to execute from an
execute-only mapping at stage-1 but trigger a permission fault at
stage-2 if the stage-2 mapping is execute-never.

In this case, the EL2 permission fault handler will attempt to translate
the faulting VA using an AT S1E1R operation, which will fail due to the
lack of read permission at stage-1. We will then return to the guest and
take the exact same fault the next time around.

Similarly to commit 55f4b215fb60 ("KVM: arm64: use `at s1e1a` for POE"),
use the S1E1A operation to bypass stage-1 permission checks when
obtaining the IPA for a stage-2 permission fault. Like FEAT_S1POE,
FEAT_S1PIE implies FEAT_ATS1A, so extend the existing AT invocation in
__translate_far_to_hpfar() to use the permission-bypassing variant when
S1PIE is implemented.

New:  KVM: arm64: Don't walk the whole IPA space when destroying a pKVM stage-2
[PATCH 1/3] KVM: arm64: Don't walk the whole IPA space when destroying a pKVM stage-2
Author: Fuad Tabba <fuad.tabba@linux.dev>

Since commit 4ddfab5436b6 ("KVM: arm64: Reschedule as needed when
destroying the stage-2 page-tables"), kvm_stage2_destroy() steps through
the IPA space in block-sized chunks, and with pKVM each chunk is a
lookup in the VM's mapping tree. However, pKVM gives every VM the host's
IPA limit, so with LPA2 a teardown makes 2^27 lookups with 16K pages
(2^22 with 4K), nearly all of them for empty space.

Walk the mapping tree once instead, and reschedule after passing each
mapping to the reclaim or unshare helper. The unshare helper can't
reschedule itself, as the map and unmap paths call it under the
mmu_lock. A failed unshare now leaves only its own mapping behind, not
the rest of its chunk.

Fixes: 4ddfab5436b69 ("KVM: arm64: Reschedule as needed when destroying the stage-2 page-tables")

Two fixes for stage-2 teardown, which since 4ddfab5436b6 takes time
