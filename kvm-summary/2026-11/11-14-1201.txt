New:  vsock: assign the guest vsock device to a
[PATCH net-next v6 0/8] vsock: assign the guest vsock device to a
Author: Bobby Eshleman <bobbyeshleman@meta.com>

vsock network namespaces let a host put each VM in a namespace of its
own. A guest has no equivalent yet. It has a single G2H device that
cannot be assigned to a network namespace.

This series lets a guest move that device into a network namespace. A
new generic netlink family, "vsock", supports the command
VSOCK_CMD_DEV_NETNS_SET which assigns the device to the namespace given
by fd or PID, or else to the namespace the request was sent from. The namespace's existing ns_mode then decides who
may use it: a "global" namespace shares the device with every other
global namespace, and a "local" namespace keeps the host connection to
itself. The device starts out in the initial namespace, so until the
command is issued nothing has moved and no mode has changed. There is no
explicit unassign as assigning the device back to the initial namespace
is equivalent.

The command requires CAP_NET_ADMIN in the initial user namespace, so
that an unprivileged user namespace cannot claim the device.

Connections that can no longer reach the device after a move are reset,
so that a namespace which has lost access cannot keep using a socket it
opened while it still had access. The assignment holds a reference on
the namespace, so deleting that namespace does not move the device; only
another assignment does.

Transports opt in through a new netns_assign_allow flag. Only
virtio-vsock sets it here, because it is the only guest transport
that I am able to test against.

Based off of Stefano's original series:

New:  vsock: only undo SS_CONNECTING when
[PATCH net-next v6 1/8] vsock: only undo SS_CONNECTING when
Author: Bobby Eshleman <bobbyeshleman@meta.com>

vsock_connect() sleeps with the socket unlocked. Meanwhile the transport
can complete the handshake, setting sock->state to SS_CONNECTED, and then
reset the connection, e.g. in vhost_vsock_reset_orphans(),
virtio_vsock_reset_sock() or vmci_transport_handle_detach(). When
connect() gets the lock back, it finds sk_err set and moves the socket
back to SS_UNCONNECTED. Userspace can then connect() the socket again,
and a connect() to a CID on another transport makes
vsock_assign_transport() release the transport the socket was connected
on.

Only move the socket back to SS_UNCONNECTED if it is still
SS_CONNECTING. A socket that got connected stays SS_CONNECTED, and
another connect() fails with -EISCONN.

Fixes: d021c344051a ("VSOCK: Introduce VM Sockets")

New:  KVM: Implement per-plane memory attributes
[RFC PATCH v2 01/31] KVM: Implement per-plane memory attributes
Author: David Woodhouse <dwmw2@infradead.org>


Memory attributes lived solely on struct kvm and the page role carried
no plane identity, so every plane shared one attribute array and one
set of TDP roots. A VTL1 guest protecting VTL0 pages therefore revoked
its *own* access too: the Windows secure kernel's first
HvCallModifyVtlProtectionMask made its own hypercall page
non-executable, and the next VTL transition died on an unhandled
protection fault.

Give each non-zero plane its own attribute xarray. Plane 0 keeps
kvm->mem_attrs, which also carries partition-wide attributes such as
KVM_MEMORY_ATTRIBUTE_PRIVATE. KVM_SET_MEMORY_ATTRIBUTES is accepted on
plane fds, restricted to the NR/NW/NX protection bits, and the plane
joins kvm_mmu_page_role so each plane builds its own roots with its own
protections applied at fault time.

Guest accesses are checked against the attributes of the plane doing
the access, not plane 0's:

 - the vCPU-context hva lookups and kvm_vcpu_map();
 - the guest page read/write helpers, which gain a kvm_plane argument
   (the VM-level variants keep checking plane 0);
 - the software page walker's PTE reads;
 - the emulator's memory-fault classification (an access its own plane
   protects becomes KVM_EXIT_MEMORY_FAULT, not MMIO) and its instruction
   fetch NX check;
 - the slow-form Hyper-V hypercall inputs (TLB flush, send IPI and the
   sparse VP sets and flush entries they read) and the pvclock wall
   clock written by an MSR, all of which run with the issuing vCPU at
   hand and so switch from kvm_read_guest()/kvm_write_guest() to the
   vCPU variants.

Without that, a higher plane is refused access to pages it has itself
protected against plane 0; the secure kernel's VP assist page
registration and the walks through its own protected page tables both
fail exactly there.

Cached gfn->hva translations (gfn_to_hva_cache and pfncache, used for
steal time, PV EOI and pvclock) have no plane context at use time, so
they are refused when *any* plane protects the range with NR or NW.

Hugepage mixed-attribute tracking still follows plane 0 only. Faults
on other planes clamp to 4KiB whenever the plane carries any attribute
within the maximal mapping range, and TDP MMU huge-page recovery skips
their roots, so a recovered 2MiB or 1GiB SPTE cannot lift a 4KiB
protection on a neighbouring gfn.

The plane arrays are memcg-accounted like plane 0's. An attribute update
that fails part-way now releases the xa_reserve() placeholders it left
behind, on the VM fd as well as on plane fds, so a failed update cannot
look like an attribute to the range lookups.

role.smm gives up its eighth bit to make room for role.plane. It
only had a whole byte to be faster to load, and it stays at the top
of the word so kvm_memslots_for_spte_role() still extracts it with a
shift.

Mushahid Hussain supplied the !KVM_GENERIC_MEMORY_ATTRIBUTES stub of
kvm_plane_get_memory_attributes() that keeps the other architectures
building.

Signed-off-by: David Woodhouse <dwmw@amazon.co.uk>

New:  KVM: x86: Hyper-V VSM (Virtual Trust Levels) on VM planes
[RFC PATCH v2 00/31] KVM: x86: Hyper-V VSM (Virtual Trust Levels) on VM planes
Author: David Woodhouse <dwmw2@infradead.org>


This is v2 of the Hyper-V VSM support¹: Windows Virtualization Based
Security running natively on KVM planes, with the secure kernel in
VTL1 isolated from the normal kernel in VTL0, instead of using nested
virtualization.

This is still largely AI-written with minimal oversight so far; it's
presented to show the direction and for testing, not for detailed
review.

As before, it boots Windows Server 2016 through 2025 with Credential
Guard active, on both Intel and AMD hosts, with VTL1 protecting its
memory from VTL0, and survives hibernate/resume. It also runs VBS
enclaves: the full CreateEnclave / LoadEnclaveImage / InitializeEnclave
/ CallEnclave cycle behaves as it does on real Hyper-V. The userspace
side is still a separable, permissively-licensed library, pulled into
QEMU for testing.

Since v1:

 • Rebased to v7.4-rc2. Paolo's memory protection attributes are now
   merged in from kvm.git² rather than carried as patches.
 • Three parts grew up and left home: the fixes to Jörg's series³,
   the forwarding of unimplemented Hyper-V hypercalls to userspace⁴
   and the generic plane userspace API⁷ are posted separately, and
   this series is based on them.
 • This is now the *minimum* VSM: what it takes to boot Windows with
   Credential Guard and keep VTL1's memory protected. The parts it
   can live without — KVM_TRANSLATE on plane fds, VTL-switch
   statistics, the Hyper-V vCPU suspended state and the TLB flush
   inhibit (KVM_HYPERV_SET_TLB_FLUSH_INHIBIT) — sit above it in git⁵
   and will follow once this part makes sense to people.
 • KVM_TRANSLATE2 is gone. The userspace library walks the guest
   page tables itself for HvTranslateVirtualAddress, which it turned
   out to need to do anyway.
 • The hypercall exit gained a flags field (KVM_HYPERV_HCALL_UD) for
   fault injection instead of stealing bit 63 of the result, so a
   forwarded hypercall can return a full 64-bit result.
 • A pile of fixes from review, each noted in its commit.

The base is Jörg's KVM Planes + SEV-SNP series⁶ with the fixes³ and
the plane userspace API⁷ applied; kvm-memprot-v4² and the hypercall
forwarding⁴ are merged on top. None of that is reposted here. The
whole assembly, and the userspace to drive it:

 • https://git.infradead.org/?p=users/dwmw2/linux.git;a=shortlog;h=refs/heads/vsm2/vsm-min (tag vsm2-min1)
 • https://git.infradead.org/?p=users/dwmw2/qemu.git;a=shortlog;h=refs/heads/vsm-v2
 • https://git.infradead.org/?p=users/dwmw2/kvm-unit-tests.git;a=shortlog;h=refs/heads/vsm-v2

The 31 patches here are VSM itself: per-plane memory
attributes and overlays, the per-plane Hyper-V state (GUEST_OS_ID,
hypercall page, reference TSC page, SynIC, STIMER), VTL call/return
and the VTL-protection fault path, interrupt preemption and forced
VTL entry, and the register intercepts Windows actually uses.

Patch 28 (KVM: SVM: Keep TPR[3:0] across exits without a guest CR8
write) is a fix in its own right: the bug exists without planes, so
it should probably be applied standalone. I can send it separately

New:  KVM: planes: Userspace API
[RFC PATCH 00/13] KVM: planes: Userspace API
Author: David Woodhouse <dwmw2@infradead.org>


The VSM work¹ drives planes from userspace, which takes a little
more API than the planes series² itself provides: an explicit
userspace opt-in (enabling KVM_CAP_PLANES with the plane count,
before any vCPU is created), KVM_GET/SET_PLANE_RUN_STATE vCPU
ioctls, and the mechanics to go with them — per-plane requests
fanned out to the twin vCPUs, XCR0 shared across twins (with every
twin's fpstate sized for the dynamic xfeatures that allows), and
APICv inhibited while planes are enabled (for now). With selftests,
including Paolo's plane infrastructure tests from the original
planes RFC³, ported forward.

Posted separately from the VSM RFC v2 (to follow) so this part can

New:  KVM: x86: Let userspace opt in to multiple planes with KVM_CAP_PLANES
[RFC PATCH 01/13] KVM: x86: Let userspace opt in to multiple planes with KVM_CAP_PLANES
Author: David Woodhouse <dwmw2@infradead.org>


A VMM implementing a software privilege model such as Hyper-V VSM
needs more than one plane, but kvm_arch_max_planes() returns the
vendor ceiling, which is 1 everywhere except SEV-SNP (where VMPLs are
guest-architectural), so KVM_CREATE_PLANE rejects every id above zero.

Make KVM_CAP_PLANES a VM enable capability taking the number of planes
userspace is going to manage, up to KVM_MAX_USER_PLANES (4), which the
system fd now reports. It must be set before any vCPU or extra plane
exists, so nothing is sized against the old limit, and cannot be changed
once set. It also needs a split irqchip, which kvm_arch_max_planes()
already requires before it reports more than one plane, so enabling it
without one fails instead of silently granting a single plane, and
KVM_CREATE_IRQCHIP is refused afterwards. Non-default VM types are
rejected: SEV-SNP keeps deriving its count from the supported VMPLs,
and protected-state VM types need their own audit first. So is more
than one plane without TDP: with shadow paging every plane would
write-track the guest page tables, and the per-gfn write-track count
is only 16 bits wide. The same count is why the opt-in stops at four
planes even with TDP: nested guests still have write-tracked shadow
pages, each plane can add its own for a gfn, and four planes is the
most that keeps the count below 2^16. KVM_MAX_PLANES stays 16, the
bound for plane ids. A VM that does not enable the capability keeps
reporting a single plane.

New:  KVM: selftests: Make the x86 SSE register helpers volatile
[PATCH] KVM: selftests: Make the x86 SSE register helpers volatile
Author: David Woodhouse <dwmw2@infradead.org>


read_sse_reg() and write_sse_reg() were borrowed from KVM's
_kvm_read_sse_reg() and _kvm_write_sse_reg(). The kernel is built
without SSE, so the compiler never uses the XMM registers itself and a
plain asm() is enough there. Selftest guest code is built with SSE, and
there the asm statements have to tell the compiler what they do.

read_sse_reg() has an output and is not volatile, so the compiler may
treat it as a pure computation and move it, for example ahead of the
hypercall whose XMM output it is meant to read. write_sse_reg() has no
outputs and is therefore implicitly volatile, but it doesn't declare the
register it overwrites, so a value the compiler was keeping there does
not survive.

Mark both volatile, and declare the register each write_sse_reg() case
writes as clobbered. A read_sse_reg() after __hyperv_hypercall() now
stays after it.

That still leaves the compiler free to use an XMM register for its own
code between a write_sse_reg() and the asm which consumes it.
hyperv_write_xmm_input() in the hyperv_ipi and hyperv_tlb_flush tests
relies on that not happening; GCC 11.5 at -O2 emits nothing there.
Closing that window entirely would mean passing the XMM values as
operands of the hypercall asm itself.

New:  KVM: x86: Leave nested if vendor specific logic fails on RSM
[PATCH] KVM: x86: Leave nested if vendor specific logic fails on RSM
Author: Sean Christopherson <seanjc@google.com>

Force the vCPU into L1 before synthesizing SHUTDOWN if RSM to L2 fails due
to vendor specific checks, e.g. because SMRAM was corrupted with illegal
state, and the bad state was detected *after* starting the transition back
to L2.  Architecturally, any fatal error when loading CPU state during RSM
is supposed to send the CPU into SHUTDOWN *before* switching to guest mode,
and leaving the vCPU in L2 is all but guaranteed to effectively corrupt
vCPU state (which doesn't matter for the guest since it's already hosed,
but matters if userspace misbehaves and ignores the SHUTDOWN, i.e. runs the
vCPU even though it's in a bad state).

New:  vsock: add datagram support to virtio and vhost
[PATCH RFC v3 0/8] vsock: add datagram support to virtio and vhost
Author: Sergio Lopez <slp@redhat.com>

This RFC adds SOCK_DGRAM support to virtio-vsock and vhost-vsock through
the existing AF_VSOCK API. It is intended for guest and host services
that exchange independent requests, responses, or events and need message
boundaries and sender addresses without a stream connection or application
framing.

VIRTIO_VSOCK_F_DGRAM gates virtio traffic in both directions. Each virtio
send carries zero to 64 KiB of payload in one VIRTIO_VSOCK_TYPE_DGRAM
packet. On the RX virtqueue, the device may split a datagram across
page-sized guest buffers.
START and EOM delimit the message; the guest reassembles at most 64
fragments and 64 KiB before delivering it to a socket. Invalid or
incomplete messages are discarded. Datagram delivery is best effort:
there are no peer credits, acknowledgements, or retransmissions. Send
admission uses the socket send-memory limit, and SIOCOUTQ reports charged
send memory.

Datagram sockets have a separate port space from stream and seqpacket
sockets. The latter two continue to share their port space. Datagram
routes are chosen per destination among guest-to-host, host-to-guest, and
loopback transports, with VMCI as a fallback. VMCI still owns its socket
handle when it is present; loopback works without a directional transport.
Hyper-V continues to reject datagram sockets.

The Sashiko review of v2 also reported that a VMCI datagram bind in a
local-mode network namespace creates a receive handle in VMCI's global
port space, so a sender outside the namespace can deliver datagrams
across the namespace isolation boundary. The issue predates this series
and it's getting addressed in a separate patch:

https://lore.kernel.org/all/20261113-vsock-vmci-netns-isolation-v1-1-ced02054ea61@redhat.com

Within this series, local-mode namespaces bind datagrams only in the
core table and never create a VMCI handle.

Bobby Eshleman and Amery Hung explored this feature in their v6 series
and v7 work-in-progress branch. This series is a fresh implementation
against the current vsock code. It follows the separate datagram port
space, per-destination routing, and VMCI fallback requirements discussed
there. For guest receive buffers, it uses bounded fragmentation and
reassembly rather than full-message buffers or the earlier drop/error
queue approach:

https://lore.kernel.org/r/20240710212555.1617795-1-amery.hung@bytedance.com
https://github.com/ameryhung/linux/tree/vsock-dgram-v7

A corresponding virtio specification update has been drafted separately.
The wire format and feature negotiation still need specification review
before this series can be considered for merging.

The first patches expose the core port allocator and add datagram queue
reporting, then implement the common data path, guest and host feature
negotiation, routing, and RX fragmentation. The last patch extends
vsock_test with local and peer tests for message boundaries, routing,
connected peers, port sharing, queue accounting, and delayed reads.

Testing used QEMU with the F_DGRAM property patch below, an x86-64
KASAN/lockdep kernel, paired guest tests, and a nested Linux vhost-vsock
backend. The tested paths include 64 KiB messages, delayed-read bursts,
feature-disabled ingress, stream and seqpacket controls, and header-only
guest RX buffers. A temporary userspace backend still fails stream test
21 on both the series base and tip; that case passes with Linux vhost.
VMCI's host personality was exercised in a QEMU guest, including
coexistence with virtio and self-send without loopback. A VMware VMCI guest
device and Hyper-V hardware were not exercised.

https://lists.gnu.org/archive/html/qemu-devel/2026-10/msg08074.html

Code was written and reviewed both manually and assisted by Codex
(GPT-6.1-Sol) and Claude (Opus 4.6).

New:  KVM: x86: hyper-v: Add KVM_CAP_HYPERV_FORWARD_HCALL
[PATCH v2 1/4] KVM: x86: hyper-v: Add KVM_CAP_HYPERV_FORWARD_HCALL
Author: David Woodhouse <dwmw2@infradead.org>


A VMM that implements Hyper-V hypercalls KVM does not know about has
no way to receive them. kvm_hv_hypercall() fails an unknown code with
HV_STATUS_INVALID_HYPERCALL_CODE, and only a fixed set (the synthetic
debugger, memory-based extended hypercalls, HvCallPostMessage and the
HvCallSignalEvent fallback) ever exits to userspace.

Add a VM capability whose KVM_CHECK_EXTENSION value is a bitmask of the
hypercall handling features the kernel implements, as KVM_CAP_XEN_HVM

probe for exactly the behaviour it relies on.

KVM would have failed as unknown, and an extended hypercall in fast
form, out through the existing KVM_EXIT_HYPERV_HCALL. That exit already
carries the control value and both parameter registers, and XMM state
is reachable through the ordinary vCPU state ioctls, so no new exit
format is needed.

New:  KVM: x86: hyper-v: Forward unimplemented hypercalls to userspace
[PATCH v2 0/4] KVM: x86: hyper-v: Forward unimplemented hypercalls to userspace
Author: David Woodhouse <dwmw2@infradead.org>


KVM implements a fixed set of Hyper-V hypercalls and fails every other
code with HV_STATUS_INVALID_HYPERCALL_CODE. A VMM that wants to
implement more of the TLFS, such as the VSM hypercalls Windows uses for
Virtualization Based Security, never sees them.

This series adds KVM_CAP_HYPERV_FORWARD_HCALL. As with KVM_CAP_XEN_HVM
and KVM_CAP_EXIT_HYPERCALL, KVM_CHECK_EXTENSION returns a bitmask of
features and KVM_ENABLE_CAP takes the subset to enable, rejecting any
bit the kernel does not report. The first feature,
KVM_HYPERV_HCALL_FORWARD_UNKNOWN, sends the hypercalls KVM does not
implement, and extended hypercalls in fast form, out through the
existing KVM_EXIT_HYPERV_HCALL exit, whose format does not change at
all. Further mask bits will follow for HvCallVtlCall and HvCallVtlReturn
on VMs with planes, so that KVM can handle VTL transitions in the
kernel.

Patch 2 lets userspace cancel the pending completion of a hypercall
that exited to userspace, with a new KVM_VCPUEVENT_CANCEL_HCALL flag on
KVM_SET_VCPU_EVENTS. The guest then re-executes the hypercall, unless
the same ioctl queued an exception to be delivered at it. That is how a
VMM makes a hypercall raise #UD (or #PF with CR2, or anything else the
events machinery can queue), which the TLFS specifies for some invalid
uses, instead of returning a status. It is independent of the rest of
the series: in v1 this was a #UD request flag in the hcall exit itself,
but the KVM_EXIT_VMWARE series [1] wants the same for other exits and
other vectors, and KVM_SET_VCPU_EVENTS already knows how to queue every
exception shape, so v2 adds only the cancel primitive and lets the
existing machinery do the rest. KVM_SET_VCPU_EVENTS has no flag
discovery, so KVM_CHECK_EXTENSION(KVM_CAP_VCPU_EVENTS) becomes a
feature mask (bit 0 keeps truth-value checks working, bit 1 advertises
the cancel). The KVM_VCPUEVENT_ namespace so far only holds VALID_*
field gates; if the action flag wants a different name, I am not
attached to this one.

Patch 3 reports HV_X64_HYPERCALL_XMM_OUTPUT_AVAILABLE, since a VMM
handling a forwarded fast hypercall can write the XMM output itself.
Patch 4 adds the Hyper-V forwarding selftest; the generic cancel error
paths come with patch 2's own selftest.

v1->v2:
 - Drop KVM_HYPERV_HCALL_RAISE_UD, KVM_HYPERV_HCALL_UD and the hcall
   exit's flags field; cancel the completion through
   KVM_SET_VCPU_EVENTS instead (patch 2).
 - Selftests: a generic vcpu_events_cancel_test, and forwarding-test
   legs for cancel+#UD (RIP and RAX untouched), cancel alone (the
   hypercall exits a second time), and EBUSY with nothing cancellable
   pending.

The series is based on v7.4-rc2. Tested on a bare-metal AMD EPYC
(Zen 4) system: vcpu_events_cancel_test and hyperv_forward_hcall pass,
as do hyperv_clock, hyperv_cpuid, hyperv_extended_hypercalls,
hyperv_features, hyperv_ipi, hyperv_tlb_flush and hyperv_svm_test, plus
triple_fault_event_test and nested_exceptions_test for the
KVM_SET_VCPU_EVENTS change. Not yet retested on Intel.

New:  attestation: Add a common subsystem and TDX support
[PATCH RFC v2 0/9] attestation: Add a common subsystem and TDX support
Author: Jiri Pirko <jiri@resnulli.us>


Linux has several attestation interfaces, each tied to one technology.
Extending a measurement takes device-specific flows for TPM, CCA, TDX
and SEV, none of them discoverable, and requesting a signed quote takes
another set, SPDM included. A new root of trust has no logical home
short of squeezing it into tsm_report and tsm_mr: tsm_report covers
reports alone, the MRs went to tsm_mr, and SPDM fits neither.

This series adds a common attestation subsystem. Its goal is to support
platform, TEE and device roots of trust through one model, including
TPM2, TDX, SEV-SNP, Arm CCA, FIRME, Caliptra and PCI/TSM-backed
devices, so that a program extends a register or asks for evidence
without knowing the hardware behind it. This first series implements
the common subsystem and a TDX provider. The native TDX interfaces,
/dev/tdx_guest, tsm_report and tsm_mr, stay as they are.

RFC v1 [1] posted this and CTLV as one patchset. For convenience, v2
splits it in two, and this series applies on top of the CTLV series,
posted alongside as

  [PATCH RFC v2 00/15] ctlv: Add a schema-driven TLV uAPI for character devices

Each attestation device has a node, /dev/attestation/attestationN,
that speaks CTLV: a request is checked against the family's schema and
executed at once, rather than assembled through several files. The
base family, ctlv-attestation, has what every provider shares, so a
tool written against it works with any provider. TDX's family,
ctlv-attestation-tdx, inherits it and adds no ops. It fills the base
family's extension points: device-get's info with the TD's MRCONFIGID,
MROWNER and MROWNERCONFIG, and evidence-vendor-format with the two TDX
Quote formats.

The base family's ops, as ctlvgen --signatures prints them, with the
purpose of each:

  # What the device supports, fixed for its life, and its family's fields.
  device-get() ->
      { caps: { evidence?: { objects[16]: { id, class, formats[4]?,
                                            vendor-formats[4]?, max-length,
                                            challenge-lengths[8]?: { length?,
                                                                     min-length?,
                                                                     max-length? } } },
                mr?: { flags } }, info: device-info }

  # Evidence: each object named, written to a blob the caller supplies,
  # a signed one made by the call over the challenge.
  evidence-get(challenge?, objects[16]: { id, data: out blob }) ->
      { results[16]: { format?, vendor-format?, length }, mr-generation? }

  # Describe every MR, or the one an ID names.
  mr-get(id?) -> { items[]: { id, mr-desc } }

  # One MR's values, a digest per bank, and the MR generation they
  # reflect.
  mr-read(id) -> { mr-generation, mr-values[hash-algo]: mr-value }

  # Extend banks of one MR by the caller's digests.
  mr-extend(id, mr-values[hash-algo]: mr-value) -> { mr-generation }

An mr-desc is an MR's name, its banks, what it allows and its register
index, and an mr-value one bank's hash algorithm and digest. The
userspace ABI gives each op's request, reply, errors and access.

New:  ctlv: Add a schema-driven TLV uAPI for character devices
[PATCH RFC v2 00/15] ctlv: Add a schema-driven TLV uAPI for character devices
Author: Jiri Pirko <jiri@resnulli.us>


RFC v1 [1] posted CTLV together with its first user, the attestation
subsystem. v2 posts them as two series: this one, and the attestation
series, which applies on top of it and is posted alongside as

  [PATCH RFC v2 0/9] attestation: Add a common subsystem and TDX support

CTLV is a schema-driven TLV uAPI on a character device, meant for uAPIs
too unconstrained for fixed structures: lists of records, nested and
variable-sized data, optional fields. Every request is checked against
the family's YAML schema before the driver sees it, and the UAPI
header, the bindings and the docs are generated from the same schema.
A family grows without versions, by new ops and optional fields. One
ioctl over a global number space lets strace or a seccomp supervisor
decode any family, and a query whose answer is larger than the
caller's buffer is answered in parts, with a cursor and a generation
that keep them consistent.

An ioctl with structures of its own fixes their layout, needs pointers
to more structures for variable data, and has to be validated and
decoded on its own. sysfs and configfs would assemble one request
through several files, where CTLV checks and executes it at once.
Netlink is built around sockets and network namespaces, while these
devices want an fd and the DAC model of a device node, and it was
turned down for the TSM's SPDM uAPI [2]. For a value or two, sysfs or a
plain ioctl stays simpler, and CTLV is not meant for that.

The uAPI is one ioctl on the device's fd:

  struct ctlv_op_exec {
          __u32 size;
          __u32 flags;
          __aligned_u64 op_id;
          __aligned_u64 request;
          __aligned_u64 reply;
          __u32 request_len;
          __u32 reply_len;
          __aligned_u64 generation;
          __aligned_u64 cursor;
  };

  ioctl(fd, CTLV_IOC_OP_EXEC, &exec);

An op is an action, executed once, or a query, which the generation
and the cursor carry across replies. Each op needs read or read-write
access, checked against the mode the device was opened with. A failed
op returns an errno, and in the reply buffer why the request was
refused and the offset of the offending TLV.

A family is specified in YAML. The root family, which every device
answers, lets a program not compiled against a family discover it. Its
first op:

  ops:
    # The families this device answers, this one first and the device family
    # last. The only names any reply of this family carries.
    family-get:
      type: query
      fd-access: read
      reply:
        # One entry per family of the chain.
        families[]:
          # The family ID, which bits 63..48 of the family's types carry.
          id: uint
          # The registry name, also what a uevent carries. Bounded here, this
          # being the only place a message carries a family name.
          name: string(..63)

ctlvgen --signatures prints a family's ops as calls, ? marking what
may be absent and [] what may repeat. The root family's three, with
the purpose of each:

  # The device's family chain, root first.
  family-get() -> { families[]: { id, name } }

  # Every op the device publishes, with its type, access and lengths.
  op-get() ->
      { ops[]: { id, type, availability?, disabled?, request-max-len?,
                 action-reply-max-len?, query-reply-min-len?,
                 query-reply-suggested-len?, fd-access?, error-info-max-len? } }

  # The tree of one op's request and reply.
  op-schema-get(id) -> { request?: schema-node, reply?: schema-node }

device by its family, building requests, parsing replies, reassembling
queries and building blob descriptors, with typed bindings generated

New:  KVM: x86: Let userspace opt in to multiple planes with KVM_CAP_PLANES
[RFC PATCH 01/13] KVM: x86: Let userspace opt in to multiple planes with KVM_CAP_PLANES
Author: David Woodhouse <dwmw2@infradead.org>


A VMM implementing a software privilege model such as Hyper-V VSM
needs more than one plane, but kvm_arch_max_planes() returns the
vendor ceiling, which is 1 everywhere except SEV-SNP (where VMPLs are
guest-architectural), so KVM_CREATE_PLANE rejects every id above zero.

Make KVM_CAP_PLANES a VM enable capability taking the number of planes
userspace is going to manage, up to KVM_MAX_USER_PLANES (4), which the
system fd now reports. It must be set before any vCPU or extra plane
exists, so nothing is sized against the old limit, and cannot be changed
once set. It also needs a split irqchip, which kvm_arch_max_planes()
already requires before it reports more than one plane, so enabling it
without one fails instead of silently granting a single plane, and
KVM_CREATE_IRQCHIP is refused afterwards. Non-default VM types are
rejected: SEV-SNP keeps deriving its count from the supported VMPLs,
and protected-state VM types need their own audit first. So is more
than one plane without TDP: with shadow paging every plane would
write-track the guest page tables, and the per-gfn write-track count
is only 16 bits wide. The same count is why the opt-in stops at four
planes even with TDP: nested guests still have write-tracked shadow
pages, each plane can add its own for a gfn, and four planes is the
most that keeps the count below 2^16. KVM_MAX_PLANES stays 16, the
bound for plane ids. A VM that does not enable the capability keeps
reporting a single plane.

Signed-off-by: David Woodhouse <dwmw@amazon.co.uk>

New:  KVM: arm64: Keep firmware Spectre-v4 mitigation on for protected guests
[PATCH] KVM: arm64: Keep firmware Spectre-v4 mitigation on for protected guests
Author: Fuad Tabba <fuad.tabba@linux.dev>

EL2 handles a protected guest's ARM_SMCCC_ARCH_WORKAROUND_2 discovery
query from the host's Spectre-v4 state at init. If the system is
mitigated and the guest doesn't have SSBS, it returns NOT_REQUIRED,
which means that firmware mitigation is permanently enabled. However,
the host can disable the mitigation before running a protected vCPU,
with an ARM_SMCCC_ARCH_WORKAROUND_2 call that EL2 forwards to the
firmware.

The host makes that call for its own userspace, so keep forwarding it,
without hints so that the firmware decodes it as EL2 does. Track it per
CPU, and on a mitigated system enable the mitigation again before
running a protected vCPU on a CPU where the host has disabled it.
Firmware enables it when a CPU powers up, so the tracked state isn't
reset on CPU_ON or resume.

Fixes: fe40ff87ead5c ("KVM: arm64: Implement HVC handling for protected guests at EL2")
Reported-by: Ryan Roberts <ryan.roberts@arm.com>
Closes: https://lore.kernel.org/all/5fa8a1fb-4e2c-4746-8a70-a47f387ef0d6@arm.com/
Signed-off-by: Fuad Tabba <fuad.tabba@linux.dev>
---

Notes:
    Tested on QEMU with TF-A. Upstream TF-A implements the dynamic
    workaround only for Cortex-A76, so I patched it to advertise the
    workaround on the Cortex-A57 that QEMU models. With a host that
    disables the mitigation before running a protected vCPU, TF-A gets the
    call to enable it again from EL2 with this patch, and doesn't without
    it. TF-A's handler for the call does nothing there and QEMU doesn't
    model the mitigation, so this tests the calls and not their effect.
    
    Calling the firmware before every protected vCPU run would do without
    the tracking, at the cost of an SMC per run.
    
    Based on Linux 7.4-rc2 (7475ea8b58616).
