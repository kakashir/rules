Author: Borislav Petkov <bp@alien8.de>

Date: Thu, 29 Oct 2026 19:25:27 -0700

so if a commit message contains "TDx" as in

  the TDxE (Transmit Data Empty) flag

for example, see

  https://lore.kernel.org/r/20261026-g2ul_sci-v3-3-b3097163edd5@bp.renesas.com

obviously is a completely unrelated patch.

  drivers/power/reset/tdx-ec-poweroff.c

patches.

So switch the x86 TDX patterns to files and directories (N:) type
patterns and group them by path, for less false positives.

[PATCH kvmtool v2] Makefile: Fix the feature checks when SHELL isn't /bin/sh
Author: Mika Tammi <mikatammi@gmail.com>

try-build and try-cc pass their test program to the compiler with
echo "$(1)" in a $(shell sh -c '...'). The newlines in the program
survive only while make's SHELL is its default, /bin/sh: GNU make then
runs the command without a shell, splitting it into arguments itself,
and the whole script is one single-quoted argument to sh -c.

With any other SHELL, GNU make runs "$(SHELL) -c" with the command
line, which it first rewrites with a backslash before each special
character and then parses again. A newline becomes a backslash-newline
there, which make removes [1]. The compiler gets the program as one
line, ignores everything after its first #include, and fails to link
it:

  <stdin>:1:20: warning: extra tokens at end of '#include' directive
  (.text+0x1b): undefined reference to `main'

So with make SHELL=/bin/bash, and in every nixpkgs build, as its stdenv
passes SHELL to make, every feature check fails:

 - without HAVE_STRLCPY, include/kvm/strbuf.h declares strlcpy() and
   strlcat(), which glibc 2.38 and later and musl declare too, and the
   build stops at -Werror=redundant-decls
 - no static libc is found, so the guest init is left out
 - on arm64, powerpc and riscv, the build stops as libfdt isn't found,
   unless LIBFDT_DIR is given
 - none of the optional libraries is found

Give printf each line of the program as an argument of its own, so that
the command line has no newlines for make to remove. This needs nothing
newer from make than the rest of the file, unlike writing the program
into a file with $(file), which needs GNU make 4.0. And printf "%s\n"
leaves backslashes alone, which echo doesn't in every shell.

[1] construct_command_argv_internal() in src/job.c of GNU make 4.4.1

Fixes: 328a03bc3f07 ("kvm tools: Add conditional compilation of symbol resolving")
Fixes: 2c82d39a080d ("kvm tools: Add test for -static libc present")
Assisted-by: Claude:claude-opus-5-5
Signed-off-by: Mika Tammi <mikatammi@gmail.com>
---
v2: Add my Signed-off-by, which v1 lacked.
v1: https://lore.kernel.org/kvm/20261030003934.30456-1-mikatammi@gmail.com/

I used Claude Opus 5.5 to track down the cause, write this patch and
its description, and run the tests below; I have reviewed the result.

Tested with nixpkgs' kvmtool package, without its workaround for this
(it defines HAVE_STRLCPY): natively on x86_64 and arm64 with glibc,
linked dynamically and statically, and with static musl on arm64;
cross-compiled for arm64, riscv32 and riscv64. With this patch, the
feature checks give the same results with SHELL=bash as with make's
default SHELL, and with the default SHELL the same results as before.
The dynamically linked lkvm is byte-identical to the one built with the
workaround, a statically linked lkvm now includes the guest init, and
a static musl lkvm on QEMU rv32 and rv64 KVM hosts still boots a guest.

[PATCH 2/3] vfio: selftests: Skip tests when the IOMMU mode is not available
Author: David Matlack <dmatlack@google.com>

Skip tests when the IOMMU mode they need is not available on the current
system, instead of failing. Add iommu_mode_is_available() to check whether
a given IOMMU mode (or, if NULL, any IOMMU mode) is available, and
SKIP_IF_IOMMU_MODE_UNAVAILABLE() to skip a kselftest harness test if not.

On a kernel without iommufd, for example, all of the iommufd and
iommufd_compat test variants currently fail on an assert in iommu_init().
Skip them instead, with a message that explains why:

  ok 33 vfio_pci_driver_test.iommufd.send_msi # SKIP IOMMU mode not available: iommufd

Use SKIP_IF_IOMMU_MODE_UNAVAILABLE() in all tests that run across multiple
IOMMU modes, and in the tests that let the library pick the mode by
passing NULL to iommu_init(). Also skip vfio_pci_driver_test, which calls
iommu_init() from main() to probe the device, if no IOMMU mode is
available.

Skip from the test via the kselftest harness's SKIP(), rather than from
within iommu_init() via ksft_exit_skip(). ksft_exit_skip() is not aware of
the harness, and so would emit a bogus "1..0 # SKIP" plan line in the
middle of the TAP output, and the harness would report the reason for the
skip as "unknown".

[PATCH 1/3] vfio: selftests: Automatically detect the IOMMU mode in iommu_init()
Author: David Matlack <dmatlack@google.com>

current system when iommu_init() is passed a NULL mode, rather than always

[PATCH 0/3] vfio: selftests: Automatically detect the IOMMU mode
Author: David Matlack <dmatlack@google.com>

This series makes the VFIO selftests library automatically detect which
IOMMU mode to use, rather than hardcoding iommufd as the default, and
makes tests skip, rather than fail, when the IOMMU mode they need is not
available. This was suggested by Sean while reviewing the KVM IRQ test,
which currently has to probe for the IOMMU mode itself [1].

iommufd is an optional feature, and VFIO's iommufd support additionally
requires CONFIG_VFIO_DEVICE_CDEV. On otherwise functional kernels that
only support the legacy VFIO container, the VFIO selftests (and the KVM
IRQ test, when using a VFIO device) currently fail with an unhelpful
assert:

  tools/testing/selftests/vfio/lib/iommu.c:448: Assertion Failure

  Expression: iommu->iommufd > 0
  Observed: 0xffffffffffffffff > 0
  [errno: 2 - No such file or directory]

Patch 1 makes iommu_init(NULL) pick the most preferred IOMMU mode that is
available on the current system, and drops the global default_iommu_mode.
iommu_modes[] is now ordered by preference: iommufd, vfio_type1v2_iommu,
vfio_type1_iommu, iommufd_compat_type1v2, iommufd_compat_type1. A mode is
considered available if its container (or /dev/iommu) can be opened and,
for container modes, if VFIO_CHECK_EXTENSION reports support for the
mode's IOMMU type. iommufd mode additionally requires VFIO device cdevs.

Patch 2 adds iommu_mode_is_available() and
SKIP_IF_IOMMU_MODE_UNAVAILABLE(), and uses them to skip tests when the
IOMMU mode they need is not available. Tests skip via the kselftest
harness's SKIP() rather than iommu_init() calling ksft_exit_skip(), since
the latter produces malformed TAP output when called from within a
harness test.

Patch 3 converts the KVM IRQ test to use the VFIO selftests library to
pick the IOMMU mode, and drops its probe_iommu_type().

This series is based on vfio/next (vfio-v7.4-rc1).

[1] https://lore.kernel.org/kvm/aiIG2L_KdPwuxYA1@google.com/

[PATCH 5/5] vfio: selftests: Add test for device power state transitions
Author: David Matlack <dmatlack@google.com>

Add vfio_pci_power_state_test to exercise VFIO's handling of device
power state changes initiated by userspace through the PM capability in
config space.

The test covers:

 - Closing a device while it is in D3hot, which must return the device
   to D0.
 - Enabling SR-IOV while the PF is in D3hot, which must return the PF to
   D0 and prevent it from leaving D0 while VFs are enabled.
 - Racing a close of the device while it is in D3hot against enabling
   SR-IOV, both of which transition the device back to D0.

The SR-IOV tests are skipped if the device does not support SR-IOV or
already has VFs enabled.

Bugs in VFIO's power state handling, such as the race above, often only
manifest as kernel warnings (e.g. WARN() or KASAN reports). So fail the
test if /sys/kernel/warn_count changes between fixture setup and
teardown.

Signed-off-by: David Matlack <dmatlack@google.com>

[PATCH 2/5] vfio/pci: Annotate lockless accesses to vdev->sriov_active
Author: David Matlack <dmatlack@google.com>

Use READ_ONCE() and WRITE_ONCE() to annotate the read of
vdev->sriov_active in vfio_pci_set_power_state() and the lockless write
that clears it in vfio_pci_core_sriov_configure().

vfio_pci_core_sriov_configure() intentionally clears sriov_active
without holding memory_lock, so the write can race with the read in
vfio_pci_set_power_state() (which runs under memory_lock). The race
itself is benign, at worst it results in a spurious -EBUSY while the
device stays in D0, but the accesses should be marked to prevent the
compiler from tearing or otherwise optimizing them and to document the
intentional data race (e.g. for KCSAN).

The write that sets sriov_active is done under memory_lock and is
serialized against the lockless write by device_lock, so it does not
need to be annotated.

[PATCH 0/5] vfio/pci: Fix power state race with SR-IOV enablement
Author: David Matlack <dmatlack@google.com>

This series fixes a race in VFIO's handling of device power state
transitions and a related missing data race annotation, both found while
reviewing Raghavendra's sriov_active patch [1]. It also adds a selftest
to exercise VFIO's handling of device power state transitions.

Patch 1 fixes a race between vfio_pci_core_disable() and
vfio_pci_core_sriov_configure(), both of which transition the device to
D0, but only the latter holds memory_lock. If userspace puts the device
into D3hot via config space and then closes the device while
concurrently enabling SR-IOV, both threads can transition the device
from D3hot to D0 at the same time. For devices with NoSoftRst-, this can
result in VFIO restoring the PF's BARs after VFs have been enabled
(triggering a WARN in pci_iov_update_resource()), or in a double-free of
vdev->pm_save. The fix is to hold memory_lock for all calls to
vfio_pci_set_power_state() and to assert it unconditionally.

Patch 2 annotates the intentional lockless accesses to
vdev->sriov_active with READ_ONCE() and WRITE_ONCE().

Patches 3-5 add vfio_pci_power_state_test, which covers closing a device
in D3hot, enabling SR-IOV while the PF is in D3hot, and racing the two.
Since power state bugs often only manifest as kernel warnings, the test
fails if /sys/kernel/warn_count changes during a test case. Patches 3
and 4 add the library helpers the test needs.

[PATCH 1/5] vfio/pci: Hold memory_lock for all calls to vfio_pci_set_power_state()
Author: David Matlack <dmatlack@google.com>

Hold vdev->memory_lock for write when calling vfio_pci_set_power_state()
from vfio_pci_core_disable() and vfio_pci_core_register_device(), and
assert that the lock is held for all power state transitions, not just
transitions out of D0.

vfio_pci_core_disable() calls vfio_pci_set_power_state(vdev, PCI_D0)
without holding memory_lock, which allows it to race with
vfio_pci_core_sriov_configure() when userspace writes to sriov_numvfs
while the device is being closed. If the user left the device in D3hot
via a config space write (which leaves the device RPM_ACTIVE, so
pm_runtime_resume() does not bring it back to D0), both threads can
transition the device from D3hot to D0 concurrently.

For devices that need_pm_restore (NoSoftRst-), this can result in:

 - vfio_pci_core_disable() restoring the PF's BARs after
   vfio_pci_core_sriov_configure() has enabled VFs, since the D3hot->D0
   transition sleeps before restoring device state. This is easy to hit
   and triggers the following warning:

     vfio-pci 0000:01:00.0: can't update enabled VF BAR0 [mem 0xe0200000000-0xe020001ffff 64bit pref]
     WARNING: drivers/pci/iov.c:1062 at pci_iov_update_resource+0x170/0x3b0
     Call Trace:
      pci_update_resource+0x1a3/0x5b0
      __pci_set_power_state+0x597/0xb90
      vfio_pci_core_disable+0x13b/0x1180
      vfio_pci_core_close_device+0x144/0x260
      vfio_df_close+0xf2/0x210
      vfio_df_unbind_iommufd+0x89/0x140
      vfio_device_fops_release+0x85/0xf0
      __fput+0x2d6/0x720
      fput_close_sync+0xe8/0x180
      __x64_sys_close+0x7f/0xc0
      do_syscall_64+0xbc/0x320
      entry_SYSCALL_64_after_hwframe+0x76/0x7e

 - Both threads observing pdev->current_state >= PCI_D3hot and calling
   pci_load_and_free_saved_state(pdev, &vdev->pm_save) concurrently,
   resulting in a double-free of vdev->pm_save.

vfio_pci_core_register_device() cannot race with other callers since
the device is not yet registered and device_lock is held across probe,
but take the lock there as well so that the lockdep assertion can be
made unconditional and catch any future unlocked callers.

Taking memory_lock in these paths does not introduce any new lock
dependencies. vfio_pci_core_disable() already acquires memory_lock
under dev_set->lock via vfio_pci_runtime_pm_exit(), and
vfio_pci_core_sriov_configure() already acquires memory_lock under
device_lock.

[PATCH] KVM: x86: Fix lost EOI when unmasking a pending level IOAPIC pin
Author: Denis V. Lunev <den@openvz.org>

When the guest unmasks a level-triggered redirection entry whose line is
already asserted, ioapic_write_indirect() injects the pending interrupt
first and only then asks the destination vCPUs to rescan their
ioapic_handled_vectors and EOI exit bitmaps. If the same write also set
the vector or the trigger mode, a destination vCPU can take the interrupt
and EOI it before the rescan. A posted interrupt reaches a running vCPU
without a VM exit, and the EOI is then either virtualized without an exit
or dropped by kvm_ioapic_send_eoi() because the vector is not in
ioapic_handled_vectors yet. Remote IRR stays set and the pin delivers no
more interrupts until the guest reprograms it.

Linux programs the entry masked and unmasks it with a separate write, so
the vector is scanned before anything can be injected. Windows writes
the vector, the trigger mode and the mask bit in one go. A virtio balloon
on INTx whose line is already up when the driver connects its interrupt
then stops receiving interrupts for the rest of the boot, and the guest
ignores every later balloon target.

Make the scan request before servicing the pending IRR. The request
waits for the destination vCPUs to leave guest mode, and each of them
rescans the routes and reloads its EOI exit bitmap before it can enter
the guest and take the interrupt.

Fixes: c7c9c56ca26f ("x86, apicv: add virtual interrupt delivery support")
Fixes: 3bb345f387dd ("KVM: x86: store IOAPIC-handled vectors in each VCPU")
Signed-off-by: Denis V. Lunev <den@openvz.org>

[PATCH 4/6] i386: Add Bus Lock Detect support
Author: Ben Cheatham <Benjamin.Cheatham@amd.com>


Bus Lock Detect is enumerated with cpuid Fn0000_0007_ECX_x0
bit [24 / BUSLOCKTRAP]. It can be enabled through MSR_IA32_DEBUGCTLMSR.
When enabled, hardware clears DR6[11] and raises a #DB exception on
occurrence of Bus Lock if CPL > 0. More detail about the feature can be
found in AMD APM[1].

Qemu supports remote debugging through host gdb (the "gdbstub" facility)

breakpoints relies on the same hardware infrastructure (#DB, DR6 etc.)
that Bus Lock Detect also uses. Instead of handling internally, KVM
forwards #DB to Qemu when remote debugging is ON and #DB is being
intercepted. It's Qemu's responsibility to re-inject the exception to
guest when some of the exception source bits (in DR6) are not being
handled by Qemu remote debug handler. Bus Lock Detect is one such case.

[PATCH v2 0/5] PCI/sysfs: Wait for config access lock in sysfs attributes
Author: Matthew Wood <thepacketgeek@gmail.com>

Many PCI sysfs attributes that read from config space are using kernel
accessors that don't wait for pci_cfg_access_lock() holders before reading:

- serial_number
- max_link_width
- current_link_*
- *_bus_number

If userspace attempts to read from these attributes while config space is not
available (e.g. during a reset) there's no telling what values will be
returned: All ones, zeros, or garbage.

for VPD writes, timing out with a "firmware bug" warning.

/proc/bus/pci still return ~0 data.

[PATCH v2 5/5] PCI/sysfs: Use user config accessors for serial_number

[PATCH v3 7/8] ath12k: use KVM MSI domain for VM passthrough
Author: Jose Ignacio Tornos Martinez <jtornosm@redhat.com>

device BAR registers for CE/SRNG ring interrupt delivery, bypassing
the standard PCI config MSI path managed by QEMU/VFIO. In a VM, the
firmware receives the guest virtual APIC address instead of the host

compiled out and the behavior is identical to the original. If
CONFIG_PCI_KVM_MSI_DOMAIN is enabled (e.g. distribution kernels), the
KVM MSI functions detect baremetal at runtime and return immediately,
preserving the original behavior with no side effects.

[PATCH v3 3/8] PCI: add KVM MSI domain guest module
Author: Jose Ignacio Tornos Martinez <jtornosm@redhat.com>

Add a guest-side PCI MSI IRQ domain driver for KVM virtual machines
that intercepts MSI composition for devices whose firmware programs
MSI addresses directly into BAR registers.

The problem: Qualcomm WiFi devices (ath11k/ath12k) have embedded
firmware that programs MSI target addresses from values cached at
driver init time. In a VM with VFIO passthrough, the driver sees
the guest's virtual APIC address instead of the host's physical
IRTE address. When the firmware writes this guest address to BAR
registers, the resulting MSI goes to a stale or invalid IRTE,
causing DMAR faults.

The solution: This module creates a custom MSI parent IRQ domain
(modeled on pci-hyperv.c) that interposes between the PCI MSI layer
and the platform's existing MSI domain. It provides two exported
functions for use by device drivers:

  - kvm_pci_msi_wait_ready(): Polls a KVM hypercall
    (KVM_HC_PCI_MSI_ALLOC, introduced in a previous patch) until the
    host returns non-zero MSI address/data. Caches the result in
    per-vector chip_data and updates msi_desc->msg for the base
    vector.

  - kvm_pci_msi_get_address(): Returns cached host MSI address/data
    previously obtained by wait_ready. Allows drivers that read MSI
    addresses on-the-fly (like ath12k) to get the host values without
    another hypercall.

On baremetal (no KVM), kvm_para_available() returns false and
wait_ready returns 0 immediately, so drivers guarded with
IS_ENABLED(CONFIG_PCI_KVM_MSI_DOMAIN) have zero overhead.

The compose callback is maintained for completeness: if the MSI
framework recomposes after wait_ready has populated the cache, the
cached host values are returned instead of the guest virtual address.

The module matches devices by PCI ID table, attaches the custom MSI
domain before driver probe via bus notifier, and requires the
pci-kvm-msi module to load before the wireless drivers via
MODULE_SOFTDEP in the driver patches.

Author: Jose Ignacio Tornos Martinez <jtornosm@redhat.com>

Some PCI devices (e.g. Qualcomm WiFi adapters) have firmware that
programs MSI addresses directly into device BAR registers, bypassing
the standard PCI config MSI path. When these devices are passed

allowing the guest to poll until the host MSI is ready.

[RFC PATCH 0/4] KVM: x86/mmu: don't zap secondary MMU on permission upgrade
Author: Carlos López <clopez@suse.de>

Prevent x86 KVM from over-zapping its secondary MMU on PTE permission
upgrades, which leave the PFNs unchanged and do not revoke access.
Permissions for SPTEs that KVM holds are updated on the next fault, so
dropping them early gains nothing.

Do this by adding a new MMU notifier flag to signal that a
MMU_NOTIFY_PROTECTION_VMA strictly upgrades (loosens) permissions on a
particular range.

See below for benchmark results.

Background
==========

change_protection() pairs every protection change with an
MMU_NOTIFY_PROTECTION_VMA invalidation, and KVM zaps its SPTEs in
response, as it cannot tell whether permissions widened or narrowed.
This is costly e.g. during a QEMU background snapshot, which relies on
uffd-wp to write-protect guest RAM and then restore permissions as each
page is saved. Without this series, the permission restore causes the
guest to re-fault read-only memory needlessly.

Note, the reverse situation is already handled for secondary MMUs
that reuse the CPU page tables (e.g. ARM SMMU, IOMMU/ATS). They cannot
refault, so they are notified of a permission upgrade on the CPU
TLB-flush path [1].

KVM, however, owns separate page tables and faults permissions on demand,
so it needs no such notification (as Sean noted when that signalling
was first proposed on the fault path [2]). This series applies the same
principle to the change_protection() path, signalling the permission
upgrade so KVM can avoid the unnecessary zap.

RFC Considerations
==================

1. Having the zap skip in KVM's arch-independent code does not seem
   obviously correct, as s390 caches additional translation state
   that may not be rebuilt by refaults. Maybe an expert can correct
   me. The skip could be extended to arm64 and RISC-V, but I have not
   benchmarked the benefits and I'd like to get feedback first. Hence,
   x86-only for now.

2. change_protection() could simply not emit the invalidation at all
   for a pure permission upgrade (shared-page-table MMUs invalidate
   on the CPU TLB-flush path, as noted above, so they do not need it).
   But again, the s390 case could be broken, and even then, that would
   seem too much intrusion for KVM's benefit.

3. The flag reaches KVM as a bool on struct kvm_gfn_range.
   Alternatively, KVM could forward the notifier event, as Claudio
   Imbrenda suggested at LPC [3] and others have proposed in the past
   for different purposes [4] [5]. That, along with the event flags,
   could serve the same purpose. I'd be happy to take that approach if
   there is agreement that other consumers would want it.

   (The LPC talk recording has some audio issues so I am not too sure
   on what the final agreement was)

Benchmarks
==========

AMD EPYC 9654 96-Core Processor host running a recent Linux kernel
(6b4b543fa187), with a 64GB, 64-vCPU guest running stress-ng --vm while
the host takes a QEMU background snapshot. All results are aggregated
over 5 runs, and compared between the stock kernel and one with this
patch series. Guest is rebooted across each individual run, and NUMA
balancing is disabled.

pf/s and tlb/s (per-second deltas of KVM's pf_taken and remote_tlb_flush
debugfs stats) clearly improve:

  guest pattern          baseline                    patched
  -----------------------------------------------------------------------
  read64   (read)        pf/s=950,015   tlb/s=1,440  pf/s=2,503 tlb/s=0.1
  rand-set (read+write)  pf/s=1,004,353 tlb/s=862    pf/s=4,073 tlb/s=0.3
  write64  (write)       pf/s=968,018   tlb/s=94     pf/s=2,292 tlb/s=0.3

Guest read latency was sampled with a paced probe thread in the
guest, reading one byte per page with an idle gap between reads, while
stress-ng ran with read64. Each figure is the median across 5 runs, with
the run-to-run min and max, in ns:

  metric           baseline             patched
  ------------------------------------------------------
  p50 (min max)      340     (270 380)   260   (250 260)
  p99 (min max)    19789 (16885 20200)  5207 (4076 5638)
  p99.9 (min max)  23445 (22845 24036)  6850 (6259 7110)

The median improves modestly and the refault cost shows in the tail,
where p99 drops ~3.8x.

A separate stress-ng run with write64 and --verify showed no data
corruption and no livelocks.

[RFC PATCH 4/4] KVM: x86/mmu: don't zap the secondary MMU on permission upgrade
Author: Carlos López <clopez@suse.de>

When an mmu_notifier invalidation only upgrades permissions
(MMU_NOTIFIER_RANGE_PERM_UPGRADE), keep the existing SPTEs instead of
zapping them. The PFN is unchanged and no access is revoked, so a held
SPTE is at most as permissive as before. Permissions for the SPTE are
updated on the next fault, so dropping them early gains nothing.

The motivating case is a userfaultfd-wp dirty tracker such as QEMU's
background snapshot, which unprotects every guest page as it saves it.
Zapping on each unprotect makes the guest refault its whole working
set. On a 64GB guest under a background snapshot, a read-mostly workload
drops secondary-MMU refaults from ~1M/s to ~2.5K/s and cross-vCPU TLB
shootdowns from ~1400/s to near zero. Uses of mprotect() that only add
access benefit likewise.

[PATCH v5 4/7] KVM: s390: Improve unmapping of large ranges
Author: Claudio Imbrenda <imbrenda@linux.ibm.com>

When unmapping guest ranges, each individual leaf DAT entry is
invalidated. When unmapping large ranges, this results in a very large
amount of invalidations, which is time consuming. Moreover, since the
unmap callback is called by KVM while holding a spinlock, this also
leads to stall warnings.

Improve the situation by invalidating DAT entries higher in the tree,
instead of each leaf individually.

For small invalidations (up to 1 segment = 1M of guest memory), and
special cases (like protected VMs) regardless of the size, the old and
slow invalidation is performed; all leaf entries are invalidated one by
one.

For large invalidations (larger than 1M of guest memory), the new
strategy is used:
 - Invalidate prefixes on the whole range, extending start and end to
   1M granularity
 - Iterate through the page table pointed to by each pmd and unshadow
   entries as needed
 - Detach (invalidate) the pmd
 - Save storage keys as needed
 - Invalidate each (now detached) pte by simply overwriting it
 - Reattach the old pmd to point to the updated page table

[PATCH v5 7/7] KVM: s390: Allocate page tables when CMMA is used
Author: Claudio Imbrenda <imbrenda@linux.ibm.com>

When ESSA is executed in the guest for the first time, allocate all
page tables and split all existing large page mappings, regardless of
the hpage parameter.

With the page tables present (even if all the entries within are not
present), ESSA will not cause page faults.

Without this fix, ESSA will cause a fault on the first page of each
segment (1M block). If userspace is backing the guest with huge pages
(hugetlbfs or THP), the page fault will be resolved by faulting in the
whole huge page. The result is that at startup the whole guest memory
is faulted in, since the guest will mark all of its memory at boot.

With this fix, no extra guest memory is allocated. This will also
prevent the first page in each segment from being faulted in, regardless
of hugepages.

[PATCH RFC 1/1] x86/irq/i8259: Ack PIC vectors in the LAPIC ISR
Author: Dongli Zhang <dongli.zhang@oracle.com>

This is to fix a LAPIC ISR stall that can happen in a kdump kernel, but can
also happen in other scenarios.

The issue can be intermittently reproduced in a QEMU/KVM guest when there
are large number of VMs on the same host.

Device interrupts can use the PIC, IOAPIC, or MSI-X. Nowadays, most x86
device interrupts use MSI-X or the IOAPIC. However, the PIC handler does
not send a LAPIC EOI, even when the interrupt it handles has set a bit in
the LAPIC ISR.

For example, suppose there is a QEMU/KVM guest using virtio-net.

1. virtio-net is about to deliver vector 52 to CPU 2 (APIC ID 2), but the
guest suddenly panics on that CPU.

2. The kdump kernel boots on APIC ID 2, which becomes CPU 0 in the new
kernel.

3. Suppose delivery of the interrupt is delayed, so vector 52 has not
reached the CPU yet.

4. On the new CPU 0, init_ISA_irqs() initially sets up the legacy IRQs to
use the PIC. Vector 52 maps to IRQ4, which is normally used by the serial
console.

5. Before these legacy IRQs are handed over to the IOAPIC, suppose the
delayed vector 52 arrives through the LAPIC and sets its ISR bit.

6. The new kernel handles it as PIC IRQ4. Since mask_and_ack_8259A()
does not send a LAPIC EOI, the ISR bit for vector 52 remains set.

The below is an example when vector is 55.

(qemu) info lapic 2
dumping local APIC state for CPU 2

LVT0	 0x00010700 active-hi edge  masked                      ExtINT (vec 0)
LVT1	 0x00000400 active-hi edge                              NMI
LVTPC	 0x00000400 active-hi edge                              NMI
LVTERR	 0x000000fe active-hi edge                              Fixed  (vec 254)
LVTTHMR	 0x00010000 active-hi edge  masked                      Fixed  (vec 0)
LVTT	 0x000400ec active-hi edge                 tsc-deadline Fixed  (vec 236)
Timer	 DCR=0x0 (divide by 2) initial_count = 0 current_count = 0
SPIV	 0x000001ff APIC enabled, focus=off, spurious vec 255
ICR	 0x000c0400 physical edge de-assert all
ICR2	 0x00000000
ESR	 0x00000000
ISR	 55
IRR	 37 38 39 40 48 56

APR 0x00 TPR 0x10 DFR 0x0f LDR 0x00 PPR 0x30

This is painful when it happens in production. The kdump kernel stalls, so
we cannot collect a vmcore for analysis.

The issue is easier to reproduce with a customized KVM host kernel that
allows arbitrary vectors to be injected through debugfs and
kvm_apic_set_irq(). I can stall the guest kernel by injecting vector 50
into vCPU 0, even after the guest has booted successfully. Vector 50 maps
to IRQ2, the cascade interrupt between the two 8259A chips. IRQ2 is not
taken over by the IOAPIC.

For other vectors, I can reproduce the issue by adding mdelay() at the
beginning of setup_IO_APIC() and injecting the vectors during the delay
through the modified KVM host kernel.

In theory, a normal kexec reboot may also hit this issue if device
interrupts arrive late.

Fix this by checking the LAPIC ISR bit corresponding to the PIC vector and
sending a LAPIC EOI only if it is set. Cover both normal and auto-EOI
modes.

[RFC PATCH v2 0/9] iommu/riscv: Add nested translation (vIOMMU) support
Author: Gong Shuai <gong.shuai@sanechips.com.cn>

An IOMMU allows an OS to restrict device DMA to the intended memory.
It also gives device drivers an IOVA space that is independent of the
physical memory layout. A guest OS needs these capabilities when it
directly controls a device, just as a native OS does.

Exposing a vIOMMU to the guest is not enough for a passthrough device.
DMA from the physical device must also obey the mappings that the guest
creates through its vIOMMU. Otherwise the guest cannot use its IOMMU to
protect guest memory or provide IOVA mappings for the assigned device.

The RISC-V IOMMU architecture supports this usage with two-stage
translation. Stage 1 applies the guest's vIOMMU configuration. Stage 2
is controlled by the hypervisor and restricts the device to memory
assigned to the VM. This division gives the guest control of its own
DMA mappings without allowing the device to escape the VM.

The Linux RISC-V IOMMU driver does not yet support this model through
iommufd. A VMM cannot provide the guest stage 1 configuration to the
physical IOMMU or synchronize its translation caches after the guest
updates its page tables. This series adds the missing nested
translation support so device passthrough can work with a guest that
uses its own vIOMMU.

This is an RFC and comments on the design are welcome.

Patch organization

Patch 1 prepares device context handling for nested translation.
Patches 2 and 3 add the uAPI for nested allocation and cache
invalidation.
Patches 4 to 6 add the vIOMMU, nested domains and cache invalidation.
Patches 7 and 8 allow a VMM to discover the physical IOMMU
capabilities.
Patch 9 adds nested device attachment.

Dependencies

The series applies on top of linux-iommu/next at 20bfd25757659f with
the generic iommu page table for SMMUv3 v2 [1], the RISC-V hardware
dirty tracking series v5 [2], and the generic_pt fix that adds Svpbmt
to the RISC-V supported feature mask.

Testing

The test requires MSI support, but the related dependencies are still
under review, so the interrupt changes are not included in this series.
The test needs the MSI remapping series v6 [3], the irqbypass series
RFC v3 [4] and a KVM client from Andrew's github repo [5].A branch with
the complete test stack, including the additional nested interrupt
support, is available at github repo [6].

The host is a RISC-V machine whose physical IOMMU is provided by an outer
QEMU riscv-iommu model, which implements both translation stages. An NVMe
controller under it is bound to vfio-pci and passed through to the guest.
The guest is started by a QEMU built with the accel series [7][8], which
exposes a first stage IOMMU to the guest and leaves the second stage to
the host IOMMU. For simplicity the guest runs the same kernel as the host,
and inside the guest it mainly uses the normal IOMMU driver and the NVMe
driver.

The layering of the setup is

Host HW, a RISC-V virt machine from latest QEMU(v11.1.2), with a
riscv-iommu model that implements two stage translation and with the NVMe
controller

    Host OS, the kernel with this series
      riscv-iommu driver, second stage and MSI table vfio-pci and KVM

        Guest HW, QEMU with the accel series [7][8]
          riscv-iommu accel, first stage only

            Guest OS, the same kernel as the host
              riscv-iommu driver, NVMe driver

A DMA address from the NVMe controller is translated by the guest first
stage and then by the host second stage on the physical IOMMU. An MSI
address is translated by the guest first stage into a guest IMSIC address,
which the flat MSI table then resolves straight to the interrupt file of
the target vCPU, instead of walking the second stage.

    DMA    device --> guest first stage --> host second stage --> RAM
    MSI    device --> guest first stage --> MSI table --> VS-file

The host was started with

$HOST_QEMU \
  -M virt,aia=aplic-imsic,aia-guests=7,iommu-sys=on \
  -cpu rva23s64,sv48=on -nographic \
  -smp 16 -m 16G \
  -kernel $HOST_KERNEL \
  -append "root=/dev/vda rw earlycon=sbi console=ttyS0 iommufd.allow_unsafe_interrupts=1" \
  -drive file=$HOST_ROOTFS,if=none,id=d0,format=qcow2 -device virtio-blk-device,drive=d0 \
  -device pcie-root-port,id=port0,chassis=0,slot=0,addr=3.0 \
  -drive file=fake-nvme-disk.img,if=none,id=nvme0,format=qcow2 \
  -device nvme,drive=nvme0,serial=deadbeef,bus=port0,addr=0.0

and the guest with

$GUEST_QEMU \
  -machine virt,accel=kvm,aia=aplic-imsic,aia-guests=5 \
  -cpu host -nographic \
  -smp 4 -m 4G \
  -object iommufd,id=iommufd0 \
  -device riscv-iommu-pci,addr=1.0,s-stage=on,g-stage=off,accel=on \
  -device vfio-pci,host=0000:01:00.0,iommufd=iommufd0 \
  -kernel $GUEST_KERNEL \
  -append "root=/dev/vda rw earlycon=sbi console=ttyS0 iommu.passthrough=0 iommu.strict=1" \
  -drive file=$GUEST_ROOTFS,if=none,id=d0,format=qcow2 -device virtio-blk-device,drive=d0

Correctness was checked by running fio with verification enabled against
the passed through disk.

Known limitations and future work

PASID and the process directory table are not supported, PDTV is rejected
and PSCID is fixed at 0. The ATS, PRI and T2GPA fields are validated on
the nested domain, but ATS.INVAL and the PRI queue are not forwarded. A
vIOMMU is bound to a single physical IOMMU instance. The new uAPI types
have no selftest coverage yet.

[PATCH RFC v2] KVM: arm64: nVHE: Flush all TLBs when freeing a
Author: Francesco Boccola via B4 Relay <devnull+francesco.boccola.unina.it@kernel.org>


kvm_free_stage2_pgd() frees a VM's stage-2 page tables without invalidating
the TLBs. That is correct: the VM's VMID is not reused before the next VMID
rollover, and flush_context() then invalidates the entries of all VMIDs on
all CPUs (TLBI ALLE1IS).

In nVHE mode, however, a CPU that ran a guest makes the host's broadcast
TLB invalidations more expensive for the whole system until then, which
with 16-bit VMIDs usually means until the host reboots. With stress-ng
--tlb-shootdown on three CPUs of a cluster, the cyclictest maximum on a
fourth, isolated CPU goes, before and after one guest:
- Cortex-A53 (Zynq UltraScale+ KV260, no VHE, 6.1.70-rt): 53-72 us ->
  83-164 us;
- Cortex-A55 (RK3588, kvm-arm.mode=nvhe, kvmarm/next): 18-23 -> 78-97 us;
- Cortex-A76 (RK3588, kvm-arm.mode=nvhe, kvmarm/next): 16-30 -> 74-80 us.
It crosses clusters: after a guest on an A55, an isolated A76 goes from
14-18 us to 129-154 us. The same happens on kernel 6.12.113 (20-24 -> 44-49
us on the A55) and on 7.1.9 with and without PREEMPT_RT.

One guest that turns its stage-1 MMU on, even for a few microseconds, is
enough; a guest that keeps its MMU off is not. With VHE nothing changes.

The state is in the CPU that ran the guest: a local TLBI ALLE1 on that CPU
at teardown removes the effect on every CPU, the same on all the other CPUs
does not. Invalidating the dead VM's VMID (TLBI VMALLS12E1IS, as pKVM does
at teardown) does not remove it either, whether stage 2 is disabled while
it is issued (as __kvm_tlb_flush_vmid() does from the host's context) or
enabled; nor does invalidating VMID 0 or the host's stage 1 (A53).

So do the rollover's invalidation when the stage 2 of a VM that has run is
freed, in nVHE mode. That costs one TLB refill on every CPU per VM
teardown; 500 VMs created, run and torn down one after the other take 32.1
ms each with it and 33.4 ms without, and an isolated CPU meanwhile sees no
change in latency (15 us against 13 us).

Signed-off-by: Francesco Boccola <francesco.boccola@unina.it>
---
On Cortex-A53, A55 and A76 hosts in nVHE mode, a CPU that has run a guest
with its stage-1 MMU on makes the host's broadcast TLB invalidations more
expensive for the whole system until the next VMID rollover, which usually
means until the host reboots. The patch does the rollover's invalidation
(TLBI ALLE1IS) when the stage 2 of a VM that has run is freed; its commit
message has the measurements.

RFC because we can only describe what these cores do, not explain it. Which
per-CPU state survives the invalidation of the VM's VMID, and why it slows
the broadcast invalidations of other CPUs, is microarchitectural; an
explanation from someone who knows these TLBs would be welcome.
Questions:
- Is this known behaviour of these cores in nVHE mode (A53, A55 and A76
  here)?
- ALLE1IS also drops the host's own EL1&0 entries on every CPU. A local
  TLBI ALLE1 on the CPUs the VM ran on (mmu->last_vcpu_ran) is enough in
  our tests, but needs IPIs; would you prefer that?
- In protected mode, the host itself runs with stage 2, and the same test
  gives 112-153 us from boot, guest or not (18-23 us in nVHE mode before
  any guest). Is that expected?
- Should VHE hosts also invalidate (we see no effect there)?

Reproducer (below): tinyvm.c, a ~110-line KVM VMM running a guest (guest.S)
that turns its MMU on and powers off, and run.sh: stress-ng --tlb-shootdown
and cyclictest (SCHED_FIFO 99) on a freshly booted host, 3 x 20 s before
and after one such guest. Controls: a guest that keeps its MMU off (no
change), the same kernel in VHE mode (no change), this patch on kvmarm/next
(A55 19-22 -> 20-32 us, A76 14-24 -> 13-15 us).

To run it: make (or make CROSS_COMPILE=aarch64-linux-gnu- LDFLAGS=-static),
then, as root on a freshly booted host with stress-ng and cyclictest,
./run.sh -v <cyclictest CPU> -c <three other CPUs of its cluster> -g <guest
CPU>. The defaults (-v 3 -c 0-2 -g 2) fit a 4-CPU cluster; -m 0 runs the
control guest (MMU off). In our tests the cyclictest CPU was isolated
(isolcpus, nohz_full, rcu_nocbs).

on these boards.

/*
 * guest.S - the guest of tinyvm: with MMU=1 it turns its stage-1 MMU and
 * caches on (identity map of its RAM), writes a marker through the MMU, spins
 * for SPIN seconds (virtual counter) and powers the VM off (PSCI SYSTEM_OFF);
 * with MMU=0 it does the same with the MMU off.
 * Linked at the start of the guest RAM (0x40000000):
 *   gcc -nostdlib -static -Wl,-Ttext=0x40000000 -Wl,--build-id=none -DMMU=1 \
 *       -o guest-mmu.elf guest.S && objcopy -O binary guest-mmu.elf guest-mmu.bin
 */
#ifndef MMU
#define MMU 1
#endif
#ifndef SPIN
#define SPIN 0
#endif
#define MARKER_ADDR	0x40100000	/* 1 MB into the RAM, read back by tinyvm */

	.text
	.globl	_start
_start:
#if MMU
	movz	x0, #0xff00		/* MAIR: attr0 Device-nGnRnE, attr1 Normal WB */
	msr	mair_el1, x0
	movz	x0, #0x3519		/* TCR: T0SZ 25, WBWA inner shareable walks, */
	movk	x0, #0x0080, lsl #16	/* 4 KB granule, no TTBR1 walks, */
	movk	x0, #0x0002, lsl #32	/* 40-bit PA */
	msr	tcr_el1, x0
	adr	x0, pgtable
	msr	ttbr0_el1, x0
	isb
	tlbi	vmalle1
	dsb	ish
	isb
	mrs	x0, sctlr_el1
	movz	x1, #0x1005		/* I, C, M */
	orr	x0, x0, x1
	msr	sctlr_el1, x0
	isb
#endif
	movz	x1, #(MARKER_ADDR >> 16), lsl #16
	movz	w2, #0x4d4d		/* "MM" */
	movk	w2, #(0x55 + MMU), lsl #16
	str	w2, [x1]
	dsb	sy
#if SPIN
	mrs	x3, cntfrq_el0		/* spin SPIN seconds */
	mov	x4, #SPIN
	mul	x3, x3, x4
	mrs	x4, cntvct_el0
	add	x3, x3, x4
2:	mrs	x4, cntvct_el0
	cmp	x4, x3
	b.lo	2b
#endif
	movz	w0, #0x0008
	movk	w0, #0x8400, lsl #16	/* PSCI SYSTEM_OFF */
	hvc	#0
1:	wfi
	b	1b

	.balign	4096
pgtable:	/* level 1, 1 GB blocks: 0-1 GB Device, 1-2 GB Normal WB (the RAM) */
	.quad	0x0060000000000401
	.quad	0x0000000040000705

==> tinyvm.c <==
/*
 * tinyvm <guest.bin> [cpu] - the smallest KVM VMM: one vCPU, 16 MB of RAM at
 * 0x40000000, no interrupt controller and no devices. It loads <guest.bin> at
 * the start of the RAM, runs the vCPU (pinned to [cpu]) until the guest powers
 * the VM off through PSCI, checks the marker the guest wrote and exits 0.
 * Build: gcc -O2 -o tinyvm tinyvm.c
 */
#define _GNU_SOURCE
#include <errno.h>
#include <fcntl.h>
#include <linux/kvm.h>
#include <sched.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <sys/stat.h>
#include <unistd.h>

#define RAM_BASE	0x40000000UL
#define RAM_SIZE	(16UL << 20)
#define MARKER_OFF	0x100000UL

#define CORE_REG(x) (KVM_REG_ARM64 | KVM_REG_SIZE_U64 | KVM_REG_ARM_CORE | \
		     (offsetof(struct kvm_regs, x) / sizeof(uint32_t)))

static void die(const char *what)
{
	perror(what);
	exit(2);
}

int main(int argc, char **argv)
{
	struct kvm_userspace_memory_region region;
	struct kvm_vcpu_init init;
	struct kvm_one_reg reg;
	struct kvm_run *run;
	uint64_t pc = RAM_BASE;
	int kvm, vm, vcpu, fd, size;
	uint8_t *ram;
	struct stat st;
	uint32_t marker;

	if (argc < 2) {
		fprintf(stderr, "usage: %s <guest.bin> [cpu]\n", argv[0]);
		return 2;
	}
	alarm(120);	/* a guest that faults spins forever: give up */
	if (argc > 2) {
		cpu_set_t set;

		CPU_ZERO(&set);
		CPU_SET(atoi(argv[2]), &set);
		if (sched_setaffinity(0, sizeof(set), &set))
			die("sched_setaffinity");
	}
	kvm = open("/dev/kvm", O_RDWR | O_CLOEXEC);
	if (kvm < 0)
		die("/dev/kvm");
	vm = ioctl(kvm, KVM_CREATE_VM, 0);
	if (vm < 0)
		die("KVM_CREATE_VM");
	ram = mmap(NULL, RAM_SIZE, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
	if (ram == MAP_FAILED)
		die("mmap");
	fd = open(argv[1], O_RDONLY);
	if (fd < 0 || fstat(fd, &st) || st.st_size > (off_t)MARKER_OFF ||
	    read(fd, ram, st.st_size) != st.st_size)
		die(argv[1]);
	close(fd);
	region = (struct kvm_userspace_memory_region){
		.slot = 0, .guest_phys_addr = RAM_BASE, .memory_size = RAM_SIZE,
		.userspace_addr = (uintptr_t)ram,
	};
	if (ioctl(vm, KVM_SET_USER_MEMORY_REGION, &region))
		die("KVM_SET_USER_MEMORY_REGION");
	vcpu = ioctl(vm, KVM_CREATE_VCPU, 0);
	if (vcpu < 0)
		die("KVM_CREATE_VCPU");
	if (ioctl(vm, KVM_ARM_PREFERRED_TARGET, &init))
		die("KVM_ARM_PREFERRED_TARGET");
	init.features[0] |= 1 << KVM_ARM_VCPU_PSCI_0_2;
	if (ioctl(vcpu, KVM_ARM_VCPU_INIT, &init))
		die("KVM_ARM_VCPU_INIT");
	reg = (struct kvm_one_reg){ .id = CORE_REG(regs.pc), .addr = (uintptr_t)&pc };
	if (ioctl(vcpu, KVM_SET_ONE_REG, &reg))
		die("KVM_SET_ONE_REG pc");
	size = ioctl(kvm, KVM_GET_VCPU_MMAP_SIZE, 0);
	run = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_SHARED, vcpu, 0);
	if (run == MAP_FAILED)
		die("mmap kvm_run");
	for (;;) {
		if (ioctl(vcpu, KVM_RUN, 0) && errno != EINTR)
			die("KVM_RUN");
		if (run->exit_reason == KVM_EXIT_SYSTEM_EVENT)
			break;
		fprintf(stderr, "unexpected exit %u\n", run->exit_reason);
		return 2;
	}
	memcpy(&marker, ram + MARKER_OFF, sizeof(marker));
	printf("guest done: system event %u, marker %#x (%s)\n", run->system_event.type, marker,

[PATCH RFC] KVM: arm64: nVHE: Flush all TLBs when freeing a VM's
Author: Francesco Boccola via B4 Relay <devnull+francesco.boccola.unina.it@kernel.org>


kvm_free_stage2_pgd() frees a VM's stage-2 page tables without invalidating
the TLBs. That is correct: the VM's VMID is not reused before the next VMID
rollover, and flush_context() then invalidates the entries of all VMIDs on
all CPUs (TLBI ALLE1IS).

In nVHE mode, however, a CPU that ran a guest makes the host's broadcast
TLB invalidations more expensive for the whole system until then, which
with 16-bit VMIDs usually means until the host reboots. With stress-ng
--tlb-shootdown on three CPUs of a cluster, the cyclictest maximum on a
fourth, isolated CPU goes, before and after one guest:
- Cortex-A53 (Zynq UltraScale+ KV260, no VHE, 6.1.70-rt): 53-72 us ->
  83-164 us;
- Cortex-A55 (RK3588, kvm-arm.mode=nvhe, kvmarm/next): 18-23 -> 78-97 us;
- Cortex-A76 (RK3588, kvm-arm.mode=nvhe, kvmarm/next): 16-30 -> 74-80 us.
It crosses clusters: after a guest on an A55, an isolated A76 goes from
14-18 us to 129-154 us. The same happens on kernel 6.12.113 (20-24 -> 44-49
us on the A55) and on 7.1.9 with and without PREEMPT_RT.

One guest that turns its stage-1 MMU on, even for a few microseconds, is
enough; a guest that keeps its MMU off is not. With VHE nothing changes.

The state is in the CPU that ran the guest: a local TLBI ALLE1 on that CPU
at teardown removes the effect on every CPU, the same on all the other CPUs
does not. Invalidating the dead VM's VMID (TLBI VMALLS12E1IS, as pKVM does
at teardown) does not remove it either, whether stage 2 is disabled while
it is issued (as __kvm_tlb_flush_vmid() does from the host's context) or
enabled; nor does invalidating VMID 0 or the host's stage 1 (A53).

So do the rollover's invalidation when the stage 2 of a VM that has run is
freed, in nVHE mode. That costs one TLB refill on every CPU per VM
teardown; 500 VMs created, run and torn down one after the other take 32.1
ms each with it and 33.4 ms without, and an isolated CPU meanwhile sees no
change in latency (15 us against 13 us).

Signed-off-by: Francesco Boccola <francesco.boccola@unina.it>
---
On Cortex-A53, A55 and A76 hosts in nVHE mode, a CPU that has run a guest
with its stage-1 MMU on makes the host's broadcast TLB invalidations more
expensive for the whole system until the next VMID rollover, which usually
means until the host reboots. The patch does the rollover's invalidation
(TLBI ALLE1IS) when the stage 2 of a VM that has run is freed; its commit
message has the measurements.

RFC because we can only describe what these cores do, not explain it. Which
per-CPU state survives the invalidation of the VM's VMID, and why it slows
the broadcast invalidations of other CPUs, is microarchitectural; an
explanation from someone who knows these TLBs would be welcome.
Questions:
- Is this known behaviour of these cores in nVHE mode (A53, A55 and A76
  here)?
- ALLE1IS also drops the host's own EL1&0 entries on every CPU. A local
  TLBI ALLE1 on the CPUs the VM ran on (mmu->last_vcpu_ran) is enough in
  our tests, but needs IPIs; would you prefer that?
- In protected mode, the host itself runs with stage 2, and the same test
  gives 112-153 us from boot, guest or not (18-23 us in nVHE mode before
  any guest). Is that expected?
- Should VHE hosts also invalidate (we see no effect there)?

Reproducer (below): tinyvm.c, a ~110-line KVM VMM running a guest (guest.S)
that turns its MMU on and powers off, and run.sh: stress-ng --tlb-shootdown
and cyclictest (SCHED_FIFO 99) on a freshly booted host, 3 x 20 s before
and after one such guest. Controls: a guest that keeps its MMU off (no
change), the same kernel in VHE mode (no change), this patch on kvmarm/next
(A55 19-22 -> 20-32 us, A76 14-24 -> 13-15 us).

/*
 * guest.S - the guest of tinyvm: with MMU=1 it turns its stage-1 MMU and
 * caches on (identity map of its RAM), writes a marker through the MMU, spins
 * for SPIN seconds (virtual counter) and powers the VM off (PSCI SYSTEM_OFF);
 * with MMU=0 it does the same with the MMU off.
 * Linked at the start of the guest RAM (0x40000000):
 *   gcc -nostdlib -static -Wl,-Ttext=0x40000000 -Wl,--build-id=none -DMMU=1 \
 *       -o guest-mmu.elf guest.S && objcopy -O binary guest-mmu.elf guest-mmu.bin
 */

	.text
	.globl	_start
_start:

	movz	x0, #0xff00		/* MAIR: attr0 Device-nGnRnE, attr1 Normal WB */
	msr	mair_el1, x0
	movz	x0, #0x3519		/* TCR: T0SZ 25, WBWA inner shareable walks, */
	movk	x0, #0x0080, lsl #16	/* 4 KB granule, no TTBR1 walks, */
	movk	x0, #0x0002, lsl #32	/* 40-bit PA */
	msr	tcr_el1, x0
	adr	x0, pgtable
	msr	ttbr0_el1, x0
	isb
	tlbi	vmalle1
	dsb	ish
	isb
	mrs	x0, sctlr_el1
	movz	x1, #0x1005		/* I, C, M */
	orr	x0, x0, x1
	msr	sctlr_el1, x0
	isb

	movz	x1, #(MARKER_ADDR >> 16), lsl #16
	movz	w2, #0x4d4d		/* "MM" */
	movk	w2, #(0x55 + MMU), lsl #16
	str	w2, [x1]
	dsb	sy

	mrs	x3, cntfrq_el0		/* spin SPIN seconds */
	mov	x4, #SPIN
	mul	x3, x3, x4
	mrs	x4, cntvct_el0
	add	x3, x3, x4
2:	mrs	x4, cntvct_el0
	cmp	x4, x3
	b.lo	2b

	movz	w0, #0x0008
	movk	w0, #0x8400, lsl #16	/* PSCI SYSTEM_OFF */
	hvc	#0
1:	wfi
	b	1b

	.balign	4096
pgtable:	/* level 1, 1 GB blocks: 0-1 GB Device, 1-2 GB Normal WB (the RAM) */
	.quad	0x0060000000000401
	.quad	0x0000000040000705
	.fill	510, 8, 0

==> tinyvm.c <==
/*
 * tinyvm <guest.bin> [cpu] - the smallest KVM VMM: one vCPU, 16 MB of RAM at
 * 0x40000000, no interrupt controller and no devices. It loads <guest.bin> at
 * the start of the RAM, runs the vCPU (pinned to [cpu]) until the guest powers
 * the VM off through PSCI, checks the marker the guest wrote and exits 0.
 * Build: gcc -O2 -o tinyvm tinyvm.c
 */

		     (offsetof(struct kvm_regs, x) / sizeof(uint32_t)))

static void die(const char *what)
{
	perror(what);
	exit(2);
}

int main(int argc, char **argv)
{
	struct kvm_userspace_memory_region region;
	struct kvm_vcpu_init init;
	struct kvm_one_reg reg;
	struct kvm_run *run;
	uint64_t pc = RAM_BASE;
	int kvm, vm, vcpu, fd, size;
	uint8_t *ram;
	struct stat st;
	uint32_t marker;

	if (argc < 2) {
		fprintf(stderr, "usage: %s <guest.bin> [cpu]\n", argv[0]);
		return 2;
	}
	alarm(120);	/* a guest that faults spins forever: give up */
	if (argc > 2) {
		cpu_set_t set;

		CPU_ZERO(&set);
		CPU_SET(atoi(argv[2]), &set);
		if (sched_setaffinity(0, sizeof(set), &set))
			die("sched_setaffinity");
	}
	kvm = open("/dev/kvm", O_RDWR | O_CLOEXEC);
	if (kvm < 0)
		die("/dev/kvm");
	vm = ioctl(kvm, KVM_CREATE_VM, 0);
	if (vm < 0)
		die("KVM_CREATE_VM");
	ram = mmap(NULL, RAM_SIZE, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
	if (ram == MAP_FAILED)
		die("mmap");
	fd = open(argv[1], O_RDONLY);
	if (fd < 0 || fstat(fd, &st) || st.st_size > (off_t)MARKER_OFF ||
	    read(fd, ram, st.st_size) != st.st_size)
		die(argv[1]);
	close(fd);
	region = (struct kvm_userspace_memory_region){
		.slot = 0, .guest_phys_addr = RAM_BASE, .memory_size = RAM_SIZE,
		.userspace_addr = (uintptr_t)ram,
	};
	if (ioctl(vm, KVM_SET_USER_MEMORY_REGION, &region))
		die("KVM_SET_USER_MEMORY_REGION");
	vcpu = ioctl(vm, KVM_CREATE_VCPU, 0);
	if (vcpu < 0)
		die("KVM_CREATE_VCPU");
	if (ioctl(vm, KVM_ARM_PREFERRED_TARGET, &init))
		die("KVM_ARM_PREFERRED_TARGET");
	init.features[0] |= 1 << KVM_ARM_VCPU_PSCI_0_2;
	if (ioctl(vcpu, KVM_ARM_VCPU_INIT, &init))
		die("KVM_ARM_VCPU_INIT");
	reg = (struct kvm_one_reg){ .id = CORE_REG(regs.pc), .addr = (uintptr_t)&pc };
	if (ioctl(vcpu, KVM_SET_ONE_REG, &reg))
		die("KVM_SET_ONE_REG pc");
	size = ioctl(kvm, KVM_GET_VCPU_MMAP_SIZE, 0);
	run = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_SHARED, vcpu, 0);
	if (run == MAP_FAILED)
		die("mmap kvm_run");
	for (;;) {
		if (ioctl(vcpu, KVM_RUN, 0) && errno != EINTR)
			die("KVM_RUN");
		if (run->exit_reason == KVM_EXIT_SYSTEM_EVENT)
			break;
		fprintf(stderr, "unexpected exit %u\n", run->exit_reason);
		return 2;
	}
	memcpy(&marker, ram + MARKER_OFF, sizeof(marker));
	printf("guest done: system event %u, marker %#x (%s)\n", run->system_event.type, marker,
	       marker == 0x564d4d ? "MMU on" : marker == 0x554d4d ? "MMU off" : "BAD");
	close(vcpu);
	close(vm);
	close(kvm);
	return marker == 0x564d4d || marker == 0x554d4d ? 0 : 1;
}
